02一次上传发生了什么

入口是 DocumentService.ingest_upload()。整条链路最关键的设计是：它写三个地方，并且刻意分成两个事务。

为什么拆成两个事务

💡 为什么因为 vector_id = "{doc_id}:{chunk_index}" 需要先有 doc_id； 但更重要的理由是失败可见性：解析失败时事务 1 已经落地，用户刷新列表就能看到那条 FAILED 记录和具体原因。 如果全塞进一个事务里回滚，用户只会看到一个"上传失败"的弹窗——既不知道为什么，也看不到自己传过什么。

⚖ 代价代价是"半成品状态"是合法存在的：库里会短暂出现 UPLOADED/PARSING/… 的行， 前端必须能展示这些中间态（status 是可筛选字段，文档列表按它显示进度）。 这是用一点状态复杂度换可排障性，本项目认为值。

为什么写入顺序是"向量 → BM25 → 注册表"

⚠ 坑代码里的实际书写顺序是 chunks 行先 flush（拿 chunk_id），再写向量库，再写 BM25—— 因为 vector_id 里的 chunk_id 要放进向量元数据里。 但 chunks 这一步只是 flush 而非 commit，所以从持久化角度看，真正先落地的仍然是向量库。 读代码时容易被"代码顺序"骗，要分清语句顺序与提交顺序。

父子块：切分粒度的两难

✅ 实测6 份示例文档切出 34 个切片（11 + 6 + 2 + 6 + 2 + 7），单份入库耗时 1,160 ~ 11,005 ms（CPU，首份含模型加载）（E5）。 同一文档删除后三方计数同步回落：chunk 34→27 / vector 34→27 / bm25 34→27（E6）。

💡 为什么每个节点都写了降级分支，不是防御性编程洁癖： LLM 输出 JSON 失败是常态（经验值几个百分点），如果每次失败都中断整个问答， 用户体感就是"每几十次提问报一次错"。正确做法是降级 + 记录 + 继续。

SSE：8 种事件、一条硬性顺序

⚠ 坑SSE 路由必须写同步 def。answer_stream 是同步生成器，Starlette 会自动用 iterate_in_threadpool 逐帧取； 写成 async def 再直接 for frame in gen 会阻塞事件循环——一个流式问答期间整个服务不响应任何请求。 而正是这个 iterate_in_threadpool 引发了本项目最隐蔽的一个 bug，见 §12。

04检索层七阶段

一次 search() 分七步，每步单独计时并落进 trace span。为什么把"融合"和"归一化"分开：RRF 输出的分数没有物理含义（只是 Σ 1/(k+rank)）， 不能直接和阈值比较，必须先归一化到 [0,1]，autocut 的 ratio 与界面上显示的 score 才有可解释的含义。

七阶段各自的判据

阶段做什么关键参数（默认值）降级 / 边界
① embed_query问题 → 1024 维向量BGE-M3，CPU 约 60~200ms失败 → vector_error="embedding: …"，只走 BM25
② 向量召回Chroma 取 fetch_k 条，多 KB 合并后按分排序截断FETCH_K=20没有指定 KB 时跳过（向量库按 KB 分集合）并记原因
③ BM25 召回倒排取 fetch_k 条；无 KB 时跨库搜k1=1.5 / b=0.75内存索引为空 → 静默失效，靠 /health 暴露
④ 融合RRF（默认）或加权归一化RRF_K=60；加权 ALPHA=0.6单路模式直接用该路分数，归一化留到下一步

⑥ 重排前 RERANK_TOP_N 条用 LLM 打分，与融合分 7:3 混合RERANK_TOP_N=10，BLEND=0.70/0.30离线 / 超时 / 解析失败 → 启发式兜底（0.60 覆盖率 + 0.25 标题 + 0.15 向量分）
⑦ 闸门 + 预算双阈值 OR 判定 → 字符预算裁剪MAX_CONTEXT_CHARS=8000不过闸门 → 候选清空（短路拒答）；预算裁到至少留 1 条

⚠ 坑向量召回失败要降级而不是报错——但前提是真的接得住异常。 项目里历史上并存两套异常类：core.exceptions.EmbeddingError（有 .message）与 embeddings.base.EmbeddingError（普通 Exception）。实现方抛的是后者，而降级路径只捕获前者， 于是"向量失败 → 降级为纯 BM25"这条承诺在最需要它的时候（模型加载失败、维度不符）根本不生效，异常直接冒到 HTTP 层。 解法是把两套都接住并统一取原因文本。

⚖ 代价降低阈值（闸门更松）会让 dropped_by_gate=0 看起来"很健康"，但那是假象： 闸门失效的真实代价在评测里才看得到（误放行 = 1.000），见 §06。这个指标只在"闸门正常工作"时才有诊断价值。

阈值扫描与最终取值

🔴 正确解法是补信号，不是继续调阈值分布重叠说明单一向量阈值在原理上分离不开两类样本。 要真正解决，需要引入更强的判据：真实交叉编码器重排（bge-reranker-v2-m3，当前只做了 LLM 重排 + 启发式兜底）、 或显式的"这句话能不能回答这个问题"的可答性判断。调阈值只能在这条 ROC 曲线上左右挪，挪不出更高的上限。

07消融实验与显著性

43 条标注用例，四种检索模式跑同一套题，输出对比表 + 配对 bootstrap 检验。 这一节的重点不是数字，而是哪条能写进简历、哪条不能。

💡 为什么自己做 bootstrap 而不引 scipy项目没装 scipy，而这里只用到"重采样 + 取分位点"两件事，几十行就够，引一个 30MB 的科学计算栈不划算。 两个工程细节：① random.Random(seed) 显式实例化，不用全局 random——全局种子会被同进程其它代码影响，导致"同样数据两次跑出不同 CI"， 让 CI 门槛变成薛定谔的通过；② 用成对检验（paired）而不是两组独立检验：两次评测跑的是同一批用例，成对差分消掉了"题目难度"这个共同方差，功效高得多。 代价是要求输入等长，不等长直接 ValueError——宁可报错也不悄悄对比错数据。

08Agent 状态图为什么这么设计

与固定链的对比：控制流归谁

四个可讲的设计点

设计点为什么这么做代价 / 边界
grade 为什么用 LLM 判定，而不是复用检索分数？ 检索分数是"和 query 的字面/语义相似度"，不等于"能不能回答这个问题"。实测里经常出现"高分片段答的是另一个问题"。LLM 判定多花一次便宜的小模型调用，但能拦掉一整类错误。 多一次调用、多几百毫秒 → 做成可开关 AGENT_GRADING_ENABLED；候选 ≤3 条时直接跳过判定。
rewrite 为什么要有次数上限？ 避免"死循环烧钱"。上限 AGENT_MAX_REWRITE=2：第一次改写查询，第二次拆子问题；还没料就直接走 generate 并明确告知"知识库中没有足够信息"——宁可拒答也不编。 上限用满时答案质量确实更差，但成本上界可算。
reflect 为什么不重新检索？ 职责分离：grade 管"料找对没"，reflect 管"话有没有依据"。混在一起会出现"越反思越跑偏"——重检索会引入新上下文，让"这句有没有依据"这个判定失去稳定基准。 它只能靠"收紧约束重新生成"（把"错在哪"明确写进 system prompt），而不是换资料。
checkpointer 为什么用 trace_id 当 thread_id？ 因为 candidates / all_queries 用的是累加 reducer。若同一会话共用一个 thread，第二轮状态会与第一轮合并——上一轮的候选混进这一轮上下文，引用编号全乱。多轮记忆由 MySQL + 双重截断负责（那才是产品语义上的记忆）。 checkpointer 的作用从"记忆"变成可回溯：排障时能看到那次请求在图里走到了哪一步、每个节点的中间产出。构造失败也不阻断启动（可观测坏了不该让问答不可用）。

⚠ 与设计文档不一致（以代码为准）docs/00-架构与技术选型.md §1.2 第 4 点写的是 "按 thread_id = conversation_id 持久化状态"，而代码里是 thread_id = trace_id， 并在 agent/graph.py 注释里给了明确理由（累加 reducer 会串轮次）。 这是文档滞后于一次刻意的设计修改，读代码时不要被文档带偏。

09防幻觉的三道防线

防幻觉不是"在 prompt 里写一句不许编"。本项目把它做成三层结构约束，并且每一层都能被实测证明"真的生效了"。

怎么证明它真的生效

⚖ 代价（诚实列）三道防线都有误伤： 闸门会误杀本来能答的问题（0.60 时 recall 0.907，意味着约 9.3% 的正样本没过闸门，E7）； reflect 有 1 次重试预算，判官解析失败时默认通过（宁可漏一次纠正，也不让用户白等）； 固定话术拒答在"其实有答案但检索没召回"时会给出比"猜一个"更差的体验。 这些取舍都写在代码注释里，而不是藏起来。

11安全：21 个端点漏鉴权的事故

这是本项目唯一一个真正的安全漏洞，也是最值得单独成节的一段经历。它说明一件事：安全属性不能靠"每个人记得写"。

审计脚本的两个坑（都差点让我得出错误结论）

⚠ 坑 1 · 只扫端点自身依赖会误报 include_router(..., dependencies=[Depends(get_current_user)]) 这种"统一加鉴权"的写法挂在 include_context.dependencies 上， 不在端点的 dependant 里。只查后者会把正确写法误报成漏洞。 所以脚本既查端点自身依赖，也查从上层继承下来的依赖。

🔴 坑 2 · 直接遍历 app.routes 会漏掉几乎所有端点 FastAPI 0.142 的 include_router 是惰性的：app.routes 里只有 _IncludedRouter 占位对象 （path 与 methods 都是 None），真正的 APIRoute 藏在 original_router.routes 里，前缀在 include_context.prefix。 第一版脚本直接遍历 app.routes，只找到 1 个端点——差点得出"没有漏洞"的错误结论。 正确做法是从 original_router 递归，并逐层累加 prefix 与继承依赖。

💡 这条经验的可迁移性"审计脚本本身也会骗你"是这个事故里最有价值的副产品。 凡是扫描型工具（鉴权审计、依赖扫描、一致性校验），都必须先验证"它到底扫到了多少东西"—— 一个扫到 1 个端点的脚本和一个扫到 39 个端点的脚本，输出的"OK"含义完全不同。 所以本项目的审计脚本会把找到的每一个端点都打印出来，让人一眼看到覆盖范围。

12可观测与那个 contextvars bug

trace / span：一次请求的瀑布图

为什么 span 存 start_offset_ms 而不是绝对时间戳

💡 为什么前端画瀑布图只需要「起点偏移 + 时长」两个数字就能定位所有方块： 不用处理时区、不用处理时钟漂移、不用处理多机时间不同步，存储也从 datetime 降成 int（trace_spans 一共 12 列，其中这两列撑起整张图）。 seq 单调递增，是稳定排序键——同毫秒的 span 不会乱序。

⚖ 代价口径必须说清楚：traces.retrieval_ms / rerank_ms / generate_ms 是同类 span 耗时之和，不是墙钟时间。 多个检索并行时，三者之和可能大于 latency_ms——这是有意的：要回答的是"花在检索上的时间是多少"，而不是"第几秒在做检索"。

那个 contextvars bug：流式路径必崩

🔴 为什么 222 个 pytest 全绿也漏掉了它 因为 pytest 用 ASGITransport 打请求时不会触发这种分次线程调度——它在同一个事件循环里把响应体一次读完。 而这个 bug 只在真起 uvicorn + 真打流式接口时出现。流式恰好是本项目的主路径。 所以教训不是"要多写单测"，而是：有些缺陷类型只能由"起真服务的端到端冒烟"覆盖， smoke_http.py（70 项断言）和 222 个单测是互补关系而不是重复关系。

引用角标 [n] 怎么渲染

💡 统一错误信封为什么值所有非 2xx（包括 FastAPI 自己抛的 404/405、Pydantic 的 422）都变成 {"error":{code, message, detail, request_id, timestamp}}。 前端只写一套解包逻辑，不需要为"框架默认的 422 形状"再写一套。 实测验证：POST /chat（question 为空）→ 422 REQUEST_VALIDATION_ERROR； GET /this-path-does-not-exist → 404 NOT_FOUND；GET /kbs（无 token）→ 401 UNAUTHORIZED（E6.3）。

一个真实踩过的坑：CORS 必须 expose_headers=["X-Request-ID","X-Process-Time-Ms"]。 浏览器默认只暴露"安全列表"里的响应头，不加这一行，前端 response.headers.get('x-request-id') 永远是 null， 错误 toast 里就永远没有 request_id。

14一致性怎么保证

同一份数据存在三个地方（MySQL / Chroma / 内存 BM25），所以"它们是不是一致"必须是一个能被看到的数字，而不是一句承诺。

启动时重建 BM25：一个"静默降级"的典型案例

⚖ 代价启动时全量重建 BM25 让启动变慢（切片越多越慢），并且和"启动预热 embedding 模型"叠加后启动要多花几秒。 换来的是"不会有请求打在一个瞎了一只眼的检索系统上"。同理，/health 也必须如实上报运行期真实模式， 不能骗人——这是项目的一条硬规则。

10 个高频追问与答法

追问答法（关键数字都来自实测）
1. 为什么不用 jieba？ BM25 对这种 600 字短 chunk，1-gram + 2-gram 已经够：1-gram 保证召回、2-gram 提供区分度，而且白板可推导。 引 jieba 要带 30MB 词典、变长依赖，收益主要是词边界更准。代价我也认：词表大 2~3 倍、索引内存更高，同义词依然匹配不上——那部分交给向量兜底。 关键是切词必须全项目唯一，否则覆盖率阈值的含义会随实现漂移。
2. RRF 和加权归一化，为什么默认 RRF？ 两路分数量纲不同（cosine 0~1 vs BM25 无上界，实测 31~36），直接加权会让 BM25 主导。 实测里 RRF 在小语料上略逊于纯向量（0.849 vs 0.860，但不显著，p=0.820），因为它丢弃分数幅度。 但 hybrid 只比 vector 慢 2ms（56 vs 58，BM25 只要 5ms），鲁棒性更好。 结论：在没人持续调参的系统里，鲁棒性比理论最优更重要。
3. 你的"提升"是怎么验证的？ 43 条标注用例跑四模式消融 + 配对 bootstrap（n_boot=2000, seed=42）。 唯一显著的结论是 bm25 → hybrid_rerank：0.721 → 0.849，Δ=+0.128，95% CI [+0.035,+0.244]，p=0.010。 "vector 比 hybrid 高 1.2 个点"的 p=0.820，CI 跨 0，我不会写进简历——43 条里翻转 1 条就是 2.3 个点，那 1.2 个点纯属噪声。
4. 怎么防幻觉？ 三道结构约束：① Prompt 约束 + 引用编号（每条事实必须标 [n]，并给出固定拒答话术）； ② 无召回短路（select_contexts() 为空就不调模型，直接返回固定话术）； ③ reflect 引用校验（逐句查 [n] 支撑，数值必须完全一致，不过就带着"错在哪"重生成一次）。 证据：拒答路径的 span 树只有 ['analyze','retrieve']，generate.llm span = 0——"没资料就不生成"是可以数出来的。
5. 阈值怎么定的？ 写脚本在标注集上扫参数，输出"阈值 vs recall / 误放行 / F1"。 最有价值的一次测量：BGE-M3 上两段毫不相关的中文余弦相似度仍有 0.57 左右（负样本均值 0.5704）， 所以按直觉设的 0.35 让误放行 = 1.000——闸门完全失效，而功能测试全是绿的。 最终取 0.60 / 0.40（比 F1 最优点 0.63/0.44 略宽松，避免误杀）。 而且正负样本分布重叠严重（正 min 0.465 < 负 max 0.782），说明单一阈值在原理上救不了，正解是补信号（交叉编码器重排），不是继续调阈值。
6. 为什么 Agent 图要这么设计？模型不能自己决定吗？ 我把控制流画成图，模型只在节点内判断。好处是每步可观测、可兜底、可测试—— 四个条件边判据都是独立纯函数，能单测"给定这个 state 应该走哪条边"。 四个设计点：grade 用 LLM 因为检索分数≠可答性；rewrite 上限 2 次防死循环烧钱； reflect 不重检索（职责分离，否则"越反思越跑偏"）；checkpointer 的 thread_id 用 trace_id 而不是 conversation_id （累加 reducer 会让上一轮候选混进这一轮，引用编号全乱）。
7. 上传为什么要分两个事务？ 事务 1 只做"登记"（存文件 + 建 documents 行，status=UPLOADED）并立即 commit； 事务 2 做解析 / 切分 / 向量化 / 写三处 / 置 READY。 拆开的原因有两个：vector_id = "doc_id:chunk_index" 需要先有 doc_id； 更重要的是失败可见性——解析失败时用户能刷新列表看到那条 FAILED 和具体原因，而不是只看到一个 alert。 写入顺序（向量 → BM25 → 注册表）也是刻意的：最坏是"可清理的孤儿向量"，而不是"显示成功但搜不到"。
8. 流式是怎么做的？踩过什么坑？ 手写 SSE 产帧（不用 EventSourceResponse，因为它会插自己的心跳字段）。 三个坑：① 必须带 X-Accel-Buffering: no，否则 Nginx 会把整个响应缓冲到结束，"流式看起来不流式"； ② 路由必须写同步 def（同步生成器交给 iterate_in_threadpool），写 async def 会阻塞事件循环； ③ 最隐蔽的一个：最初用 contextvar 传 trace recorder，非流式完全正常，流式每次必崩—— iterate_in_threadpool 每个 next() 可能落在不同线程、拿到各自的 context 副本， 而 set() 的 token 只能在同一个 context 里 reset()。改成显式传 RecorderBox 后解决。 222 个单测全绿也漏掉了它，因为 pytest 用 ASGITransport 不触发分次线程调度。
9. 前后端怎么保证引用对得上？ 三段编号共用同一个 n：喂给模型的编号 = 答案里的 [n] = 落库的 message_citations.rank， 由同一个 select_contexts() 产出，所以"展示的引用"和"喂给模型的上下文"必然一致。 落库只存真正展示给用户的那几条（不是全部候选），否则引用精度这类指标会失真。
10. 你觉得这个项目最值得讲的一个 bug？ 21 个端点漏鉴权。它值得讲不是因为修起来难，而是因为它在功能测试里完全看不出来—— 这些接口返回 200 + 正常业务数据，只有"不带 token 打一次"才暴露。 所以我把它从"逐个端点声明"改成"路由级默认需要、例外公开"：默认值的方向决定了犯错时的后果。 而且审计脚本本身也差点骗了我：第一版直接遍历 app.routes，FastAPI 0.142 的 include_router 是惰性的， 只找到 1 个端点，差点得出"没有漏洞"的结论。教训：扫描型工具必须先验证"它到底扫到了多少东西"。
