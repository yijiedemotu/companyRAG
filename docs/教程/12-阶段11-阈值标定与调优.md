# 阶段 11：阈值标定与调优 ★

> **本阶段目标**：把「防幻觉闸门的两个阈值」和「检索链路的四组配置」从**直觉**改成**测量结果**，
> 并学会用配对 bootstrap 判断"这个提升到底是不是噪声"。
> **预计耗时**：120 分钟
> **前置阶段**：阶段 10
> **本阶段产出**：一条可复现的标定曲线（`data/threshold_calibration.json`）
> + 一张消融对比表 + 三个显著性结论（`data/eval_report.json`）

## 0. 为什么先做这一步

**因为闸门是"防幻觉"的唯一开关，而它的阈值不可能是拍脑袋拍对的。**

先看这个项目里真实发生的事（E7，全部来自 `backend/scripts/calibrate_threshold.py` 的实测输出）：

```
  当前配置： VECTOR_MIN_SCORE=0.35  KEYWORD_MIN_COVERAGE=0.25
  ...
      阈值   recall      误放行  precision      F1
    0.35    1.000    1.000      0.500   0.667   ← 原默认值
```

`误放行 = 1.000`：**任何一个问题都能通过闸门**。也就是说，
"答不出来就拒答"这个防幻觉机制**完全失效**——它等于不存在。

而最可怕的地方在这里：

> **这个 bug 在功能测试里完全看不出来。** 接口 200、答案有引用、流程全通。
> 你甚至会觉得"系统工作得很好"。

为什么 0.35 会失效？因为**余弦相似度没有"绝对零度"**：

```
  正样本相似度： min=0.4654 均值=0.6755 中位=0.6939 max=0.8297
  负样本相似度： min=0.4144 均值=0.5704 中位=0.5703 max=0.7819
```

BGE-M3 上两段**毫不相关**的中文，相似度也在 **0.5704** 左右。
所以"相似度 0.5"并不意味着相关，它可能只是"都是中文"。
**阈值必须落在这两个分布的"缝"里，而缝在哪里只能测出来。**

第三个理由是一句工程纪律：

> **换了 embedding 模型，必须重新标定。** 相似度的尺度完全变了。

本篇就是把这个纪律变成一条可执行的流水线。

## 1. 要解决的问题

| 现象 | 真实原因 |
| --- | --- |
| 防幻觉闸门形同虚设，任何问题都放行 | 阈值（0.35）低于负样本均值（0.5704），**统计上必然 100% 放行** |
| 功能测试全绿，但系统在"假装工作" | 缺的是**否定性断言**：没有一条用例检查"无关问题有没有被拦下" |
| 调阈值像调玄学，调完不知道好不好 | 没有 F1/recall/误放行的**扫描曲线**，只有一个孤零零的点 |
| 换成另一个 embedding 模型后，拒答率暴涨或归零 | 换模型改了相似度尺度，但阈值没重新标定 |
| 两个阈值各调各的，组合起来效果不明 | 闸门是「向量 **或** 覆盖率」，两个阈值**不独立** |
| "消融实验"跑出来 `vector recall@5 = 0.000`，且 `hybrid` 与 `bm25` **一模一样** | 向量那一路根本没参与（E7.6） |
| 把 +1.2 个点写进简历，面试官一问就露馅 | 43 条用例翻转 1 条 = 2.3 个点，那 1.2 个点**完全是噪声** |
| 得出"重排没用"的结论 | 离线模式下重排走启发式兜底，`hybrid` 与 `hybrid_rerank` 必然相同 |
| 想看阈值扫描表，结果表里没有"最优点"那一行 | 打印时按 5% 取整抽样，而最优点落在 1% 的步长上 |

最后一条是本篇一个很好的"读数据"训练：**你看到的那张表是抽过样的**。

### 2.2 关键代码 1：闸门到底是什么

先把这个"开关"的语义钉死。闸门在 `retrieval/autocut.py`，它和 autocut 是两个东西：

```python
# backend/src/knowflow/retrieval/autocut.py L1-L22（模块 docstring）
"""分数断崖截断（autocut）与相关性闸门（gate）。

**两个不同的东西，容易混为一谈：**

**1. autocut —— "结果里只有前几条是相关的"**
    检索总会返回 `top_k` 条，即使第 4、5 条其实是噪声。
    把噪声塞进 Prompt 有两个害处：占 token（花钱）、干扰模型（更容易编）。
    autocut 的做法：看分数**断崖**——排序后如果第 n 条的分数掉到第 1 条的
    某个比例以下，就把它和后面的一起丢掉。
    这是"自适应 top_k"：简单问题可能只留 1 条，复杂问题留 5 条。

**2. gate —— "这一批结果全都不相关"**
    双阈值：`向量相似度 ≥ 阈值` **或** `查询词覆盖率 ≥ 阈值`。
    两条都不满足 → **不调大模型**，直接拒答。
    为什么用"或"而不是"与"：两条信号覆盖不同的失败模式 ——
    向量强在语义改写（"房费"↔"住宿标准"），覆盖率强在专有名词
    （"PAYLOAD_TOO_LARGE"）。用"与"会把两种正确情况都误杀。

**为什么 gate 比 autocut 更重要**：autocut 省的是钱，gate 省的是**幻觉**。
模型手里没有资料时最容易编，而工程上"确保它手里有对的资料"比
"让它别编"有效得多。
"""
```

判定本体只有几行，但有一处细节直接决定了标定该怎么做：

```python
# backend/src/knowflow/retrieval/autocut.py L81-L124（evaluate_gate，节选）

    `best_vector_score` 只看**有向量分数**的候选（BM25 独有候选没有向量分，
    不能当成 0 参与 max，否则会把"关键词命中但向量没召回"的情况误杀）。
    `best_keyword_coverage` 同理是全体候选的最大值。
    """
    ...
    vector_ok = best_vector >= vector_threshold
    keyword_ok = best_coverage >= keyword_threshold

    if vector_ok:
        reason = REASON_VECTOR
    elif keyword_ok:

```

**"或"这个字决定了标定的方法论**：两个阈值不是独立的，
所以 `calibrate_threshold.py` 只给出**各自单独扫描**的建议，
并在最后明确写出这个局限：

```python
# backend/scripts/calibrate_threshold.py L272-L274

    print("  实际误放行率低于各自单独扫描的结果。要拿到联合效果，请跑")
    print("  scripts/run_eval.py（会真正过一遍 gate 并统计拒答率）。")
```

**"两个单独扫描出来的最优点，合起来不一定是最优组合"**——
这是标定脚本自己承认的边界，也是它把联合验证交给 `run_eval.py` 的原因。

四个 `reason` 是**稳定的机器可读标识**，前端与测试按它分支：

```python

REASON_KEYWORD: Final[str] = "keyword_coverage_above_threshold"
REASON_NO_CANDIDATES: Final[str] = "no_candidates"
```

E6.2 和 E6.3 分别看到了前两个 reason，E6 第 7 项看到了第四个：

### 2.3 关键代码 2：标定脚本怎么构造正负样本

这是整篇最重要的方法学。核心思路是：
**用"期望命中的文档"把语料切成正负两半，然后看这两半的分数能不能分开。**

```python
# backend/scripts/calibrate_threshold.py L85-L117（evaluate，节选）
def evaluate(settings, embedder, texts, docs, matrix, cases, show: int = 6) -> dict:
    positives: list[float] = []
    negatives: list[float] = []
    pos_cov: list[float] = []
    neg_cov: list[float] = []
    ...
    for case in cases:
        question = case["question"]
        expected = case.get("expected_doc")
        query = np.asarray(embedder.embed_query(question), dtype=np.float64)
        sims = matrix @ query  # 已归一化，点积即余弦

        pos_mask = np.array([d == expected for d in docs])
        neg_mask = ~pos_mask
        if not pos_mask.any():
            continue

        best_pos = float(sims[pos_mask].max())
        best_neg = float(sims[neg_mask].max()) if neg_mask.any() else 0.0
        positives.append(best_pos)
        negatives.append(best_neg)

        # 关键词覆盖率同理（用的是线上那份唯一实现）
        pos_texts = [t for t, d in zip(texts, docs, strict=True) if d == expected]
        neg_texts = [t for t, d in zip(texts, docs, strict=True) if d != expected]
        cov_pos = max((coverage(question, t) for t in pos_texts), default=0.0)
        cov_neg = max((coverage(question, t) for t in neg_texts), default=0.0)
```

四个方法学要点，每一个都能被质疑：

1. **`sims = matrix @ query` 用点积算余弦**——因为向量在写入前已经 L2 归一化过
   （阶段 4 的 `l2_normalize`）。**这句话把阶段 4 和阶段 11 串起来了**：
   如果归一化没做，这里算的就不是余弦，标定出来的阈值也没意义。
2. **取 `max` 而不是均值**：检索返回的是**最高分**，所以"这条题能不能通过闸门"
   取决于它的最高分。用均值会得出一个和线上行为无关的数字。
3. **负样本 = "其它文档"里最高的那个分数**——这才是"最危险的那个干扰项"。
   如果取负样本的均值，问题会显得很容易（分数低），阈值会被标得偏高。
4. **`coverage` 用的是线上那份唯一实现**（`retrieval.text.coverage`），
   而不是 `evaluation.metrics.keyword_coverage`。理由在阶段 10 讲过：

   > 线上切词是 **1-gram + 2-gram 混合 + 停用词过滤**，评测模块是**纯 2-gram、不过滤停用词**，
   > 所以"不能把评测函数的输出直接和 `KEYWORD_MIN_COVERAGE` 比大小"。

   **标定脚本 import 对了那个函数，是它结论可信的前提。**

语料侧也是"用线上同一套代码"，这一点写在脚本开头：

```python
# backend/scripts/calibrate_threshold.py L15-L21（节选）

```

### 2.4 关键代码 3：F1 扫描与"为什么表里看不到最优点"

```python
# backend/scripts/calibrate_threshold.py L149-L181（sweep_vector，节选）
def sweep_vector(data: dict) -> tuple[float, list[dict]]:
    """扫向量阈值，取 F1 最优。"""
    positives, negatives = data["positives"], data["negatives"]
    rows: list[dict] = []
    best: tuple[float, float] | None = None

    for step in range(30, 96):
        threshold = step / 100
        tp = sum(1 for v in positives if v >= threshold)
        fn = len(positives) - tp
        fp = sum(1 for v in negatives if v >= threshold)
        tn = len(negatives) - fp
        precision = tp / (tp + fp) if (tp + fp) else 0.0
        recall = tp / (tp + fn) if (tp + fn) else 0.0
        f1 = 2 * precision * recall / (precision + recall) if (precision + recall) else 0.0
        rows.append({...})
        if best is None or f1 > best[0]:
            best = (f1, threshold)
```

这段代码把"阈值选择"定义成了一个**分类问题**：

| 术语 | 在这里的含义 |
| --- | --- |
| 正样本 | 该问题的**期望文档**里的切片 |
| 负样本 | **其它文档**的切片（最高的那个） |
| `tp` | 正样本分数 ≥ 阈值 → 该放行的放行了 |
| `fn` | 正样本分数 < 阈值 → **误杀**（本该回答却拒答） |
| `fp` | 负样本分数 ≥ 阈值 → **误放行**（本该拒答却回答） |
| `recall` | `tp / (tp+fn)`：该放行的比例 |
| `误放行` | `fp / |negatives|`：不该放行的比例 |
| `F1` | precision 与 recall 的调和平均 |

**注意这里 `recall` 的定义与检索指标不同**：它是"闸门放行率"，
不是"检索召回率"。**同名不同义是标定文档里最常见的误解来源**，所以脚本里
用的是 `positives/negatives` 这套词，而不是 `retrieved/relevant`。

打印时只显示 5% 的整数倍：

```python
# backend/scripts/calibrate_threshold.py L244-L250（节选）
    for row in vec_rows:
        if int(row["threshold"] * 100) % 5 == 0:
            mark = " ←最优" if row["threshold"] == vec_threshold else ""
            print(
                f"  {row['threshold']:6.2f} {row['recall']:8.3f} {row['false_accept']:8.3f} "
                f"{row['precision']:10.3f} {row['f1']:7.3f}{mark}"
            )
```

**`% 5 == 0` 就是那张表"看不到最优点"的原因**：

- 扫描步长是 **1%**（`range(30, 96)` → 0.30~0.95）；
- 打印步长是 **5%**；
- 而真正的最优点落在 **0.63**（不是 5 的倍数）上。

从 E7 的产出物 `data/threshold_calibration.json` 里把**完整扫描**取出来对比
（本会话复核，数字与 E7 的打印表一致）：

| 阈值 | recall | 误放行 | precision | F1 | tp/fp/tn/fn |
| --- | --- | --- | --- | --- | --- |
| 0.35（原默认） | 1.000 | **1.000** | 0.500 | 0.667 | 43 / 43 / 0 / 0 |
| 0.60（最终采用） | 0.907 | 0.349 | 0.722 | 0.804 | 39 / 15 / 28 / 4 |
| **0.63（F1 最优）** | 0.791 | 0.140 | 0.850 | **0.819** | 34 / 6 / 37 / 9 |
| 0.65 | 0.721 | 0.093 | 0.886 | 0.795 | 31 / 4 / 39 / 12 |

**`0.35` 那一行的 `tp/fp/tn/fn = 43/43/0/0` 是全篇最触目惊心的四个数字**：
`tn = 0` 意味着**一条负样本都没被正确拒绝**。这不是"效果不好"，
这是"这个阈值在统计上等于没有闸门"。

> **读数据的纪律**：看到一张表，先问"它是不是全量"。
> 这里的 `← 最优` 标记**从来没有出现在打印出来的任何一行上**——
> 因为最优阈值 0.63 被 `% 5` 过滤掉了。
> 换句话说：**只看打印出来的表，你根本找不到脚本给出的那个建议值**。

### 2.5 关键代码 4：最终为什么取 0.60 / 0.40 而不是 0.63 / 0.44

脚本给的是 F1 最优点（0.63 / 0.44），项目最终配置的是 **0.60 / 0.40**。
这不是"没听脚本"，而是**F1 不是唯一的判据**。

用真实数据算一下 0.63 → 0.60 这一步的代价与收益：

| | 误杀正样本（fn） | 放行负样本（fp） | recall | 误放行 | F1 |
| --- | --- | --- | --- | --- | --- |
| 0.63 | **9** 条 | 6 条 | 0.791 | 0.140 | **0.819** |
| 0.60 | **4** 条 | 15 条 | 0.907 | 0.349 | 0.804 |

- **收益**：少误杀 **5** 条正样本（9 → 4），recall 从 0.791 升到 0.907；
- **代价**：多放行 9 条负样本（6 → 15）；
- **F1 只掉 0.015**（0.819 → 0.804）。

**为什么这个交换是划算的**——它取决于两类错误的**业务后果不对称**：

| 错误类型 | 用户感受 | 严重度 |
| --- | --- | --- |
| 误杀（fn） | "我明明有这个制度，它却说答不了" | 高：功能不可用 |
| 误放行（fp） | 模型拿到一批不太相关的资料 | 中：还有 Self-RAG 反思与引用机制兜底 |

也就是说：**闸门不是最后一道防线，它后面还有两道**（`grade` 判定与 `reflect` 反思）。
所以"松一点"的风险是被后面两道拦住的，而"紧一点"的代价是**用户直接拿不到答案**。

> ⚠ 但**这个取舍是"数据 + 判断"的组合，不是纯数据**。
> 换一个系统（后面没有反思机制）、换一批用户（更不能容忍错的答案），
> 正确的选择可能正好相反。**脚本给最优点，人给最终值——这一步不该被自动化掉。**

覆盖率一侧同理（从 `threshold_calibration.json` 复核）：

| 阈值 | recall | 误放行 | F1 |
| --- | --- | --- | --- |
| 0.40（最终采用） | 0.767 | 0.372 | 0.717 |
| **0.44（F1 最优）** | 0.744 | 0.186 | **0.771** |

**注意最终取值 0.40 比最优点更松**，理由与向量侧完全一致。

### 2.6 关键代码 5：正负样本**分布重叠**——单一阈值在原理上无法完美分离

这一节是本篇最重要的**结论**，因为它决定了"下一步该做什么"。

```
  正样本相似度： min=0.4654 均值=0.6755 中位=0.6939 max=0.8297
  负样本相似度： min=0.4144 均值=0.5704 中位=0.5703 max=0.7819
```

把它画出来（同一根数轴）：

```
 0.41        0.47              0.57            0.69          0.78      0.83
  │           │                 │               │             │         │
  ├───────────┼─────────────────┼───────────────┼─────────────┼─────────┤
              ▲                 ▲               ▲             ▲
        正样本 min=0.4654   负样本均值     正样本中位    负样本 max=0.7819
                             =0.5704       =0.6939
              └────────── 重叠区（正 min 0.4654 ~ 负 max 0.7819）──────────┘
```

**关键事实：正样本 min（0.4654）< 负样本 max（0.7819）。**
两个分布**互相穿插**，不是"两个山峰中间有个谷"。

从数据里直接数一下重叠程度（本会话从 `threshold_calibration.json` 复核）：

| 统计量 | 值 |
| --- | --- |
| 落入重叠区（`≤ 负 max`）的**正样本** | **40 / 43** |
| 落入重叠区（`≥ 正 min`）的**负样本** | **40 / 43** |

**93% 的样本（40/43）落在重叠区间里**。这意味着：

> **不存在任何一个阈值能完美分离正负样本。**
> 无论你把阈值设在哪里，都必然同时存在误杀与误放行。

这句话是有严格依据的：只要 `正 min < 负 max`，
"所有正样本都通过"与"所有负样本都被拒"就无法同时成立。

**所以正确的下一步不是继续调阈值**，而是**补信号**。E7 的结论写得很直接：

```
3. **正负样本分布重叠严重**（正 min=0.465 < 负 max=0.782），
   说明**单一向量阈值在原理上无法完美分离**——正确解法是补信号
   （真实交叉编码器重排 / 显式可答性判断），而不是继续调阈值。
```

三个"补信号"的方向，按性价比排序：

| 方向 | 原理 | 状态 |
| --- | --- | --- |
| **真实交叉编码器重排**（`bge-reranker-v2-m3`） | 用 query-doc 对的**交互式**打分替代双塔点积，对"字面像但语义无关"的判别力强得多 | ⚠ **未实现**（E11）；roadmap 已列 |
| **显式可答性判断**（answerability） | 让模型直接回答"这段资料能不能回答这个问题"，而不是用相似度**代理**它 | 已有 `grade` 节点（阶段 7），但它是二值判据、且在检索**之后** |
| **多路信号联合**（而不是"或"） | 目前是 `向量 OR 覆盖率`；可以改成"向量分 + 覆盖率 + 交叉编码器分"的加权模型 | 部分：融合已有 RRF，但闸门仍是硬"或" |

**"补信号而不是调阈值"这句话的通用形态**：
当你发现"两个类别的分布重叠"时，说明**当前特征的信息量不够**。
继续调决策边界只是在"误杀"与"误放行"之间搬家，不可能变好。
**这时候该做的是加特征，不是调参数。**

### 2.7 关键代码 6：消融实验——`run_eval.py` 怎么给出那张表

标定只管闸门，消融管整条链路。它的入口是一个 CLI：

```python

它把"我感觉更好了"变成可比较的数字：

所以除了均值，还会用 `paired_bootstrap_test` 给出 p 值与置信区间 ——

```

指标列是**固定清单**（不是随意拼的字典）：

```python

METRIC_COLUMNS = [
    ("hit_rate", "命中率", "{:.3f}"),
    ("recall_at_k", "recall@k", "{:.3f}"),
```

打印对比表（`← 基线` 是自动标的）：

```python
# backend/scripts/run_eval.py L58-L69（print_table，节选）
def print_table(results: dict[str, dict[str, Any]], baseline: str) -> None:
    header = f"  {'模式':<16s}" + "".join(f"{label:>12s}" for _, label, _ in METRIC_COLUMNS)
    print(header)
    print("  " + "-" * (len(header) - 2))
    for mode, metrics in results.items():
        row = f"  {mode:<16s}"
        for key, _label, fmt in METRIC_COLUMNS:
            value = metrics.get(key)
            row += f"{'—':>12s}" if value is None else f"{fmt.format(value):>12s}"
        if mode == baseline:
            row += "   ← 基线"
        print(row)
```

注意 `value is None` 打的是 `—` 而不是 `0`：这与阶段 10 讲的
"**没算 ≠ 0 分**"是同一条纪律（`faithfulness` 在离线模式下就是 `None`）。

显著性部分才是这个脚本的灵魂——**它会把"不显著"明说出来**：

```python
# backend/scripts/run_eval.py L100-L111（print_significance，节选）
        mark = "是" if report["significant"] else "否"
        note = ""
        if not report["significant"] and abs(delta) > 0:
            # 这是本脚本最想传达的一句话
            note = "  ← 差异不显著，不要当成改进"
        contrast = f"{mode} vs {baseline}"
        interval = f"[{low:+.4f}, {high:+.4f}]"
        print(
            f"  {contrast:<34s}{delta:>+10.4f}{report['p_value']:>10.3f}"
            f"{interval:>22s}{mark:>8s}{note}"

```

**`note = "  ← 差异不显著，不要当成改进"` 这一行是刻意写进工具输出的**。
工具不该只给数字，还该给出**读法**——因为"看见 +1.2% 就以为变好了"是人的默认反应。

逐条结果要落库才能做配对检验：

```python
# backend/scripts/run_eval.py L189-L198（节选）
            if run_id is not None:
                with container.session_factory() as session:

                        session.execute(
```

### 2.9 ⭐ `kb_ids` 缺失导致的"静默测了个空"（E7.6）

#### 现象

第一次跑消融时得到的**不是**上面那张表，而是这个：

```
  vector          recall@5 = 0.000
  bm25            recall@5 = 0.721
  hybrid          recall@5 = 0.721     ← 与 bm25 完全相同
  hybrid_rerank   recall@5 = 0.721     ← 与 bm25 完全相同
```

#### 指纹

> **"hybrid 与 bm25 一模一样"就是"向量那一路完全没参与"的指纹。**

这句话是本节的核心。为什么？

- `hybrid` = 向量 ∪ BM25 融合后的结果。如果向量那一路返回空，
  融合结果就**恰好等于** BM25 的结果；
- 同理 `hybrid_rerank` 只对 `hybrid` 的候选做重排，上游一样，结果自然一样；
- 而 `vector` 模式**只有**向量一路 → 全空 → `recall@5 = 0.000`。

四个数字连起来看，是一个**结构性**的证据链，而不是"效果差"：

| 模式 | 期望（正常） | 观测 | 差值说明 |
| --- | --- | --- | --- |
| `vector` | 0.860 | **0.000** | 完全没检索到 → 不是"差"，是"空" |
| `bm25` | 0.721 | 0.721 | 唯一在工作的那一路 |
| `hybrid` | 0.849 | **0.721** | 与 bm25 完全相同 → 向量贡献为 0 |
| `hybrid_rerank` | 0.849 | **0.721** | 与 bm25 完全相同 → 同上 |

**"三个模式完全相同"这种东西，在真实的检索系统里是不该出现的。**
真实的融合一定会有增益或损失（哪怕很小）。出现"精确相等"只有两种可能：
① 某一路恒为空；② 融合权重把某一路完全压掉了。

#### 根因

```
根因：`run_evaluation(kb_ids=None)` 时，脚本调用方没有传 KB 列表，
而检索引擎在"没有任何 KB 目标"时会**跳过向量召回**（向量库按 KB 分集合，没目标无从查起；
BM25 则可以跨库搜）。于是 `vector` 模式**根本没检索**，返回 0 —— 但接口 200、指标算得出、表打得出来。
```

用图解释这个**不对称**：

```
   向量库（Chroma）
   ┌──────────────────┐
   │ knowflow_kb_1    │  ← 按 KB 分集合
   │ knowflow_kb_2    │
   └──────────────────┘
   查询必须指定"查哪个集合"  →  没有 kb_id 时**无从查起**  →  跳过（返回空）

   BM25（内存倒排索引）
   ┌────────────────────────────────────┐
   │ 一个全局索引，payload 里带 kb_id     │  ← 可以跨库搜
   └────────────────────────────────────┘
   查询不指定 kb_id 也能搜（只是范围大）  →  正常返回
```

**这个不对称本身是合理的设计**（阶段 4 讲了"按 KB 隔离集合"的好处：
删 KB = drop 集合，且杜绝串库）。问题在于**评测层没有把这个前提补齐**。

#### 修法

```python
# backend/src/knowflow/evaluation/harness.py L433-L455（节选）
    # ⚠ kb_ids 缺省时必须在这里兜底解析（这是一次真实事故换来的）：
    # 检索引擎在"没有任何 KB 目标"时会**跳过向量召回**（向量库按 KB 分集合，
    # 没目标就无从查起；而 BM25 可以跨库搜）。于是评测会跑出一张看起来正常的表：
    #     vector recall@5 = 0.000 （不是 0 分，是根本没检索）
    #     bm25/hybrid/hybrid_rerank 三者完全相同（向量那一路完全没参与）
    # **"hybrid 与 bm25 一模一样"就是向量没参与的指纹。**
    # 如果只看总数，很容易把"向量没用"当成结论去调融合权重 —— 方向完全错了。
    # 评测工具最怕的就是静默地测了个空。
    if kb_ids is None:
        resolved_kb_ids: list[int] = [
            int(row)
            for row in session.execute(
                select(KnowledgeBase.id)
                .where(KnowledgeBase.deleted_at.is_(None))
                .where(KnowledgeBase.is_active.is_(True))
                .order_by(KnowledgeBase.id)
            ).scalars()
        ]
        logger.info("eval.kb_ids_resolved", count=len(resolved_kb_ids), kb_ids=resolved_kb_ids)
        if not resolved_kb_ids:
            logger.warning("eval.no_active_kb", detail="没有任何启用的知识库，评测结果必然全为 0")
    else:
        resolved_kb_ids = list(kb_ids)
```

**修法选在评测层而不是检索引擎层，这是刻意的**：

```
（另一个候选修法是"让检索引擎在向量模式下无 KB 就报错"，但那会破坏"全局 BM25 检索"这个合法用法，
所以选择在评测层兜底。）
```

| 候选修法 | 后果 |
| --- | --- |
| 检索引擎在向量模式下无 KB 就抛异常 | ❌ 破坏"全局 BM25 检索"这个合法用法（有人真的想跨库搜关键词） |
| 评测层兜底解析活跃 KB（**采用**） | ✅ 评测工具自己保证"输入完整"，检索引擎的语义不变 |
| 让 `run_eval.py` 强制传 `--kb-ids` | ⚠ 能修，但下一个调用方（HTTP 接口、CI）还会忘 |

**"在哪一层修"的判据**：修在**最靠近缺陷的那一层**。
缺陷是"评测工具没有准备齐输入"，而不是"检索引擎不该跨库搜"，
所以要修在评测层。

#### 教训

```
**教训**：评测工具最怕的就是**静默地测了个空**。
凡是"跑完了、有数字、全绿"但结果不合常理的情况，先怀疑"这一步真的执行了吗"。
```

这条教训可以推广成一条**可执行的检查清单**——本文建议你在任何评测工具里都加上：

| 检查 | 为什么 |
| --- | --- |
| 每个模式的**候选数**是否 > 0 | `vector` 返回 0 条 = 没检索，而不是"检索得差" |
| 有没有**两个模式指标完全相同** | 系统里不该出现"精确相等"，出现了就说明某一路是空的 |
| 基线是否**真的更强** | 如果"改进版"与"未改进版"完全一样，先查"改进版的那一步执行了吗" |
| 用例数是否等于数据集条数 | `43 → 0` 这种"跳过"很容易被 `if not pos_mask.any(): continue` 这类代码静默吃掉 |

（最后一条是标定脚本里的真实写法：
`if not pos_mask.any(): continue`——如果 `expected_doc` 写错了名字，
那条用例会被**静默跳过**。所以它必须打印 `参与评测的用例：43 条` 与总条数对比。）

### 2.10 换 embedding 模型必须重新标定

这一条在 E7 的结论里是第 5 点，但它值得单独展开，因为它**最容易在升级时被忘掉**：

```
5. **换 embedding 模型必须重新标定**——相似度的尺度完全变了。
```

为什么"尺度完全变了"必然发生：

| | BGE-M3（1024 维，中文强） | 假设换成 all-MiniLM-L6-v2（384 维，英文） |
| --- | --- | --- |
| 无关中文对的余弦 | **0.5704**（E7 实测的负样本均值） | 可能只有 0.2~0.3 |
| 相关对的余弦 | 0.6755（正样本均值） | 可能 0.6~0.7 |
| 正负样本的"缝" | 0.46~0.78 之间 | 完全不同的区间 |

**同样的 0.60 阈值，在 BGE-M3 上是"略宽松"，在 MiniLM 上可能是"全部拒答"。**
两个方向都是灾难：

- 阈值相对偏高 → **拒答率暴涨**，用户觉得"系统坏了"；
- 阈值相对偏低 → **闸门失效**（就是本篇开头的 0.35），防幻觉机制消失。

而且这个错误**和 0.35 那次一样，功能测试看不出来**（接口 200、有引用、流程全通），
只能靠 `/health` 与拒答率指标事后发现。所以正确的流程是：

```
换 embedding 模型
  → ① EMBEDDING_DIM 改对（阶段 4，启动期就会报维度不匹配）
  → ② 清空向量库重新入库（旧向量与新向量不在同一个语义空间）
  → ③ 重跑 calibrate_threshold.py，重新取阈值 ★ 这一步最容易被忘
  → ④ 重跑 run_eval.py，确认 recall 没有整体退化
  → ⑤ 重跑 smoke_pipeline.py，确认三方一致性（34/34/34）
```

**第 ③ 步之所以最容易被忘**，因为前两步是"会报错的"（维度不匹配会炸、
旧向量检索结果明显错乱），而第 ③ 步**不报错**——
它只是让闸门悄悄变松或变紧。

> 同样的道理适用于**换融合策略**（rrf → weighted）、**换 chunk_size**、
> 甚至**换文档的语言分布**。凡是改变了"分数尺度"的改动，都要重新标定。

### 2.11 关键代码 8：把结果固定下来（为什么 `--out` 不是可选项）


**为什么必须存"原始样本"而不只是"扫描表"**：

1. **论文级可复核**：`positives` / `negatives` 是 43 + 43 个数字，
   别人可以拿它重新算任何阈值下的 F1，不必相信你的表；
2. **换判据不用重跑**：想改成"最大化 recall 且误放行 < 0.2"？直接拿 JSON 算，不用再加载 2GB 模型；
3. **本教程就靠它做了一次零成本复核**：本篇 2.4/2.5/2.6 三节里那些"从
   `threshold_calibration.json` 复核"的数字，都是直接读这个文件算出来的——
   **没有加载模型**。这就是"把原始数据存下来"的直接收益。

`run_eval.py` 同理，而且它还额外存了**逐条 recall**：

```python
# backend/scripts/run_eval.py L240-L243（节选）
                    "per_case_recall": {
                        mode: {str(k): v for k, v in values.items()}
                        for mode, values in per_case.items()
                    },
```

**`per_case_recall` 是配对 bootstrap 的原料**。存了它，就意味着：
**任何时候都能重新算 p 值，而不必重跑一次评测（不必再花 30 分钟和几块钱）**。
本篇的验证 2 正是靠它复现了 E7.5 的 `p=0.010`。

存 JSON 时还有一个小细节值得注意：

```python
# backend/scripts/run_eval.py L223-L225（节选）
    if args.out:
        out_path = Path(args.out)
        if not out_path.is_absolute():
            out_path = settings.data_dir.parent / args.out
```

**相对路径的基准是 `data_dir.parent`（仓库根），而不是当前工作目录**。
这样"在仓库根跑"和"在 backend 里跑"得到同一个结果——
**一个工具的行为不该取决于你在哪个目录调用它**。

### 2.12 关键代码 9：口径必须与线上一致（`utf-8-sig` 的小心思）

读用例文件时用了 `utf-8-sig`：

```python
# backend/scripts/calibrate_threshold.py L73-L82
def load_cases(settings) -> list[dict]:
    path = settings.data_dir / "eval_cases.jsonl"
    cases: list[dict] = []
    with path.open(encoding="utf-8-sig") as fh:
        for line in fh:
            line = line.strip()
            if not line or line.startswith("#"):
                continue
            cases.append(json.loads(line))
    return cases
```

三个细节：

1. **`utf-8-sig` 而不是 `utf-8`**：这个编码在解码时会**吃掉 BOM**
   （如果有的话）。标注文件常常是"用 Excel / 记事本另存为 UTF-8"导出的，
   那些工具**默认加 BOM**。如果第一条数据的 key 变成 `"\ufeffquestion"`，
   `case["question"]` 会直接 `KeyError`——**而报错信息完全指不到"是 BOM 的问题"**
   （阶段 3 的编码嗅探里也有同一类坑）。
2. **`startswith("#")` 跳过注释行**：标注文件需要能写注释（"这条题为什么这么标"），
   否则维护者只能把说明写到另一个文件里，然后它就丢了。
3. **一行一个 JSON（JSONL）而不是一个大 JSON 数组**：追加一条新用例不需要改动整个文件，
   git diff 也只显示新增的那一行——**对"会被反复修改的标注文件"来说这很重要**。

⚠ 顺带一个**本会话实测的工具链坑**：在 **Windows PowerShell 5.1** 里直接
`Get-Content data\eval_cases.jsonl` 看这个文件，会显示成一片乱码
（`{"question": "涓€绾垮煄甯備綇瀹挎爣鍑嗘槸澶氬皯"`）——
因为 PS 5.1 默认按系统 ANSI（本机 GB2312）读。**Python 侧读得完全正确**
（它显式声明了 `utf-8-sig`），所以这不是数据坏了，是**查看方式**错了。
要看请用 `Get-Content data\eval_cases.jsonl -Encoding UTF8`。

| 用哈希兜底模式标定出来的阈值配到生产 | 哈希向量无语义，尺度完全不同 | 标定必须用**真实 embedding**；兜底模式只能验证"脚本能跑通" |

| 两次跑同一份数据得到不同的 p 值 | 用了全局 `random` | `random.Random(seed)` 显式实例化（脚本已用 `seed=42`） |
