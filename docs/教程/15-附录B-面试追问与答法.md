## 一、RAG 与检索（Q1~Q9）

### Q1. 为什么要做混合检索？只用向量不行吗？

**要点**
- **两路的盲区互补**：稠密向量强在"同义改写/口语提问"，盲区是**专有名词、错误码、型号**；
  BM25 强在精确词面与罕见词，盲区是"换个说法就查不到"。
- **有实测的显著结论**：`bm25 → hybrid_rerank`，recall@5 **0.721 → 0.849**，
  Δ **+0.128**，95% CI **[+0.035, +0.244]**，**p = 0.010**（配对 bootstrap，43 条用例）（E7.5）。
- **量化代价几乎为零**：BM25 只花 **5ms**，向量召回 **58ms**，混合 **56ms**（E7.5）
  —— 多一路信号的边际成本可以忽略。
- **小语料上它不是"最优"但更鲁棒**：RRF 在这 34 个切片上略逊纯向量（0.849 vs 0.860，**不显著**），
  但**专有名词类问题靠 BM25 兜底**（E7.5 结论 3）。

**如果被追问**：那为什么不只用 BM25？
→ 因为纯 BM25 的 recall@5 是 **0.721**，且它完全无法处理"同义改写"
（E7 里正样本相似度均值 **0.6755** 正是向量那一路在干活的证据）。

### Q2. 融合为什么用 RRF，而不是加权归一化？

**要点**
- **量纲不同，不能直接加权**：向量分是 cosine（约 0~1），BM25 分无上界、量级可能差两个数量级
  —— 所以"加权"之前**必须先归一化**，这是第一层复杂度。
- **RRF 只用排名不用分数**（`Σ 1/(k + rank)`，本项目 `rrf_k=60`），
  对"某一路分数尺度漂移"免疫；加权 min-max 的话，**换一个 embedding 模型就要重调权重**。
- **代价我承认且量过**：小语料上 RRF 略逊纯向量（0.849 vs 0.860，p=0.820，**不显著**）——
  原因是 RRF 丢弃分数幅度，BM25 挤进了几个候选，把部分正确的向量命中往下压（E7.5 结论 3）。
- **结论**：**在没人持续调参的系统里，鲁棒性比理论最优更重要**（E7.5 原话）。
  两种都实现了，`FUSION=weighted` 可切。

**如果被追问**：`rrf_k=60` 是怎么定的？
→ 工业界默认（原论文与 Elasticsearch 的常用值）；本项目**没有单独标定 `rrf_k`**
——这是一个诚实的空白，标定它需要更大的评测集，43 条用例区分不出来。

### Q3. BM25 的 IDF 为什么要 `+1`？

**要点**
- 经典形式的 IDF 是 `log((N - df + 0.5) / (df + 0.5))`，当 **`df > N/2` 时会变负**。
- 后果：**包含该高频词的文档反而被扣分** —— 用户看到的表现是
  **"越常见的关键词越查不到"**，而且不报任何错。
- 本项目实现里取 `+1` 保证 **IDF 恒正**；`backend/tests/test_bm25.py` 的第一条承诺就是
  "**IDF 恒正**"，并且用手算值逐条对照（E1.5）。
- 为什么必须手算对照：BM25 分数**没有"看起来对不对"这回事**——参数或归一化写错，
  排序整体变样但不会报错（`test_bm25.py` 的 docstring 原话）。

**如果被追问**：`k1` / `b` 取多少？
→ 本项目用 BM25 的常规默认（`k1≈1.5`、`b≈0.75` 一档），
**没有在评测集上标定过它们**；标定收益在 43 条用例上不可分辨。

### Q4. 中文为什么用 1-gram + 2-gram，不引 jieba？

**要点**
- **`split()` 在中文上直接失效**：`一线城市住宿标准` 用空格切出来是 **1 个词**，
  BM25 的倒排索引形同虚设（`docs/00` §2.1）。
- 本项目的切词是 **1-gram + 2-gram 混合**：`一线城市` →
  `一 线 城 市 一线 线城 城市`。
  **1-gram 保证召回（不会漏），2-gram 提供区分度**（`城市`/`住宿` 比单字有信息量）。
- 全项目**只有这一份切词实现**（`retrieval/text.py`）：BM25 打分与闸门的
  `keyword_coverage` 都建立在它上面 —— 两份实现漂移一点，`KEYWORD_MIN_COVERAGE` 的语义就跟着漂
  （`test_retrieval_text.py` 的 docstring）。
- 还有一个被修过的边界：**文本切不出词元时覆盖率必须是 0.0，不能是 1.0**
  （否则 `"!!!"` 会被判成"完全命中查询"，放行一段毫无意义的文本）。

**如果被追问**：为什么不引 jieba？
→ 三个理由：**零依赖**（不引额外分词器/词典）、**可复现**（不依赖词典版本）、
**白板可推导**（面试能讲到 n-gram 为什么会命中）。
代价是**没有词性/实体信息**，长词会被 2-gram 切碎 —— 这正好由向量那一路补。

### Q5. 父子块（parent-child chunk）解决了什么？

**要点**
- **"用小检索、用大写答案"**：子块小 → 向量更精准、命中率高；父块完整 → 模型看到完整小节，
  不会因为"只看到半句"答错。
- **同窗口共享同一段父块**（这是刻意的）：命中窗口内任意一个子块，
  拿到的上下文**完全一致**，回答不会因为"命中第 2 块还是第 3 块"而漂移 ——
  **上下文确定性**（`chunkers.py::_assign_parents` 的 docstring）。
- **父块不是"子块文本拼接"**，而是**按区间回原文取**：相邻子块本来就有
  `chunk_overlap=120` 的重叠，直接拼会得到"同一句话出现两遍"的父块（浪费 token、主导向量）。
- **不跨小节、不跨页**（小节自带 `page_no`）：跨边界会让"引用来源"变成一个说不清的范围。

**如果被追问**：父块存哪？
→ **不落盘，只活在 BM25 的内存 payload 里**（`to_bm25_payload` 带 `parent_content`）；
MySQL 里只存子块。这样"父块"这个派生物不需要和主库保持同步。

### Q6. 重排为什么只对 top-N 做？

**要点**
- 重排是**贵且慢**的一步（本项目是 LLM 重排 + 启发式兜底），只配用在"已经召回的少量候选"上。
- 配置层面**强制约束**：`RERANK_TOP_N ≤ FETCH_K` 有交叉校验，违反**启动期就炸**
  （`core/config.py` 的 `_cross_check`）："重排只能作用于已召回的候选"。
- 实测的数据流也能看出来：`/search` 的 debug 里
  `vector_candidates=20, bm25_candidates=12, fused=20, after_autocut=12, after_rerank=12`（E6.3）
  —— 20 条融合 → autocut 砍到 12 → 重排作用在这 12 条上。
- 重排本身很快（E6.3 里 `rerank_ms=1`），**慢的是它依赖的模型调用**；
  离线模式下走启发式，所以那 1ms 不代表真实 LLM 重排的延迟。

**如果被追问**：为什么不重排全量？
→ 成本与延迟随候选数线性（至少）增长，而**收益集中在头部**：
尾部候选即使重排到前面，也大概率不是答案。这是"把预算花在头部"的典型取舍。

### Q7. autocut 的 `min_keep` 为什么不能是 0？

**要点**
- autocut 的语义是"保留分数不低于 `top_score * ratio` 的前缀"（`autocut_ratio=0.35`）。
- 如果允许返回空：**本来能答的问题会因为"相对分低"变成拒答** ——
  这是**比"多给几条不相关的"更严重的错误**（`autocut.py` 的参数说明原话）。
- 所以 `min_keep=1` 是默认值，且**预算裁剪同样遵守**：
  `if len(kept) >= min_keep and used + cost > max_chars`（`autocut.py` L153）
  —— 只写 `if kept and ...` 会让 `min_keep>=2` 形同虚设。
- 同类取舍还出现在 grade 节点：**都没达标但确实召回了内容时，至少留最高分那条**
  （`_heuristic_relevance`），理由逐字是"全丢会让'检索到了一点东西'变成'完全拒答'，通常更糟"。

**如果被追问**：那闸门（gate）不是也会拒答吗？
→ 是的，**两者职责不同**：autocut 管"留几条"（不能留空），
gate 管"要不要答"（可以拒答，且拒答是**短路**，不调模型）。
autocut 返回空会让"gate 该看到的候选"凭空消失 —— 那是**在错误的层次上做决定**。

### Q8. 融合前为什么要归一化？（关联 Q2）

**要点**
- 向量分是 cosine（约 0~1），BM25 分**无上界**（同一批数据里可能 0.3 也可能 37）
  —— **量纲不同，不能直接加权**（`docs/00` §2.2）。
- 加权模式用 **min-max 归一化**：可解释、参数少（只有 `alpha=0.6` 一个权重）。
- 一个必须写对的边界：**所有分数相同时返回全 1.0**
  ——"大家一样好"不等于"大家一样差"（`test_fusion_autocut.py` 第一条承诺）。
- 归一化还带来一个副作用好处：`/search` 里展示的 `score` 是稳定可比的
  （E6.3 实测三条命中 `score=0.764159 / 0.729916 / 0.722104`，同时给出 `vec=` 与 `bm25=` 原始值）。

**如果被追问**：归一化会不会放大噪声？
→ 会。min-max 是**线性拉伸**，某一路分数全挤在 `[0.5, 0.51]` 时会被拉到 `[0, 1]`
—— 这正是本项目默认走 RRF 的原因之一。

### Q9. `keyword_coverage` 到底衡量什么？

**要点**
- 定义：**查询切出的词元里，有多少比例在候选 chunk 里出现过**（唯一实现在 `retrieval/text.py`）。
- 它是闸门的**第二路信号**：向量分不够时靠它兜底（E6.2 就是这么通过的）。
- 三个必须钉住的边界（`test_retrieval_text.py`）：
  **跨标点不产生假词**、**文本切不出词元时返回 0.0（不是 1.0）**、覆盖率随命中单调。
- 它同时也是 `grade` 节点启发式判定的输入：
  `vector_ok or keyword_ok`（`nodes.py::_heuristic_relevance`）——
  **与闸门用同一套语义**，避免"闸门放行了、grade 却说无关"的自相矛盾。

**如果被追问**：覆盖率会不会被高频单字刷高？
→ 会，这正是 1-gram 的代价。缓解手段有两条：**阈值定在 0.40**（E7 标定，不是拍 0.25），
以及**与向量分取 OR**（而不是只看覆盖率）。

## 二、防幻觉与阈值（Q10~Q15）

### Q10. 闸门为什么用 OR 而不是 AND？

**要点**
- 两路各有盲区：**专有名词/错误码**靠 BM25 命中但向量分可能不高；
  **同义改写**靠向量命中但词面覆盖率可能很低。用 **AND 会把这两种正确情况都误杀**。
- **有实测的正面证据**：E6.2（CI 配置、哈希向量）里闸门是**靠覆盖率通过**的：
  `gate: passed=True reason=keyword_coverage_above_threshold best_vec=0.4027 best_cov=1.0000`
  —— 向量那一路（`best_vec=0.4027` < 阈值 0.60）**完全没达标，但链路照样答对了**。
- 拒答是**短路**：两条都不过 → 固定话术，**不调大模型**（下面 Q14 有证明方法）。
- 阈值本身是**标定出来的**，不是拍脑袋的：`calibrate_threshold.py` 在 43 条标注用例上扫参。

**如果被追问**：OR 会不会放得太松？
→ 会，所以**两个阈值都要标定**。E7 的实测正是这个教训：
覆盖率阈值 0.10 时误放行 0.954；0.30 时降到 0.581（E7 的覆盖率扫描表）。

### Q11. 阈值是怎么定出来的？

**要点**
- 数据：**真实 BGE-M3 + 43 条标注用例 + 6 份示例文档切出的 34 个切片**（E7）。
- 做法：对每条问句算 **正样本分数**（与期望命中文档的最高相似度）与
  **负样本分数**（与其它文档 chunk 的最高相似度），扫阈值输出
  `recall / 误放行 / precision / F1`。
- 结果：**F1 最优点在 0.63 / 0.44**（E7 结论）；
  最终取**略宽松的 0.60 / 0.40** 以避免误杀（`core/config.py` L111 的注释逐字）。
- 关键分布（E7）：正样本均值 **0.6755**、负样本均值 **0.5704**；
  负样本 max 高达 **0.7819** —— 这不是"噪声"，是**尺度的性质**。

**如果被追问**：为什么取 0.60 而不是 F1 最优的 0.63？
→ 因为 F1 是对称指标，而**误杀的成本高于误放行**：
误杀是"能答的题直接拒答"（用户立刻感觉到），误放行只是"多给一条不那么相关的上下文"
（还有 prompt 里的"只依据 [n] 作答"兜着）。**不对称的成本要选不对称的点。**

### Q12. 为什么说 `0.35` 是错的？

**要点**
- `VECTOR_MIN_SCORE=0.35`（原默认值）在标定表上是这一行：
  `0.35 → recall 1.000, 误放行 1.000, precision 0.500, F1 0.667`（E7）。
- **误放行 = 1.000 的含义是：任何问题都能通过闸门** ——
  **防幻觉机制形同虚设**，而 bug 在功能测试里**完全看不出来**
  （接口 200、答案有引用、流程全通）（E7 结论 2）。
- 根因是**余弦相似度没有"绝对零度"**：BGE-M3 上两段毫不相关的中文，
  余弦相似度仍在 **0.57** 左右（`负样本均值=0.5704`）——
  所以"相似度 0.5"不代表相关，它可能只是"都是中文"（E7 结论 1）。
- 修完之后的可见变化：无关问题被正确拦下，`reason=below_all_thresholds`（E7 结论 4 / E6 [7]）。

**如果被追问**：这个 bug 是怎么发现的？
→ 写标定脚本、把正负样本分布画出来的时候发现的——**不是靠"看代码看出来"的**。
`0.35` 这个数在任何 code review 里都显得"很合理"。

### Q13. 正负样本分布重叠说明了什么？

**要点**
- 实测：**正样本 min=0.4654**，**负样本 max=0.7819** —— 正的最小值**小于**负的最大值。
- 结论：**单一向量阈值在原理上无法完美分离**这两类。
  继续调阈值只能移动"误杀↔误放行"的平衡点，不能消除重叠区。
- **正确解法是补信号**：真实交叉编码器重排（`bge-reranker-v2-m3`）、
  或显式的"可答性判断"（agent 的 `grade` 节点就是这一类）（E7 结论 3）。
- 这一点也让 `0.60` 这个取值显得**诚实**：它是当前信号下的平衡点，
  不是"我找到了完美阈值"。

**如果被追问**：那 0.60 的误放行率是多少？
→ **0.349**（E7 的阈值扫描表在 0.60 这一行）。
**这个数字要主动说**——它意味着"大约三分之一的无关问题还能钻过去"，
而补上交叉编码器重排正是 roadmap 里的下一步（`docs/00` §8）。

### Q14. 怎么证明拒答路径**没有**调用模型？

**要点**
- 用**可观测数据**证明，不用"我读代码看出来的"：
  E6 第 [7] 项实测——拒答那条 trace 的 span 只有 **`['analyze', 'retrieve']`**，
  且 **`generate.llm span = 0`**。
- 另外三个同向证据（E6 [7]）：
  **gate: `passed=False reason=below_all_thresholds`**、
  **拒答用的是固定话术**（说明是短路，不是模型生成的）、**拒答时不产生引用**。
- 这是"防幻觉"的**成本面**：没资料时短路 = 不花 token；
  工程上把钱花在"确保它手里有对的资料"，比花在"让它别编"更有效（`docs/00` §2.3）。

**如果被追问**：span 是怎么采到的？
→ 每个节点内用 `node_span(...)` 起的 span（`agent/nodes.py`），
落 `trace_spans` 表（E6 [12]：trace 有 **16 个 span** 的 span 树）。
**这也是"为什么要有可观测"的答案**：它是唯一能把"没发生的事"变成证据的东西。

### Q15. 换 embedding 模型后，阈值还能用吗？

**要点**
- **不能，必须重新标定** —— 余弦相似度的**尺度完全变了**（E7 结论 5）。
- 现有阈值的依据是 BGE-M3 的性质：无关文本基线约 **0.57**（E7 实测负样本均值 0.5704）。
  换一个模型，这个基线可能是 0.3 也可能是 0.8。
- 同理，`EMBEDDING_DIM=1024` 也要跟着改（BGE-M3 实测维度 1024，E2），
  并且**换模型要删掉整个向量库重建**（`hnsw:space` 与维度都写在集合 metadata 里）。
- 标定脚本是零成本的（`scripts/calibrate_threshold.py` 不连库、不调大模型），
  但它**需要真模型**来编码（所以不进 CI）。

**如果被追问**：那 CI 里怎么防"换模型忘了标定"？
→ **防不住，这是已知缺口**。CI 用哈希向量，只在语义层面之外验证链路
（E6.2 的 41 项仍然全绿）。这类"模型相关"的回归只能靠**发版前手工跑的标定与评测**，
这一点写在 `ci.yml` 的注释里（"属于发版前人工执行的一步"）。

## 三、Agent 编排（Q16~Q21）

### Q16. 为什么用状态图（LangGraph），不用 `create_agent`？

**要点**
- **控制流显式**：6 个节点 + 4 个条件边，图在 `agent/graph.py` 顶部用 ASCII 画出来，
  "读它比读任何文档都快"。
- **条件边是纯函数、可单测**：`route_after_analyze / route_after_grade /
  route_after_generate / route_after_reflect`，测试可以直接喂一个 state 断言走哪条边
  （E1.5 里 `test_agent_graph.py` 的承诺就是"四个条件边判据、拒答短路、反思重试"）。
  **内联 lambda 没法测**——这是刻意不把判据写进 `add_conditional_edges` 的原因。
- **每个节点都能被观测**：节点内 `node_span`，trace 里能看见图走到了哪一步
  （E6 [12]）。
- **`create_agent` 把控制流交给模型**：可跑，但**成本/轮数/边界不可控**，
  也无法做"这次为什么拒答"的归因。

**如果被追问**：状态图是不是过度设计？
→ 不是，因为有**实测对比**：同一套 43 条用例下 `rag` 快路径 **317ms / 1 轮检索 /
tokens 1704+255**，`agent` 全图 **691ms / 3 轮检索 / tokens 5433+739**（E6 [11]）。
**先把两条路都实现、量出差距，再决定默认走哪条** —— 这才是"编排"该有的证据链。
（注意：这是离线 Mock 下的相对对比，**不是真实模型的质量对比**。）

### Q17. 四个条件边的判据分别是什么？

**要点**
（全部是 `agent/graph.py` 里的独立函数，参数是 `state` 与 `cfg`）

| 条件边 | 判据（简化） | 为什么这么判 |
| --- | --- | --- |
| `route_after_analyze` | `finished` → END；`needs_retrieval` → retrieve，否则 → generate | 闲聊/问系统能力不该检索 |
| `route_after_grade` | 没候选 → generate；**改写次数用完 → generate**；gate 没过 或 无相关 → rewrite | 有界重试；没候选时改写也没意义 |
| `route_after_generate` | 直答/拒答/无候选/次数用完 → END；否则 → reflect | **拒答不该再校验**（本来就没编东西） |
| `route_after_reflect` | `reflect_passed` → END；次数超过 → END；否则 → generate | 反思不通过就带着"缺引用"再生成一次 |

- **共同点**：每条边都把 `finished` / 次数上限当作**第一类判据**，
  也就是**边界优先于业务判断**（避免"规则对但循环不止"）。

**如果被追问**：`reflect` 为什么不重新检索？
→ 因为**职责分层**：`rewrite`（检索层）负责"换查询再查一次"，
`reflect`（生成层）负责"回答有没有逐句被引用支撑"。
`route_after_reflect` 只回到 `generate`、**不回到 `retrieve`**
——一次提问最多一轮"改写检索"和一轮"反思重生成"，总轮数可控（Q18）。

### Q18. 为什么所有重试都要有界？

**要点**
- **每多一轮就是一次 API 调用 = 钱 + 时间**（`nodes.py` 的注释原话）。
- 四个显式上限：`MAX_TOOL_ITERATIONS = 3`、`MAX_SEARCH_CALLS = 4`、
  `AGENT_MAX_REWRITE = 2`（默认）、`AGENT_MAX_REFLECT = 1`（默认）。
- **成本可量化的证据**：E6 [11] 里 `agent` 模式比 `rag` 多 **2 轮检索**、
  token 从 `1704+255` 涨到 `5433+739`（约 3.2 倍），延迟从 **317ms** 到 **691ms**。
- **无界重试最危险的地方不是贵，而是"不可预测"**：
  同样的问题有时 3 轮、有时 30 轮，SLA 与成本都无法承诺。

**如果被追问**：上限怎么定的？
→ **保守取值 + 可配置**（`agent_max_rewrite=2` / `agent_max_reflect=1`），
并且**没有在评测集上做"上限的消融"**——这是诚实的空白，
因为离线 Mock 下"多一轮"的质量收益测不出来。

### Q19. `grade` 为什么用 LLM，而不是直接复用检索分？

**要点**
- **两个分数回答的是不同问题**：检索分回答"这段文本和问题**像不像**"，
  grade 回答"这段文本**能不能支撑回答**"。
  "相似但不可答"是检索分的经典失败模式（所以阈值才会误放行 0.349）。
- 实现上 grade 走 `judge_model.complete(...)` + span **`grade.llm`**
  （`nodes.py::_llm_grade`），逐条判定 `{relevant, reason}`。
- **有兜底，不中断**：模型失败/返回坏 JSON → `_heuristic_relevance`
  （向量分或覆盖率任一达标即算相关，且**至少留最高分那条**）；
  `MockChatModel` 离线时也能触发所有边，所以 4 条条件边在 204 个单测里都能被真实走到。
- 代价：多一次 LLM 调用（在 691ms 那组数字里）。

**如果被追问**：用 LLM 判相关性会不会引入新的不可靠？
→ 会，所以**两个信号并存**：LLM 判定失败时回落到启发式，
且 `AGENT_GRADING_ENABLED=false` 可以整体关掉。

### Q20. checkpointer 的 `thread_id` 为什么是 `trace_id`，不是 `conversation_id`？

**要点**
- **如果用 `conversation_id`，第二轮状态会与第一轮合并** ——
  因为 `AgentState` 里的 `candidates` / `all_queries` 用的是**累加 reducer**
  （`agent/state.py`：按 `vector_id` 去重取高分）。
  后果：上一轮的候选片段混进这一轮的上下文，**引用编号也全乱**（`agent/graph.py` L20-L27）。
- **"多轮记忆"另有实现**：从 MySQL 读历史消息 + **双重截断**
  （`MEMORY_MAX_TURNS=6` / `MEMORY_MAX_CHARS=4000`），那才是产品语义上的记忆。
- 那 checkpointer 还留着做什么？**可回溯**：每个 trace 的图状态被持久化，
  排障时能看到"那次请求走到了哪一步、每个节点的中间产出是什么"。
- 落地：`services/chat.py` L290/L436 传 `thread_id=trace_id`；
  `obs_bridge.py` 里 `trace_id` 同时是 **LangGraph 的 thread_id、`messages.trace_id`、
  与 `/chat` 响应里的 trace_id**（三方同一个 id）。

**如果被追问**：那怎么"接着上次聊"？
→ 靠**消息表**，不靠图状态：每次请求都把历史消息按双重截断拼进 prompt
（E6 [9] 实测"记忆条数 = 4"，第二轮"那二线城市呢"能正确指代）。

### Q21. 为什么 `trace_id` 要在最外层生成？

**要点**
- 因为 **`trace_id` 定义的是"一次请求"的边界**：SSE 帧序、span 树、token 统计、
  成本归因、`messages.trace_id`、checkpointer 的 `thread_id` 全部挂在它身上。
- 生成位置：最外层（请求进入时），沿调用链**显式传递**
  —— 这也是 `RecorderBox` 存在的原因（不能用 `ContextVar`，见 Q24）。
- 与之配套的 `request_id` 由**纯 ASGI 中间件**写进 `request.state`
  （`X-Request-ID` 实测形如 `52badcbdd3da4f0b8605d4af53c0495b`，E6.3 [14]），
  并在 `finally` 里 `clear_request_context()` —— 不清理会让**下一个请求的日志
  带上一个请求的 request_id**（`middleware/context.py` 的"三件必须做对的事"第 2 条）。
- E6.3 [12] 展示了它的产出：`requests=4 tokens={'prompt':11920,'completion':2121,'total':14041}`
  `cost_usd=0.002264 cost_cny=0.0163`
  `latency={'p50':558.5,'p95':571.05,'p99':572.61,'max':573.0,'avg':545.0}`。

**如果被追问**：为什么不用 OpenTelemetry 的 trace？
→ 可以用，本项目是**自研轻量实现**（`observability/tracing.py`），
好处是零额外依赖、直接落 MySQL、和业务表（`messages`）用同一个 id 关联。
规模上来后换成 OTel 是合理演进。

### Q22. 那 21 个漏鉴权的端点，你是怎么发现的？

**要点**
- **发现方式不是审代码，而是"不带 token 打一次"**：
  写 HTTP 冒烟时顺手打了一次 `GET /kbs`，结果返回 **200 + 正常业务数据**（E6.4）。
- 随后写脚本审计依赖图，结论是 **39 个端点里 21 个没有鉴权**，
  包括 `GET /kbs`、`GET /kbs/{id}/stats`、`GET /documents/{id}`、
  `POST /kbs/{id}/search`、`GET /eval/*`（8 个）、`GET /obs/*`（4 个）（E6.4）。
- **为什么功能测试发现不了**：它们的表现是"200 + 正常数据"，
  任何"断言字段对不对"的测试都会通过（E6.4 原话）。
- 本会话复核修复后的状态：`已鉴权端点 = 34   刻意公开 = 2` / `RESULT: OK`（退出码 0）。

**如果被追问**：审计脚本第一版为什么漏报？
→ 两个原因，都写在脚本 docstring 里：
① FastAPI 0.142 的 `include_router` 是**惰性**的，`app.routes` 里只有 `_IncludedRouter`
占位对象（`path`/`methods` 都是 None），第一版只遍历它、**只找到 1 个端点，
差点得出"没有漏洞"的错误结论**；② 路由级依赖挂在 `include_context.dependencies`，
不在端点自身的 `dependant` 里，只查后者会**把正确写法误报成漏洞**。

### Q23. 为什么鉴权改成"路由级默认需要"？

**要点**
- 原做法是"逐个端点在函数签名里声明 `user: CurrentUser`"，理由是"读起来直观"
  —— 结果是 **忘了声明 = 漏洞**。
- 现做法：`AUTH_REQUIRED = [Depends(get_current_user)]`，
  挂到每个业务子路由上（`api/router.py` L58、L80-L92）。
  **任何将来新增的端点都自动受保护**；确实要公开的只有注册/登录，必须显式排除。
- 一句话总结：**默认值的方向决定了犯错时的后果**
  ——"默认公开"时忘记写 = 漏洞；"默认需要"时忘记排除 = 多要一次登录（立刻会被发现）。
- 配套：运维三件套 `/health` `/ready` `/metrics` **在根路径且不鉴权**，
  由 `include_ops()` 单独挂载（挂载位置与业务路由**故意不同**）。

**如果被追问**：`/health` 为什么必须公开？
→ 服务"半死不活"时也要能回答；**拿不到 token 的时候，往往正是需要看 `/health` 的时候**
（`docs/01` §一之二的表格）。

### Q24. 流式为什么不能依赖 `contextvars`？

**要点**
- 报错原文（E6.5）：
  `ValueError: <Token var=<ContextVar name='current_recorder' default=None>> was created in a different Context`。
- 机制：Starlette 迭代**同步生成器**时用 `iterate_in_threadpool`，
  **每取一个元素就是一次 `run_in_threadpool(next, ...)`** ——
  每个 `next()` 可能落在不同线程、拿到**各自的 context 副本**；
  而 `ContextVar.set()` 返回的 token **只能在同一个 context 里 `reset()`**。
- 修法：**把 recorder 挂在依赖对象上显式传递**
  （`agent/nodes.py::RecorderBox` → `AgentDeps.recorder_box` → `RequestServices.recorder_box`），
  生成器在哪个线程跑都无所谓——它读的是同一个对象。
- **为什么这个 bug 值得记**：它只在流式路径出现，而 `pytest` 用 `ASGITransport`
  打请求时**不会**触发分次线程调度 → **204 个单测全绿也照样漏掉**（E6.5 原话）。

**如果被追问**：那 `ContextVar` 在本项目还用在哪儿？
→ 只用在**只读的横切标记**（如 `request_id` 写日志），且**必须在 `finally` 里清理**
（纯 ASGI 中间件里那三件事之一）。**请求级对象一律显式传递。**

### Q25. 三方一致性（MySQL / 向量库 / BM25）是怎么校验的？

**要点**
- **锚点是 `vector_id = f"{doc_id}:{chunk_index}"`**，全项目只有一个构造入口
  `db/models/knowledge.py::make_vector_id`（"散落各处手拼字符串迟早会不一致"）。
- 三个计数随时可比：`chunk_count` / `vector_count` / `bm25_doc_count` + `consistent` 布尔量。
- 实测：`seed_demo` 输出 `切片 / 向量 / BM25 : 34 / 34 / 34  一致性=✓`（E5）；
  删一份文档后 `chunk=34→27 vector=34→27 bm25=34→27`，断言"删除后仍保持一致"（E6 [14]）。
- **孤儿向量不会永远隐形**：`retrieval/engine.py::_enrich` 把"向量库有、MySQL 没有"的候选
  丢弃并计数（`debug.dropped_orphans`），`/search` 会报出来（E6.3 实测 `dropped_orphans: 0`）；
  `/health` 报 `bm25_doc_count`，为 0 直接进 `warnings`。

**如果被追问**：写入顺序为什么是"向量库 → BM25 → MySQL"？
→ 因为**中途失败最坏只是多了孤儿 chunk（可清理），
而不是"列表显示上传成功、实际检索不到"** ——
后者才是最难的排查场景：所有接口都返回 200，只有用户觉得"答不准"（`ingest/pipeline.py` L10-L13）。

### Q26. 为什么 BM25 重启要重建？

**要点**
- BM25 是**自研内存倒排索引**（`retrieval/bm25.py`，不引依赖），**不落盘**。
- **权威正文在 MySQL `chunks` 表**里，所以重建是"从权威来源重新推导索引"，
  不涉及数据丢失；父块（`parent_content`）也只活在内存 payload 里。
- 重建成本随规模线性增长：`docs/00` §8 的边界写的是
  "**十万级 chunk 内存占用约数百 MB**"，所以要换 Elasticsearch 或只保留热门 KB 索引。
- 这也是"按 KB 隔离"的一个好处：删一个 KB = drop 一个集合 + 清一段内存索引，很干净。

**如果被追问**：重启期间检索会怎样？
→ **服务启动时重建**（容器 `HEALTHCHECK` 给了 `start-period=60s`，
注释里写明"首次启动要连库、建 Chroma 客户端、**重建 BM25 索引**"）——
也就是说"没重建完"的时间被算在"未就绪"里，而不是"就绪但搜不到"。

### Q27. 降级怎么保证"不静默"？

**要点**
- **每个降级都有可观测的出口**，而不是"悄悄换个实现继续跑"：

| 降级 | 可见信号 |
| --- | --- |
| 向量召回失败 | `debug.vector_error` 字段 + gate 的 `reason` |
| 孤儿向量被丢弃 | `debug.dropped_orphans` 计数 |
| 闸门拒答 | `reason=below_all_thresholds`（**稳定标识**，不是给人看的句子） |
| 重排走启发式兜底 | `rerank_score` 仍然写回（界面能看到），模式标为 `hybrid_rerank` 但离线 |
| 无 API Key | `/health` 报 `offline=true llm_mode=offline` + `warnings=['未配置 OPENAI_API_KEY，当前为离线模式（抽取式回答）']`（E6.3 [1]） |
| BM25 空索引 | `/health` 的 `bm25_doc_count=0` 进 `warnings` |
| 埋点写库失败 | 只记日志、**绝不让用户的问答请求崩掉**（`obs_bridge.py` 的刻意设计） |

- 原则一句话：**降级可以，说谎不行**（`docs/教程/04` 对"占位行 + warning"的总结）。
- E6.2 是最好的例证：CI 用哈希向量时，闸门**明确报告自己换了一条路**
  （`reason=keyword_coverage_above_threshold`、`best_vec=0.4027`），
  而不是假装"闸门正常放行"。

**如果被追问**：这些信号怎么被"消费"？
→ 三种消费者：**前端**（`reason` 是稳定标识，用来显示"为什么拒答"）、
**测试**（断言 `reason` 的具体取值）、**人**（`/health` 的 `warnings` 数组）。

### Q28. 前后端契约为什么要单独写一个校验脚本？

**要点**
- 因为**双方"照着同一份文档各自实现"依然可能对不上**——文档没约束到
  "路径参数叫什么名字"这种细节（`check_api_contract.py` docstring 原话）：
  ```
  前端  GET /api/v1/conversations/${id}/messages
  后端  GET /api/v1/conversations/{conversation_id}/messages
  ```
- 双方各自自测时**都是 200**（前端自测时后端还没写；后端自测用 pytest 造的路径），
  **只有真正联调才会 404**。
- 做法：抠出前端所有接口路径 → 取后端 OpenAPI 的全部路径 →
  **把路径参数名归一**（`${id}` / `{conversation_id}` → `{}`）后做集合比对。
- 实测结果：前端调用 **28** 个路径，后端暴露 **30** 个，
  **28/28 全部对得上**，另有 2 个后端有而前端没调（`/metrics`、`/ready`，运维探针，UI 不需要）（E6.6）。

**如果被追问**：这个脚本自己踩过什么坑？
→ 两个，都写在 docstring 里：① 前端写的是**相对路径**（`get('/kbs')` +
`baseURL='/api/v1'`），必须自己拼 base，第一版漏了只找到 4 个路径；
② **不能全仓库扫**——`router/index.ts` 里的 `/kbs/:id` 是 Vue Router 的 `:param` 语法，
不是 HTTP 路径，全扫会多报 6 个假警、把真问题淹掉。

## 五、评测（Q29~Q33）

### Q29. 你怎么证明"混合检索真的更好"？

**要点**
- **同一批数据、同一套指标、四种模式**：43 条标注用例、top-k=5、同一融合参数（E7.5）。
- 结果（recall@k）：

| 模式 | 命中率 | recall@k | MRR | nDCG | 平均延迟 |
| --- | --- | --- | --- | --- | --- |
| vector | 0.930 | **0.860** | 0.428 | 0.586 | 58ms |
| bm25 | 0.814 | **0.721** | 0.356 | 0.485 | 5ms |
| hybrid | 0.930 | **0.849** | 0.422 | 0.576 | 56ms |
| hybrid_rerank | 0.930 | **0.849** | 0.422 | 0.576 | 56ms |

- **唯一显著的结论**：`bm25 → hybrid_rerank`，**Δ = +0.128**，
  95% CI **[+0.035, +0.244]**，**p = 0.010**（配对 bootstrap，`n_boot=2000, seed=42`）（E7.5）。
- 所以准确的说法是"**混合检索显著优于纯关键词检索**"，
  而不是"混合检索全面最优"（它在小语料上略逊纯向量，见 Q2）。

**如果被追问**：为什么不和"更弱的基线"比？
→ 比了：`bm25` 就是那条更弱的基线，而且它**不是稻草人**——
它是"只用关键词"的真实方案，在生产里很常见。

### Q30. 为什么必须做显著性检验？

**要点**
- 因为**评测集只有 43 条**：**翻转 1 条就是 2.3 个百分点**（E7.5 结论 2）。
- 实测打脸的例子：`vector vs hybrid_rerank` 的 Δ 是 **+0.0116（1.2 个百分点）**，
  但 **p = 0.820**、95% CI **[-0.0233, +0.0581] 跨 0** —— **完全是噪声**。
- 方法与可复现性：**配对 bootstrap**（`paired_bootstrap_test`，`n_boot=2000, seed=42`），
  所以别人能跑出同样的 p 值与 CI。
- 不做这一步的后果很具体：**把随机波动当成果写进简历**，
  面试官问一句"这个提升显著吗"就答不上来。

**如果被追问**：为什么用 bootstrap 不用 t 检验？
→ 指标（recall@k、MRR）**不正态**，而且是**配对**样本（同一批用例、同一份标注），
bootstrap 对分布没有假设；`seed=42` 保证可复现。

### Q31. 这个项目里，哪条结论能写简历，哪条不能？

**要点**
- ✅ **能写**：`bm25 → hybrid_rerank`，recall@5 **0.721 → 0.849**，
  **p = 0.010**（配对 bootstrap，43 条标注用例）——**它过了显著性检验**。
- ✅ **能写（注明条件）**：延迟对比 **BM25 5ms / 向量 58ms / 混合 56ms**
  ——这是"混合检索的边际成本几乎为零"的量化依据，
  但要说明**这是 34 个切片的小库**，库变大时 BM25 的倒排优势会更明显（E7.5 结论 5）。
- ❌ **不能写**："vector 比 hybrid 高 1.2 个百分点"——**p = 0.820，CI 跨 0**，是噪声。
- ❌ **不能写**："重排带来了提升"——`hybrid` 与 `hybrid_rerank` **完全相同（Δ = 0）**，
  因为**离线模式下重排走的是启发式兜底**（E7.5 结论 4），这一列**测不出 LLM 重排的价值**。
- ✅ **能写（能力项）**：**阈值标定**把 `VECTOR_MIN_SCORE` 从 0.35 改到 0.60，
  把误放行率从 **1.000** 降到 **0.349**（E7）。

**如果被追问**：那你怎么知道"重排有没有用"？
→ **现在不知道**。接上真实 API Key 后必须重跑 `run_eval.py`——
这是写在 E7.5 结论 4 里的一句"必须重跑"，我把它当成**待办**而不是**结论**。

### Q32. `hybrid` 与 `hybrid_rerank` 完全相同，说明什么？

**要点**
- **指纹**：说明"重排这一步实际上没有产生任何区别"。
- 根因：`MockChatModel.offline=True` → **不调 LLM 重排**，走**启发式兜底**
  （覆盖率 + 标题命中的组合打分）（E7.5 结论 4）。
- **不能**解读成"重排没用"——那会把"没测到"说成"测到了没有"。
- 正确表述：**"在离线模式下测不出 LLM 重排的价值，接 Key 后必须重跑"**；
  同时承认这条也暴露了一个**工具缺陷**：评测报告里应该有一个"本次是否真的调用了重排模型"的标记
  （现在还只能靠人记得 `LLM 判官：False` 这一行，E7.5 的报告头部确实打了这一行）。

**如果被追问**：那你怎么保证评测不是"又一次静默测了个空"？
→ 靠**指纹检查**（这正是 E7.6 那个 bug 教的）：
**如果 `hybrid == bm25`（或 `hybrid == vector`），立刻怀疑另一路没干活。**
E7.6 的真实事故就是 `vector recall@5 = 0.000` 且 `bm25/hybrid/hybrid_rerank`
三者完全相同 —— 根因是 `kb_ids=None` 时**向量那一路根本没检索**（E7.6）。

### Q33. 43 条用例够吗？

**要点**
- **不够**，但**足以判断"大差异"**：`bm25` 与 `hybrid_rerank` 差了 0.128（p=0.010），
  这种量级的差距 43 条能看出来；1~2 个百分点的差距**看不出来**（Q30）。
- 不确定性是**量化过的**（CI 而不是"感觉"），所以结论的适用范围可以写清楚：
  **"在这个小库（34 个切片）上，混合检索显著优于纯关键词"**。
- 语料规模同样是限制：**34 个切片 / 6 份文档**（E5）——
  库变大后 BM25 的行为会变（倒排优势更明显），
  所以"RRF 在小语料上略逊纯向量"这条结论**不能外推**（E7.5 结论 3）。
- 评测集本身覆盖三类难点：同义改写、专有名词、多跳（`eval_datasets` / `eval_cases` 的标注设计）。

**如果被追问**：怎么扩？
→ 三步：① 用例扩到 200+（同义改写与多跳各占一半）；
② 语料换成真实企业文档（万级切片）；③ 把标定与评测变成"发版前必跑"
（现在它靠人记得，因为它需要真模型、不在 CI 里）。

### Q34. 这个项目最大的不足是什么？

**要点**
- **一条"未实测"的清单**（主动说，不要等追问）（E11）：

| 项目 | 状态 | 原因 |
| --- | --- | --- |

| 并发 / 压测 | **未测** | 检索路径含同步阻塞调用，瓶颈已知但未量化 |

**如果被追问**：那你凭什么说这个系统"能用"？

生成质量未实测"**。前者是事实，后者是边界。

### Q35. 检索路径有同步阻塞调用，影响有多大？

**要点**
- 现状：BGE-M3 与 Chroma 都是**同步 API**，本项目把它们收口在**线程池**里
  （Starlette 对同步处理函数/生成器会用 `iterate_in_threadpool` / `run_in_threadpool`），
  所以"阻塞"被限制在**线程池**里，不会直接卡死事件循环（`docs/00` §8 第 1 行）。
- 量级：CPU 上**编码约 81 ms/条**（E2，3 条 0.24s 的均值），
  首次加载模型 1.7s（E2）；`/search` 端到端 **177ms**，其中 `embedding_ms=168`
  —— **向量化占了 95% 的延迟**（E6.3 [8]）。
- 也就是说：**瓶颈是吃 CPU 的编码，不是检索本身**（`vector_ms=3`、`bm25_ms=0`）。
- **未量化**：并发下的吞吐与排队（E11 明确写"瓶颈已知但未量化"）。
  修法在 roadmap 里：GPU 推理服务 / async 客户端 / 独立推理服务（`docs/00` §8）。

**如果被追问**：那你怎么敢说"已收口"？
→ "收口"指的是**代码结构**（所有同步调用集中在可替换的适配层，
`Embedder` / `VectorStore` 两个协议），不是指"性能已达标"。**这两件事不要混为一谈。**

### Q36. 如果重做一遍，你会改什么？

**要点**
1. **把"鉴权默认安全"从第一天就做**：21 个漏鉴权端点的根因不是"忘了写"，
   而是**默认值方向错了**（Q23）。这一条要提前到接口层设计的第一行。
2. **阈值标定提前**：它现在在阶段 11，但"0.35 让闸门 100% 失效"这个 bug
   在阶段 5 就已经埋下了。**任何"拍脑袋的常数"都该在写下它的当天就被标定**。
3. **评测的"指纹检查"进 CI**：`hybrid == bm25` 这类指纹应该是一条自动断言
   （E7.6 那个 bug 是靠人眼看出"三个数字一样"才发现的）。
4. **Docker 实测从第一天纳入清单**：现在 `docker-compose.yml` / 两个 Dockerfile
   都是"写了但没验证"的资产——**未验证的资产在故障时会变成负资产**（你会以为它能用）。
5. **测试分层想清楚再写**：`smoke_http.py` 不是"多余的重复"，它是唯一能抓到
   contextvars（Q24）与 SSE 缓冲（A10）的那一层。**先想"这层能看见什么"，再动手写。**

**如果被追问**：那"离线优先"这条会改吗？
→ **不会，反而要加强**。`MockChatModel + HashEmbedder + InMemoryVectorStore + SQLite`
这套组合是 204 个用例 4.63 秒跑完的全部原因（E1.5），
也是 CI 零成本的原因（E6.2）。要改的是"**别把离线当成'质量已验证'**"，
而不是放弃离线。

### Q37. 你觉得这个项目最"值钱"的一次测量是什么？

**要点**
- **阈值标定**（E7）。因为它同时具备三个特征：
  ① **结论反直觉**（0.35 看起来合理，实际误放行 100%）；
  ② **可复现**（`calibrate_threshold.py` 零成本、不连库、不调大模型，输入是 43 条标注用例）；
  ③ **改动了产品行为**（阈值 0.35 → 0.60，无关问题被正确拦下，`reason=below_all_thresholds`）。
- 它演示了一句我认为最重要的话：
  **"'我实测过'和'我猜的'在文档里长得一模一样"** ——
  只有把原始输出固定下来（`data/threshold_calibration.json`），别人才可能复核。
- 附带发现的两件事比阈值本身更有价值：
  **余弦相似度没有绝对零度**（负样本基线 0.5704）、
  **单一阈值原理上无法分离重叠分布**（正 min 0.4654 < 负 max 0.7819）。

**如果被追问**：第二个值钱的是什么？
→ **E7.6 那个"静默测了个空"的 bug**（`kb_ids` 缺失导致 `vector recall@5 = 0.000`）。
它教我一条通用纪律：**"跑完了、有数字、全绿"但结果不合常理时，
先怀疑"这一步真的执行了吗"**。

### Q38. 现在让你把它往生产推，第一步做什么？

**要点**
1. **把"未实测"变成"实测"**：Docker 构建 + compose 一键起（含 nginx 的 SSE 关缓冲）、
   真实模型下的答案质量、并发压测。**这三件事是"能不能上线"的前置条件，不是优化项。**
2. **多租户**：`tenant_id` + 行级过滤 + **向量库签名强制带 tenant_id**
   （`VectorStore` 协议已经留好接口，见附录 C 练习 8）。
3. **异步化检索路径**：把编码换成独立推理服务（GPU）或 async 客户端（Q35）。
4. **把标定与评测变成发版前必跑的门禁**（现在需要真模型、只能人工跑，Q15/Q33）。
5. **限流与熔断**：配置里已有 `RATE_LIMIT_ENABLED` / `RATE_LIMIT_PER_MINUTE` 开关，
   但**默认关闭且未压测**——上生产前必须打开并验证（附录 C 练习 11）。

**如果被追问**：为什么不是先加功能（比如更多文件格式、更多 Agent 工具）？
→ 因为**功能的价值可以被验证，可靠性的缺失不能**。
现在的系统"能演示"，但"没在真实部署形态下跑过、没在多租户下隔离过、
没在并发下量过"——继续加功能只会让这三件事更难补（附录 C 里我故意把
"加文件格式"排在难度 ★1、"多租户/异步化"排在 ★4~★5）。
