## A. 迁移与数据库

### A1 跑 alembic 时 `UnicodeDecodeError: 'gbk' codec can't decode byte ...`

**现象**

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0xbf in position 2: illegal multibyte sequence
  File "...\configparser.py", line 1060, in _read_inner
```

**报错信息完全指不到 `alembic.ini`**——栈里全是 `configparser` 内部帧。
第一次遇到会以为是代码问题。

**根因**：Alembic 用 `configparser` 读 `alembic.ini`，而它按**系统 locale 编码**打开文件
（`read(file, encoding="locale")`）。中文 Windows 上 locale 是 **GBK（cp936）**，
文件里只要有一个中文字符就炸。

**解决**：`backend/alembic.ini` 的注释保持**纯 ASCII**。
中文说明写进 `backend/MIGRATIONS.md` 或 `alembic/env.py`（Python 源码永远是 UTF-8）。

**相关文件**：`backend/alembic.ini`、`backend/MIGRATIONS.md` §2 坑 1、`backend/alembic/env.py`

**怎么发现**：`docs/03` E4 的"踩过的坑"里逐字记着；`MIGRATIONS.md` 坑 1 记录了
`byte 0x82 in position 18` 的另一种形态。本会话**复现了机制**：

```
=== PYTHONUTF8=0 ===
locale = cp936
=== configparser.read(encoding='locale') on ini with Chinese comment ===
UnicodeDecodeError: 'gbk' codec can't decode byte 0xbf in position 2: illegal multibyte sequence
```

⚠ **诚实补充**：本机默认 `PYTHONUTF8=1`（UTF-8 模式，实测 `locale = utf-8`），
此时 `encoding="locale"` 也变成 UTF-8，**这个坑不会复现**；
必须显式 `$env:PYTHONUTF8='0'` 才会变成 cp936。所以"是否踩到这个坑"取决于机器是否开了 UTF-8 模式。

**怎么防止再犯**：把中文注释放在 `MIGRATIONS.md`（人类读）而不放进 `.ini`（机器读）。
真要机器兜底，可以在 CI 里加一行 `python -c "open('backend/alembic.ini', encoding='ascii')"`
——它会把"非 ASCII"变成一条**指明文件**的错误。

### A2 `alembic: error: unrecognized arguments: -x db_url=...`

**现象**：想临时切库（CI / 测试）时传 `-x`，被当成未知参数。

**根因**：`-x` 是 **alembic 自身的全局选项**，argparse 要求它出现在**子命令之前**。

**解决**

```powershell
# ✅ 正确：-x 在子命令之前
..\.venv\Scripts\python.exe -m alembic -x "db_url=mysql+pymysql://..." upgrade head

# ❌ 错误：-x 在子命令之后
..\.venv\Scripts\python.exe -m alembic upgrade head -x "db_url=..."
```

**相关文件**：`backend/MIGRATIONS.md` §1、`docs/03` E4（命令块里就带这行注释）、
`.github/workflows/ci.yml` L106/L132（CI 里不需要 `-x`，它用 `DATABASE_URL` 环境变量）

**怎么发现**：E4 的命令注释里明确写着"先注：`-x` 必须放在子命令之前，否则报 unrecognized arguments"。

**怎么防止再犯**：CI 与 `tasks.ps1 migrate` 都**不用** `-x`，改用 `DATABASE_URL` 环境变量——
**"不要给同一个配置留两条设置路径"**。要临时切库时照抄 `MIGRATIONS.md` §1 的整行命令。

### A18 `sqlite3.OperationalError: no such table: users`（刚建过表）

**现象**：测试里明明调了 `Base.metadata.create_all(engine)`，查询却报表不存在。
**而且它只在"第二个连接"出现时才报错**，所以极容易被误判成"建表逻辑写错了"。

**根因**：`sqlite:///:memory:` 的作用域是**那一个连接**。SQLAlchemy 默认用连接池，
建表发生在连接 A，查询用了连接 B（另一个全新的空库）。

**解决**：内存库必须共享同一个连接：

```python
# backend/src/knowflow/db/session.py L42-L46
if _is_sqlite(url):
    kwargs["connect_args"] = {"check_same_thread": False}
    if ":memory:" in url or url.endswith("sqlite://"):
        # 内存库必须共享同一个连接，否则每次 connect 都是一个新空库
        kwargs["poolclass"] = StaticPool
```

（`check_same_thread: False` 是另一个独立问题：SQLite 默认禁止跨线程使用连接。）

**相关文件**：`backend/src/knowflow/db/session.py`、`backend/tests/conftest.py`（`db_engine` fixture
刻意复用 `create_engine_from_settings` 而不是手写引擎参数）

**怎么发现**：这一条是"测试基建"阶段暴露的典型问题（手册 7.15）。
它的价值在于：**如果测试里手写一份引擎参数，这个坑就会留到生产**。

**怎么防止再犯**：`conftest.py` 的 `db_engine` **复用生产代码的 `create_engine_from_settings`**
——测试与生产用同一份引擎构造逻辑，配置差异只允许通过 `Settings` 表达。

### A19 MySQL `(1452, 'Cannot add or update a child row...')` 外键约束失败，SQLite 不报

**现象**：同一段"造测试数据"的代码，SQLite 上跑得好好的，换 MySQL 就报 1452。

**根因**：`messages` 表有外键约束，**必须先有父行**：

```python
# backend/src/knowflow/db/models/chat.py L80-L81
conversation_id: Mapped[int] = mapped_column(
    BigIntType, ForeignKey("conversations.id", ondelete="CASCADE"), nullable=False
)
```

而 `conversations.user_id → users.id`（同文件 L52-L53）。
链条是 **`users` → `conversations` → `messages`**（还有 `message_citations → messages/chunks`）。
**SQLite 默认不强制外键**（本仓库源码里没有任何 `PRAGMA foreign_keys=ON`），
所以 SQLite 不报、MySQL 报。

**解决**：按 `users → conversations → messages` 的顺序造数据；
或者直接用 `alembic upgrade head` + `scripts/seed_demo.py`（它就是按依赖顺序建的）。

**相关文件**：`backend/src/knowflow/db/models/chat.py`、`backend/src/knowflow/db/models/identity.py`、
`backend/scripts/seed_demo.py`、`docs/01-数据库与接口契约.md` §三

**怎么发现**：`docs/教程/03-阶段2-数据库与迁移.md` §4 的错误表把这条列为"SQLite 不报错、
MySQL 报 1452"，并在附录 A（本表）里给出解释。

**怎么防止再犯**：造数据/写测试时**永远按外键依赖顺序**；
更彻底的做法是在 SQLite 上开 `PRAGMA foreign_keys=ON`，让测试环境与 MySQL 行为一致
（本项目**没做**这一步——这是一个已知的、可以改进的点，见附录 C 练习 12 的同类思路）。

> ⚠ **诚实标注**：1452 的**原文文本**本会话没有复现（需要真在 MySQL 上造一次违规数据）。
> 这里给出的是机制与依赖链，源码证据可核对。

## B. 向量库与向量化

### A3 `KeyError: 'vector_id'`

**现象**：入库时报 `KeyError: 'vector_id'`；更糟的形态是——**不报错**，
但向量库里多了一批"MySQL 里没有的向量"（**孤儿向量**）。

**根因**：BM25 的 payload 漏了 `vector_id` 字段。`BM25Registry.add_chunks` 用它做
倒排索引的 `doc_key`，检索命中后也靠它回 MySQL 查权威正文。而项目的写入顺序是
**向量库 → BM25 → 注册表（MySQL）**，所以"向量已写、事务回滚"的结果就是孤儿向量。

**解决**：payload 必须带 `vector_id`（其实整条链路都该用唯一构造入口
`db/models/knowledge.py::make_vector_id`）：

```python
# backend/src/knowflow/ingest/pipeline.py L126-L130
**`vector_id` 是必须的**：`BM25Registry.add_chunks` 用它做倒排索引的 doc_key，
检索命中后也靠它回 MySQL 查权威正文。漏了它会在入库时报 `KeyError: 'vector_id'`——
而这恰好是本项目"写入顺序"设计的价值体现：向量库已写、MySQL 事务回滚，
结果是一批**孤儿向量**（`retrieval` 的 `dropped_orphans` 会如实报出来），
而不是"列表显示成功但搜不到"。
```

**相关文件**：`backend/src/knowflow/ingest/pipeline.py`（`to_bm25_payload`）、
`backend/src/knowflow/retrieval/bm25.py` L245-L250、
`backend/src/knowflow/retrieval/engine.py` L198-L203（`dropped_orphans`）、
`backend/src/knowflow/db/models/knowledge.py`（`make_vector_id`）

**怎么发现**：`test_retrieval_engine.py` 的承诺里就有"孤儿向量丢弃"（E1.5 的测试职责表）；
`docs/教程/05-阶段4-向量化与向量库.md` 也记了这条。
在整链路上，`/search` 的 `debug.dropped_orphans` 会把它报出来（E6.3 实测 `dropped_orphans: 0`）。

**怎么防止再犯**：三件事已经做到位——
1. `vector_id` 只有 `make_vector_id` 一个构造入口（"散落各处手拼字符串迟早会不一致"）；
2. 孤儿向量**被计数而不是被忽略**（`_enrich` 丢弃并 `dropped_orphans += 1`）；
3. 三方计数一致性（`chunk_count / vector_count / bm25_doc_count` + `consistent`）随时可比。

### A4 `FutureWarning: get_sentence_embedding_dimension ...`

**现象**：加载 BGE-M3 时日志被 `FutureWarning` 刷屏（旧方法名仍可用，不报错）。

**根因**：`sentence-transformers 6.1.0` 把 `get_sentence_embedding_dimension()`
改名为 `get_embedding_dimension()`。

**解决**：优先用新名，取不到再退回旧名：

```python
# backend/src/knowflow/embeddings/local_bge.py L286-L298（节选）
def _read_embedding_dim(model: SentenceTransformer) -> int:
    """读取模型输出维度，兼容 sentence-transformers 6.x 的方法改名。

    6.1.0 起 `get_sentence_embedding_dimension()` 改名为 `get_embedding_dimension()`
    （旧名仍可用但会打 FutureWarning）。这里优先用新名，避免启动日志被警告刷屏。
    """
    getter = getattr(model, "get_embedding_dimension", None)
    if getter is None:
        getter = getattr(model, "get_sentence_embedding_dimension", None)
```

**相关文件**：`backend/src/knowflow/embeddings/local_bge.py` L286-L303、
`backend/pyproject.toml`（`sentence-transformers==6.1.0`）

**怎么发现**：升级依赖后看启动日志（深度学习栈的 `FutureWarning` 是**下个版本要删 API** 的预告）。
`docs/教程/01-阶段0-环境与骨架.md` §2.2 把它当成"依赖必须钉版本"的例证。

**怎么防止再犯**：`requirements.txt` 里全部 `==` 钉版本；
写法上用 `getattr(..., None)` 探测新名——**新旧两个版本都能跑**，
这样升级依赖不会变成一次"必须立刻改代码"的事件。

> ⚠ **诚实标注**：本会话**没有加载 BGE-M3**（那要 2GB 模型），
> 所以这条 `FutureWarning` 的原文没被复现；代码证据在 L286-L298。

### A5 `KeyError: 'page_no'`（只在 Chroma 后端出现）

**现象**：同一个检索结果，内存后端能取到 `metadata["page_no"]`（值是 `None`），
换 Chroma 后端**这个键直接不存在** → 下游 `metadata["page_no"]` 抛 `KeyError`。
**写入时不报任何错**。

**根因**：**Chroma 写入时会静默丢弃值为 `None` 的 metadata 键**
（写完 `get()` 回来那个键就没了）。

**解决**：两个后端统一在 `sanitize_metadata` 里丢弃 `None`，
并且**下游一律写 `.get()`**：

```python
# backend/src/knowflow/vectorstore/base.py L18-L21
5. `metadata` 的值**不允许是 None**：实测 Chroma 写入时会**静默丢弃** None 值的键
   （写完 `get()` 回来那个键就没了）。所以两个实现统一在 `sanitize_metadata`
   里丢弃 None，保证返回的 metadata 一模一样。
   ⚠️ 下游取值请统一写 `metadata.get("page_no")`，不要写 `metadata["page_no"]`。
```

**相关文件**：`backend/src/knowflow/vectorstore/base.py`（`sanitize_metadata`、
`REQUIRED_METADATA_KEYS` 与 `OPTIONAL_METADATA_KEYS`）、
`backend/src/knowflow/vectorstore/chroma_store.py`、
`backend/src/knowflow/retrieval/engine.py` L135-L140（`_safe_int(meta.get("page_no"))`）

**怎么发现**：写"两后端等价"的对照测试时暴露（E1.5 里 `test_embeddings_vectorstore.py`
的承诺就是"两后端等价"）——**这是"同一份代码换后端结果不同"的典型**。

**怎么防止再犯**：把"哪些键必须存在、哪些可以为空"写成常量
（`REQUIRED_METADATA_KEYS = ("doc_id", "doc_name", "chunk_index")`），
两个实现都过同一个 `sanitize_metadata`；下游用 `Optional` 语义取值。

### A6 `ValueError: Expected where to have exactly one operator`

**现象**：按文档过滤时传 `{"doc_id": 1, "page_no": 2}`，Chroma 直接拒绝。

**根因**：Chroma 的 `where` **每一层只允许一个条件**；
而且一个键后面也只能跟**一个**算子（`{"page_no": {"$gte": 1, "$lte": 5}}` 也非法）。

**解决**：多条件必须显式 `$and`：

```python
{"$and": [{"doc_id": 1}, {"page_no": 2}]}
{"$and": [{"page_no": {"$gte": 1}}, {"page_no": {"$lte": 5}}]}
```

**相关文件**：`backend/src/knowflow/vectorstore/base.py` L64-L67 与 `validate_where`（L211-L292）

**怎么发现**：E1.5 的 `test_embeddings_vectorstore.py` / 实机试写时暴露；
`validate_where` 的 docstring 把三条规则连报错原文一起记下来（规则"全部来自对
chromadb 1.5.9 的实测"）。

**怎么防止再犯**：**两个后端进门先跑同一个校验器**（`validate_where`），
不支持就抛 `VectorStoreError`，**绝不透传、绝不静默忽略**：

> 同一份代码换后端结果不同是最难查的 bug，所以两个后端进门先跑同一个校验器。

### A7 Chroma `delete()` 返回 `{"deleted": N}`、空输入抛 `ValueError`

**现象**（三个小坑，同一个根因：**Chroma 的 API 返回形状与直觉不同**）：

1. 以为 `collection.delete(...)` 返回删除条数，实际返回 `{"deleted": N}` 字典；
2. `delete(ids=[])` → `ValueError: Expected ids to be a non-empty list`；
3. 空 `upsert`（`items` 为空列表）→ 同样直接抛 `ValueError`。

**根因**：Chroma 内部会对空输入做非空校验并抛错；删除的返回值是统计字典。

**解决**：在适配层**抹平差异**，空输入提前返回：

```python
# backend/src/knowflow/vectorstore/chroma_store.py L143-L144
if not items:
    # Chroma 对空列表直接抛 ValueError（实测），提前返回更省事也更清晰
```

```python
# backend/src/knowflow/vectorstore/chroma_store.py L304-L307
def _delete_ids(self, collection: Collection, kb_id: int, targets: Sequence[str]) -> int:
    """按 id 删除；空列表要提前返回（Chroma 对空 ids 抛 ValueError，实测）。"""
    if not targets:
        return 0
```

```python
# backend/src/knowflow/vectorstore/chroma_store.py L445-L450
def _deleted_count(result: object, *, fallback: int) -> int:
    """Chroma 的 delete 返回 `{"deleted": N}` 而不是整数（实测），这里抹平差异。"""
    try:
        deleted = result.get("deleted")
        if isinstance(deleted, int):
            return deleted
```

**相关文件**：`backend/src/knowflow/vectorstore/chroma_store.py`（L143、L304-L315、L445-L450）、
`backend/src/knowflow/vectorstore/memory_store.py`（同样语义）

**怎么发现**："两个后端返回同一个 `int`"这条约定是被**实测**逼出来的：
内存后端天然返回 `int`，Chroma 返回 dict。E6.1 第 [14] 项的
`删除结果: {'doc_id': 6, 'removed_vectors': 7, 'removed_chunks': 7}` 是**服务层**的返回，
它要正确就得先把 Chroma 的 `{"deleted": N}` 抹平。

**怎么防止再犯**：**协议层写死返回类型**（`delete(...) -> int`），
实现层用一个小函数（`_deleted_count`）把"后端特色"挡在里面。
这也是 `VectorStore` 协议的价值：上层只看见 `int`。

### A8 日志里在下载 ONNX 模型（约 79MB）

**现象**：建集合后日志出现模型下载；更糟的是有人调
`collection.add(documents=...)` 而**没给向量**时，Chroma 会用它自带的
all-MiniLM 算一组 **384 维**向量——**只有维度不符时才报错**。

**根因**：建集合时没传 `embedding_function=None`，Chroma 会把默认的 ONNX all-MiniLM
记进集合配置。

**解决**：建集合时显式禁用 Chroma 的内置 EF：

```python
# backend/src/knowflow/vectorstore/chroma_store.py L19-L23
3. **显式传 `embedding_function=None`**：不传的话 Chroma 会把默认的
   ONNX all-MiniLM 记进集合配置，一旦有人写了 `add(documents=...)` 而没给向量，
   它会**静默下载 79MB 模型**再算一组 384 维向量（维度不符才报错）。
   我们的向量一律来自 `knowflow.embeddings`，所以禁用它的内置 EF；
   同时也避免了「集合已存在不同 EF」的配置冲突异常。
```

代码落点：`chroma_store.py` L111-L116 的 `get_or_create_collection(..., embedding_function=None)`。

**相关文件**：`backend/src/knowflow/vectorstore/chroma_store.py` L110-L122

**怎么发现**：对"零网络"的硬要求做核对时发现——**"它自己会静默失败"不算零网络**。
这和 `conftest.py` 里显式关掉 Chroma 遥测（`ANONYMIZED_TELEMETRY=False`）是同一条纪律。

**怎么防止再犯**：
1. 建集合时显式禁用内置 EF；
2. 测试里显式关遥测（而不是指望它静默失败）；
3. 集合的 `metadata` 里记 `dim`，维度不符时能立刻报错。

### A9 `hnsw:space` 只在**建集合**时生效

**现象**：集合已经用默认的 `l2` 空间建好了，之后再怎么传 `hnsw:space=cosine`
**不会改回来，也不报错**——于是"余弦相似度"这个假设从一开始就是错的，
而所有下游计算（`score = 1 - distance`、阈值比较）都建立在它之上。

**根因**：`hnsw:space` 是**建集合**参数，不是可变更的运行时配置。

**解决**：只在**一个地方**、用**一次**建集合，并把空间写死：

```python
# backend/src/knowflow/vectorstore/chroma_store.py L111-L116
collection = self._client.get_or_create_collection(
    name=name,
    metadata={_SPACE_KEY: _COSINE, _DIM_KEY: self.dim},
    # 见模块 docstring 第 3 条：禁止 Chroma 用自带 EF
    embedding_function=None,
)
```

配套规则——**只在 `upsert` 里创建集合**（模块 docstring 第 4 条）：
`count` / `query` / `list_vector_ids` 对不存在的集合直接返回 `0` / 空列表，
**不产生"查一下就把集合建出来"的副作用**。

**相关文件**：`backend/src/knowflow/vectorstore/chroma_store.py` L24-L25、L56-L58、L98-L122、L232

**怎么发现**：这是"删库重来才发现"的典型——如果集合曾被别的代码建过，
新建的 `hnsw:space` 参数就失效了。**判据是距离到相似度的换算是否自洽**：
`chroma_store.py` L232 明确写着"`hnsw:space=cosine` 返回 `d = 1 - cos(a, b)`，
所以 `score = 1 - distance`"。

**怎么防止再犯**：**保持"集合在哪建"只有一个入口**。
一旦读路径也建集合，就会出现"这个集合是什么参数建的"说不清的局面。
换 embedding 模型时**删掉整个 `data/chroma/` 重建**（同时必须重新标定阈值，见 E7 结论 5）。

### A10 流式接口被缓冲："转圈很久然后一次性出全文"

**现象**：本地直连 uvicorn 时流式正常；一挂中间件就变成"转圈很久然后一次性出全文"。
**接口 200、内容正确**，所以断言"响应体对不对"的测试全绿。

**根因**：`starlette.middleware.base.BaseHTTPMiddleware` 用"一个任务跑下游 app +
一个内存对象管道传消息"的方式实现。对流式响应（`StreamingResponse` / `text/event-stream`）
这条路径会引入**缓冲**：下游 `await send(...)` 之后消息先落进管道，由另一个任务再取出写出去。

**解决**：写**纯 ASGI 中间件**（`async def __call__(self, scope, receive, send)`），
把 `send` 换成一层次薄包装，**同一协程内同步调用**。

```python
# backend/src/knowflow/middleware/context.py L3-L18（节选）
# 为什么不用 `BaseHTTPMiddleware`
...
纯 ASGI 中间件没有这一层：它就是一个 `async def __call__(self, scope, receive, send)`，
把 `send` 换成自己的一层薄包装**同一协程内同步调用**，`await send(message)`
返回时数据已经交给服务器。零缓冲、零额外任务、零额外队列。
```

**相关文件**：`backend/src/knowflow/middleware/context.py` L1-L37、
`frontend/nginx.conf`（部署侧的同一条：`proxy_buffering off`）、
`backend/src/knowflow/api/routes/chat.py`（返回 `X-Accel-Buffering: no`，双保险）

**怎么发现**：阶段 9 的 SSE 自测（`frontend/scripts/sse-selftest.mjs`，14 项）
+ E6.3 的 51 帧事件序列校验（`backend/scripts/smoke_http.py`，70 项断言）——
**只有"手写解析 SSE 分帧、逐帧看事件顺序"才能发现缓冲**（E6.3 就是这么做的）。

**怎么防止再犯**：
1. 代码层：纯 ASGI 中间件（本项目的选择）；
2. 部署层：nginx `proxy_buffering off` + `proxy_cache off` + 拉长 `proxy_read_timeout`；
3. 验证层：`smoke_http.py` 真起服务、真解析分帧、校验
   `首帧 meta / 末帧 end / sources 在 token 之前 / 无 error 帧`。

### A14 `Page["MessageOut"]` 被解析成**另一个** `MessageOut`

**现象**：接口 200、字段名都对，**但 `items` 里是提示文案**（`{"message": "..."}`）。

**根因**：字符串注解是 `ForwardRef`，Pydantic 用**定义 `Page` 的那个模块**

（提示文案，现名 `SimpleMessageOut`，旧名保留为兼容别名）。

```python
    """`GET /conversations/{id}/messages` 的分页响应：`Page[MessageOut]`。

    （`schemas/common.py`）的命名空间去解析它，而那里也有一个 `MessageOut`
    （提示文案，现名 `SimpleMessageOut`，旧名仍为别名），于是
    `Page["MessageOut"]` 会静默解析成 `Page[SimpleMessageOut]`——
    """
```

```python
# backend/src/knowflow/schemas/conversation.py L157-L158
assert get_args(MessagePage.model_fields["items"].annotation) == (MessageOut,), (
    "MessagePage.items 必须是 list[MessageOut]（会话消息），"
```

**相关文件**：`backend/src/knowflow/schemas/conversation.py`、
`backend/src/knowflow/schemas/common.py` L174-L193、
`backend/src/knowflow/schemas/__init__.py` L47-L142（含三条 import 期断言）、
`backend/src/knowflow/api/routes/conversations.py` L10-L12

**怎么发现**：前端联调时在 `.citations` 上炸——**后端接口本身一切正常**。
`schemas/__init__.py` 的注释还记了"为什么不能靠 import 顺序解决"：
ruff 的 isort 会按字母序重排，**改一次 import 就可能静默把 `MessageOut` 换回错的**。

### A11 启动时 `JSONDecodeError`（逗号形式的 `CORS_ORIGINS`）

**现象**：`.env` 里写 `CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173`，
进程**起不来**，报 JSON 解析错误。

**根因**：pydantic-settings 对复杂类型（`list[str]`）默认先做一次 `json.loads`，

**解决**：给字段加 `Annotated[list[str], NoDecode]`，自己写校验器处理逗号/JSON 两种写法：

```python
# backend/src/knowflow/core/config.py L63-L67
# NoDecode 关掉 pydantic-settings 对复杂类型的 JSON 预解析，交给下面的校验器统一处理。
# 不加 NoDecode，逗号写法会在**启动时**抛 JSONDecodeError —— 真实踩过的坑。
cors_origins: Annotated[list[str], NoDecode] = Field(
    default_factory=lambda: ["http://localhost:5173", "http://127.0.0.1:5173"]
)
```

**相关文件**：`backend/src/knowflow/core/config.py` L65（`cors_origins`）、
L146（`allowed_extensions` 同一个坑）、L169-L182（`_split_comma_or_json`）、
`backend/tests/test_config.py`（两种写法都钉住）

**怎么发现**：`test_config.py` 的 docstring 直接把它列为第 2 条承诺：
"两种列表写法都要能解析：不加 `NoDecode` 时逗号写法会在启动时抛 `JSONDecodeError`"。

**怎么防止再犯**：**所有"列表型配置"都走同一个校验器**，
并在测试里**两种写法各来一条**。最小复现（手册 §7 动手验证）：
把 `cors_origins` 的 `NoDecode` 临时去掉，`Settings()` 立刻抛错。

## E. 切分

### A13 块边界从句中砍断、不报错（`separators` 里的空串）

**现象**：检索质量下降，**不报任何错**；极端情况下切出远超 `chunk_size` 的巨型块
（注释里记录"曾观察到 300 字文档只切出 1 块"）。

**根因**：`langchain-text-splitters 1.1.3` 的 `RecursiveCharacterTextSplitter._split_text`
遇到空分隔符会**直接 `break`**：

```python
for i, s_ in enumerate(separators):
    if not s_:                       # 碰到空串就 break
        separator = s_; break
    if re.search(separator_, text):  # 碰到出现的分隔符也 break
        separator = s_; new_separators = separators[i + 1:]; break
```

空串写在中间 → 更"高级"的分隔符（`\n\n`、`。`）**全部被跳过**，
而且 `new_separators` 为空导致**递归下降彻底失效**。

**解决**：空字符串只能放**最后一位**，并且在构造 splitter 前**主动校验**：

```python
# backend/src/knowflow/ingest/chunkers.py L234-L240
if "" in separators[:-1]:
    raise ValueError(
        "separators 中除最后一项外不允许出现空字符串：RecursiveCharacterTextSplitter "
        "遇到非末位的空分隔符会跳过所有更高级分隔符、放弃递归下降，"
        "导致块边界从句子中间砍断（且不报错）。"
        f" 当前 separators={list(separators)!r}"
    )
```

**相关文件**：`backend/src/knowflow/ingest/chunkers.py` L56-L94（`DEFAULT_SEPARATORS` + 原理注释）、
L225-L244（`_validate_separators`）、`backend/tests/test_ingest_loaders.py`、
`docs/教程/04-阶段3-文档解析与切分.md` §2.6

**怎么发现**：动手做"每个分隔符都有文本命中"的对照实验时暴露——
正确配置下块开头是 `'。第二句话！'`（从句子边界开始），
空串插在中间时块开头变成 `'话！第三句话？'`、`'四句话，第五'`。

**怎么防止再犯**：**"看起来成功了但结果是错的"必须主动抛错拦下，不能只记 warning**。
因为它不会在功能测试里暴露，只会在几周后被用户投诉"搜索不准"。

### A15 ruff 报"行太长"，且都在中文注释行

**现象**：一行"看起来只有 60 个字符"的中文注释被 ruff 判为超长（默认 `line-length = 88`），
**而报错只会说"行太长"，完全不会提"因为你写了中文"**。

**根因**：ruff 的行宽按 **unicode 显示宽度**算，**一个汉字 = 2 列**。
所以 45 个汉字的注释 = 90 列 > 88。

**解决**：`backend/pyproject.toml` 里设 `line-length = 100`（本仓库现有代码的实际排布宽度）。

**相关文件**：`backend/pyproject.toml` L104-L109、`.github/workflows/ci.yml` L65-L67（CI 里重复了一次原因）

**怎么发现**：第一次跑 `ruff check` 时一片红；观察"超长的行全是中文注释"才定位到口径问题。

**怎么防止再犯**：把原因**写在配置里**（不是写在某个人的记忆里）。
这条坑的教训是"报错信息可能指向错误的修改方向"——
人第一反应会去拆行，而正确动作是改口径。

### A20 `SyntaxError: bytes can only contain ASCII literal characters`

**现象**：想写一段固定字节（比如 BOM 前缀、测试用中文样本）时，
直接写 `b"中文"` 报语法错。

**根因**：这是 **Python 语言本身的限制**——bytes 字面量只能包含 ASCII 字符。

**解决**：先编码再字面量化：

```python
"中文".encode("utf-8")          # 首选
b"\xe4\xb8\xad"                 # 或用转义（本项目里 BOM 就是这么写的）
```

**相关文件**：`backend/src/knowflow/ingest/loaders.py` L69-L75
（`BOM_SIGNATURES` 用的是 `b"\xef\xbb\xbf"` 这种转义形式）、
`backend/src/knowflow/embeddings/hash_embedder.py`（`token.encode("utf-8")`）、
`docs/教程/04-阶段3-文档解析与切分.md` §3 验证 2（`b"\xef\xbb\xbf" + "# 标题\n".encode("utf-8")`）

**怎么发现**：本会话复现（`x = b"中文"`）：

```
    x = b"中文"
        ^^^^^
SyntaxError: bytes can only contain ASCII literal characters
```

**怎么防止再犯**：约定"**中文一律走 `str`，需要字节时显式 `.encode("utf-8")`**"。
项目里唯一直接写 bytes 字面量的地方是编码嗅探的 BOM 表——那里**必须**是字节。

### A21 `SyntaxError: name 'PORT' is used prior to global declaration`

**现象**：在函数里先用了某个全局名，再写 `global`，直接语法错误。

**根因**：`global` 声明必须在函数体内**第一次使用该名字之前**（实际上必须是函数体的**第一条语句**之一）。

**解决**：把 `global` 放在函数体最前面——**先声明再使用**：

```python
# backend/scripts/smoke_http.py L83-L91
def main() -> int:
    # 注意：`global` 必须是函数体的**第一条语句**。
    # 写在 `parser.add_argument(default=PORT)` 之后会报
    # SyntaxError: name 'PORT' is used prior to global declaration。
    global PORT, BASE

    parser = argparse.ArgumentParser()
    parser.add_argument("--hash", action="store_true", help="用哈希向量（不加载 2GB 模型）")
    parser.add_argument("--port", type=int, default=PORT)
```

**相关文件**：`backend/scripts/smoke_http.py` L83-L95；
`backend/src/knowflow/core/logging.py` L47、`backend/src/knowflow/db/session.py` L81/L90/L150
（模块级单例也是同样的写法）

**怎么发现**：本会话复现（先 `print(PORT)` 再 `global PORT`）：

```
    global PORT
    ^^^^^^^^^^^
SyntaxError: name 'PORT' is used prior to global declaration
```

**怎么防止再犯**：这条是**语法层**的，跑一次就暴露，不需要额外防线。
真正的价值是它被**写进了注释**——`smoke_http.py` 里的那段注释就是为了
"下一个人想在 `default=PORT` 后面加 `global`"时不踩。

### A22 PowerShell 5.1 读 `.ps1`：中文乱码 + 解析失败

**现象**：脚本里有中文（提示信息、`## 帮助` 注释）时，PowerShell 5.1 输出乱码
（`涓枃杈撳嚭` 这种），甚至会解析失败。

**根因**：**PowerShell 5.1 读 `.ps1` 时，没有 BOM 就按 ANSI 代码页解释**
（本机 cp936 / GBK），而文件实际是 UTF-8 → 字节被逐对解成别的汉字。
PowerShell 7 默认按 UTF-8 读，所以**同一个文件在 pwsh 7 下完全正常**。

**解决**：给 `.ps1` 加 **UTF-8 BOM**。本仓库的 `tasks.ps1` 就是带 BOM 的：

```
tasks.ps1                        EF BB BF        ← UTF-8 BOM（本会话实测前 3 字节）
```

**相关文件**：`tasks.ps1`（285 行，含大量中文提示）、`backend/scripts/*.py`
（`.py` **不需要** BOM：Python 3 默认按 UTF-8 读源码）

**怎么发现**：本会话**直接对比复现**（同一个内容，只差分不分 BOM，
用 `powershell.exe` = PowerShell 5.1，本机版本 `5.1.26100.9168`）：

```
=== powershell.exe 5.1 -File no_bom.ps1 ===
涓枃杈撳嚭 OK                    ← 乱码

=== powershell.exe 5.1 -File with_bom.ps1 ===
中文输出 OK                      ← 正确
```

**怎么防止再犯**：
1. 所有 `.ps1` 一律**存成 UTF-8 with BOM**；
2. 编辑器/生成脚本要显式设置（很多工具默认"UTF-8 无 BOM"）；
3. 排查纪律：**"脚本在 Linux/pwsh7 正常、在这台 Windows 乱码"先查 BOM**。

### A23 ⭐ `ValueError: <Token ...> was created in a different Context`

**现象**（`docs/03` E6.5 原文）：

> 非流式 `/chat` 完全正常，但 `/chat/stream` 每次都在最后发一个 `error` 帧，
> `done` 帧永远不出现。服务端日志：

```
[error] chat.stream_failed
error="ValueError: <Token var=<ContextVar name='current_recorder' default=None>>
       was created in a different Context"
```

**根因**（`agent/nodes.py::RecorderBox` 的 docstring 逐字）：

> 原因是 Starlette 迭代**同步生成器**时会用 `iterate_in_threadpool`，
> **每取一个元素就是一次 `run_in_threadpool(next, ...)`** ——
> 也就是每个 `next()` 可能落在不同的线程、拿着**各自的 context 副本**上。
> 而 `ContextVar.set()` 返回的 token 只能在**同一个 context** 里 `reset()`。
> 生成器第 1 次 yield 时 set，第 N 次 yield 后退出 `with` 时 reset → 直接抛异常。

**解决**：**不用 contextvar 传 recorder，改成挂在依赖对象上显式传递**：

```
agent/nodes.py::RecorderBox  →  AgentDeps.recorder_box  →  RequestServices.recorder_box
```

```python
# backend/src/knowflow/agent/nodes.py L60-L80（节选）
class RecorderBox:
    """一次请求的 `TraceRecorder` 持有者（显式传递，不用 contextvars）。
    ...
    流式恰好是本项目的主路径，所以这个问题必须从根上解决：
    **把 recorder 挂在依赖对象上显式传递**，不依赖任何隐式上下文。
    生成器在哪个线程跑都不影响 —— 它读的是同一个对象。
    """
```

**相关文件**：`backend/src/knowflow/agent/nodes.py` L60-L109、
`backend/src/knowflow/container.py` L65-L69（`recorder_box` 字段）、
`backend/src/knowflow/services/chat.py` L424、`backend/tests/conftest.py`（离线装配）

**怎么发现**：**真起 uvicorn 打流式接口**（`scripts/smoke_http.py`）——
`pytest` 用 `ASGITransport` **不会**触发分次线程调度，
所以 204 个单测全绿也照样漏掉它（E6.5 原话）。修复后 70 项 HTTP 断言全绿。

**怎么防止再犯**（这条的"再犯"指**同类错误**：依赖隐式上下文传请求级状态）：
1. **请求级状态一律显式传递**（依赖对象上挂字段），不用 `ContextVar` 存"请求级对象"；
2. `ContextVar` 只用于**只读的横切标记**（如 `request_id` 写日志），且必须在 `finally` 里清理
   （`middleware/context.py` 的"三件必须做对的事"第 2 条讲的就是不清理会让
   **下一个请求的日志带上一个请求的 request_id**）；
3. **保留一层真起服务器的冒烟**——它是唯一能抓到这类"只在真实调度下出现"的 bug 的层。

### A25 ⭐ 评测静默测了个空：`vector recall@5 = 0.000`，且三模式相同

**现象**：第一次跑消融得到的是这样一张表（`docs/03` E7.6 原文）：

```
  vector          recall@5 = 0.000
  bm25            recall@5 = 0.721
  hybrid          recall@5 = 0.721     ← 与 bm25 完全相同
  hybrid_rerank   recall@5 = 0.721     ← 与 bm25 完全相同
```

**接口 200、指标算得出、表打得出来、全程不报错。**

**根因**：`run_evaluation(kb_ids=None)` 时调用方没有传 KB 列表，
而检索引擎在"**没有任何 KB 目标**"时会**跳过向量召回**
（向量库按 KB 分集合，没目标无从查起；BM25 则可以跨库搜）。
于是 `vector` 模式**根本没检索**，返回 0。

**解决**：`kb_ids=None` 时由 harness **自己从库里取活跃 KB**，一个都没有时打 warning
（而不是让"向量那一路"静默缺席）：

```python
# backend/src/knowflow/evaluation/harness.py L446（节选）
.where(KnowledgeBase.deleted_at.is_(None))
```

**相关文件**：`backend/src/knowflow/evaluation/harness.py`（L92-L104 的候选唯一标识、
L446 附近的活跃 KB 兜底）、`backend/scripts/run_eval.py`、`docs/03` E7.6

**怎么发现**：**靠"结果不合常理"**——`hybrid` 与 `bm25` **一模一样**就是
"向量那一路完全没参与"的指纹。E7.6 的教训逐字：

> **教训**：评测工具最怕的就是**静默地测了个空**。
> 凡是"跑完了、有数字、全绿"但结果不合常理的情况，先怀疑"这一步真的执行了吗"。

（另一个候选修法是"让检索引擎在向量模式下无 KB 就报错"，但那会破坏
"全局 BM25 检索"这个合法用法，所以选择在**评测层**兜底。）

**怎么防止再犯**：
1. **把"某一层没参与"变成可见信号**：`/search` 的 `debug` 里有
   `vector_candidates / bm25_candidates / fused / dropped_orphans / vector_error`
   （E6.3 实测能看到每一段的真实数字）；三方计数一致性（`consistent`）随时可比；
2. **看"指纹"**：如果 `hybrid == bm25`（或 `hybrid == vector`），立刻怀疑另一路没干活；
3. **对不合常理的结果立一条纪律**：先问"这一步真的执行了吗"，再问"参数对不对"。
