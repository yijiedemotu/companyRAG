## C1. 加一个新文件格式（docx）

**目标**：让 `POST /kbs/{id}/documents` 能收 `.docx`，并且**逐段落解析、保留页码/序号**，

**通过判据**
- ✅ `parser = docx`（**不能**退化成 `txt` 或 `unknown`）；
- ✅ `chunks` 数 > 0，且 `index 连续: True`（这是阶段 3 的不变量）；

2. `docx` 本质是 **ZIP + XML**：`zipfile` 读 `word/document.xml` 就能拿到段落文本，

3. `ParsedDocument` 的字段要照抄现有实现：`parser` / `pages`（`ParsedPage(text, page_no)`）/
   `char_count` / `line_count` / `warnings`。**别自己发明字段**——上层依赖它们。
4. 单测至少要钉三条：**段落顺序**（不是字典序）、**空文档 → `DocumentEmptyError`**、
   **表格里"列名: 值"的对应关系不丢**（这条正是 CSV 那次真实事故的同类）。
5. 加完记得同步 `config.py` 的默认白名单**和** `.env.example` 的说明
   —— 只改一处会出现"测试能过、真实上传 400 `UNSUPPORTED_FILE_TYPE`"。

## C2. 把闸门改成可 per-hit 判定

**目标**：现在的闸门是"整批候选 → 一个 `passed`"。
改成**每条 hit 各自有判定结果**（`vector_ok` / `keyword_ok` / `passed`），
整批的 `passed = any(hit.passed)` —— 语义等价，但**为将来的 per-hit 过滤/解释打基础**。

**难度**：★2　**预计耗时**：1~1.5 h

**涉及文件**
- `backend/src/knowflow/retrieval/autocut.py`（`evaluate_gate` L81-L120 + `GateResult`）
- `backend/src/knowflow/retrieval/types.py`（`GateResult` 与候选类型 L183）
- `backend/src/knowflow/schemas/search.py`（`SearchDebug.dropped_orphans` 附近的 debug 结构）
- `backend/src/knowflow/agent/nodes.py`（`_heuristic_relevance` 用同一套语义，别让它漂）
- `backend/tests/test_fusion_autocut.py`（"闸门 OR 语义"那条承诺）

**验收标准**

```powershell
cd D:\Projects\pythonProjects\knowflow\backend
..\.venv\Scripts\python.exe -m pytest tests/test_fusion_autocut.py -q
..\.venv\Scripts\python.exe -m pytest -q          # 仍是 204 passed
```

```powershell
# 语义等价性 + per-hit 字段存在（纯计算，零依赖）
cd D:\Projects\pythonProjects\knowflow
@'
import sys; sys.path.insert(0, r"D:\Projects\pythonProjects\knowflow\backend\src")
from knowflow.retrieval.autocut import evaluate_gate
from knowflow.retrieval.types import Candidate

def c(vid, vec, cov):
    return Candidate(vector_id=vid, content=vid, doc_id=1, doc_name="d",
                     chunk_index=0, keyword_coverage=cov, vector_score=vec)

# 一条走向量、一条走覆盖率、一条都不走
batch = [c("1:0", 0.70, 0.0), c("1:1", None, 0.55), c("1:2", 0.10, 0.05)]
g = evaluate_gate(batch, vector_threshold=0.60, keyword_threshold=0.40)
print("整批 passed =", g.passed, "| reason =", g.reason)
per = getattr(g, "per_hit", None)
print("有 per_hit 字段 =", per is not None)
if per:
    for vid, ok in per.items():
        print(f"  {vid} -> {ok}")
    print("any(per_hit) == passed:", any(per.values()) == g.passed)
'@ | .\.venv\Scripts\python.exe -
```

**通过判据**
- ✅ 上面的脚本打印 `any(per_hit) == passed: True`（**语义等价**，这是最重要的判据）；
- ✅ `reason` 仍然是四个**稳定标识**之一（`vector_score_above_threshold` /
  `keyword_coverage_above_threshold` / `no_candidates` / `below_all_thresholds`）——
  **前端与测试按它分支，不能改成给人看的句子**（`autocut.py` L33-L37 的注释）；
- ✅ `best_vector_score` 仍然**只统计有向量分**的候选（BM25 独有候选不能被当成 0）；
- ✅ `test_fusion_autocut.py` 与全套 204 条全绿。

**提示**
1. **不要改 `reason` 的取值集合**。前端的"为什么拒答"、`smoke_http.py` 的断言都读它。
   per-hit 判定应该是**新增字段**，不是替换现有语义。
2. 别把 per-hit 判定塞进 `retrieval/engine.py::query` 的热路径——
   那是"每次检索都要算"的地方。放在 `evaluate_gate` 里（它本来就已经遍历了一遍候选）。
3. `Candidate.vector_score` 是 `float | None`。**`None` 不等于 0**：
   这是"BM25 命中但向量没召回"的正常情况（`autocut.py` 的 docstring 专门说了这点）。
4. 顺手做一件好事：让 `SearchDebug` 里多一个 `per_hit_passed` 计数，
   这样 `/search` 的调试面板能看出"几条过了闸门"——**可观测性改造比功能改造更值钱**。

**通过判据**（这是本练习的**核心**）
- ✅ **`hybrid_rerank` 不再等于 `hybrid`**。E7.5 里两者完全相同（Δ = 0），
  因为离线模式重排走了启发式兜底（E7.5 结论 4）。接上真模型后**必须出现差异**，
  否则说明你的重排根本没被调用（这就是 E7.6 那类"静默测了个空"）。
- ✅ 用**配对 bootstrap** 报告 Δ、95% CI、p 值（`run_eval.py` 已有，`n_boot=2000, seed=42`）。
- ✅ 报告头部的 `LLM 判官` / 重排标记为 `True`（**别让"这一列代不代表真重排"靠人记得**）。
- ✅ 离线（无模型）时链路**照旧可跑**：`pytest` 204 条全绿、`smoke` 41 项全绿。

**提示**
1. **交叉编码器的输入是 `(query, passage)` 对**，不是"两次独立编码再算余弦"
   ——这是它和 bi-encoder（BGE-M3）的本质区别，也是它更强、更慢的原因。
2. **只能用在 top-N**：`RERANK_TOP_N ≤ FETCH_K` 有启动期校验。
   CPU 上批量打分很慢，先量一条样本再决定 `--top-k` 与 batch size。
3. **降级必须保留**：模型加载失败/超时 → 回启发式，并且**要可见**
   （`/search` 的 debug 与 `/health` 的 warnings 都要能看出来）。
   E1.5 里 `test_rerank.py` 的承诺就是"**降级不中断链路**"。
4. ⚠ **换重排会改变最终排序，但不改变 `VECTOR_MIN_SCORE` 的语义**——
   不过如果你把重排分也拿去和阈值比，那就**必须重新标定**（E7 结论 5 的同一条纪律）。
5. **别急着进 CI**：真模型要 2GB 下载与 CPU 时间，CI 的"零成本"承诺（`ci.yml` 的
   三个环境变量）会被破坏。正确做法是"发版前人工跑"（`ci.yml` 注释里已有这句话）。

## C5. 上传改成异步任务 + 进度轮询

**目标**：`POST /kbs/{id}/documents` 立即返回 `202 + task_id`，
后台线程/进程完成解析+切分+向量化+入库，客户端轮询任务状态拿进度。

**难度**：★4　**预计耗时**：4~6 h

**涉及文件**
- `backend/src/knowflow/api/routes/documents.py`（上传端点）
- `backend/src/knowflow/services/document.py`（`ingest_upload` 的拆分）
- `backend/src/knowflow/db/models/knowledge.py`（`documents.status` 字段已有枚举）
- `backend/src/knowflow/schemas/document.py`（响应模型）
- `backend/src/knowflow/container.py`（任务执行器/线程池的装配）
- 新增：`backend/src/knowflow/services/tasks.py`（或类似）

**验收标准**

```powershell

..\.venv\Scripts\python.exe ..\backend\scripts\smoke_pipeline.py   # PASS = 41 / FAIL = 0
```

**再加一条你自己的断言**（用 `httpx.ASGITransport` 或 `smoke_http.py` 的风格）：
- ✅ 上传返回 **202**，响应体里有任务 id；
- ✅ 立刻轮询状态是 `PENDING/PROCESSING`（**不是** `READY`）；
- ✅ 轮询到 `READY` 后，**三方计数一致**（`chunk_count == vector_count == bm25_doc_count`）；
- ✅ 失败任务的状态是 `FAILED` 且**能取到错误原因**（不是永远 `PROCESSING`）。

**提示**
1. **复用 `documents.status`**，不要新建一张"任务表"——除非你真的需要重试/优先级。
   `smoke_pipeline.py` 与 `seed_demo.py` 都读这个字段。
2. **幂等**：同一 `sha256` 重复上传必须命中 `DOCUMENT_DUPLICATE`（`docs/01` §二的错误码表里已有）。
   异步化之后，这个判断要在**入队前**做，否则两个并发上传会都进队列。
3. **后台任务不能持有请求级 session**：`api/deps.py` 的 `get_session` 是**请求级**的，
   请求返回后就 `close()` 了。任务要自己开 session（或从容器拿 `session_factory`）。

  如果 `N` 或 `df` 没更新对，B 的分数会整体漂移）；

**提示**
1. **`idf` 依赖 `N`（文档总数）与 `df`**。删掉文档后 `N` 变小，
   所以"其他文档的分数变化"是**正常的**——但你要能**说清变化方向与幅度**。

4. 幂等要和现有实现一致：`test_bm25.py` 里已经有"幂等"这条承诺，
   你的增量删除不能破坏它（重复删同一个 `doc_key` 不应把计数减两次）。

**提示**
1. **别用"给同步 SDK 套一个 `async def`"这种假 async** ——
   那样事件循环还是被阻塞的，问题一点没解决（而且更隐蔽）。
   两条真路线：
   - **A. 独立推理服务**：模型跑在单独进程/容器，主服务用 async HTTP 客户端调用
     （`httpx.AsyncClient`）。优点是进程隔离、可独立扩容；缺点是引入网络跳数与超时处理。
   - **B. 显式线程池**：现状其实就是这条（Starlette 的 `run_in_threadpool` /
     `iterate_in_threadpool`）；把它**显式化、可配置、可观测**也是有效改造
     （至少能回答"线程池多大、排了多久"）。
2. **先量瓶颈再改**：E6.3 里一次 `/search` 的 **177ms 中 `embedding_ms=168`** ——
   所以真正要优化的是**编码**，不是检索（`vector_ms=3`）。
   把 API 层 async 化但模型还是同步，等于没做。
3. **注意 SSE 生成器**：流式路径本来就跑在线程池里分次驱动，
   而且正是这里踩过 `contextvars` 的坑（E6.5 / 附录 A A23）。
   改 async 时**重新审视一遍 recorder 的传递方式**（现在是 `RecorderBox` 显式传递）。
4. **批处理是更便宜的优化**：`EMBEDDING_BATCH_SIZE` 默认 16；
   把多个请求的 query 凑批、或把 chunk 编码真正批量化，
   往往比"改 async"更有效——**先做这个，再考虑架构改造**。
5. 做完之后，`docs/00` §8 那一行要从"检索路径有同步阻塞调用……瓶颈已知但未量化"
   改成**带数字的实测结论**（例如"QPS 从 X 提到 Y，p99 从 A 降到 B"）。
   **没写进文档的实测等于没做**（这是 `docs/03` 存在的全部理由）。

## 完成顺序建议

按"依赖关系 + 性价比"排，推荐这样串：

```
C1 (docx)  ──►  C2 (per-hit 闸门)  ──►  C10 (评测指标)
   ★1              ★2                       ★3
   └─ 熟悉解析链路   └─ 熟悉检索后处理        └─ 让"改得好不好"可测量
                                              │
                             ┌────────────────┴────────────────┐
                             ▼                                 ▼
                    C3 (交叉编码器重排)                 C4 (LLM 判官)
                       ★3 · 需要 2GB 模型                 ★3 · 需要 Key
                             │                                 │
                             └────────────┬────────────────────┘
                                          ▼
                              C9 (BM25 增量) → C11 (限流熔断) → C6 (Redis)
                                 ★3              ★3              ★3
                                          │
                                          ▼
                          C5 (异步上传)  →  C7 (pgvector)  →  C12 (async 化)
                             ★4               ★4                 ★5
                                          │
                                          ▼
                                   C8 (多租户隔离) ★5 · 工程量最大
```

**为什么这样排**：
- **C1/C2 是"通读一遍关键模块"的最好借口**——做完你会对 `ingest` 与 `retrieval`
  有肌肉记忆，而不是"看过文档"。
- **C3/C4 决定你能不能讲"质量"**：在此之前，你所有的数字都是"检索"的；
  做完之后你才有"生成"的数字（而且要把它写进 `docs/03`）。
- **C6/C7/C9/C11 是"工程能力"的证据**，共同点：都要**在不破坏 204 条离线用例的前提下**做，
  这才是难点（不是"能不能写出来"）。
- **C8/C12 是"上生产"的两大件**，也是最花时间的。别同时开两个。

## 别做的三件事

1. **不要为了让测试变绿而改测试**。
   `backend/tests/` 里的每条断言都对应一条设计承诺（每个 `test_*.py` 的 docstring 就是承诺清单）。
   测试红了先问"**我是不是破坏了某个承诺**"（例如 E6.5 的 contextvars、E7 的阈值口径）。
2. **不要在没有基线的情况下调参数**。
   E7 的全部价值来自"标定前 0.35 / 标定后 0.60"这个对比；
   没有基线的调参，得到的数字**无法解释也无法复现**（`docs/03` 的头两句话就是讲这个）。
3. **不要把"没实测"说成"实测过"**。
   Docker、真实模型答案质量、交叉编码器重排、并发压测、多租户——这五项都是 `docs/03` E11
   明确标注的**未实测**。做完哪个，就**把它从 E11 挪到一份新的实测记录里**（并写清环境与命令），
   没做完的继续留在 E11。**这张表是你可信度的来源，不要污染它。**
