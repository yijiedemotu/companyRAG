# 阶段 5：BM25 与混合检索

> **本阶段目标**：加上第二路召回（稀疏 BM25），把两路"量纲不同"的分数融合成一个可比的分，再用双阈值闸门决定"这批结果能不能回答这个问题"。
> **预计耗时**：150 分钟
> **前置阶段**：阶段 4（第 6 步"重排"会 `import` 阶段 6 的 `llm/`，见 §0 的说明）
> **本阶段产出**：`retrieval/` 八个模块（1,814 行）+ 一个**七阶段、每段单独计时**的混合检索引擎

## 0. 为什么先做这一步

因为**一路召回的盲区是结构性的，不是调参能补的**（`docs/00` 第 2.1 节）：

| 信号 | 强项 | 盲区 |
| --- | --- | --- |
| 稠密向量（BGE-M3） | 同义改写、口语提问 | 专有名词 / 错误码 / 型号 |
| 稀疏 BM25 | 精确词面、罕见词 | 换个说法就查不到 |

用户搜 `PAYLOAD_TOO_LARGE`、`bge-m3`、`2026-01-01`，向量模型很可能把它
"理解"成一个普通名词；而这类串恰恰是**必须精确命中**的。反过来，
用户问"房费能报多少"、文档里写的是"住宿标准"，向量能捞到，BM25 一个字都对不上。
**所以要两路都留。**

第二个理由：**两路分数不能直接相加**。这一条是本阶段最容易被忽略、后果又最严重的坑：

```
向量分数：cosine 相似度，压在 [0, 1]，实测集中在 0.4~0.9
BM25 分数：无上界，取决于 IDF 与文档长度（本会话小样例里出现过 6.93，E6.3 里出现过 35.59）
```

如果写成 `0.6 * vector + 0.4 * bm25`，**BM25 会完全主导**（数值大 10 倍以上），
表现是"关键词搜出来的东西永远排第一，向量检索形同虚设"——而且**接口 200、结果看起来很正常**。

第三个理由：**闸门是防幻觉的最后一道，而且它比"让模型别编"便宜得多**。
两条阈值都不过就**不调大模型**，直接返回固定话术（E6 的拒答路径
`gate: passed=False reason=below_all_thresholds` 就是这个分支）。
工程上把钱花在"确保它手里有对的资料"，比花在"求它别编"有效。

第四个理由：**阶段 7 的 `grade` 判据要用到这里产出的两个字段**——
`vector_score` 与 `keyword_coverage`。两路信号必须先在这里存在并且含义稳定，
`agent/nodes.py::_heuristic_relevance` 才有东西可判。

> ⚠ **一个诚实的顺序说明**：本阶段第 6 步的**重排**（`retrieval/rerank.py`）
> `import` 了 `knowflow.llm.base` 与 `knowflow.llm.prompts`，也就是**阶段 6 的产出**。
> 严格按顺序敲的话有两条路：
> 1. 先做前 5 步（切词 → BM25 → 融合 → autocut → 闸门），它们**不依赖任何模型**
>    （`HybridRetriever` 的 `chat_model` 是可选的，`mode=hybrid` 完全不需要它）；
> 2. 敲完阶段 6 再回来补 `rerank.py`。
> 教程按"阶段 5 全讲完"的顺序写，但你敲的时候可以先跳过 §2.10。

## 1. 要解决的问题

不做这一步，你会遇到的具体失败现象：

| 现象 | 真实原因 |
| --- | --- |
| 中文文档用关键词一个字都搜不到 | 用了 `text.split()`——中文没有空格，`一线城市住宿标准` 被切成 **1 个词** |
| 越常见的关键词越查不到（含它的文档反而排后面） | IDF 忘了 `+1`，`df > N/2` 时 IDF 变负 → 高频词**倒扣分** |
| "关键词搜出来的东西永远排第一" | 两路分数直接加权，BM25 数值大一个量级 |
| 检索质量莫名下降，但不报错 | `avgdl` / `df` 跨 KB 混在一起算，短句库污染了长文库的打分 |
| 重启服务后精确关键词查询静默变差 | BM25 是**内存索引**，忘了从 `chunks` 表重建（进程重启就丢） |
| 一条 `!!!` 被判定为"完全命中查询" | 覆盖率在"文本切不出词元"时返回了 `1.0`（真实修过的 bug） |
| 检索明明失败了，链路却"正常" | 降级路径只记 warning，没写进 `debug.vector_error` |
| 引用里出现前端点开就 404 的条目 | 孤儿向量（向量库有、MySQL 没有）没被丢弃 |
| 本来能答的问题变成拒答 | autocut 的 `min_keep=0` 把候选全砍了，闸门拿到空列表 |
| 两种正确情况都被误杀 | 闸门写成了 `AND`（向量过 **且** 覆盖率过） |
| 第 1 名权重差了 1.6% | RRF 的 `rank` 从 0 开始算（论文是 1 起） |
| `min-max` 归一化后全是 0，全被判为不相关 | 所有分数相同时返回了 0.0（"大家一样好" ≠ "大家一样差"） |
| 上下文长度在 1k~9k 之间剧烈波动 | 预算按"条数"裁剪而不是按"字符"裁剪 |

### 2.2 关键代码 1：中文为什么是 1-gram + 2-gram

```python
# backend/src/knowflow/retrieval/text.py L1-L16（节选）
"""中文切词：全项目唯一的实现。

**为什么必须唯一**：BM25 的打分和「查询词覆盖率」的阈值都建立在这套切词上。
如果两处各写一份，词表稍微不一致，阈值就不再可比 ——
配置里写 `KEYWORD_MIN_COVERAGE=0.25` 的含义会随实现漂移，
调参调出来的数字下次就失效。所以：**要用切词，就 import 这里。**

**为什么不用 jieba**：引入一个 30MB 词典 + 变长依赖，收益主要是词边界更准。
但 BM25 对本项目这种短文档（600 字 chunk）用 **1-gram + 2-gram** 已经足够：
- 1-gram 保证召回（任何包含相同字的片段都能被捞到，不会因分词错误漏召回）；
- 2-gram 提供区分度（"城市"、"住宿"比单字承载更多信息）；
- 且**白板可推导**——面试时能完整讲清楚，比"我调了个库"有价值。
"""
```

切词实现（**跨标点的字不组成 bigram**，这一条是重点）：

```python
# backend/src/knowflow/retrieval/text.py L197-L214（节选）
for segment in _SEPARATOR.split(normalized):
    if not segment:
        continue
    # 一个 segment 里可能同时含汉字和拉丁（如 "住宿600元"），分别处理
    for match in _CJK.finditer(segment):

        for i in range(len(run) - 1):

            if not drop_stopwords or bigram not in STOPWORDS_2:
                tokens.append(bigram)
    for match in _LATIN.finditer(segment):

        if not drop_stopwords or word not in STOPWORDS:
            tokens.append(word)
```

**「一线城市」到底被切成什么**（这是本阶段最该背下来的一张对照）：

```
"一线城市住宿标准".split()            -> ['一线城市住宿标准']        ← 1 个 token，BM25 直接失效
tokenize_zh("一线城市住宿标准")       -> 1-gram: 线 城 市 住 宿 标 准（8 个汉字的"一"是停用词被丢）
                                        2-gram: 一线 线城 城市 市住 住宿 宿标 标准
```

**四个判断各有理由**：

1. **为什么要 1-gram**：中文一个字的错误都会导致"召不回"。1-gram 是**保召回的下界**——
   只要有一个共同字就能进候选池，配合 IDF 与长度归一，最终排序仍然可靠。
2. **为什么要 2-gram**：`城市`、`住宿` 这种双字词承载的信息明显多于单字。
   没有 2-gram，`住宿` 与 `宿住` 无法区分。
3. **为什么不用 jieba**：引 30MB 词典 + 变长依赖，换来的主要是词边界更准；
   而**词边界错一次就是静默漏召回**（"一线城市" 被切错，用户一个字都搜不到）。
   固定 n-gram 没有这个问题，代价只是词表大 2~3 倍。
4. **为什么"跨标点不组 bigram"**：`报销，标准` 如果跨过逗号组出 `销标`，
   那就是一个**只可能造成假命中的词**（真实文本里不会有人写"销标"）。

成本要诚实说（就写在模块 docstring 里）：**词表比 jieba 大 2~3 倍，索引内存占用更高；
同义词（"房费" vs "住宿费"）依然匹配不上，那部分交给向量检索兜底。**

### 2.3 关键代码 2：BM25 公式逐项推导

```python
# backend/src/knowflow/retrieval/bm25.py L1-L28（节选，公式就在源码里）
"""自研 BM25：倒排索引 + 中文 n-gram。

**BM25 公式（白板可推导，面试重点）**

    对查询 Q 中的每个词 t，对每篇文档 D：

        score(D, Q) = Σ_t  IDF(t) · ──────────────────────────────
                                    tf(t,D) + k1 · (1 - b + b · |D|/avgdl)

        IDF(t) = ln( 1 + (N - df(t) + 0.5) / (df(t) + 0.5) )

    其中：
      tf(t,D)  词 t 在文档 D 中出现的次数
      df(t)    包含词 t 的文档数
      N        文档总数
      |D|      文档 D 的长度（词元数）
      avgdl    平均文档长度
      k1=1.5   词频饱和系数：词出现 100 次不等于相关 100 倍，收益递减
      b=0.75   长度归一强度：长文档天然更容易命中，要惩罚
"""
```

**三项分别解决什么问题**（这张表是把公式讲成"设计"的关键）：

| 项 | 形式 | 解决什么问题 | 不写它会怎样 |
| --- | --- | --- | --- |
| **词频饱和** `k1` | `tf·(k1+1) / (tf + k1·(…))` | 词出现 100 次不该等于相关 100 倍 | 复读式文档（把关键词刷 50 遍）霸榜 |
| **IDF** | `ln(1 + (N-df+0.5)/(df+0.5))` | 罕见词的权重必须大于"几乎每篇都有"的词 | `的`、`公司` 与专有名词同权 |
| **长度归一** `b` | `1 - b + b·|D|/avgdl` | 长文档天然更容易命中任何词 | 长文档一律排前面（长度成了得分来源） |

`k1=1.5` / `b=0.75` 不是本项目拍的，是 **Lucene / Elasticsearch 的默认值**，
两行常量在源码里明说了这件事：

```python
# backend/src/knowflow/retrieval/bm25.py L43-L45
# 默认参数（Lucene / Elasticsearch 的默认值，工业界验证过）
DEFAULT_K1 = 1.5
DEFAULT_B = 0.75
```

打分循环（`Σ_t` 这一层）：

```python
# backend/src/knowflow/retrieval/bm25.py L177-L187（节选）
for term in terms:
    posting = self._postings.get(term)
    if not posting:
        continue
    idf = self._idf(term)
    if idf <= 0:
        continue
    for doc_key, tf in posting.items():
        doc_len = self._doc_len.get(doc_key, 1)
        denom = tf + self.k1 * (1.0 - self.b + self.b * doc_len / avgdl)
        scores[doc_key] += idf * (tf * (self.k1 + 1.0)) / denom
```

⚠ **注意 `text.tokenize_zh("住宿")` 会切出三个词元 `['住', '宿', '住宿']`**，
所以 `Σ_t` 是对**三个词**求和，不是对一个词。§3 的验证 2 会手算给你看——
第一次自己手算时几乎都会漏掉这一点（本会话第一版手算就差了 0.42）。

### 2.4 关键代码 3：IDF 为什么要 `+1`

```python
# backend/src/knowflow/retrieval/bm25.py L156-L162
def _idf(self, term: str) -> float:
    n = len(self._payload)
    df = self._df.get(term, 0)
    if n == 0 or df == 0:
        return 0.0
    # +1 保证 IDF 恒正：经典形式在 df > N/2 时变负，会让高频词"倒扣分"
    return math.log(1.0 + (n - df + 0.5) / (df + 0.5))
```

源码 docstring 里把踩坑过程也写下来了（L21-L24）：

```
**为什么 IDF 里要 `+1`**：经典 BM25 的 IDF 在 `df > N/2` 时会变成负数，
导致"包含该词的文档反而被扣分"。加 1 后恒为正（这是 Lucene 采用的形式）。
**这是一个真实踩过的坑**：早期版本忘了 +1，高频词（如"公司"）一出现就把
相关文档排到最后，表现是"越常见的关键词越查不到"。
```

**为什么这个 bug 特别难查**：它**不报错、不少结果**，只是排序反了。
本会话实跑了一个 `df = N = 4` 的极端例子（所有文档都含"制度"）：

```
IDF('制度') = 0.105361                       ← 本项目（加了 1，恒正）
经典形式(不加1)对照 IDF('制度') = -0.847298   ← 负数 = 倒扣分
IDF 恒正: True
```

### 2.5 关键代码 4：倒排索引为什么快，以及为什么按 KB 分索引

```python
# backend/src/knowflow/retrieval/bm25.py L55-L66（节选）
class BM25Index:
    """一个知识库对应一个索引实例。

    **数据结构**：
        _postings:  term -> {doc_key: tf}     倒排表（为什么快：只扫含查询词的文档）
        _doc_len:   doc_key -> 词元数
        _payload:   doc_key -> 业务元数据（chunk_id / doc_id / 正文 / 页码 / 小节路径）
        _df:        term -> 文档频次

    **时间复杂度**：查询 O(Σ 查询词的 postings 长度)，与库大小无关。
    暴力扫描是 O(N) 且每次都要分词，几万 chunk 就会明显卡顿。
    """
```

**"按 KB 分索引"不是洁癖，是正确性要求**：

```python
# backend/src/knowflow/retrieval/bm25.py L216-L228（节选）
class BM25Registry:
    """按知识库隔离的 BM25 索引注册表。

    **为什么按 KB 分索引**：`avgdl` 与 `df` 都是"库内统计量"。
    如果所有 KB 共用一个大索引，一个全是短句的 KB 会拉低 avgdl，
    从而影响另一个 KB 的打分 —— 跨库污染。分开索引还让"删除整个 KB"
    变成一次 `drop`，干净利落。

    **为什么必须有**：启动时从 MySQL 的 `chunks` 表全量重建，
    解决了"BM25 是内存索引、进程重启就丢"这个问题。
    **如果漏掉重建，服务不报错、不掉线，只是精确关键词查询静默变差** ——
    最危险的一类 bug。所以 `/health` 会把 `bm25_doc_count` 报出来。
    """
```

`avgdl` 与 `df` 出现在公式分母里——它们**是"这个库"的统计量**。
把两个库混在一起算，等于让 A 库的文档长度去惩罚 B 库的文档。
`/health` 上报 `bm25_doc_count` 的意义也在这里：E6.3 的运维接口输出里
`bm25_doc_count=34` 与 `chunk_count=34`、`vector_count=34` 三者一致，
**它就是"重建没漏"的可见证据**（三方一致 34/34/34，见 E5、E6.3）。

### 2.6 关键代码 5：融合——"为什么先归一化"与"RRF vs 加权"

```python
# backend/src/knowflow/retrieval/fusion.py L1-L27（节选）
"""多路召回融合。

**核心问题：两路分数的量纲完全不同，不能直接相加。**

- 向量分数是 cosine 相似度，范围 [0, 1]，分布集中在 0.4~0.9；
- BM25 分数无上界，取决于 IDF 与文档长度，实测可能 0.5 也可能是 37。

直接 `0.6*vector + 0.4*bm25` 的结果是 BM25 完全主导（数值大 10 倍以上），
表现为"关键词搜出来的东西永远排第一，向量检索形同虚设"。

两种主流解法，本项目都实现，**默认 RRF**：
...
**方案 B：RRF（Reciprocal Rank Fusion）**
    `score = Σ 1/(k + rank_i)`，只用排名不用分数。
    优点：**对分数尺度漂移免疫**——换 embedding 模型、改 BM25 参数都不需要重新调参；
    天然抑制单路离群值。k=60 是原论文推荐值（作用是把前几名的差距拉平一些）。
    缺点：丢弃了"分数差距"信息（第 1 名和第 2 名相差 0.5 还是 0.001，RRF 不看）。
"""
```

两种实现都在（**能讲清取舍本身就是考点**）：

```python
# backend/src/knowflow/retrieval/fusion.py L76-L87
def rrf_fuse(rankings: Sequence[Sequence[str]], *, k: int = DEFAULT_RRF_K) -> dict[str, float]:
    """方案 B：RRF。每个 ranking 是按相关性降序排列的 id 列表。

    `1/(k + rank)`，rank 从 **1** 开始（不是 0）。
    从 0 开始会让第 1 名的权重从 1/61 变成 1/60，虽然差别很小，
    但复现论文/他人结果时会发现对不上，属于低级但很烦的错误。
    """
    fused: dict[str, float] = {}
    for ranking in rankings:
        for rank, key in enumerate(ranking, start=1):
            fused[key] = fused.get(key, 0.0) + 1.0 / (k + rank)
    return fused
```

min-max 归一化的**边界处理**是个真实坑：

```python
# backend/src/knowflow/retrieval/fusion.py L44-L51
    if not scores:
        return {}
    values = list(scores.values())
    low, high = min(values), max(values)
    span = high - low
    if span <= 1e-12:
        return {key: 1.0 for key in scores}
    return {key: (value - low) / span for key, value in scores.items()}
```

**所有分数相同时返回 `1.0` 而不是 `0.0`**：`0.0` 会让下游阈值判定认为
"全都不相关"；而"大家一样好"显然不等于"大家一样差"。
同理，只有一个样本时也返回 `1.0`。

RRF 输出的分数**没有物理含义**（只是 `Σ 1/(k+rank)`），
所以引擎里融合之后**必须**再归一化一次，才能跟阈值比、才能在 UI 上显示：

```python
# backend/src/knowflow/retrieval/engine.py L361-L364
normalized = minmax_normalize(fused)
for candidate in candidates:
    candidate.fused_score = round(fused.get(candidate.vector_id, 0.0), 8)
    candidate.score = round(normalized.get(candidate.vector_id, 0.0), 6)
```

`fused_score` 与 `score` 分开存是刻意的：调试时要能回答"这条为什么排第 3"，
而重排（§2.10）还要拿 `fused_score` 当"稳定器"。

**RRF 的取舍要诚实讲**：E7.5 的消融实验里 RRF 在本项目这个小语料上
**略逊于纯向量**（`0.849 vs 0.860`，**不显著**，`p = 0.820`）。
原因写在 E7.5 里：语料只有 34 个切片时 BGE-M3 的稠密向量本身就足够强，
而 BM25 贡献的候选会把部分正确的向量命中挤下去。
但 `hybrid` 比 `vector` 慢不了多少（56ms vs 58ms，因为 BM25 只花 5ms），
**鲁棒性更好**——这就是选 RRF 做默认值的理由：
**在没人持续调参的系统里，鲁棒性比理论最优更重要。**

### 2.7 关键代码 6：autocut——"结果里只有前几条是相关的"

```python
# backend/src/knowflow/retrieval/autocut.py L40-L78（节选）
def autocut(
    candidates: list[Candidate],
    *,
    ratio: float,
    min_keep: int = 1,
    max_keep: int | None = None,
) -> list[Candidate]:
    """保留分数不低于 `top_score * ratio` 的前缀。

    参数语义：
      ratio    0.35 表示"分数掉到第 1 名的 35% 以下就不要了"
      min_keep 至少保留几条（**不能返回空**：如果只因为相对分低就全丢，
               本来能答的问题会变成拒答，这是更严重的错误）

```

**`min_keep` 为什么不能为 0**（本会话实跑，`ratio=1.5` 时第 1 名自己就低于阈值）：

```
ratio=1.5 min_keep=0 -> [] (空！)
ratio=1.5 min_keep=1 -> ['1:0']
```

空列表的后果是**连锁的**：闸门 `evaluate_gate([])` 返回
`reason=no_candidates`，`generate` 节点拿不到上下文，直接走"短路拒答"。
**检索到了东西却答"没找到"，比答错更难向用户解释**——所以 `min_keep` 默认是 1。

引擎里 `max_keep` 传的是 `fetch_k` 而不是 `top_k`（这一行有注释）：


### 2.8 关键代码 7：闸门为什么是 `OR` 而不是 `AND`

```python
# backend/src/knowflow/retrieval/autocut.py L1-L22（节选）
"""分数断崖截断（autocut）与相关性闸门（gate）。

**两个不同的东西，容易混为一谈：**
...
**2. gate —— "这一批结果全都不相关"**
    双阈值：`向量相似度 ≥ 阈值` **或** `查询词覆盖率 ≥ 阈值`。
    两条都不满足 → **不调大模型**，直接拒答。
    为什么用"或"而不是"与"：两条信号覆盖不同的失败模式 ——
    向量强在语义改写（"房费"↔"住宿标准"），覆盖率强在专有名词
    （"PAYLOAD_TOO_LARGE"）。用"与"会把两种正确情况都误杀。
```

判定函数（`best_vector_score` 只看**有向量分**的候选，这一条容易被忽略）：

虽然 `max` 的结果不变，但一旦写反成 `min` 或平均，就会把
"关键词精确命中但向量没召回"的情况**误杀**——而那恰恰是 BM25 存在的理由。

**两种通过的场景都在 E 里有真实记录**：

**一路失效时另一路兜底**。

⚠ **阈值必须标定，不能拍脑袋**。E7 的原始数据说明原因：
正样本相似度均值 **0.6755**、负样本均值 **0.5704**——**余弦相似度没有"绝对零度"**，

### 2.10 关键代码 9：重排的两条实现与"失败必须降级"

```python

"""重排（rerank）。

**为什么要重排**：召回阶段的目标是"别漏"（高召回），所以会放宽到 `fetch_k=20` 条；

1. `llm_rerank` —— 让模型逐条打 0-10 分。判据最强，但要花一次模型调用（约 0.5~2 秒）。
2. `heuristic_rerank` —— 用「查询词覆盖率 + 小节/文件名命中 + 向量分」加权。

"""
```

启发式的三个权重（每个都有理由，源码里写清了）：

**这里有一个"降级路径自己坏了"的真实踩坑**（值得单独讲）：

```python
    项目里有两套并存的异常类（历史原因）：
    - `core.exceptions.EmbeddingError` / `VectorStoreError`（`KnowFlowError` 子类，有 `.message`）；
```

## 4. 常见错误

| 错误信息 | 原因 | 解决 |
| --- | --- | --- |
| 中文关键词一个字都搜不到 | 用 `split()` 分词，中文没空格 → 整句 1 个 token | 用 `retrieval.text.tokenize_zh`（1-gram + 2-gram） |
| 越常见的关键词越查不到 | IDF 没 `+1`，`df > N/2` 时变负 → 高频词倒扣分 | IDF 用 `ln(1 + (N-df+0.5)/(df+0.5))`（Lucene 形式） |
| 关键词结果永远排第一，向量形同虚设 | 两路分数直接加权，BM25 数值大一个量级 | 先各自归一化（或直接用 RRF），再融合 |
| RRF 结果与他人复现对不上 | `rank` 从 0 开始算 | `enumerate(ranking, start=1)` |
| 归一化后全是 0，全被判为不相关 | 所有分数相同时 min-max 返回 0.0 | 返回全 `1.0`（"大家一样好"≠"大家一样差"） |
| 本来能答的问题变成拒答 | autocut 的 `min_keep=0` 把候选砍空，闸门 `no_candidates` | `min_keep=1`（至少留一条） |
| 两种正确的召回都被误杀 | 闸门写成 `AND` | 用 `OR`：向量强语义改写，覆盖率强专有名词 |
| `!!!` 被判为"完全命中查询" | 覆盖率在"文本切不出词元"时返回 1.0（修过的 bug） | 两个边界都返回 `0.0`，并写测试钉住 |
| 重启后精确关键词查询静默变差，不报错 | BM25 是内存索引，忘了从 `chunks` 表重建 | 启动时重建 + `/health` 上报 `bm25_doc_count` |
| 检索明显降级了但没人知道 | 降级只写 warning，没进 `debug.vector_error` | 把原因写进 `RetrievalDebug.vector_error` 并落 trace |
| 自写的 Embedder 抛异常后直接 502（没降级） | 抛的是裸 `RuntimeError`，不在降级捕获的类型里 | 抛 `embeddings.base.EmbeddingError`（或 core 的那套） |
| 引用点开是 404 | 孤儿向量（向量库有、MySQL 没有）没丢 | `_enrich()` 里查不到就 `dropped_orphans += 1` 丢弃 |
| `Expected where to have exactly one operator` | `where` 每层只能有一个条件（Chroma 硬性限制） | 写成 `{"$and": [{"a": 1}, {"b": 2}]}`（阶段 4 的 `validate_where` 会拦住） |
| 按 `doc_id` 过滤一条都查不到（不报错） | 传了字符串 `"3"`，Chroma 比较是**强类型**的 | metadata 强制 `int`（`sanitize_metadata`） |
| `page_no` 取回来是 `KeyError` | Chroma **静默丢弃** `None` 值的 metadata 键 | 下游统一写 `metadata.get("page_no")` |
| 第一次写向量时静默下载 79MB ONNX | 没传 `embedding_function=None` | 显式传 `None`（阶段 4 的坑，本阶段会在检索时复现） |
| 改了 `hnsw:space` 已存在的集合不生效 | 该参数只在**创建**集合时生效 | drop 集合重建（本项目按 KB 隔离，天然可重建） |
| 上下文长度在 1k~9k 之间抖动 | 按条数裁上下文，而父块长度差 9 倍 | `trim_to_budget` 按**字符**裁，装不下整条跳过 |
| `bm25_doc_count` 与 `chunk_count` 不一致 | 重建漏了某些 KB，或删文档时没清 BM25 | `remove_document` 按 `doc_id` 清；启动重建覆盖所有 KB |
