# 阶段 10：可观测与评测

> **本阶段目标**：让系统能回答三个问题——「这次请求为什么慢」「这个功能一天花多少钱」
> 「我改的那个参数到底让效果变好了还是变差了」。
> **预计耗时**：120 分钟
> **前置阶段**：阶段 9
> **本阶段产出**：`observability/`（4 个文件）+ `evaluation/`（5 个文件）+ 4 个 obs 端点
> + `/health` 的如实上报

## 0. 为什么先做这一步

因为**前 9 个阶段做出来的东西，只有在这一步之后才能被"证明"**。

到阶段 9 为止，你能说"系统能跑"；但下面这三句话一句都答不上来：

| 问题 | 没有这一层时的回答 | 有了这一层之后的回答 |
| --- | --- | --- |
| 这次请求为什么慢了 800ms？ | "可能是检索吧……" | `retrieve` span 641ms，其中 `embed_query` 180ms、向量库 60ms、重排 160ms |
| 这个功能一天多少钱？ | "应该不贵" | `requests=4 tokens={'prompt':11920,'completion':2121,'total':14041} cost_usd=0.002264 cost_cny=0.0163` |
| 我把 top_k 从 5 改成 10 有用吗？ | "感觉好像好一点" | `recall@5 0.721 → 0.849，Δ=+0.128，95% CI [+0.035,+0.244]，p=0.010` |

第三行是这一阶段最值钱的产出。它有一个**前提**：指标口径必须定死
（同一批用例、同一套公式），否则比大小没有意义。所以本阶段的顺序是：

```
span 埋点（为什么慢）  →  成本归因（多少钱）  →  评测指标（好不好）  →  显著性（是不是噪声）
   observability/                                  evaluation/
```

阶段 11 会在此基础上做阈值标定与消融——**那一篇的所有结论，都建立在本篇定义的指标口径上**。

## 1. 要解决的问题

| 现象 | 真实原因 |
| --- | --- |
| 日志里只有"请求耗时 812ms"，不知道慢在哪 | 没有分阶段 span；且埋点靠手写 `time.perf_counter()` 污染业务代码 |
| 前端画瀑布图时区错乱、跨机器时间对不齐 | span 存了绝对时间戳而不是**相对偏移** |
| 一次问答的上下文 20KB 全量进了 JSON 列，几万次请求后表被撑爆 | payload 没截断 |
| 序列化一个 `Session` 对象时触发了一串懒加载 SQL | `json.dumps(default=str)` 会试着序列化 ORM 对象 |
| 服务记日志时又抛了一个异常，原始错误被覆盖 | 异常路径上的日志本身没被保护 |
| 接口一切正常，但 `/obs` 里一条 trace 都没有 | `persist` 只 `flush`，**没人 commit** |
| 流式问答的瀑布图出现"重影"（同一步骤两条） | 第二次 persist 直接 append span，没先删 |
| 埋点失败把一次成功的问答变成了 500 | 可观测没有遵守"旁路不许影响主流程" |
| 成本数字对不上账（差几厘） | 用 `float` 算钱，二进制浮点误差累加 |
| 所有模型都按兜底价算钱，数字看着有其实全错 | 价格表用**精确匹配**，而供应商会在模型名后挂版本号 |
| `recall@k` 虚高到 1.0，但人工看明明没捞到 | 检索结果里有重复 chunk，没去重 |
| 无标准答案的用例被当成满分，指标整体偏乐观 | `relevant` 为空时返回了 1.0 |
| `/obs/stats` 返回的字段和前端写死的形状不一样，图表全空白 | 服务层形状（`latency_ms` / `series` / `by_mode` 字典）与契约模型不同 |
| `hybrid` 与 `bm25` 指标**一模一样** | 向量那一路根本没参与（阶段 11 的 E7.6） |

倒数第一条是"面板全空但接口 200"的典型：**接口能跑，数据形状不对**。

### 2.2 关键代码 1：零侵入埋点

"零侵入"不是形容词，它有具体的实现手段：

```python
# backend/src/knowflow/observability/tracing.py L14-L30（模块 docstring，节选）
**关键设计取舍**：

1. **零侵入靠 `ContextVar`，不靠"传参"**。把 recorder 一路当参数传下去会污染
   所有函数签名（尤其是 LangGraph 的节点签名是固定的）。`ContextVar` 在
   `asyncio` 任务里自动隔离，同时 `threading.Lock` 保证多线程写 span 不丢数据
   （LangGraph 的节点可能跑在线程池里，contextvar 会随 `run_in_threadpool` 复制，
   但 `list.append` 与计数器仍必须加锁）。
2. **埋点绝不能影响主流程**。序列化失败、日志失败、落库失败——三类失败全部
   吞掉只记日志。理由：可观测是"旁路"，为了记录而让用户请求 500 是本末倒置。
   唯一的例外是**业务异常必须原样抛出**（`span()` 里 `raise` 而不是吞掉）。
3. **`start_offset_ms` 存相对偏移而不是绝对时间戳**：前端画瀑布图只需要
   「起点偏移 + 时长」，不用处理时区、时钟漂移与多机时间不同步，
   存储也从 datetime 降成 int。
4. **payload 用"白名单 + 截断"而不是 `json.dumps(default=str)`**：
   `json.dumps` 遇到 `Session` 会试着序列化整个 ORM 对象（连带 lazy 关系），
   既慢又可能触发额外 SQL；白名单直接把它标成 `_unserializable`。
```

> ⚠ **注意上面第 1 条与阶段 9 的 E6.5 是同一个技术点的一体两面**：
> `ContextVar` 适合"一路传下去"的同步调用链（图节点），
> 但**不适合被 Starlette 分次跨线程驱动的同步生成器**。
> 所以本项目在服务层改用 `RecorderBox` 显式传递，而在图节点内部仍保留 contextvar
> ——两者的失败模式不同，处理方式也必须不同。

`@traced` 装饰器在**没有 recorder 时直接执行、零序列化开销**：

```python
# backend/src/knowflow/observability/tracing.py L450-L467（decorator，节选）
    def decorator(func: F) -> F:
        @functools.wraps(func)
        def wrapper(*args: Any, **kwargs: Any) -> Any:
            rec = current_recorder.get()
            if rec is None:
                # 无 recorder：只多一次 contextvar 读（纳秒级），不做任何序列化
                return func(*args, **kwargs)

            payload: Any = None
            if capture:
                payload = {"args": _dump(args), "kwargs": _dump(kwargs)}
            with rec.span(name, span_type=span_type, input=payload) as span_ctx:
                result = func(*args, **kwargs)
                if capture:
                    span_ctx.set_output(result)
                return result

        return cast(F, wrapper)  # cast：wrapper 通过 wraps 保住了签名，mypy 看不出来
```

三个细节值得抄下来：

1. **`functools.wraps` 不能省**："否则 FastAPI 的依赖注入与 LangGraph 的节点
   introspection 会认不出被装饰的函数"；
2. **`current_recorder` 的 `default=None`**："脚本/单元测试里直接用被装饰的函数
   **也不会报错**，只是'没有记录'而已。这个默认值是'埋点可缺席'这条设计能成立的前提"；
3. **`capture=True` 会过滤 `self` / `cls`**："把 service 对象整个序列化会连带它的
   `Session`、配置甚至 API Key 字段，这是**信息泄露**风险"。

### 2.3 关键代码 2：为什么 span 存"相对偏移"而不是时间戳

```python
# backend/src/knowflow/observability/tracing.py L84-L101
@dataclass
class SpanRecord:
    """一个 span 的"可落库形态"。

    刻意**不是** ORM 对象：`TraceRecorder` 可能在没有数据库会话的地方使用
    （脚本、单元测试、离线评测），不应该强迫调用方准备 Session。
    `seq` 单调递增，是前端瀑布图的稳定排序键（同毫秒的 span 不会乱序）。
    """

    name: str
    span_type: str
    start_offset_ms: int
    duration_ms: int
    status: str = STATUS_OK
    input_json: Any | None = None
    output_json: Any | None = None
    error: str | None = None
    seq: int = 0
```

**"相对偏移"这个决定一次性解决了四个问题**：

| 用绝对时间戳 | 用 `start_offset_ms` |
| --- | --- |
| 前端要处理时区（服务器 UTC、浏览器本地） | 不需要，纯数字 |
| 多机部署时机器之间时钟可能差几百毫秒，瀑布图会错位 | 不需要，同一次请求的偏移都来自同一个 `time.monotonic()` |
| 存储是 `DATETIME(6)`（8 字节 + 解析成本） | `int`（毫秒） |
| 同毫秒的 span 排序不稳定 | 有 `seq` 单调递增，排序稳定 |

起点用的是 **`time.monotonic()` 而不是 `time.time()`**：

```python
# backend/src/knowflow/observability/tracing.py L223-L238（节选）
    def start(self) -> None:
        """记 t0。**幂等**：重复调用不重置起点（否则并发分支的偏移会全部错位）。"""
        with self._lock:
            if self._start is None:
                self._start = time.monotonic()

    def elapsed_ms(self) -> int:
        """从 `start()` 到现在的毫秒数；未 start 过则返回 0。"""
        ...
    def _offset_now(self, start: float) -> int:
        return max(round((time.monotonic() - start) * 1000), 0)
```

**`monotonic()` 不受系统时钟调整影响**（NTP 校准、夏令时、人工改时间）。
如果用 `time.time()`，一次 NTP 回拨就会让 `duration_ms` 变成负数——
而负数耗时会静默毁掉百分位统计（`p95` 直接变小）。所以这里还有个 `max(..., 0)` 兜底。

契约侧也把这件事写进了字段说明：

```python
# backend/src/knowflow/schemas/observability.py L168-L173
class TraceSpanOut(BaseModel):
    """trace 内部的一个步骤（契约 5.9 的瀑布图数据）。

    `start_offset_ms` 是**相对 trace 起点**的偏移，不是绝对时间戳：
    前端画瀑布图只需要「偏移 + 时长」两个数字就能定位所有方块，
    不用处理时区与时钟漂移。
    """
```

### 2.4 关键代码 3：payload 的"白名单 + 截断"

```python
# backend/src/knowflow/observability/tracing.py L107-L129（_jsonable，节选）
def _jsonable(value: Any, *, _depth: int = 0) -> Any:
    """把任意对象转成"能进 JSON 列"的结构；不认识的对象降级成类型名描述。

    **绝不抛异常**是这个函数的契约：它跑在埋点路径上，抛一次就等于让业务请求失败。
    """
    if value is None or isinstance(value, (bool, int, float, str)):
        if isinstance(value, str) and len(value) > _PRE_TRUNCATE_CHARS:
            return value[:_PRE_TRUNCATE_CHARS] + f"…(+{len(value) - _PRE_TRUNCATE_CHARS}字)"
        return value
    if isinstance(value, dict):
        if _depth >= _MAX_DEPTH:
            return {"_depth_limit": True}
        ...
    # 到这里就是"不认识的对象"：Session / VectorStore / 自定义 dataclass 等。
    # 只记类型名，不记 repr()：repr 会把 ORM 对象的字段（可能含正文、路径）带进 trace。
    return {"_unserializable": f"{type(value).__module__}.{type(value).__name__}"}
```

**"只记类型名、不记 `repr()`"** 是一个安全决定，不是省事：
ORM 对象的 `repr()` 会把字段值（正文、文件路径、用户名）一起带进 trace 表，
而 trace 表是**排障用的、会被很多人看到**的表。

还有一层"提前验证"的设计：

```python
# backend/src/knowflow/observability/tracing.py L132-L146
def _dump(payload: Any) -> Any:
    """`_jsonable` + 一次真实 `json.dumps` 试跑。

    为什么要额外 dumps 一遍：SQLAlchemy 的 JSON 列**在 flush 时才序列化**，
    那时才发现不可序列化对象，异常会发生在事务提交阶段（更难定位，
    而且会连带把同事务的业务写入一起回滚）。提前在这里验证，失败就降级。
    """
    if payload is None:
        return None
    try:
        safe = _jsonable(payload)
        json.dumps(safe, ensure_ascii=False, default=str)
    except Exception:  # noqa: BLE001 - 埋点不能影响主流程
        return {"_unserializable": f"{type(payload).__module__}.{type(payload).__name__}"}
    return safe
```

**"在埋点这一层试跑一次 `json.dumps`"** 的价值：
把"不可序列化"这个错误从**事务提交阶段**提前到**埋点阶段**。
前者会连带回滚同事务的业务写入（灾难），后者只是一条埋点丢了（无所谓）。

落库前还有第二道截断（`truncate_payload`，在 `db/models/observability.py`）：

```python
# backend/src/knowflow/observability/tracing.py L596-L599
                    # ★ 必须过 truncate_payload：span 是排障用的，不是存全文的。
                    # 一次问答的上下文可能 20KB，几万次请求后 JSON 列会把表撑爆。

                    output_json=truncate_payload(record.output_json),
```

**两道截断不是重复**：第一道在埋点阶段（防止把 2MB 文本带进内存与日志），
第二道在落库前（保证进 JSON 列的体积有上限）。中间还隔着一次 `summary()` 计算。

### 2.5 关键代码 4：`span()` 记录异常，但**不吞**异常

```python
# backend/src/knowflow/observability/tracing.py L187-L202
    def __enter__(self) -> Self:
        return self

    def __exit__(
        self,
        exc_type: type[BaseException] | None,
        exc: BaseException | None,
        tb: TracebackType | None,
    ) -> Literal[False]:
        # 返回 False = **不吞异常**。这是硬规则：埋点只观察，不改变控制流。
        # 返回 True 会把"检索失败"记成成功，用户拿到空答案却看不到错误。
        # 返回类型写 `Literal[False]`（而不是 `bool`）：mypy strict 会把 `bool`
        # 当成"可能返回 True"，从而认为这个上下文管理器可能吞掉异常，直接报错。
        _ = (exc_type, tb)
        self._recorder.finish(self, exc)
        return False
```

**最后那三行注释是本篇最值得学的一处类型技巧**：
`__exit__` 的返回类型在类型论上是"可能吞异常"与"不吞异常"的区分依据。
写 `-> bool` 会让 mypy strict 认为这里**可能**吞掉异常，
于是所有 `with rec.span(...)` 里抛出的异常在静态检查下都变成"被处理了"——
那会让真正的 bug 藏起来。写 `Literal[False]` 才是准确的类型。

`span()` 上下文管理器把"计时 + 记异常"收在一处：

```python
# backend/src/knowflow/observability/tracing.py L284-L314（节选）
    @contextmanager
    def span(self, name, *, span_type=SPAN_NODE, input=None, output=None) -> Iterator[SpanContext]:
        """计时上下文管理器；**异常记录后照原样抛出**。"""
        ...
        try:
            yield ctx
        except BaseException as exc:  # 记录后必须原样抛出（BaseException：Ctrl-C 也要留痕）
            self.finish(ctx, exc)
            raise
        else:
            self.finish(ctx, None)
```

**捕获 `BaseException` 而不是 `Exception`** 的理由写在注释里：`Ctrl-C`（`KeyboardInterrupt`）
也要在 trace 里留痕——一个跑到一半被人为中断的请求，其 span 树比"什么都没有"有用得多。

### 2.6 关键代码 5：`persist` 只 `flush`，`commit` 在唯一出口

这是本阶段**最容易出错**的一处。先看 `persist` 的收尾：

```python
# backend/src/knowflow/observability/tracing.py L509-L540（persist，节选）
    """把 recorder 的 span 落到 `trace_spans`，并 upsert 一条 `traces` 行。

    返回 `trace_id`；**失败时同样返回 trace_id，但不抛异常**。

    ★ **硬规则**：可观测失败绝不能影响业务。这里任何异常（表不存在、
    连接断开、字段超长）都只记 error 日志 + rollback，让调用方的请求继续走完。

    为什么 upsert 而不是 insert：流式场景会"边跑边落"，同一次请求可能被
    persist 两次（首帧落一次、结束时补全一次）。按 `trace_id` 查到就更新，
    保证始终只有一行 trace。

    为什么 `trace_spans` 要"先删后插"：同理，第二次 persist 若直接 append
    会让 span 翻倍，瀑布图出现"重影"——而且**不会报错**，只是图看起来怪。
    删的时候用 Core `delete()` + `flush()`：显式让 DELETE 先落到连接上，
    避免 unit of work 把 INSERT 排在 DELETE 前面（MySQL 上没有唯一约束兜底，
    顺序错了就是静默重复）。
    """
```

注意这段 docstring 里**没有一句提到 `commit()`**——因为 `persist` 刻意不 commit：

```
        # 覆盖式写入 span：见 docstring（避免重复 persist 造成重影）
        session.execute(delete(TraceSpan).where(TraceSpan.trace_id == trace_id))
        session.flush()
        ...
        session.flush()
    except Exception as exc:  # noqa: BLE001 - ★硬规则：可观测失败不能让业务请求失败
        _safe_log_error("observability.persist.failed", trace_id, exc)
        _safe_rollback(session)
    return trace_id
```

`commit` 被放在**唯一出口** `obs_bridge.safe_persist` 里：

```python
# backend/src/knowflow/services/obs_bridge.py L108-L134（节选）
    """落库 trace。**任何异常都吞掉**：可观测失败不该让一次成功的问答变成 500。

    **这里负责 commit**（真实实现的 `persist` 只 flush，事务边界交给调用方）。
    为什么把 commit 放在这一层而不是每个调用点：调用点有 4 处（非流式成功/失败、
    流式成功/落库失败），任何一处忘了 commit 都会变成
    "接口一切正常、但 /obs 里一条 trace 都没有" —— 一个静默丢失埋点的 bug。
    放在唯一的出口上，这类错误在结构上就不可能发生。
    """
    if recorder is None or not OBSERVABILITY_AVAILABLE:
        return None
    try:
        trace_id = persist(recorder, session, ...)
        session.commit()
        return trace_id
    except Exception as exc:  # noqa: BLE001
        logger.warning("observability.persist_failed", error=f"{type(exc).__name__}: {exc}"[:200])
        try:
            session.rollback()
        except Exception:  # noqa: BLE001
            pass
        return None
```

**`flush` vs `commit` 的语义差别，正是这个 bug 的根源**：

| | `flush()` | `commit()` |
| --- | --- | --- |

### 2.7 关键代码 6：成本归因——为什么必须用 `Decimal`

```python
# backend/src/knowflow/observability/pricing.py L10-L21（模块 docstring，节选）
**关键设计取舍**：

1. **必须用 `Decimal`，且只能用 `Decimal(str(x))` 构造**。`Decimal(0.00014)` 会把
   二进制浮点误差原样带进来（``Decimal(0.00014) == Decimal('0.0001400000000000000106581...')``），
   再乘几百万 token 就是肉眼可见的偏差。配置项是 `float`（pydantic 侧），
   所以这里是**唯一**允许"转一手字符串"的地方。
2. **价格表按模型名前缀匹配**，不做精确匹配：供应商会在模型名后面挂版本号
   （``deepseek-chat-2026xx``、``gpt-4o-2024-11-20``），精确匹配会全部落到兜底价，
   而"所有模型都按兜底价算"是一种**静默错误**——数字看着有，其实全错。
3. **价格表只是量级估算**：真实账单还有缓存命中价、阶梯价、批处理折扣。
   这里的目标是"能回答这个功能一天花多少钱"，不是财务对账。
```

`float` 的误差到底有多大？看一眼就明白了：

```powershell

.\.venv\Scripts\python.exe -c "from decimal import Decimal; print(Decimal(0.00014)); print(Decimal(str(0.00014)))"
```


**第一行那个尾巴就是 float 的二进制表示**。单次误差可以忽略，
但 `metrics` 会把几万次请求的 `cost_usd` 加起来——误差是**累加**的，
而且会在"对账"这种场景下暴露成"差了几分钱"。

实现上的三个细节：

```python
# backend/src/knowflow/observability/pricing.py L82-L104（_dec / resolve_price，节选）
def _dec(value: str | float | Decimal) -> Decimal:
    """统一把外部数值转成 `Decimal`。

    `float` 走 `str()` 中转是**刻意**的：`Decimal(0.00014)` 会把浮点误差冻进 Decimal，
    而 `Decimal(str(0.00014))` 得到干净的 `Decimal('0.00014')`。
    """
    if isinstance(value, Decimal):
        return value
    return Decimal(str(value))


def resolve_price(model: str, settings: Settings) -> Price:
    """按模型名前缀查价，未命中则回落到配置里的默认单价。

    为什么用"前缀"而不是"相等"：见模块 docstring 第 2 条。
    """
    name = (model or "").strip().lower()
    if name:
        for prefix, prompt, completion in _PRICE_TABLE:
            if name.startswith(prefix):
                return Price(prompt_per_1k=Decimal(prompt), completion_per_1k=Decimal(completion))
```

价格表本身有一条**顺序依赖**，注释里专门提醒了：

```python

#: 因为匹配是"第一个命中的前缀"。
_PRICE_TABLE: Final[tuple[tuple[str, str, str], ...]] = (
    # (模型名前缀, prompt 每 1K 美元, completion 每 1K 美元)
    ("deepseek-reasoner", "0.00055", "0.00219"),  # R1 类推理模型，输出贵 4 倍
    ("deepseek-chat", "0.00014", "0.00028"),  # V3 类，与项目默认配置一致
```

最后是估算函数，它有两个"防呆"：

```python

    负数 token 按 0 处理：上游偶发会返回 ``-1`` 表示"未知"，

    `ROUND_HALF_UP` 而不是默认的 `ROUND_HALF_EVEN`：财务口径四舍五入更符合直觉，
    也避免"0.0000005 舍成 0"时对不上账。
```

- **`max(..., 0)`**：上游返回 `-1`（表示未知）时，如果直接参与运算，

- **`ROUND_HALF_UP`**：默认的 `ROUND_HALF_EVEN`（银行家舍入）在

- **量化位数 `COST_QUANT = Decimal("0.000001")` 与 `messages.cost_usd DECIMAL(12,6)` 一致**：
  "不一致的话，写库时会被数据库四舍五入，而日志里还是全精度，对账时对不上"。

### 2.10 关键代码 9：检索指标的定义与边界

```python
# backend/src/knowflow/evaluation/metrics.py L9-L18（模块 docstring，节选）
**关键设计取舍**：

1. **纯函数、零依赖、无 IO**：指标算错是最隐蔽的 bug（图形看起来对，结论全反），
   所以这里不碰数据库、不碰模型，输入输出都是普通 list/float，能用手算值逐条对照。
2. **所有函数先去重再算**（`_dedup`）：检索层返回重复 chunk 时（多路召回合流很容易
   出现），不去重会让 `recall@k` 虚高、"命中数"超过真实命中数。这是**指标虚高**
   最容易被忽略的一处。
3. **无标准答案的用例约定为 0 分**（`relevant` 为空 -> `0.0`，而不是 `1.0` 或抛异常）：
   评测集里允许出现"这条题本来就没有必中片段"的用例，约定 0 分能让它**拉低**
   平均分、逼标注者补全，而不是被静默当成满分（那会让指标系统性偏乐观）。
```

三个指标各自的"边界行为"都写在 docstring 里，而且都被断言覆盖：

```python
# backend/src/knowflow/evaluation/metrics.py L106-L123（recall_at_k，节选）
    """Recall@k = |top-k 命中| / |relevant|。

    边界行为（评测点）：

    - `k <= 0` -> `0.0`（截断到空集合，没检索就没有召回）；
    - `relevant` 为空 -> `0.0`（**刻意不是 1.0**：无标准答案的用例约定 0 分，
      见模块 docstring 第 3 条）；
    - 检索结果少于 k 条：不补空、不惩罚，直接按实际条数算（真实系统就是这样）；
    - 重复检索结果先去重，否则同一片段出现两次会让 recall 虚高。
    """
    if k <= 0:
        return 0.0
    relevant = set(_dedup(relevant_ids))
    if not relevant:
        return 0.0
    top_k = set(_dedup(retrieved_ids)[:k])
    return len(top_k & relevant) / len(relevant)
```

| 指标 | 回答什么问题 | 关键边界 |
| --- | --- | --- |
| `recall_at_k` | 该捞的有没有捞全 | `k<=0` → 0；`relevant` 空 → **0（不是 1）**；先 `_dedup` |
| `mrr` | 用户第一眼看到的东西对不对 | 只看**第一条**相关结果；未命中 → 0 |
| `ndcg_at_k` | 排序质量（考虑位置折扣） | `i` 从 **1** 开始；`IDCG==0` → 0 |
| `hit_rate` | 按**用例**平均的命中率 | 空输入 → 0 |
| `citation_precision` | 答案引的 `[1][2]` 是不是真有依据 | 引用为空 → **0**（不引用不能算满分） |
| `keyword_coverage` | 查询词元有多少比例出现在文本里 | 切不出词元 → 0 |

**`recall` 与 `hit_rate` 为什么两个都要报**：

```python
# backend/src/knowflow/evaluation/metrics.py L172-L181（hit_rate，节选）
    """命中率 = 命中用例数 / 总用例数。空输入返回 `0.0`。

    与 Recall 的区别：HitRate 是**按用例**平均（每条题只要有一条相关就算 1），
    Recall 是**按相关片段**平均。评测集里"一题多个必中片段"时两者会明显不同，
    所以两个都报，避免用单一数字掩盖问题。
    """
```

`nDCG` 的计算细节：

```python
# backend/src/knowflow/evaluation/metrics.py L159-L169（ndcg_at_k，节选）
    top_k = _dedup(retrieved_ids)[:k]
    dcg = sum(
        1.0 / math.log2(index + 1)
        for index, doc_id in enumerate(top_k, start=1)
        if doc_id in relevant
    )
    ideal_hits = min(k, len(relevant))
    idcg = sum(1.0 / math.log2(index + 1) for index in range(1, ideal_hits + 1))
    if idcg == 0.0:
        return 0.0
    return dcg / idcg
```

**`enumerate(..., start=1)` 这个 `start=1` 是必须的**：DCG 的第 1 名折扣系数是
`1/log2(2) = 1`（不折扣），如果写成 `start=0` 会得到 `1/log2(1) = 除以 0` → `ZeroDivisionError`
或者得到一个全部为 `inf` 的结果。**边界条件在这种"看起来只是下标"的地方最容易错**。

还有一个**必须知道的跨模块口径差异**（否则标定时会用错阈值）：

```python
# backend/src/knowflow/evaluation/metrics.py L23-L28（节选）
   ⚠ **与线上闸门 `retrieval.text.coverage` 有一处刻意的差异，必须知道**：
   线上切词是 **1-gram + 2-gram 混合 + 停用词过滤**，本模块是**纯 2-gram、不过滤停用词**。
   后果：同一条 query/文本对，本模块算出的覆盖率**数值会比线上闸门低**
   （分母少了那些单字词元），**不能把本函数的输出直接和 `KEYWORD_MIN_COVERAGE=0.25`

   本函数面向的是**评测指标**（同一套口径内部可比、可回归）。
```

**"两个都叫 coverage 的函数，数值不可直接比大小"**——这种坑如果不写下来，
下一个人做阈值标定时一定会踩。这也是阶段 11 的 `calibrate_threshold.py`
**刻意去 import `retrieval.text.coverage`（线上实现）而不是这里的 `keyword_coverage`** 的原因。

### 2.11 关键代码 10：配对 bootstrap——为什么"提升 1.2 个点"不能写进简历

```python
# backend/src/knowflow/evaluation/stats.py L8-L15（模块 docstring，节选）
**为什么要做显著性检验**（这段是回答"你做过什么工程判断"的关键）：
本项目的评测集只有 28 条用例。28 条里 recall@5 从 0.78 "涨"到 0.82，
```

算法只有 20 行，但每一步都有理由：

```python
    size = len(diffs)

    rng = random.Random(seed)
    boot_deltas: list[float] = []
    for _ in range(max(int(n_boot), 0)):
        total = 0.0
        for _ in range(size):
            total += diffs[rng.randrange(size)]
        boot_deltas.append(total / size)
    ...
    # 双侧 p 值：观测 delta 偏正 -> 数落在 0 及以下的（含 0）比例，反之亦然
    if delta >= 0:
        opposite = sum(1 for value in boot_deltas if value <= 0.0)
    else:
        opposite = sum(1 for value in boot_deltas if value >= 0.0)
    p_value = min(max(2.0 * opposite / len(boot_deltas), 0.0), 1.0)
```

四条设计取舍（docstring 里都写了）：

1. **手写实现，不依赖 scipy**：项目没装 scipy，"只用到重采样 + 取分位点两件事，
   几十行就够，引一个 30MB 的科学计算栈不划算"；
2. **`random.Random(seed)` 显式实例化**："全局函数的种子会被同一进程里其它代码影响，
   导致'同样的数据两次跑出不同 CI'，而这种不确定性会让 CI 门槛变成薛定谔的通过"；
3. **`p_value` 必须夹到 `[0,1]`**："比例可能略大于 0.5（分布整体偏向反侧），
   `2 * 0.51 = 1.02` 会输出'p 值大于 1'这种非法数字"；
4. **长度不等直接 `ValueError`**："成对检验的前提是'同一批用例、同一顺序'，
   长度不等说明对比的是两次不同的数据集，结论没有意义"。

```python
# backend/src/knowflow/evaluation/stats.py L143-L148
    if len(a) != len(b):
        raise ValueError(
            f"成对检验要求两次评测的用例数相同（同一批用例、同一顺序），"
            f"实际得到 a={len(a)} 与 b={len(b)}。"
            "长度不等通常意味着对比了两个不同的数据集，这时任何 delta 都没有意义。"
        )
```

**为什么"成对"（paired）而不是两组独立检验**：

```python
# backend/src/knowflow/evaluation/stats.py L25-L27（设计取舍，第 3 条）
3. **成对检验（paired）而不是两组独立检验**：两次评测跑的是**同一批用例**，
   成对差分消掉了"题目难度"这个共同方差，检验功效高得多。
   代价是要求输入等长——不等长直接 `ValueError`，宁可报错也不悄悄对比错数据。
```

用图说明"消掉共同方差"：

```
  独立检验（两组的方差都要算进去）：
      组A: [难0.2, 易0.9, 难0.1, 易0.8]    组B: [难0.3, 易0.95, 难0.2, 易0.85]
      共同方差（题目难度）混在噪声里 → 检验功效低

  配对检验（同一道题做差，难度被消掉）：
      d = [+0.1, +0.05, +0.1, +0.05]      ← 干净得多，n=4 就能看出方向
```

`significant` 的门槛是**硬编码 0.05**，并说明了原因：

```python
# backend/src/knowflow/evaluation/stats.py L137-L138（节选）
    `significant = p_value < 0.05`（本项目约定的门槛，不做可配置——
    门槛可配置时大家总会调到自己满意的那个值，这就是 p-hacking）。
```

**"不做可配置"本身是一个工程决定**：把显著性门槛做成环境变量，
就等于给"调到想要的结论"开了一扇门。**能挡住 p-hacking 的不是自觉，是接口设计**。

### 2.12 关键代码 11：评测的落库与"没算 ≠ 0 分"

评测的产物落在两张表：`eval_runs`（一轮）与 `eval_case_results`（逐条）。
`run_evaluation` 的返回值结构是**固定契约**：

```python
# backend/src/knowflow/evaluation/harness.py L366-L377（run_evaluation docstring，节选）
    返回（**结构固定，调用方依赖它**）::

        {
          "run_id": int,          # eval_runs.id —— 顶层，调用方要回查 eval_case_results
          "dataset_id": int,
          "mode": str,            # 实际执行的模式（agent 会退化成 hybrid_rerank）
          "metrics": {...},       # 字段与 schemas.evaluation.EvalMetrics 对齐
        }

    `metrics` 里除 `case_count` 之外**全部允许 `None`**：`None` 的语义是"没算"
    （判官关闭时 faithfulness / answer_relevance 无从计算），
    给 0 会被读成"算出来是 0 分"——那是完全相反的结论（见 `EvalMetrics` 的说明）。
```

**"没算"与"0 分"必须能区分**——这是指标系统里最容易被忽略的一条：

| 值 | 含义 | 前端应该显示 |
| --- | --- | --- |
| `None` | 本次没启用 LLM 判官，这一项**没测** | "—" / "未测" |
| `0.0` | 测了，结果确实是 0 分 | `0.0` |

E7.5 的输出里就体现了这一点：

```
  闸门阈值 : 向量 0.6 / 覆盖率 0.4      LLM 判官 : False     ← 未配 Key，故不测生成质量
```

**"未配 Key，故不测生成质量"这句话是诚实的一部分**：它明确告诉读者
`faithfulness` / `answer_relevance` 这两列**为什么不存在**，
而不是让大家以为"这两项是 0 分"。

同一段代码里还有阶段 11 会重点讲的"兜底解析活跃 KB"：

```python
# backend/src/knowflow/evaluation/harness.py L433-L453（节选）

```

### 2.13 关键代码 12：`/metrics` 为什么不是 JSON

```python
# backend/src/knowflow/api/routes/ops.py L44-L50
#: Prometheus 文本格式的 Content-Type。`version=0.0.4` 是 exposition format 的版本，
#: 抓取器按它解析；写成普通 `text/plain` 有些抓取器会拒绝。
_PROMETHEUS_MEDIA_TYPE = "text/plain; version=0.0.4; charset=utf-8"

#: `/metrics` 的默认统计窗口。1 小时是折中：够覆盖"最近发生了什么"，
#: 又不会让一次抓取拉太多行（Prometheus 默认 15s 抓一次，每次都很便宜）。
_METRICS_WINDOW_HOURS = 1
```

```python
# backend/src/knowflow/api/routes/ops.py L115-L122
@router.get("/metrics", summary="Prometheus 文本指标")
def metrics(services: Services, settings: SettingsDep) -> Response:
    """窗口内的请求量 / token / 成本 / 延迟分位，Prometheus 文本格式。

    **没有响应模型**（见模块 docstring 第 4 条）。
    """
    stats = collect_stats(services.session, hours=_METRICS_WINDOW_HOURS, settings=settings)
    return Response(content=prometheus_text(stats), media_type=_PROMETHEUS_MEDIA_TYPE)
```

**"加 `response_model` 会让 FastAPI 尝试按 JSON 校验并失败"**——
所以这里显式返回 `Response`。这类"框架默认行为与协议要求冲突"的地方，
必须显式指定而不是"试试看"。

`/metrics` 的时间窗口（1 小时）与 `/obs/stats`（默认 24 小时）**故意不同**：
抓取器每 15 秒来一次，给它 24 小时的数据是浪费；
而面板是人在看，需要更长的窗口。**同一个底层函数，两个不同的调用参数**——
这也是为什么 `collect_stats` 要把 `hours` 做成必传参数（而不是在函数内部读配置）。

## 4. 常见错误

| 错误信息 / 现象 | 原因 | 解决 |
| --- | --- | --- |
| 瀑布图里所有 span 都是同一时刻 / 时区错乱 | span 存了绝对时间戳 | 存 `start_offset_ms`（相对偏移，用 `time.monotonic()`） |
| `duration_ms` 出现负数，百分位统计崩了 | 用了 `time.time()`，被 NTP 回拨 | `time.monotonic()` + `max(..., 0)` 兜底 |
| 一次问答后 `trace_spans` 的 JSON 列撑到几 MB | payload 没截断 | `_jsonable` 预警截断 + `truncate_payload` 落库截断 |
| 埋点序列化时触发一串懒加载 SQL | `json.dumps(default=str)` 试着序列化 ORM 对象 | 白名单：不认识的对象只记 `_unserializable` + **类型名**（不记 `repr()`） |
| trace 里出现了用户正文 / 文件路径 | 记了 `repr(obj)` | 只记类型名；正文类字段显式截断 |
| `TypeError: Object of type X is not JSON serializable`（在**提交阶段**） | 没提前试跑 `json.dumps` | `_dump` 里先试跑一次，失败就降级 |
| 埋点日志自己抛异常，把原始错误盖掉了 | 异常路径上的日志没被保护 | `_safe_log_error`（连日志都不可用时只能静默） |
| 接口全 200 但 `/obs` 一条 trace 都没有 | `persist` 只 `flush`，没人 `commit` | commit 放唯一出口 `obs_bridge.safe_persist` |
| 流式问答的瀑布图出现"重影" | 第二次 persist 直接 append span | 先 `delete(TraceSpan).where(trace_id=...)` + `flush()`，再插 |
| 埋点失败让一次成功的问答变成 500 | 可观测没有"不许影响主流程" | `safe_persist` 吞异常 + rollback；`span()` 只记录不吞业务异常 |
| 成本数字对不上（差几厘） | 用 `float` 算钱 | `Decimal`，且只从 `str` 构造（`Decimal(str(x))`） |
| 所有模型都按兜底价算 | 价格表精确匹配，而模型名带版本号 | 前缀匹配（长前缀写前面） |
| 上游返回 `-1` token，费用被算小了 | 负数 token 直接参与运算 | `max(int(x), 0)` |
| `/obs/stats` 前端图表全空白 | 服务层形状 ≠ 契约模型（`latency_ms` / `series` / `by_mode` 字典） | 路由层 `_to_stats_out` 重塑；**写断言前先读契约模型** |
| 断言 `body["errors"]` 一直失败 | `errors` / `error_rate` **不在** `ObsStatsOut` 里 | 按契约模型写断言（`latency.p50` / `tokens.total`） |
| `recall@k` 算出来大于 1 | 用了 `len(top_k)/len(relevant)` 且没去重 | 用 `len(top_k & relevant)/len(relevant)` + `_dedup` |
| 无标准答案的用例把指标刷高了 | `relevant` 为空返回 1.0 | 返回 **0.0**（约定：没有信号不算通过） |
| `ZeroDivisionError`（在 `nDCG` 里） | `log2(i)` 的 `i` 从 0 开始 | `enumerate(..., start=1)`；`IDCG==0` 提前返回 0 |
| p 值大于 1 | 双侧检验的 `2 * 比例` 没夹取 | `min(max(..., 0.0), 1.0)` |
| 同一批数据两次跑出不同的 CI | 用全局 `random`（种子被别的代码影响） | `random.Random(seed)` 显式实例化 |
| 把 `keyword_coverage`（评测层）的输出直接和 `KEYWORD_MIN_COVERAGE` 比 | 两处切词口径不同（纯 2-gram vs 1-gram+2-gram+停用词） | 标定请用 `retrieval.text.coverage`（线上实现） |
| `faithfulness = 0.0` 被当成"判官测出来是 0 分" | 没区分"没算"与"0 分" | `None` = 没算；前端显示"—" |
| `/metrics` 报 JSON 校验失败 | 给它加了 `response_model` | Prometheus 文本格式不加响应模型 |
