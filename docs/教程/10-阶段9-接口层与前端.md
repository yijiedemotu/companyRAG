# 阶段 9：接口层与前端

> **本阶段目标**：把服务层暴露成 39 个契约稳定的 HTTP 端点，做到「**默认安全**」与「**真流式**」，
> 并配一个能证明「前端调的每个路径后端都有」的联调前保险。
> **预计耗时**：150 分钟
> **前置阶段**：阶段 8
> **本阶段产出**：`api/`（10 个文件）+ `schemas/`（10 个文件）+ `main.py` + `middleware/`
> + Vue 前端（`api/` + `composables/` + `pages/`）

## 0. 为什么先做这一步

因为**只有在业务逻辑已经被验证过之后上 HTTP，报错才指得到根因**。
这句话不是套话，它的具体含义是：

- 如果 `POST /chat` 返回 500，而你在阶段 8 已经用 `smoke_pipeline.py` 证明过
  「同一批输入、直接调 service 全绿」，那么问题**一定**在路由/依赖/序列化这三层里，
  排查范围从"整个项目"缩到"三个文件"；
- 反过来，如果服务层没验证过就上 HTTP，你会在"是检索挂了还是路由挂了"之间来回猜。

这一阶段还要解决三个**只有到了 HTTP 层才会出现**的问题：

1. **契约的形状**。39 个端点的字段、错误信封、SSE 帧格式——前端照着写，
   后端也照着写，**依然可能对不上**（E6.6 就是抓这个的）。
2. **安全属性**。它可以被"断言字段对不对"的功能测试完全绕过（E6.4 的 21 个端点）。
3. **真流式**。一个中间件、一行响应头、一次线程调度，都能让"流式"退化成"一次性返回"（E6.5）。

## 1. 要解决的问题

| 现象 | 真实原因 |
| --- | --- |
| 前端 toast 里永远没有 `request_id`，排障无门 | CORS 没写 `expose_headers`，浏览器不把自定义响应头暴露给 JS |
| `/docs` 上分页参数显示成一个 JSON body 而不是两个输入框 | 写成 `Depends(PageParams)` 而不是 `Annotated[PageParams, Depends()]` |
| 422 返回的是 FastAPI 默认形状，前端要为它再写一套解包 | 没注册 `RequestValidationError` 处理器 |
| 500 里带着文件路径 / SQL 片段 | 兜底处理器把 `str(exc)` 直接回给用户了 |
| `/chat/stream` 看起来不流式，转圈几秒后整段出现 | ① 挂 `BaseHTTPMiddleware`；② 没写 `X-Accel-Buffering: no` |
| 一个流式问答期间整个服务不响应任何请求 | SSE 路由写成了 `async def` 却直接 `for` 同步生成器，**阻塞事件循环** |
| 答案打到一半连接断掉，前端只能等超时 | 生成器里的异常冒泡出去了（响应头已发出，异常处理器救不了） |
| `GET /kbs` 不带 token 返回 200 + 正常数据 | **鉴权漏了**（E6.4：39 个端点里 21 个） |
| 流式接口每次都在最后发一个 `error` 帧 | `ValueError: Token ... was created in a different Context`（E6.5） |
| 前端联调时 404，但双方各自自测都是 200 | 路径参数名不一致：`${id}` vs `{conversation_id}` |
| `GET /conversations/{id}/messages` 返回的 items 是 `{message: "..."}` | `Page["MessageOut"]` 的字符串 ForwardRef 被用了**错的命名空间**解析 |
| 登录页上出现一个 OAuth2 的 form 登录框，和真实登录接口不一样 | 用了 `OAuth2PasswordBearer`（它只适合 form 登录） |

倒数第四条是这个项目里**代价最高**的一个坑：它不会让任何功能测试变红。

业务路由的挂载位置**故意不同**：

### 2.3 关键代码 2：依赖注入只写一种写法

全项目的路由签名里注入分页参数**只有一个正确写法**：

```python
# backend/src/knowflow/api/routes/knowledge_bases.py L43-L46
# **必须写 `Annotated[PageParams, Depends()]`**：写成 `Depends(PageParams)`
# FastAPI 会把 page/size 推导成一个 JSON body 参数（实测确认，见 schemas/common.py）。
# `Depends()` 不带参数才对——它让 FastAPI 去调用 `PageParams.__init__` 并解析其 Query 默认值。
PageDep = Annotated[PageParams, Depends()]
```

而 `PageParams` 自己在 `schemas/common.py` 里也把这件事写了一遍（这样从任何一头看都能查到）：

```python
# backend/src/knowflow/schemas/common.py L75-L101（节选）
class PageParams:
    """分页查询参数（FastAPI 依赖）。

    用类而不是 `BaseModel`：这些值来自 query string，用 `Annotated[PageParams, Depends()]`
    注入后 FastAPI 会在 `/docs` 上渲染出两个真正的查询参数输入框
    （page / size），而不是一个 JSON body——分页参数放 body 里是反直觉的。

    上限 `le=100` 来自契约文档第一节：`size` 默认 20、最大 100。
    没有上限时，前端一句 `size=100000` 就能让 MySQL 全表扫描把库拖死。

    **用法必须写 `Annotated[PageParams, Depends()]`**（`Depends()` 不带参数）：
    ...
    """

    def __init__(
        self,
        page: int = Query(1, ge=1, description="页码，从 1 开始"),
        size: int = Query(20, ge=1, le=100, description="每页条数，默认 20，最大 100"),
    ) -> None:
        ...
```

**"上限 `le=100`"这条约束是可验证的安全属性**，E6.3 第 14 项就是打它：

```
GET /kbs?size=999 -> 422（分页上限生效）
```

其余依赖统一用 `Annotated` 类型别名，路由签名里只写一个名字：

```python
# backend/src/knowflow/api/deps.py L154-L165
# --------------------------------------------------------------------------------------
# 类型别名：路由函数签名里写 `services: Services` 就够了。
# 用 `Annotated[...]` 而不是 `= Depends(...)` 的默认值写法：mypy 能正确推导类型，
# 且 FastAPI 0.142 对两种写法都支持（本项目统一用 Annotated）。
# --------------------------------------------------------------------------------------
ContainerDep = Annotated[Container, Depends(get_container)]
SessionDep = Annotated[Session, Depends(get_session)]
Services = Annotated[RequestServices, Depends(get_services)]
CurrentUser = Annotated[User, Depends(get_current_user)]
AdminUser = Annotated[User, Depends(get_admin_user)]
SettingsDep = Annotated[Settings, Depends(get_settings_dep)]

```

`deps.py` 里还有两条**与事务/生命周期有关**的纪律（阶段 8 讲过一半，这里是另一半）：

```python
# backend/src/knowflow/api/deps.py L80-L86
def get_session(container: ContainerDep) -> Iterator[Session]:
    """请求级 session。**只负责关闭**，不 commit（事务边界在 service 层）。"""
    session = container.session_factory()
    try:
        yield session
    finally:
        session.close()
```

- **`finally` 里必须 `close()`**：漏掉会耗尽连接池，表现是"服务越跑越慢然后全线 500"；
- **不在这里 commit**：一次问答要「写消息 + 写引用 + 写 trace」要么全成要么全败，
  这个边界属于 `ChatService`。

顺带一个真实的选择理由：

```python
# backend/src/knowflow/api/deps.py L98-L110（bearer_token，节选）
def bearer_token(request: Request) -> str:
    """从 `Authorization: Bearer <token>` 里取 token。

    手写解析而不用 `OAuth2PasswordBearer`（见模块 docstring 第 5 条）。
    """
    header = request.headers.get("Authorization") or ""
    parts = header.split(None, 1)
    if len(parts) != 2 or parts[0].lower() != _BEARER_PREFIX:
        raise UnauthorizedError(_UNAUTHORIZED)
```

**不用 `OAuth2PasswordBearer` 的理由**：它会在 `/docs` 上渲染出一个 form 登录框，
而本项目的登录接口是 JSON（`POST /auth/login`）。**文档上的登录方式与真实方式不一致，
比没有文档更糟**。

### 2.4 关键代码 3：统一错误信封 + 四个异常处理器

契约第二节规定：所有非 2xx 都是同一个形状。落点是 `_install_exception_handlers`：

```python
# backend/src/knowflow/main.py L124-L154（节选）
def _install_exception_handlers(app: FastAPI) -> None:
    """注册四个异常处理器（顺序无关，类型匹配由 FastAPI 自己做）。"""

    @app.exception_handler(KnowFlowError)
    async def _knowflow_error(_request: Request, exc: KnowFlowError) -> JSONResponse:
        """业务异常：`code` / `http_status` 都来自异常类，不再做映射。"""
        return JSONResponse(
            status_code=exc.http_status,
            content=exc.to_dict(request_id=_request_id_of(_request)),
        )

    @app.exception_handler(RequestValidationError)
    async def _validation_error(request: Request, exc: RequestValidationError) -> JSONResponse:
        """Pydantic 422 -> 统一信封（契约第二节要求改写成统一形状）。

        `exc.errors()` 里可能带 `ValueError` 对象（自定义校验器抛的），
        直接塞进 JSONResponse 会在序列化时抛 `TypeError`（"Object of type ValueError
        is not JSON serializable"），于是 422 变成 500。
        所以先过一遍 `jsonable_encoder`，再用 `str` 兜底。
        """
        return _envelope(
            code="REQUEST_VALIDATION_ERROR",
            message="请求参数校验失败",
            status_code=422,
            request_id=_request_id_of(request),
            detail=jsonable_encoder(exc.errors(), custom_encoder={Exception: str}),
        )
```

第三个处理器把框架自带的 `HTTPException`（含 FastAPI 的 404/405）也拉进同一个形状，
并用一张状态码→错误码的表，**不认识的码用 `HTTP_<status>` 兜底**：

```python
# backend/src/knowflow/main.py L71-L88
#: Starlette/FastAPI 自带 HTTPException 的状态码 -> 契约错误码（第二节）。
#: 不在表里的状态码用 `HTTP_<status>` 兜底：**稳定且可判断**，
#: 比统一塞一个 `NOT_FOUND` 强（405 被报成 404 会让人以为是路由没注册）。
_STATUS_CODES: dict[int, str] = {
    400: "VALIDATION_ERROR",
    401: "UNAUTHORIZED",
    403: "FORBIDDEN",
    404: "NOT_FOUND",
    405: "METHOD_NOT_ALLOWED",
    409: "CONFLICT",
    413: "FILE_TOO_LARGE",
    415: "UNSUPPORTED_FILE_TYPE",
    422: "REQUEST_VALIDATION_ERROR",
    429: "RATE_LIMITED",
    500: "INTERNAL_ERROR",
    502: "UPSTREAM_ERROR",
    503: "NOT_READY",
}
```

第四个是兜底，**它的价值在于"不回什么"**：

```python
# backend/src/knowflow/main.py L177-L194
    @app.exception_handler(Exception)
    async def _unhandled(request: Request, exc: Exception) -> JSONResponse:
        """兜底：记完整 traceback，响应里只回通用文案（见模块 docstring 第 5 条）。"""
        request_id = _request_id_of(request)
        logger.error(
            "http.unhandled_exception",
            request_id=request_id,
            path=request.url.path,
            method=request.method,
            error=f"{type(exc).__name__}: {exc}"[:500],
            exc_info=True,
        )
        return _envelope(
            code="INTERNAL_ERROR",
            message="服务内部错误，请稍后重试",
            status_code=500,
            request_id=request_id,
        )
```

**把 `str(exc)` 直接回给用户**等于把文件路径、SQL 片段、依赖版本一起送给对方。
所以：**细节进日志（`exc_info=True`），响应里只留 `request_id`**——
用户拿着它来找你，你拿着它去捞日志。

E6.3 验证了三条路径的形状：

```
[2] 鉴权：未带 token
      GET /kbs（无 token）-> 401
      {"error":{"code":"UNAUTHORIZED","message":"缺少或格式错误的 Authorization 头（应为 `Bearer <token>`）",...}}

[5] 422 / [6] 404 都是统一错误信封
```

### 2.5 关键代码 4：SSE 端点——手写帧、三个响应头、同步 `def`

```python
# backend/src/knowflow/api/routes/chat.py L8-L26（模块 docstring，节选）
**关键设计取舍**（这一层是全项目踩坑最密集的地方）：

1. **不用 `sse-starlette` 的 `EventSourceResponse`**：它会额外插入自己的心跳帧与字段，
   而契约 5.6 把帧格式钉死成 `event: <name>\ndata: <json>\n\n`。
   手写产帧只有 3 行代码，换来的是"前端拿到的每一帧都完全可控"。
2. **必须带 `X-Accel-Buffering: no`**：这是给 Nginx 的。不加的话生产环境上
   Nginx 会把整个响应缓冲到结束才吐给浏览器——**流式接口看起来"不流式"了**，
   而本地直连 uvicorn 时完全正常，属于最难复现的那类问题。
   `Cache-Control: no-cache` / `Connection: keep-alive` 同理，缺一个都可能在中间层被改写。
3. **路由函数写同步 `def`**。`ChatService.answer_stream` 是**同步生成器**，
   Starlette 对同步生成器会自动用 `iterate_in_threadpool` 逐帧取；
   写成 `async def` 再直接 `for frame in gen` 会**阻塞事件循环**——
   一个流式问答期间整个服务不响应任何请求。
```

三行产帧的实体：

```python
# backend/src/knowflow/api/routes/chat.py L51-L69
#: SSE 响应头。三个都不能省，原因见模块 docstring 第 2 条。
SSE_HEADERS: dict[str, str] = {
    "Cache-Control": "no-cache",
    "Connection": "keep-alive",
    "X-Accel-Buffering": "no",
}


def encode_frame(payload: dict[str, Any]) -> str:
    """把 `{"event": ..., ...}` 编码成一帧 SSE 文本。

    `data` 用 `ensure_ascii=False`：中文答案如果被转义成 `\\u4e00` 这样的形式，
    帧体积会翻好几倍，抓包排障时也完全没法读。
    Pydantic 对象直接 `model_dump`，避免调用方还要记着"这一帧是 dict 还是模型"。
    """
    frame = dict(payload)
    event = str(frame.pop("event", "message"))
    body = _jsonable(frame)
    return f"event: {event}\ndata: {json.dumps(body, ensure_ascii=False, default=str)}\n\n"
```

**异常必须变成 `error` 帧 + `end` 帧**，这是 SSE 与普通接口最本质的区别：

```python
# backend/src/knowflow/api/routes/chat.py L189-L214（_sse_frames，节选）
    except KnowFlowError as exc:
        if not sent_meta:
            yield encode_frame(_fallback_meta(embedding_mode))
        yield encode_frame(
            {"event": "error", "code": exc.code, "message": exc.message, "request_id": request_id}
        )
    except Exception as exc:  # noqa: BLE001 - SSE 边界：任何异常都必须变成帧
        logger.error("chat.stream_failed", error=f"{type(exc).__name__}: {exc}"[:300], exc_info=True)
        if not sent_meta:
            yield encode_frame(_fallback_meta(embedding_mode))
        yield encode_frame(
            {"event": "error", "code": "INTERNAL_ERROR",
             "message": "服务内部错误，请稍后重试", "request_id": request_id}
        )
    finally:
        # `end` 帧**始终**是最后一帧（无论成功、出错还是客户端断开）。
        # 前端收到它就收尾；没有它前端只能等超时，用户会觉得"卡住了"。
        yield encode_frame({"event": "end"})
```

**为什么异常不能冒泡**：`StreamingResponse` 开始之后响应头**已经发出去了**，
此时再抛异常，`main.py` 的异常处理器**不可能**再改状态码——
客户端只会看到一个断掉的连接（"答案打到一半没了，且没有任何提示"）。
所以 SSE 的异常处理**只能在生成器内部完成**，这也是 `main.py` docstring 第 6 条的内容。

`_fallback_meta` 是给"一帧都没发出去就炸"准备的，它的注释很值得抄：

```python
# backend/src/knowflow/api/routes/chat.py L145-L159
def _fallback_meta(embedding_mode: str) -> dict[str, Any]:
    """兜底 `meta` 帧：只在"一帧都没发出去就抛异常"时使用。

    `conversation_id=0` / `trace_id=""` 是显式的"这一轮没建立起来"，
    比缺字段更安全：前端拿 `undefined` 去建气泡会直接崩在渲染里。
    """
```

**"给一个显式的空值而不是缺字段"**——这是接口设计里很通用的一条：
缺字段会让前端在**渲染阶段**崩，而那是最难和"网络问题"区分开的。

### 2.6 ⭐ 鉴权：默认需要、例外公开

#### 事故经过（E6.4）

最初的做法是「逐个端点在函数签名里声明 `CurrentUser`」，理由是"读起来直观"。
后来写 HTTP 冒烟时发现 `GET /kbs` 不带 token 竟然返回 **200 + 正常业务数据**：


#### 为什么功能测试发现不了

它们的表现是**返回 200 + 正常业务数据**。任何"断言字段对不对"的测试都会通过：

| 测试类型 | 会不会发现 |
| --- | --- |
| 单元测试（直接调 service） | ❌ 完全绕过了路由 |
| pytest 打 HTTP（带 token） | ❌ 带了 token 当然 200 |
| pytest 打 HTTP（**不带** token，只断言字段） | ❌ 仍然 200 且字段全对 |

**这是一整类 bug 的共性**：缺的是一种**否定性断言**（"不该发生的事有没有发生"），

#### 审计脚本自己的两个坑（`scripts/audit_auth.py`）

```python
# backend/scripts/audit_auth.py L8-L19（节选）
**两个实现细节值得记下来**：

1. **必须从 `original_router` 递归**，不能直接遍历 `app.routes`。
   FastAPI 0.142 把 `include_router` 做成了**惰性**的：`app.routes` 里放的是
   `_IncludedRouter` 占位对象（`path` 和 `methods` 都是 None），
   真正的 `APIRoute` 藏在 `original_router.routes` 里，前缀在 `include_context.prefix`。
   第一版脚本直接遍历 `app.routes`，只找到 1 个端点，**差点得出"没有漏洞"的错误结论**。
2. **必须继承路由级依赖**。`include_router(..., dependencies=[Depends(get_current_user)])`
   这种"统一加鉴权"的写法不会出现在单个端点的 `dependant` 里，
   而是挂在 `include_context.dependencies` 上。只查端点自身的依赖会**误报**。
```

对应实现（递归 + 依赖继承）：

```python
# backend/scripts/audit_auth.py L72-L92
def walk_routes(routes: Any, prefix: str = "", inherited: frozenset[str] = frozenset()):
    """递归产出 `(完整路径, methods, 端点自带的依赖名, 继承的依赖名)`。"""
    for route in routes:
        name = type(route).__name__
        if name == "APIRoute":
            yield (
                prefix + route.path,
                sorted(getattr(route, "methods", None) or []),
                _call_names(getattr(route, "dependant", None)),
                inherited,
            )
        elif name == "_IncludedRouter":
            context = getattr(route, "include_context", None)
            sub_prefix = prefix + (getattr(context, "prefix", "") or "")
            sub_inherited = inherited | _deps_from_include_context(context)
            yield from walk_routes(
                route.original_router.routes, sub_prefix, frozenset(sub_inherited)
            )
```

这条经验的通用形态是：**审计工具本身必须先被审计**。
一个"只找到 1 个端点"的脚本，比没有脚本更危险——它给出的是**虚假的安全感**。

### 2.7 ⭐ contextvars 跨线程失效：204 个测试全绿也漏掉的 bug

#### 现象（E6.5）

非流式 `/chat` 完全正常，但 `/chat/stream` **每次**都在最后发一个 `error` 帧，
`done` 帧永远不出现。服务端日志：

```
[error] chat.stream_failed
error="ValueError: <Token var=<ContextVar name='current_recorder' default=None>>
       was created in a different Context"
```

#### 根因

```
Starlette 迭代**同步生成器**时用 `iterate_in_threadpool`，
**每取一个元素就是一次 `run_in_threadpool(next, ...)`** ——
也就是每个 `next()` 可能落在不同线程、拿到**各自的 context 副本**。
而 `ContextVar.set()` 返回的 token 只能在**同一个 context** 里 `reset()`。
生成器第 1 次 `yield` 时 set、第 N 次退出 `with` 时 reset → 直接抛异常。
```

用图表示就是：

```
  正常理解（错的）：            实际发生（对的）：
  ┌──────────────────┐         ┌──────────────────┐
  │ 同一个线程跑完整个 │         │ 线程1: next() →  │ set(token) 在这里
  │ 生成器            │         │ 线程3: next() →  │
  │ set → yield → ... │         │ 线程3: next() →  │
  │ reset（同一 context）│       │ 线程7: next() →  │ reset(token) 在这里
  └──────────────────┘         └──────────────────┘  ✗ 跨 context 复位 → ValueError
```

#### 修法：显式传递，而不是靠 context

不再用 contextvar 传 recorder，改成挂在依赖对象上：

```python
# backend/src/knowflow/container.py L63-L69（RequestServices，节选）
    #: 本次请求的 trace 持有者。`ChatService` 创建 recorder 后写进来，图里的节点从它读。
    #: **显式传递而不是 contextvar**：流式路径的生成器会被 Starlette 用
    #: `iterate_in_threadpool` 在不同线程上分次驱动，`ContextVar.set()` 返回的 token
    #: 无法在另一个 context 里 `reset()`（实测报
    #: `ValueError: Token ... was created in a different Context`）。
    #: 详见 `agent/nodes.py::RecorderBox`。
    recorder_box: RecorderBox
```

`ChatService` 侧就三行：

```python
# backend/src/knowflow/services/chat.py L419-L448（answer_stream，节选）
        recorder = obs_bridge.build_recorder("chat", trace_id=trace_id, settings=self.settings)
        accumulated: dict[str, Any] = {}
        status = "ok"

        # 把 recorder 写进本次请求的持有者（**不用 contextvar**：流式生成器会被
        # Starlette 用 iterate_in_threadpool 在不同线程上分次驱动，token 无法跨 context 复位）

            self.recorder_box.value = recorder

                ...
```

**关键洞察**：生成器在哪个线程跑**无所谓**，因为它读的是**同一个对象**
（`RecorderBox` 是普通 Python 对象，跨线程可见）。
而 `ContextVar` 的语义是"每个 context 一份"，天生不适用于"跨线程被分次驱动的生成器"。

#### 为什么 204 个 pytest 全绿也漏掉了它

```

所以 204 个单测全绿也照样漏掉它 —— **只有真起 uvicorn 打一次流式接口才会暴露**。
```

这条教训的价值远大于这个 bug 本身，它回答了一个很常见的问题：

因为**测试的执行模型与生产的执行模型不同**。`ASGITransport` 把整个 ASGI 调用

**凡是依赖"执行模型"的代码（contextvar、线程局部变量、生成器、异步上下文管理器），
单测都测不到它的真实行为**——这是本项目引入 `smoke_http.py`（真起 uvicorn）的根本原因。

### 2.8 关键代码 5：中间件为什么是纯 ASGI

```python
# backend/src/knowflow/middleware/context.py L3-L21（模块 docstring，节选）
# 为什么不用 `BaseHTTPMiddleware`

这是本项目一个真实的技术决策点，不是风格偏好：

`starlette.middleware.base.BaseHTTPMiddleware` 用「一个任务跑下游 app + 一个内存
对象管道传消息」的方式实现。它把下游的 `send` 换成自己包装的版本，并通过
`anyio` 的内存对象流把响应消息回传给真正写出的那个任务。对流式响应
（`StreamingResponse` / `text/event-stream`）来说，这条路径会引入**缓冲**：
下游 `await send(...)` 之后消息先落进管道，由另一个任务再取出写出去。
实践中表现为 SSE 的帧被攒成一批才发出，"边生成边推"的效果失效——用户看到的
是转圈很久然后一次性出现整段答案，而不是逐字出现。这正是 `/chat/stream`
最核心的体验，不能有。

纯 ASGI 中间件没有这一层：它就是一个 `async def __call__(self, scope, receive, send)`，
把 `send` 换成自己的一层薄包装**同一协程内同步调用**，`await send(message)`
返回时数据已经交给服务器。零缓冲、零额外任务、零额外队列。
```

代价是"看不到解析好的 Request 对象"，所以要自己处理 headers / client / path：

```python
# backend/src/knowflow/middleware/context.py L139-L150（send_wrapper，节选）

            nonlocal status_code
            if message["type"] == "http.response.start":

                # 用 MutableHeaders 在原有头上追加，而不是重建 headers：
                # 覆盖式写入会把下游设置的 Content-Type / CORS 头一起丢掉。
                # 传 `raw=` 而不是 `scope=`：`raw=` 原地改列表，
                # 不会把 `message["headers"]` 换成一个新对象（下游可能持有旧引用）。

                headers[PROCESS_TIME_HEADER] = f"{(time.perf_counter() - started) * 1000:.2f}"
```

```typescript
// frontend/src/api/sse-parser.ts L51-L67
export function parseSSEChunk(buffer: string): ParseSSEChunkResult {
  // 统一换行：服务端可能发 CRLF（sse-starlette 默认就是 \r\n）
  const normalized = buffer.replace(/\r\n/g, '\n').replace(/\r/g, '\n')

  const events: ParsedSSEEvent[] = []
  const blocks = normalized.split('\n\n')

  // 最后一段永远可能是「半帧」：留在 rest 里等下一批数据补齐
  const rest = blocks.pop() ?? ''

  for (const block of blocks) {
    const parsed = parseEventBlock(block)
    if (parsed) events.push(parsed)
  }

  return { events, rest }
}
```

**"最后一段永远留在 `rest`"是状态机的核心**：网络给的字节流会在任意位置切断
（包括切在 `data:` 中间）。把"未闭合的尾部"还回去、下批数据拼前面，
是唯一正确的做法。另外两个规范细节也不能漏：

```typescript
    const isCitation = Number.isInteger(rank) && rank > 0 && (!validRanks || validRanks.has(rank))

```

`validRanks` 来自 `collectRanks(sources)`：**只有真正落在 `sources` 里的 rank
才变成可点击角标**。否则一句"2024 年的标准 [2024] 元"里的 `[2024]`
会被渲染成一个点击后什么都不发生的角标。对应组件里的注释：

```vue

/** 引用角标：只有落在 sources 里的 rank 才变成可点击角标（避免把 `[2024]` 误判成引用） */
const validRanks = computed<Set<number>>(() => collectRanks(props.message.sources))
const nodes = computed(() => splitCitations(props.message.content, validRanks.value))
```

模板部分是**两条分支的 v-for**，而不是 `v-html`：

```vue
<!-- frontend/src/components/MessageBubble.vue L102-L118（节选） -->
      <div class="bubble__body">
        <!-- 助手回答里的 [n] 渲染成角标；文本节点与角标节点分开渲染，不走 v-html -->

              type="button"
              class="bubble__citation"
```

**`v-html` 的问题不只是 XSS**：它还会让"角标点击"变成字符串拼接出来的内联事件，
没法用 Vue 的响应式与事件系统。分成两类节点之后，
`citationClick` 是一个正常的事件，页面可以据此滚动 + 高亮对应引用卡片

### 2.12 关键代码 9：Agent 思考过程与 9 种事件

`useChatStream.ts` 的职责是"把 9 种 SSE 事件映射进 store"，它的注释解释了为什么值得单独抽一层：

### 2.13 关键代码 10：401 只处理一次 + `main.ts` 的安装顺序

并发请求时，token 过期会同时收到好几个 401。如果每个都弹 toast + 跳登录页，
用户会看到**一串一模一样的提示**：

```typescript
// frontend/src/api/client.ts L107-L138（节选）
/* ------------------------------------------------------------------ 401 全局处理 */

/** 401 只处理一次：这个标记在第一次 401 时置位，避免并发请求弹多个 toast */
let handling401 = false

const unauthorizedHandlers = new Set<() => void>()

/**
 * 注册 401 处理器（auth store 初始化时调用）。
 * 用「订阅」而不是直接 import store，是为了避免 client ↔ store 循环依赖。
 */
export function onUnauthorized(handler: () => void): void {
  unauthorizedHandlers.add(handler)
}

/** 401 处理入口：只执行一次，直到 resetUnauthorizedFlag() 被调用 */
function triggerUnauthorizedOnce(): void {
  if (handling401) return
  handling401 = true
  ...
}

/** 登录成功后复位标记，否则第二次过期不会再被处理 */
export function resetUnauthorizedFlag(): void {
  handling401 = false
}
```

**`resetUnauthorizedFlag()` 这一行不能省**：只在第一次 401 置位、登录成功后复位，
才能表达"每个登录会话只处理一次"。少了它，第二次 token 过期就没人管了——
用户会觉得"页面卡住不动"。

`main.ts` 里则是一条 Vue 3 组合式的经典顺序要求：

```typescript

 * 会报 `getActivePinia() was called but there was no active Pinia`
```

### 2.14 关键代码 11：前后端契约对齐（`check_api_contract.py`）

前端与后端**照着同一份契约各自实现，依然可能对不上**：

```
前端  GET /api/v1/conversations/${id}/messages
后端  GET /api/v1/conversations/{conversation_id}/messages
```

双方各自自测时**都是 200**，只有真正联调才会 404。所以做一次集合比对：

```python
# backend/scripts/check_api_contract.py L75-L84
def normalize(path: str) -> str:
    """把路径里的参数名抹掉，只比结构。

    `/{conversation_id}/messages` 与 `/1/messages` 都会归一成 `/{}/messages`，
    这样"参数叫什么名字"就不会造成假报警 —— 那本来就不影响路由匹配。
    """
    path = path.split("?")[0]  # 去掉 query
    path = path.rstrip("/") or "/"
    path = _TEMPLATE_PARAM.sub("{}", path)
    return _PATH_PARAM.sub("{}", path)
```

而它自己也踩了两个坑（第一版因此**报了一堆假警**）：

```python
# backend/scripts/check_api_contract.py L90-L99（节选）
    三处细节决定了这个脚本有没有用，每一处都是第一版踩出来的：

    1. **前端写的是相对路径**（`get('/kbs')` + `baseURL='/api/v1'`），
       所以要**自己把 base 拼上去**，否则永远匹配不上后端的 `/api/v1/kbs`。
       第一版漏了这一步，只找到 4 个路径、还报了两个假警。
    2. **只扫 API 层（`src/api/**`）**。全仓库扫会把**前端路由**当成接口路径：
       `router/index.ts` 里的 `/kbs/:id`、`/obs/traces/:traceId` 用的是
       Vue Router 的 `:param` 语法，和 HTTP 路径根本不是一个东西 ——
       全扫会多报 6 个假警，把真问题淹掉。
       （本项目所有接口 URL 都集中在 `src/api/` 下，这正是这样分层的好处。）
```

第二个坑尤其值得记：**假警报会把真问题淹掉**。
一个报 6 个假警的脚本，比没有脚本更糟——用两次之后大家就不看它了。

## 4. 常见错误

| 错误信息 / 现象 | 原因 | 解决 |
| --- | --- | --- |
| SSE 帧被攒成一批才发出（"不流式"） | 挂了 `starlette.middleware.base.BaseHTTPMiddleware`（引入对象管道缓冲） | 用纯 ASGI 中间件（一个 `async def __call__(scope, receive, send)`） |
| 本地流式正常，上线（Nginx 后）变成一次性返回 | 缺 `X-Accel-Buffering: no` | `SSE_HEADERS` 三个头都要带 |
| 一个流式问答期间整个服务不响应 | SSE 路由写成 `async def` 却 `for` 同步生成器，阻塞事件循环 | 路由写**同步 `def`**，让 Starlette 用 `iterate_in_threadpool` |
| 答案打到一半连接断掉，无任何提示 | 异常从生成器里冒泡（响应头已发出，异常处理器救不了） | 生成器内部 `try/except` → `error` 帧 + `finally` 里补 `end` 帧 |
| 前端拿不到 `X-Request-ID`（永远是 `null`） | CORS 缺 `expose_headers=["X-Request-ID","X-Process-Time-Ms"]` | 补上；浏览器默认只暴露"安全列表"响应头 |
| 启动时 `pydantic_settings` 抛 `JSONDecodeError` | `CORS_ORIGINS` 用逗号写法但没加 `NoDecode` | `Annotated[list[str], NoDecode]`（见 `core/config.py`） |
| `/docs` 上分页参数变成一个 JSON body | 写了 `Depends(PageParams)` | 写 `Annotated[PageParams, Depends()]`（`Depends()` 不带参数） |
| `/docs` 上出现 OAuth2 的 form 登录框 | 用了 `OAuth2PasswordBearer`，而真实登录是 JSON | 手写 `bearer_token` |
| 422 的形状和别的错误不一样，前端要写两套解包 | 没注册 `RequestValidationError` 处理器 | 注册四个处理器，统一走 `_envelope` |
| 422 变成了 500 | `exc.errors()` 里有 `ValueError` 对象，直接 JSON 序列化失败 | 先 `jsonable_encoder(exc.errors(), custom_encoder={Exception: str})` |
| 500 里带着文件路径 / SQL 片段 | 兜底处理器把 `str(exc)` 回给用户 | 只回通用文案 + `request_id`；细节进日志（`exc_info=True`） |
| `GET /kbs` 不带 token 返回 200 + 数据 | 鉴权逐个端点声明，漏了（E6.4：21 个） | 改成路由级 `AUTH_REQUIRED`（默认安全） |
| 审计脚本报"没有漏洞"但实际有 | 直接遍历 `app.routes` 只看到 `_IncludedRouter` 占位对象（FastAPI 0.142 惰性 `include_router`） | 从 `original_router.routes` 递归 + 继承 `include_context.dependencies` |
| 审计脚本把正确写法误报成漏洞 | 只查了端点自身的 `dependant` | 同时查 `include_context.dependencies` |
| 流式接口最后总发一个 `error` 帧 | `ValueError: Token ... was created in a different Context` | 用 `RecorderBox` 显式传 recorder，不用 contextvar |
| 单元测试全绿但流式上线崩 | `ASGITransport` 不触发分次线程调度 | 真起 uvicorn 跑 `smoke_http.py` |
| `GET /conversations/{id}/messages` 的 items 是 `{message: "..."}` | `Page["MessageOut"]` 的 ForwardRef 用了 `schemas/common.py` 的命名空间（那里也有个 `MessageOut` 别名） | 定义 `class MessagePage(Page[MessageOut])` 子类 + import 期断言 |
| 日志里两个不同请求混成一条链 | 中间件没在 `finally` 里 `clear_request_context()` | 必须清理（contextvar 线程内共享） |
| `getActivePinia() was called but there was no active Pinia` | `app.use(router)` 在 `app.use(pinia)` 之前 | 先 pinia、后 router |
| 并发 401 弹出一串相同 toast | 每个 401 都处理 | `handling401` 标记 + 登录成功后 `resetUnauthorizedFlag()` |
| 契约检查脚本报 6 个假警 | 全仓库扫，把 Vue Router 的 `/kbs/:id` 当成接口路径 | 只扫 `src/api/**`（运维绝对路径单独扫） |
| 契约检查脚本报"前端只调了 4 个路径" | 前端写的是相对路径，没拼 `baseURL` | 从 `client.ts` 读 `VITE_API_BASE_URL` 再拼 |
