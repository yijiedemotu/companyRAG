# KnowFlow 从零动手教程

> **这不是一份"看懂就够了"的文档，而是一份"照着敲、每一步都能验证"的操作手册。**
>
> 三份文档分工不同，别搞混：
>
> | 文档 | 定位 | 什么时候读它 |
> | --- | --- | --- |
> | `知识库学习手册.md` | 按章节**读代码**的教科书 | 想理解某个模块的设计动机 |
> | `03-knowflow-项目实现详解.html` | **图解实现** | 想一眼看清数据怎么流动 |
> | **`docs/教程/`（本目录）** | **从零动手重建**的分步操作手册 | 想自己敲一遍、并确认自己敲对了 |
>
> 本教程的核心价值只有两个字：**顺序 + 验证**。
> 每个阶段都告诉你「为什么必须先做这一步」和「敲完怎么证明你做对了」。

### 依赖关系（为什么不能跳）

| 阶段 | 它必须在前一个之后，因为 |
| --- | --- |
| 1 | 后面每个模块都 `from knowflow.core.config import get_settings`；配置是唯一真相来源 |
| 2 | `chunks.vector_id` 是"向量库 ↔ 关系库"的一致性锚点；没有它，阶段 4 写向量时无从对齐 |
| 3 | 向量化的输入是 chunk；切分错了，后面"检索不准"会被误判成"模型不行" |
| 4 | 阶段 5 的融合需要两路"同量纲可比"的分数，向量分必须先有稳定含义（归一化 + 越大越相似） |
| 5 | 阶段 7 的 `grade` 判据要用到 `vector_score` 与 `keyword_coverage`，两路都得先存在 |
| 6 | 阶段 7 的每个节点都是"调模型 + 解析 JSON"；模型协议与解析器必须先稳定 |
| 7 | 阶段 8 的服务层只是"给图喂 session 并落库"，图本身必须先能独立跑 |
| 8 | 阶段 9 的路由是薄薄一层；业务逻辑没验证过就上 HTTP，报错会指不到根因 |
| 9 | 阶段 10 的 trace 需要 `request_id` 与 SSE 帧序才能对齐"一次请求"的边界 |
| 10 | 阶段 11 的标定需要"同一批用例、同一套指标"，指标口径没定死就没法比大小 |
| 11 | 阶段 12 的 CI 门槛要拿标定后的基线当参照，否则不知道该拦什么 |
| 12 | 前面 12 个阶段的产出都要被回归测试保护起来 |

## 3. 怎么用这套教程

### 3.1 每个阶段文件的固定 7 节

```
§0 为什么先做这一步   ← 依赖关系（教程区别于普通文档的地方）
§1 要解决的问题       ← 不做会怎样？给出具体失败现象
§2 动手实现           ← 目标 → 关键代码（真摘自仓库）→ 逐行解释"为什么这么写"
§3 怎么验证我做对了   ← 可执行命令 + 预期输出（数字来自 E-n）
§4 常见错误           ← 表格：错误信息 / 原因 / 解决
§5 自测问题           ← 3~6 个，确认真的理解了
§6 本阶段小结         ← 加了哪些文件 / 多少行 / 下一步
§7 延伸阅读           ← 手册章节 / 源码文件 / 官方文档
```

### 3.2 三条使用纪律

1. **不许跳 §3**。"敲完了"和"敲对了"是两件事。这个项目里最多的 bug
   是"接口 200、返回正常数据、但结果是错的"——E6.4 那 21 个漏鉴权端点就是这么藏住的。
2. **先跑再改**。§3 的命令请原样跑一遍，看到预期输出之后再去动代码。
   否则你分不清"是我改坏了"还是"本来就该这样"。
3. **数字以 E 为准**。如果你跑出来的数字和 E 不一致，先怀疑自己的环境（依赖版本、
   是否配了 API Key、是否装了 GPU），**不要怀疑 E**——E 里每一条都记录了原始命令。

### 3.3 约定

| 记号 | 含义 |
| --- | --- |
| `E1`、`E6.3`、`E7` | `docs/03-实测证据.md` 的第几节 |
| `backend/src/knowflow/xxx.py L12-L40` | 仓库里的真实文件与行号（**教程里的代码片段都从这里摘**） |

## 4. 环境准备（所有阶段共用）

```powershell
# 1) 仓库根目录
cd D:\Projects\pythonProjects\knowflow

# 2) 虚拟环境（Python 3.13）
python -m venv .venv

# 3) 装后端依赖（版本已钉死）
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
.\.venv\Scripts\python.exe -m pip install -r backend\requirements-dev.txt

# 4) 拷配置样例
Copy-Item backend\.env.example backend\.env

# 5) 依赖自检
.\.venv\Scripts\python.exe backend\scripts\check_env.py
```

预期最后一行是：

```
RESULT: ALL OK
```

⚠ **不想下 2GB 模型**的话，在 `backend\.env` 里设 `EMBEDDING_PROVIDER=hash`，
整条链路照样能跑通（质量差，但零下载、零网络）——这是阶段 4 会详细讲的"降级路径"。

MySQL 需要先建库（不建也能跑 SQLite 测试，但阶段 2 的建表检查需要它）：

```sql
CREATE DATABASE knowflow      DEFAULT CHARSET utf8mb4;
CREATE DATABASE knowflow_test DEFAULT CHARSET utf8mb4;  -- 冒烟脚本会用
```

## 5. 一份"最小成功"的定义

如果你只想知道**怎么证明这套系统真的工作**，下面这一串命令就是答案。
它们对应教程的最后几个阶段，每一条都有原始输出记录（E-n）：

```powershell

# ② 204 个离线用例，4 秒级
cd backend; ..\.venv\Scripts\python.exe -m pytest; cd ..            # E1.5 → 204 passed

# ③ ORM 能在真实 MySQL 上建出 14 张表
```
