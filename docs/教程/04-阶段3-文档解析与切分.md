# 阶段 3：文档解析与切分

> **本阶段目标**：把 6 种格式的原始字节变成归一化纯文本，再切成"子块（检索单位）+ 父块（喂模型单位）"。
> **预计耗时**：120 分钟
> **前置阶段**：阶段 2
> **本阶段产出**：`ingest/` 三个模块（1,050 行）+ 可复现的三级边界切分

## 0. 为什么先做这一步

因为**切分决定了检索的上限**。这里的每一个决定都会一路传到最终答案：

| 决定 | 上游看不出来的后果 |
| --- | --- |
| 编码嗅探顺序错了 | 一篇看似正常、内容全错的文档入库（静默乱码） |
| CSV 不转自然语言 | 列名与值的对应关系在切分后丢失，模型答错了还"看起来很有依据" |
| 块在句子中间被砍断 | 检索命中率静默下降，不报任何错 |
| 父块窗口跨页 | 引用页码说谎（"第 3 页"其实内容在第 5 页） |
| `chunk_index` 不连续 | `vector_id` 与向量库对不上，三方一致性校验永远报差异 |

而且这一步是**"可复现性"的源头**：`chunk.index` 直接变成
`chunks.chunk_index` 与 `vector_id="{doc_id}:{index}"`。
同一份文档、同一套参数**必须切出完全一样的块**，否则向量库和 MySQL 会对不上。

第三个理由：这是**唯一一处能纯本地、零依赖、秒级验证**的核心算法。
不需要 MySQL、不需要模型、不需要网络——所以它也是**最值得写测试**的地方。

---

## 1. 要解决的问题

不做这一步，你会遇到的具体失败现象：

| 现象 | 真实原因 |
| --- | --- |
| 中文文档入库后全变成 `锟斤拷` 或乱码汉字 | 编码嗅探用了"逐个 codec 试着 decode，成功就用"的写法，`utf-8-sig` 把不带 BOM 的 UTF-8 也吃了，`utf-16` 把随机二进制"成功"解成乱码 |
| 生僻字变成另一个"看起来正常"的汉字 | GBK 排在 GB18030 前面，GBK 把生僻字解成合法汉字**且不报错** |
| CSV 入库后模型答错列 | 表头在第一行、值在下面几百行，切分后列对应关系丢失 |
| PDF 引用只能定位到"某文档"，不能到页 | 解析时没保留页码，后面任何环节都补不回来 |
| 检索质量明显变差但不报错 | 空字符串分隔符被放在了 `separators` 中间，块边界从句中砍断 |
| 200 行短条款文档被切成 200 个 13 字小块 | 把"看起来像标题的行"当成了切分边界 |
| 父块看起来像复读（同一句话出现两遍） | 父块用"拼接子块文本"实现，而相邻子块本来就有 `chunk_overlap` 重叠 |
| `unique constraint failed: chunks(doc_id, chunk_index)` | 切分不可复现，同一文档两次切出不同的块数 |

## 2. 动手实现

### 2.1 目标

```
原始 bytes
  │
  ├─ ① 扩展名白名单（最便宜，先做）
  ├─ ② 零字节检查（不做会一路撞到"无法识别编码"，报错原因完全误导）
  ├─ ③ 分派解析（最贵）
  │     ├─ 编码嗅探：BOM > 严格 UTF-8 > 统计探测器 > CJK 兜底
  │     ├─ 各格式解析：md / txt / pdf / csv / json
  │     └─ 归一化：统一换行 → 删零宽字符 → 压缩空行
  └─ ④ 空文本检查 → ParsedDocument
             │
             └─ ⑤ 三级切分：页 → 小节 → 递归标点
                      └─ ⑥ 父子块：子块检索，父块喂模型
```

### 2.2 关键代码 1：编码嗅探的顺序就是设计本身

```python
# backend/src/knowflow/ingest/loaders.py L79-L94
BOM_SIGNATURES: Final[tuple[tuple[bytes, str], ...]] = (
    (b"\xef\xbb\xbf", "utf-8-sig"),
    (b"\xff\xfe\x00\x00", "utf-32-le"),
    (b"\x00\x00\xfe\xff", "utf-32-be"),
    (b"\xff\xfe", "utf-16-le"),
    (b"\xfe\xff", "utf-16-be"),
)

#: 探测器不可用时的中文编码兜底顺序。
#: **GB18030 必须排在 GBK 之前**：GB18030 是 GBK 的严格超集，
#: 反过来先试 GBK 时，生僻字会被解成"另一个合法汉字"而**不报错**，
#: 得到一篇看似正常、内容全错的文档（静默乱码，真实踩过的坑）。
CJK_FALLBACK_ENCODINGS: Final[tuple[str, ...]] = ("gb18030", "gbk", "gb2312", "big5")
```

🔻 **这里有一个非常值得学的 bug 修复过程**。第一版写的是
"逐个 codec 试着 decode，成功就用"，结果：

```python
# backend/src/knowflow/ingest/loaders.py L68-L78
#: ⚠ 这里不能用"直接 `raw.decode("utf-16")` 成功就算 utf-16"的写法（第一版就是这么写的，
#: 被验证脚本抓出来了）：
#:
#: * ``utf-8-sig`` 解码**不带 BOM** 的 UTF-8 也完全成功，于是所有 UTF-8 文件都被标成
#:   ``utf-8-sig``，而 BOM 那一轮会直接吃掉严格 UTF-8 这一轮 —— 顺序设计形同虚设；
#: * ``utf-16`` / ``utf-32`` 在没有 BOM 时按本机字节序解码且**从不报错**，
#:   于是随机二进制会被"成功"解成一篇乱码汉字文本，永远走不到"无法识别编码"。
#:
#: 所以 BOM 检测必须落到字节层面：**先看字节前缀，再决定用哪个 codec**。
```

**教训**："试着 decode，成功就用"看起来是个很自然的启发式，
但它的失败模式是**"成功了，但是错的"**——比直接报错难查一百倍。
正确做法是**用确定性信号（字节前缀）**，只在确定性信号缺失时才猜。

主流程：

```python
# backend/src/knowflow/ingest/loaders.py L226-L268
tried: list[str] = []

# ---- 1. BOM：按字节前缀判定，命中才用对应 codec 解 ----
bom_encoding = _match_bom(raw)
if bom_encoding is not None:
    tried.append(bom_encoding)
    # utf-8-sig 自己会吞掉 BOM；utf-16-le/be 与 utf-32-le/be 不会，所以要切掉，
    # 否则 U+FEFF 会混进第一个 chunk（既污染检索，也会让文本首字符看起来是"乱码"）
    payload = raw[3:] if bom_encoding == "utf-8-sig" else raw
    return payload.decode(bom_encoding), bom_encoding, tried

# ---- 2. 严格 UTF-8 ----
tried.append("utf-8")
try:
    return raw.decode("utf-8"), "utf-8", tried
except UnicodeDecodeError:
    pass

# ---- 3. 统计探测器 ----
detected = _detect_encoding(raw)
if detected:
    tried.append(detected)
    try:
        return raw.decode(detected), detected, tried
    except (LookupError, UnicodeDecodeError):
        # LookupError: 探测器返回了本机不认识的编码名
        # UnicodeDecodeError: 猜错了。两种都继续往下走，不要在这里中断。
        logger.debug("encoding_detector_missed", encoding=detected)

# ---- 4. CJK 兜底顺序 ----
for encoding in CJK_FALLBACK_ENCODINGS:
    try:
        decoded = raw.decode(encoding)
    except (UnicodeDecodeError, LookupError):
        continue
    tried.append(encoding)
    return decoded, encoding, tried

# ---- 5. 全失败 ----
raise DocumentParseError(
    "无法识别文件编码",
    detail={"tried": tried, "size_bytes": len(raw)},
)
```

**四个判断为什么按这个顺序**（每条都有具体理由，可直接背）：

1. **BOM 优先**：BOM 是文件自己声明的编码，是**零误判**的确定性信号。
2. **严格 UTF-8 次之**：UTF-8 的字节结构校验很强，一段 GBK 字节几乎不可能通过。
   反过来**不成立**——UTF-8 的字节序列用 GBK 解也是"合法汉字"，
   所以**绝不能**让 GBK 插到 UTF-8 前面。
3. **统计探测器第三**：UTF-8 失败说明不是 UTF-8，此时让 `charset-normalizer` 判断。
   它对长文本很准、极短文本会错，所以放在第三位而不是第一位。
4. **CJK 兜底最后**：`GB18030 → GBK → GB2312 → Big5`。
   `GB2312` 是 GBK 的子集，只在 GBK 也失败时才有意义；`Big5` 覆盖繁体中文。

失败时把 `tried` 放进 `detail`——排查时能直接看到"到底试过什么"。

### 2.3 关键代码 2：归一化的三步顺序不能交换

```python
# backend/src/knowflow/ingest/loaders.py L292-L315
def _normalize(text: str) -> str:
    """归一化。**三步顺序有意义，不能交换**：

    1. **统一换行**（``\\r\\n`` / ``\\r`` -> ``\\n``）：必须最先做。
       否则后面按行/按段落处理时，``\\r\\n`` 会被当成两个字符，行尾多出空行，
       连"连续换行压缩"的计数都会算错。
    2. **删不可见字符**（零宽空格/零宽非连接符/LRM/软连字符）：这些字符
       不影响人眼阅读，但会让 BM25 把 ``住宿`` 和 ``住\\u200b宿`` 当成两个不同的词，
       检索命中率静默下降。必须放在换行压缩之前，避免它们把空行计数撑大。
    3. **压缩空行**（3 个以上换行 -> 2 个）：保留段落边界（Markdown 的段落语义），
       但去掉粘贴/转换产生的大片空白。

    **刻意不做** ``strip()`` 每一行：Markdown 的缩进有语义
    （代码块、列表续行、嵌套列表），strip 掉会把结构压平、让切分和展示都变形。
    这里只做末尾 ``rstrip()``（去掉文件尾部空白，它永远是噪声）。
    """
    normalized = text.replace("\r\n", "\n").replace("\r", "\n")

    for invisible in _INVISIBLE_CHARS:
        if invisible in normalized:
            normalized = normalized.replace(invisible, "")

    normalized = _BLANK_LINES_RE.sub("\n\n", normalized)
    return normalized.rstrip()
```

**为什么"删零宽字符"这一条特别重要**：从 Word / PDF / 网页复制出来的文本里
零宽字符非常多。它们的后果是**检索静默变差**：用户搜"住宿标准"搜不到
`住\u200b宿标准`，因为 BM25 的倒排索引里是两个不同的 token，
**而整个链路不报任何错**。

**"刻意不做 `strip()` 每一行"这个决定值得单独理解**：
Markdown 的四个空格缩进 = 代码块，两个空格 = 嵌套列表。
`strip()` 会把结构压平——代码块不再是代码块，嵌套列表变成平铺。
这类"看不见的语义损失"最终会体现在"模型答得不对"上，而你会去查模型。

### 2.4 关键代码 3：CSV 必须转成自然语言（这是一次真实事故）

```python
# backend/src/knowflow/ingest/loaders.py L462-L479（节选）
def _parse_csv(text: str) -> tuple[list[ParsedPage], list[str]]:
    """CSV -> **自然语言行**，每行形如 ``姓名: 张三 | 部门: 研发部 | 住宿标准: 600``。

    **为什么必须转成自然语言（真实事故）**：
    CSV 直接当纯文本喂给向量模型时，表头在第一行、值在下面几百行，
    列的对应关系在切分后彻底丢失。用户问"谁的住宿标准是 600"，
    模型看到的上下文里只有一堆 ``张三 研发部 600``，没有任何线索说明
    600 是住宿标准 —— 模型会一本正经地答错，而且看起来很有依据。
    转成"列名: 值"后，每一行都自带完整的字段语义，切分到哪都自洽。
    """
```

转换的核心循环：

```python
# backend/src/knowflow/ingest/loaders.py L499-L517（节选）
lines: list[str] = []
for row in data_rows:
    pairs: list[str] = []
    for column_index, value in enumerate(row):
        name = header[column_index] if column_index < len(header) else f"col_{column_index}"
        # 列名为空时退回 col_i，否则会生成 ": 值" 这种无法解释的行
        key = name or f"col_{column_index}"
        pairs.append(f"{key}{CSV_KV_SEP}{value.strip()}")
    if pairs:
        lines.append(CSV_FIELD_SEP.join(pairs))
```

**为什么分隔符是 ` | ` 而不是 `,`**（同文件 L102-L105）：

```python
#: CSV 自然语言行里列与值、列与列之间的分隔符。
#: 用 ` | ` 而不是 `,`：值本身可能含逗号，`|` 在中文语料里几乎不出现，可无歧义切回。
CSV_FIELD_SEP: Final[str] = " | "
CSV_KV_SEP: Final[str] = ": "
```

这个 ` | ` 记号还有**第二个用途**：切分层要用它来**排除伪标题**——
`NATURAL_LANGUAGE_ROW_MARKERS = (" | ",)`。不排除的话，
CSV 的每一行都会被"看起来像标题"的启发式判定当成标题，
`section_path` 会变成垃圾。

中文 CSV 的表头判断也必须自己兜底：

```python
# backend/src/knowflow/ingest/loaders.py L426-L459（节选）
def _first_row_looks_like_header(rows: list[list[str]], full_text: str) -> bool:
    """判断第一行是否是表头。

    优先用 ``csv.Sniffer.has_header``（它比较两行的列"类型一致性"），
    但它在两种真实场景下会给出错误答案，所以必须自己兜底：

    * **中文表头猜不出来**：``姓名;城市`` 与 ``张三;北京`` 在它眼里"都是字符串"，判为无表头；
    * **样本太短直接抛 ``csv.Error``**（只有一行时）。

    兜底规则（两条都满足才算有表头，宁可少一行数据也不要让列名变成数据）：
    1. 第一行多数单元格"不含数字"——数据行一般含数字（金额、数量、日期）；
    2. 第一行与第二行至少有一列取值不同——完全相同说明两行是同类数据。
    """
```

**注意这里的取舍是"宁可少一行数据，也不要把数据当列名"**：
两种错误都会发生，但危害不对称。把表头当数据 → 每一行都缺字段名 → **检索直接失效**；
把数据当表头 → 少一行数据 → 影响很小。**不对称时选危害小的那一边**，
这是工程判断的常见形态。

### 2.5 关键代码 4：JSON 递归展平

```python
# backend/src/knowflow/ingest/loaders.py L530-L545（节选）
def _flatten_json(node, path, lines, warnings, depth, seen) -> None:
    """递归展平：``{"a": {"b": [1, 2]}}`` -> ``a.b[0]: 1`` / ``a.b[1]: 2``。

    数组用 ``[i]`` 下标（保留顺序信息，检索时能知道"这是第几个"），
    字典用 ``.`` 连接（路径可读）。
    """
    if depth > JSON_MAX_DEPTH:
        # 截断而不是继续递归：畸形/自引用结构会把内存打满。
        message = f"JSON 嵌套深度超过 {JSON_MAX_DEPTH} 层，超出的部分已截断"
        if message not in warnings:
            warnings.append(message)
        # **必须落一行占位**：如果整份文档深到"一层都没落下来"，
        # 产物就是空列表，上层会报"JSON 解析后没有任何字段" —— 但那不是事实，
        # 事实是"太深被截断了"。占位行 + warning 才是如实描述。
        lines.append(f"{path or '$'}: <截断：嵌套超过 {JSON_MAX_DEPTH} 层>")
        return
```

**`scalar` 转文本时 `null` 要显式写出来**：

```python
# backend/src/knowflow/ingest/loaders.py L576-L582
def _json_scalar_to_text(value: Any) -> str:
    """标量转字符串；``null`` 显式写出，避免"路径: "这种空值行被误读成缺字段。"""
    if value is None:
        return "null"
    if isinstance(value, bool):
        return "true" if value else "false"
    return str(value)
```

**`isinstance(value, bool)` 必须在 `str(value)` 之前**：Python 里
`str(True)` 是 `"True"`（大写），而 JSON 里是 `true`。虽然看起来是小事，
但一致性对"同一份文档两次入库切出的块完全一样"这条承诺有意义。

**"占位行 + warning"这个技巧值得记**：截断时如果什么都不落，
上层会得到"JSON 解析后没有任何字段"这个**错误的原因**。
落一行占位 + 一条 warning 才是如实描述。**降级可以，说谎不行。**

### 2.6 关键代码 5：三级切分与"空分隔符只能放最后"

```python
# backend/src/knowflow/ingest/chunkers.py L56-L94
#: 三级切分的标点分隔符，**顺序即优先级**：段落 -> 行 -> 中文句末 -> 英文句末 -> 中文句内。
#:
#: ⚠ **空字符串 ``""`` 只能放在最后一位**（真实踩过的坑）。
#: ``RecursiveCharacterTextSplitter._split_text`` 的实现是：
#:
#: .. code-block:: python
#:
#:     for i, s_ in enumerate(separators):
#:         if not s_:                       # 碰到空串就 break
#:             separator = s_; break
#:         if re.search(separator_, text):  # 碰到出现的分隔符也 break
#:             separator = s_; new_separators = separators[i + 1:]; break
#:
#: 空串写在中间会让循环**在它那里直接 break**：更"高级"的段落/句末分隔符全部被跳过，
#: 而且 ``new_separators`` 为空导致递归下降彻底失效。实测（每个分隔符都有文本命中）：
#:
#: * 正确配置：块边界落在句末，块开头都是 ``'。第二句话！'``；
#: * 空串插在中间：块开头变成 ``'话！第三句话？'``、``'四句话，第五'`` ——
#:   成句被**从中间砍断**，检索质量下降，而且不报任何错。
DEFAULT_SEPARATORS: tuple[str, ...] = (
    "\n\n", "\n", "。", "！", "？", "；", ".", "!", "?", ";", "，", ",", " ", "",
)
```

对应的强制校验：

```python
# backend/src/knowflow/ingest/chunkers.py L225-L244
def _validate_separators(separators: tuple[str, ...]) -> None:
    """校验分隔符列表，**空字符串只允许出现在最后一位**。

    为什么主动抛错而不是记 warning 后继续：空串写在中间会让
    ``RecursiveCharacterTextSplitter`` 跳过所有更高级的分隔符并放弃递归下降
    （原理见 :data:`DEFAULT_SEPARATORS` 的注释），产出的是"看起来成功、
    实际块边界全乱/块超大"的检索库 —— 属于最难排查的静默故障，
    必须在上传请求里就失败掉，而不是入库后靠人发现检索质量变差。
    """
    if "" in separators[:-1]:
        raise ValueError(
            "separators 中除最后一项外不允许出现空字符串：RecursiveCharacterTextSplitter "
            "遇到非末位的空分隔符会跳过所有更高级分隔符、放弃递归下降，"
            "导致块边界从句子中间砍断（且不报错）。"
            f" 当前 separators={list(separators)!r}"
        )
```

🔻 **这条坑值得完整理解**。`langchain-text-splitters 1.1.3` 的
`RecursiveCharacterTextSplitter._split_text` 长这样（上面注释里就是真实代码）：

```python
for i, s_ in enumerate(separators):
    if not s_:                       # 碰到空串就 break
        separator = s_; break
    if re.search(separator_, text):  # 碰到出现的分隔符也 break
        separator = s_; new_separators = separators[i + 1:]; break
```

**它是 `break` 而不是 `continue`**。所以空串写在中间时：

1. 更"高级"的分隔符（`\n\n`、`\n`、`。`）**全部被跳过**——循环在空串处就断了；
2. `new_separators` 为空，**递归下降彻底失效**。

实测结论（写在注释里）：正确配置下块开头是 `'。第二句话！'`（从句子边界开始）；
空串插在中间时块开头变成 `'话！第三句话？'`、`'四句话，第五'`
——**成句被从中间砍断**，而且**不报任何错**。
更糟的组合（`keep_separator=False`）下，空串分隔符会让整段文本不再被切开，
直接产出远超 `chunk_size` 的巨型块（曾观察到 300 字文档只切出 1 块）。

**这条经验的一般化**："看起来成功了，但结果是错的"必须**主动抛错拦下**，
不能只记 warning。因为它不会在功能测试里暴露，只会在几周后被用户投诉"搜索不准"。

### 2.7 关键代码 6：定位块在源文本中的区间（三次尝试）

父块要"回原文取一段"，所以需要知道每个子块在源文本中的**字符区间**。
但 `split_text()` 只返回字符串，不返回偏移量。这里踩了两次坑：

```python
# backend/src/knowflow/ingest/chunkers.py L440-L481（节选）
def _locate_spans(text, pieces, *, chunk_size, chunk_overlap) -> list[tuple[int, int]]:
    """把切分产物对齐回源文本的字符区间。

    **定位策略：期望位置 + 窗口查找**（试过两种更朴素的写法，都会被真实文本坑）：

    * ``cursor = 上一块终点 - 1``：相邻块本来就有 overlap，后一块的起点**早于**
      前一块的终点，于是永远找不到，退化成"挂在游标处"。实测 200 行短条款文档
      6 块里 3 块的区间晚了一两百字符，父块取到完全不搭的文本，而且**不报错**。
    * ``cursor = 上一块起点 + 1``：在"每行都是同一句话"这种高重复文本里会命中
      更早的同名片段，区间不再单调，父块被压成一个小片段。

    正确做法是别把定位问题当成"纯字符串查找"，而要利用切分器的语义：
    **相邻块的起点差刚好是 ``chunk_size - chunk_overlap``**（这是 ``_merge_splits``
    推进窗口的方式）。所以下一块的起点可以精确预测，只在预测值附近开一个
    ``±chunk_overlap`` 的窗口去找，找到就用真实位置、找不到再退回全局查找，
    最后兜底挂在预测位置上。
    """
    spans: list[tuple[int, int]] = []
    expected = 0
    for piece in pieces:
        window_start = max(0, expected - chunk_overlap)
        index = text.find(piece, window_start)
        if index < 0 or index > expected + chunk_overlap:
            index = text.find(piece)  # 兜底：全文中第一次出现的位置
        if index < 0:
            index = expected
        spans.append((index, index + len(piece)))
        expected = index + max(len(piece) - chunk_overlap, 1)
    return spans
```

**这段代码最值得学的是"三次尝试"的记录方式**：
两种朴素写法都**能跑通小样例**，只在特定真实文本上失败（200 行短条款 / 高重复文本）。
把失败模式和原因写进 docstring，比只留最终实现有价值得多——
下一个人想"简化"这段代码时会先看到代价。

### 2.8 关键代码 7：小节只标注不切分（避免切出 200 个碎片）



方法不是"把启发式做得更准"（做不到），而是**改变它的用途**，

### 2.9 关键代码 8：父块窗口（"用小检索、用大写答案"）

```python
# backend/src/knowflow/ingest/chunkers.py L587-L605（节选）
def _assign_parents(pieces: list[_Piece], parent_chunk_size: int) -> list[str]:
    """为每个子块生成 ``parent_content``，返回与 ``pieces`` 等长的列表。

    父块 = 同一小节内**连续子块覆盖的原文窗口**，累积到 ``parent_chunk_size`` 就换窗。
    同一窗口内的子块共享同一段 ``parent_content``，这是刻意的：
    检索仍然用精准的小子块，模型看到的是完整小节 —— 命中任意一个子块，
    拿到的上下文都一致，回答不会因为"命中的是第 2 块还是第 3 块"而漂移。

    **不可跨小节**、**不可跨页**（小节自带 ``page_no``）：跨边界会让"引用来源"
    变成一个说不清的范围。
    """
```

**为什么"窗口内共享同一段父块"很重要**：如果每个子块各自拼一份父块，
那么命中第 2 块和第 3 块会让模型看到**不同**的上下文，
同一个问题两次提问可能得到不同答案——用户会觉得"这个系统不稳定"。
共享窗口让上下文**确定性**。

父块必须是"原文的一段"而不是"子块的拼接"：

```python
# backend/src/knowflow/ingest/chunkers.py L644-L661（节选）
def _fill_parent(pieces, start, end, parents) -> None:
    """把 ``pieces[start:end]`` 归入同一个父块窗口。

    窗口内所有块同源 -> 按区间回原文取（这是常态，能自动去掉 overlap 的重复部分）；
    跨源（窗口里混进了跨小节合并出来的块）-> 退化为 "\\n" 拼接块文本。
    """
    window = pieces[start:end]
    first = window[0]
    if all(piece.source is first.source for piece in window):
        parent_text = first.source[first.start : window[-1].end]
    else:
        parent_text = "\n".join(piece.text for piece in window)
```

**为什么按区间回原文取**：相邻子块本来就有 `chunk_overlap`（120 字符）的重叠。
直接拼接会得到"同一句话出现两遍"的父块——既浪费 token，
也会让向量被重复内容主导。按区间取**自动去重**。

### 2.10 关键代码 9：不可变量与兜底断言

```python
# backend/src/knowflow/ingest/chunkers.py L755-L759
# 兜底断言：不变量一旦被破坏，宁可在上传请求里炸掉，也不要写进向量库
if [chunk.index for chunk in chunks] != list(range(len(chunks))):
    raise AssertionError("chunk index 不连续：切分逻辑被破坏")
if any(not chunk.content for chunk in chunks):
    raise AssertionError("存在空 content 的 chunk：切分逻辑被破坏")
```

docstring 里明确列出的三条不变量（L690-L695）：

```
* ``[chunk.index for chunk in chunks] == list(range(len(chunks)))``；
* 每个 ``chunk.content.strip()`` 非空；
* 空文档返回 ``[]``；
```

**为什么"宁可在上传请求里炸掉"**：`chunk_index` 不连续会让
`vector_id="{doc_id}:{index}"` 出现空洞，而空洞的后果是
"三方一致性校验一直报差异"——但**检索本身照常工作**。
于是你会花几天时间查一个"不影响功能但永远修不掉"的告警。
在上传时就炸掉，问题就是可定位的。

## 4. 常见错误

| 错误信息 | 原因 | 解决 |
| --- | --- | --- |
| 中文文档入库后是乱码汉字（看起来正常但内容全错） | GBK 排在 GB18030 之前，生僻字被解成另一个合法汉字 | 兜底顺序必须是 `gb18030 → gbk → gb2312 → big5` |
| UTF-8 文件被标成 `utf-8-sig` | BOM 检测用了"试着 decode"而不是"看字节前缀" | 用 `_match_bom` 按字节前缀匹配 |
| 随机二进制被"成功"解成乱码汉字 | `utf-16` 无 BOM 时按本机字节序解码且不报错 | BOM 必须字节级判定；严格 UTF-8 必须排在探测器之前 |
| `DocumentParseError: PDF 中没有可提取的文本（可能是扫描件，需要 OCR）` | 扫描件 PDF 页对象里只有图像 | 这不是 bug，是明确的错误。需要 OCR（roadmap） |
| `DocumentEmptyError: 文档解析后没有有效文本` | 全空白 txt / 只有表头的 CSV / `[]` 的 JSON | 检查 `_normalize` 后是否为空 |
| 块边界从句中砍断、不报错 | `separators` 非末位出现空串 | `_validate_separators` 会拦下；改配置别改校验 |
| 200 行短条款被切成 200 个 13 字小块 | 把伪标题当成了切分边界 | 只标注不切分（`_heading_ranges`） |
| 父块像复读（同一句出现两遍） | 父块用子块文本拼接，而相邻子块有 overlap | 按区间回原文取（`_fill_parent`） |
| `AssertionError: chunk index 不连续` | 切分逻辑被改坏，或有块被过滤掉没重建索引 | 检查 `_merge_fragments` / `_split_section` 的过滤位置 |
| `csv.Error: Could not determine delimiter` | 单列 CSV / 只有一行 | `_csv_delimiter` 已经退回 `","`，不该再抛；检查是否绕过它 |
| CSV 每一行都成了"标题"，`section_path` 是垃圾 | 伪标题判定没排除 `" | "` | 加 `NATURAL_LANGUAGE_ROW_MARKERS` |
