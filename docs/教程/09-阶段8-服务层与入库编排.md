# 阶段 8：服务层与入库编排

> **本阶段目标**：把「写三处（MySQL / 向量库 / BM25）并保证一致」这件事收进 `services/`，
> 并且让**失败可见**——解析失败要留下一条 `FAILED` 记录，而不是一个说不清原因的 alert。
> **预计耗时**：120 分钟
> **前置阶段**：阶段 7
> **本阶段产出**：`services/`（7 个文件）+ `container.py`（装配入口唯一）

## 0. 为什么先做这一步

因为阶段 9 的路由**必须是薄薄一层**。如果业务逻辑还散在路由函数里，那么
「上传文档」这条路径上的每一次报错都要穿过 HTTP 层才能被理解——
你会分不清「是路由参数错了」还是「是切分器炸了」还是「是向量库写失败了」。

这一层要解决的三个问题，每一个都是**阶段 9 之前必须先钉死的**：

1. **一次入库到底要写哪几处、按什么顺序写**。写三处就有三种可能的中间状态，
   而中间状态是 bug 的温床。顺序定错了，最坏结果是「列表显示成功、但搜不到」。
2. **失败要怎么被看见**。`document.status` 有 `UPLOADED / PARSING / CHUNKING /
   EMBEDDING / READY / FAILED` 六个状态，就是为了让失败**定格在某个具体阶段**上。
3. **一个请求要用到哪些对象、什么时候造、什么时候丢**。这是 `container.py` 的全部职责。

而且这一层是本项目**事务边界**的落点：

> `services/` 决定「什么时候 commit」，`api/` 只负责「请求结束一定 close session」。

`api/deps.py` 的注释把这条规矩写得很清楚（阶段 9 会细讲）：

```
4. **不在这里 commit**。事务边界属于 service 层（一次问答要"写消息 + 写引用 + 写 trace"
   要么全成要么全败），依赖只负责"一定关闭"。
```

---

## 1. 要解决的问题

不做这一步，或者做错顺序，你会遇到的具体失败现象：

| 现象 | 真实原因 |
| --- | --- |
| 上传失败后列表里什么都没有，用户只看到一个 alert | 全流程挤在一个事务里，异常一抛全回滚，失败**不可见** |
| 文档列表显示 `READY`，但搜不到任何切片 | 先置 `READY` 再写向量库/BM25；写完失败也不回改状态 |
| 删掉文档后「检索还能搜到它的正文」 | 只软删了 DB 行，没清向量库/BM25（或清了但顺序反了） |
| 服务重启后，「`PAYLOAD_TOO_LARGE` 这种精确关键词」查不到了 | BM25 是内存索引，**启动时没重建** → 静默降级 |
| `/health` 报 `embedding_mode=local`，实际跑的是哈希 | 没在启动时预热，降级直到第一次上传才暴露 |
| 用户 A 的检索用了用户 B 的数据库会话 | 把带 session 的 service 实例做成了单例（`build_request_services` 被复用） |
| 并发提问时 `message_count` 比实际消息数少 | 用 Python 线程锁保护「读计数 → 加一 → 写回」，跨进程失效 |
| 一次问答的 trace 在 `/obs` 里一条都没有，但接口全 200 | `persist` 只 `flush` 没 `commit`，谁都没提交 |
| 一个 KB 有两万切片时上传 OOM | 重建 BM25 时一次性 `all()` 把整库对象读进内存 |

倒数第三条是"接口正常但功能缺失"的典型：**没有任何报错，只是数据不见了**。

### 2.2 关键代码 1：分层的硬规矩

这一层的两条规矩没有例外，**唯一的例外自己写明了理由**：

| 层 | 禁止出现 | 为什么 |
| --- | --- | --- |
| `api/` | `select()` / `session.add()` 等 SQLAlchemy 查询 | 业务规则写进路由后，脚本/后台任务/单测全部无法复用；而且路由里没有事务边界的概念 |
| `services/` | `HTTPException` / `Request` / `status_code` | service 要能被 CLI、后台线程、pytest 直接调用（阶段 12 的 204 个用例有一大半就是直接调 service） |

例外只有一个：`api/routes/observability.py` 里的纯只读聚合查询。
该文件 docstring 第 1 条就是给自己写的"为什么可以破例"：

```python
# backend/src/knowflow/api/routes/observability.py L10-L14
1. **本文件里有 `select()`，这是刻意的例外**（见 `api/__init__.py`）。
   这里的查询是**纯只读聚合**：没有业务规则、不改状态、被复用的可能性为零
   （只有面板会用"最近 N 小时的 trace 列表"）。为它建一个 service，
   只会多一层什么都不做的转发。`observability/metrics.py` 已经把重活都做完了，
   本文件只负责"过滤条件 + 分页 + 串起来"。
```

**"规则 + 一个写清了理由的例外"比"绝对没有例外"更可信**：前者说明规矩是被人真正
使用过的（用着用着发现了一处别扭，于是显式讨论、显式记录），而不是一句口号。

还有一个**反向**的例子：检索层不该 import SQLAlchemy，所以它在 `retrieval/types.py` 里
只声明一个 Protocol，由 `services/chunks.py` 实现并注入：

```python
# backend/src/knowflow/services/chunks.py L1-L7
"""切片访问助手 + `ChunkEnricher` 的 SQL 实现。

**为什么需要 `ChunkEnricher` 这一层**：检索层（`retrieval/`）不该 import
SQLAlchemy —— 一旦 import，它的单测就必须起数据库，跑得慢且脆。
所以检索层定义一个 Protocol，由这里实现并注入。这是**依赖倒置**的一个实际收益，
不是为了架构图好看。
"""
```

这就是"分层不是为了画图"的具体形态：`retrieval/` 的单测因此可以**完全离线**跑，
它是 E1.5 那 204 个用例 4 秒跑完的原因之一。

### 2.3 关键代码 2：入库为什么必须拆成两个事务

这是本阶段最重要的一个设计决定。先看服务自己的说明：

```python
# backend/src/knowflow/services/document.py L1-L17（模块 docstring）
"""文档服务：上传入库、列表、删除、切片查看。

**入库分两个事务，这是刻意的**：

    事务 1：保存原文件 + 建 documents 行（status=UPLOADED）→ 立即 commit
    事务 2：解析 → 切分 → 向量化 → 写向量库 → 写 chunks → 写 BM25 → 置 READY

为什么要拆？因为 `vector_id = "{doc_id}:{index}"` 需要先有 `doc_id`。
更重要的是**失败可见性**：解析失败时，事务 1 已经落地，
用户可以刷新列表看到那条 `FAILED` 记录和具体错误原因；
如果全在一个事务里回滚，用户只会看到一个"上传失败"的 alert，
既不知道为什么，也看不到自己传过什么。
"""
```

对应代码（事务 1 与事务 2 的分界就在 `self.session.commit()` 那一行）：

```python
# backend/src/knowflow/services/document.py L137-L173（ingest_upload，节选）
        # ---- 事务 1：原文件 + 文档行（让失败可见）----
        path = self._store_file(data=data, sha256=sha256, ext=ext)
        doc = Document(
            kb_id=kb_id,
            filename=filename,
            ext=ext,
            size_bytes=len(data),
            sha256=sha256,
            storage_path=str(path.relative_to(self.settings.data_dir)).replace("\\", "/"),
            status=DOC_STATUS_UPLOADED,
        )
        self.session.add(doc)
        self.session.commit()          # ← 事务 1 在这里结束，doc.id 已经确定
        doc_id = doc.id
        logger.info("document.uploaded", doc_id=doc_id, kb_id=kb_id, ext=ext, bytes=len(data))

        # ---- 事务 2：解析 → 切分 → 向量化 → 写三处 ----
        try:
            self._process(doc=doc, data=data, kb_id=kb_id, filename=filename, ext=ext)
        except KnowFlowError as exc:
            self._mark_failed(doc_id=doc_id, code=exc.code, message=exc.message)
            raise                          # ← 抛出去，让 HTTP 层回统一错误信封
        except Exception as exc:  # noqa: BLE001
            self._mark_failed(
                doc_id=doc_id, code="INTERNAL_ERROR", message=f"{type(exc).__name__}: {exc}"
            )
            raise
```

**两个事务带来了两个具体收益，缺一不可**：

1. **`doc_id` 先有**：`vector_id = f"{doc_id}:{chunk_index}"`（阶段 2 定的规则）。
   向量 id 必须与 MySQL 的 `chunks.vector_id` 逐字一致，否则阶段 4/5 的
   "按 id 回表补权威正文"就全断。所以 `documents` 行必须**先落库拿到自增 id**。
2. **失败可见**：解析失败时事务 1 已经提交，那条记录会留在库里、
   状态是 `FAILED`、`error_code` / `error_message` 都有。
   用户刷新列表就能看到"这份文件为什么没进来"。

> **反面教材**：把两段合成一段，异常时整体回滚。用户看到的是一个纯前端 alert，
> 服务端只留一行日志——**用户与运维都拿不到"到底哪一步错了"**。
> 这是"事务原子性"被误用成"信息黑洞"的典型案例。

注意 `except KnowFlowError` 与 `except Exception` 是分开的两支：
前者是**可预期的业务错误**（编码嗅探失败、切分后为空、不支持的类型），
`code` 直接取自异常类；后者是兜底，code 固定 `INTERNAL_ERROR`。
两支都要 `raise`——**失败要记下来，但也要让调用方知道**。

### 2.4 关键代码 3：写入顺序（向量库 → chunks → BM25 → READY）

```python
# backend/src/knowflow/services/document.py L230-L284（_process，节选）
        # ---- 写向量库 ----
        items = [
            VectorItem(
                id=row.vector_id,
                vector=vectors[position],
                content=row.content,
                metadata={
                    **build_vector_metadata(...),
                    "chunk_id": row.id,
                },
            )
            for position, row in enumerate(chunk_rows)
        ]
        written = self.vector_store.upsert(kb_id=kb_id, items=items)
        if written != len(items):
            # 不静默放过：向量少写了会让"检索不到"变成悬案
            logger.warning(
                "document.vector_upsert_mismatch",
                doc_id=doc.id, expected=len(items), written=written,
            )

        # ---- 写 BM25 ----
        self.bm25.add_chunks(kb_id, [to_bm25_payload(...) for ...])

        # ---- 置 READY ----
        doc.chunk_count = len(chunk_rows)
        doc.token_count = prepared.total_tokens
        doc.char_count = prepared.total_chars
        doc.ingest_ms = int((time.perf_counter() - started) * 1000)
        doc.error_code = None
        doc.error_message = None
        self._set_status(doc, DOC_STATUS_READY)
        self.session.commit()          # ← 事务 2 的唯一一次 commit
```

顺序的理由写在模块 docstring 里：

```
**事务 2 内部的写入顺序也是刻意的**（见 `ingest/pipeline.py` 的说明）：
向量库 → chunks → BM25 → 注册表置 READY。中途失败最坏是孤儿向量（可清理），
而不是"显示成功但搜不到"。
```

**为什么"孤儿向量"是可接受的、"显示成功但搜不到"不可接受**：

| 中间状态 | 用户看到 | 可恢复性 |
| --- | --- | --- |
| 向量写成功、chunks 写失败 | `status=PARSING/CHUNKING`（未 READY），列表里状态异常 | 孤儿向量可按 `doc_id` 清（阶段 4 的 `delete(doc_id=...)`） |
| chunks 写成功、向量写失败 | 同上（**状态还没置 READY**） | 重试上传即可 |
| 先置 READY、再写向量 | **列表显示 READY，但搜不到** | 用户以为成功，不会重试；只能靠 `consistent` 红点事后发现 |

第三种就是最难查的一类 bug：**状态字段在撒慌**。所以
`_set_status(doc, DOC_STATUS_READY)` 必须是这条流水线的**最后一步**，
`self.session.commit()` 紧随其后。

顺带注意 `written != len(items)` 那一段：**写入条数不符也要打 warning**。
两个后端（Chroma / 内存）理论上都返回写入条数，但"少写了一部分"这种事
一旦静默，就会变成下一阶段的"检索莫名少召回"。

### 2.5 关键代码 4：`_mark_failed` 为什么要 rollback 后再取对象

```python
# backend/src/knowflow/services/document.py L290-L305
    def _mark_failed(self, *, doc_id: int, code: str, message: str) -> None:
        """把失败写进库并提交。**必须用新的会话状态**：
        上层事务已经因为异常处于不可用状态，直接改当前 session 上的对象不会落库。
        """
        try:
            self.session.rollback()                     # ← 先把会话拉回可用状态
            doc = self.session.get(Document, doc_id)    # ← 重新取（身份映射已失效）
            if doc is None:
                return
            doc.status = DOC_STATUS_FAILED
            doc.error_code = code
            doc.error_message = message[:1000]
            self.session.commit()
        except Exception as exc:  # noqa: BLE001 - 记录失败本身失败时只能记日志
            logger.error("document.mark_failed_error", doc_id=doc_id, error=str(exc)[:200])
            self.session.rollback()
```

三个细节都不能省：

1. **`rollback()` 必须在前**。`_process` 抛异常后，这个 session 处于
   "事务已失败"状态；此时任何 `flush()/commit()` 都会报
   `PendingRollbackError`——**连"记录失败"这个动作本身都会失败**。
2. **必须重新 `get`**。`rollback()` 会把 session 里的对象**过期**（expire），
   紧接着 `get` 会重新发一条 SELECT；如果拿的是外部传进来的 `doc` 引用，
   读它的属性会触发一次意料之外的隐式加载，甚至在会话不可用时直接抛错。
   `doc_id` 是值、`doc` 是引用，**跨事务传值不传引用**。
3. **记录失败本身也要被保护**。`except` 里再 `rollback()` 一次，
   保证这个 session 最终回到可用状态，不会污染后续请求。

> 这一段是整个"失败可见"设计的最后一环：`ingest_upload` 已经把
> `doc_id` 拿在手里了，所以哪怕解析炸得再离谱，`_mark_failed` 也一定能写进去。

### 2.6 关键代码 5：三方一致性与 `consistent` 字段

写入端写了三处（MySQL `chunks`、Chroma、BM25），读取端就必须有一个地方
**把三者的条数放在一起比一比**。这就是 `GET /kbs/{id}/stats`：

```python
# backend/src/knowflow/services/knowledge_base.py L154-L198（stats，节选）
    def stats(self, kb_id: int) -> dict[str, Any]:
        """`/kbs/{id}/stats`：**核心是 `consistent`**。

        `chunk_count != vector_count` 意味着向量库与 MySQL 不一致
        （写入中断、手动删过库、索引重建失败）。把这个布尔量暴露到前端，
        是为了让"静默不一致"变成"界面上一个红点"。
        """
        kb = self.get(kb_id)
        ...
        chunk_count = self._chunk_counts([kb_id]).get(kb_id, 0)
        ...
        vector_count = self.vector_store.count(kb_id=kb_id)
        bm25_count = self.bm25.doc_count_of(kb_id)

        return {
            "kb_id": kb_id,
            "doc_count": sum(status_counts.values()),
            "ready_doc_count": status_counts.get(DOC_STATUS_READY, 0),
            "status_counts": status_counts,
            "chunk_count": chunk_count,
            "vector_count": vector_count,
            "bm25_doc_count": bm25_count,
            "total_chars": int(totals[0] or 0),
            "total_tokens": int(totals[1] or 0),
            # 三者一致才算健康。任何一个不等都要让运维看见。
            "consistent": chunk_count == vector_count == bm25_count,
            "embedding_provider": kb.embedding_provider,
            "embedding_model": kb.embedding_model,
            "embedding_dim": kb.embedding_dim,
        }
```

**为什么是 `a == b == c` 而不是两个布尔**：Chroma 与 BM25 的条数各自都可能
与 MySQL 不一致（例如清向量失败但清了 BM25），链式比较一次就能表达
"三者完全一致"，前端也只需要一个红点。

> ⚠ 注意契约文档 5.2 写的是 `consistent = chunk_count == vector_count`，
> 而**实现是三路比较**（更严）。这属于"实现比文档更严格"，不是不一致——
> 阶段 3 的教程里也有同样的措辞习惯：**能变严的地方就变严，但要写下来**。

E5/E6 的真实数字说明这个设计是有效且被验证过的：

```
[4] 一致性校验：MySQL chunks vs 向量库 vs BM25
      chunk_count        = 34
      vector_count       = 34
      bm25_doc_count     = 34
      consistent         = True
  [PASS] 三者一致（consistent）
```

其中 `34` 这个数字来自 6 份样例文档（3 篇 md + 1 个 csv + 1 个 json + …），
E5 还给了每份文档的切片数与入库耗时（`1.2~11 s`，CPU，首份含模型加载）。

### 2.7 关键代码 6：删除文档——先清外部索引，再软删行

```python
# backend/src/knowflow/services/document.py L393-L425（delete_document，节选）
    def delete_document(self, doc_id: int) -> dict[str, Any]:
        """软删文档 + 物理清向量 + 物理清 chunks + 重建该 KB 的 BM25。

        **顺序**：先清外部索引（向量、BM25），再软删行。
        反过来的话，清索引失败就会留下"删不掉的孤儿向量"。

        BM25 直接整库重建而不是按 doc_id 精确删：
        内存索引的删除要靠遍历 payload（没有反向映射表），
        而重建是 O(n) 且行为绝对可靠 —— 删除是低频操作，选可靠的那个。
        """
        doc = self.get_document(doc_id)
        kb_id = doc.kb_id

        removed_vectors = 0
        try:
            removed_vectors = self.vector_store.delete(kb_id=kb_id, doc_id=doc_id)
        except Exception as exc:  # noqa: BLE001
            logger.warning("document.vector_delete_failed", doc_id=doc_id, error=str(exc)[:200])

        removed_chunks = int(self.session.execute(
            select(func.count(Chunk.id)).where(Chunk.doc_id == doc_id)
        ).scalar() or 0)
        # chunk 行物理删：它们已经没有引用价值，留着只会让 verify_consistency 一直报差异
        self.session.execute(delete(Chunk).where(Chunk.doc_id == doc_id))

        doc.mark_deleted()
        doc.chunk_count = 0
        self.session.commit()

        self.kb_service.rebuild_bm25_for_kb(kb_id)
```

这里有**四个**都值得单独讲的取舍：

1. **先清外部索引、再软删 DB 行**。反过来的话，一旦清索引失败，
   DB 里已经看不到这个文档了，它的向量却还在库里——一堆**查不到也删不掉**的垃圾。
   同样的顺序也出现在 `KBService.delete`（先 `vector_store.reset` + `bm25.drop_kb`，
   最后 `mark_deleted`），理由完全一样。
2. **向量删失败只记 warning，不中断**。用户视角的"删除"是 DB 软删：
   如果因为向量库抖动就整个失败，用户会觉得"删不掉"。
   残留向量由 `scripts/verify_consistency.py` 报告并清理——
   **把不可恢复的失败降级成"可被巡检发现的不一致"**。

   > ⚠ **诚实标注**：上面这句是**源码 docstring 的原话**（`services/knowledge_base.py` L294-L295），
   > 但 `backend/scripts/verify_consistency.py` **不在当前工作区**——它和 README §0
   > 提到的那些测试文件属于同一类"被引用但不在本工作区"的东西。
   > 所以"残留向量会被巡检发现"这条**在本工作区无法执行验证**；
   > 能验证的是 `consistent` 字段本身（本阶段验证 1/2）。
3. **chunk 行是物理删，文档行是软删**。`chunks` 没有历史价值，
   留着只会让一致性校验永远报差异；而 `documents` 行要保留（用户要能看到"我删过什么"）。
   这是"软删"这个词在本项目里的**具体含义分界线**。
4. **BM25 整库重建而不是精确删**。内存索引没有 `doc_id → 文档` 的反向映射表，
   精确删要遍历所有 payload；而重建是 O(n) 且行为绝对可靠。
   **删除是低频操作，选可靠的那个**。

E6 第 14 项验证了这条路径（真实输出）：

```
[14] 删除文档：向量与 BM25 是否同步清理
      删除 考勤与休假管理办法.md（7 切片）
      删除结果: {'doc_id': 6, 'removed_vectors': 7, 'removed_chunks': 7}
      chunk=34→27 vector=34→27 bm25=34→27
  [PASS] 删除后仍保持一致  → chunk=27 vec=27 bm25=27
```

**"删除后仍保持一致"是这条设计的验收标准**，而不是"删除接口返回 204"。

### 2.8 关键代码 7：container.py——唯一装配入口

```python
# backend/src/knowflow/container.py L1-L19（模块 docstring）
"""依赖容器：**全项目唯一的装配入口**。

**为什么必须有这一层**（面试常问）：

1. **启动即失败**：所有重组件（配置校验、数据库连通、向量库目录、embedding 模型）
   在 `build_container()` 里一次性初始化。出问题进程直接起不来，
   而不是"服务起来了，第一个请求才 500" —— 后者在容器化环境里最难查。
2. **装配入口唯一**：全项目只有这里 `new` 向量库/模型/图。
   如果散落在各处，测试里就没法替换成假实现，也没人能说清"到底装了些什么"。
3. **请求级隔离**：`build_request_services(session)` 为每个请求组装一套
   带 session 的服务（检索器、工具、图运行器）。
   **每次请求重建而不是共享一个带 session 的实例** —— 共享就会串号，
   这是"用户 A 的检索用了用户 B 的数据库会话"这类事故的根源。
   代价是每次请求多几毫秒的对象构造，换来的是不可能出错。

生命周期：
    build_container()          进程启动一次（lifespan）
      └─ build_request_services()  每个请求一次（api/deps.py）
"""
```

**"每请求重建"这条纪律的代价与收益要能算清楚**：收益是
"不可能出错"（结构上不存在共享 session 的可能），代价是每个请求多造
几个 dataclass 对象（几毫秒，且没有 IO）。对一个检索一次要几十毫秒的系统，
这笔账毫无疑问是赚的。

`RequestServices` 里有一个字段值得单独看——它不是服务，是**本次请求的 trace 持有者**：

### 2.9 关键代码 8：启动时预热模型 + 重建 BM25

`build_container()` 里有两件"看起来像性能优化、其实是正确性"的事：

### 2.10 关键代码 9：并发安全——`SELECT FOR UPDATE` 而不是线程锁

```python
# backend/src/knowflow/agent/memory.py L114-L135
def append_message(
    session: Session,
    *,
    conversation_id: int,
    role: str,
    content: str,
    **fields: Any,
) -> Message:
    """写入一条消息并原子地自增会话计数。

    `with_for_update()` 锁住会话行 —— 同一会话的并发写入会串行化，
    保证 `message_count` 与实际条数一致。
    """
    conversation = session.get(Conversation, conversation_id, with_for_update=True)
    if conversation is None:
        raise ValueError(f"会话 {conversation_id} 不存在")

    message = Message(conversation_id=conversation_id, role=role, content=content, **fields)
    session.add(message)
    conversation.message_count = (conversation.message_count or 0) + 1
    session.flush()
    return message
```

它上面的模块注释把"为什么不用线程锁"写全了：

```
**为什么用 `with_for_update()` 而不是 Python 的 `threading.Lock`**：
...
`SELECT ... FOR UPDATE` 把并发控制交给数据库，跨进程也正确。
```

三条理由，按重要性排序：

1. **跨进程正确**。uvicorn 可以起多 worker，`gunicorn -w 4` 更常见。
   线程锁只保护一个进程，"同一会话并发写入"照样能把计数写错。
2. **锁的粒度天然正确**。`FOR UPDATE` 锁的是**这一行会话**，
   不同会话之间完全不互相阻塞；用一把全局线程锁会把所有会话串起来。
3. **不需要额外的生命周期管理**。锁随事务结束自动释放；
   自己维护的锁在异常路径上漏 `release()` 就是死锁。

代价是"多一次带锁的 SELECT"——但这本来就是 `session.get` 那一跳，
等于**零额外成本**。

> ⚠ 已知边界（E11 的诚实清单）：本项目**没有做过并发压测**，
> 上面这些是"设计上正确"，不是"实测吞吐量"。

### 2.11 关键代码 10：可观测的桥接——降级但不完全静默

`services/obs_bridge.py` 是本层唯一"允许吞异常"的地方，但它把边界划得很清楚：

```python
# backend/src/knowflow/services/obs_bridge.py L1-L13（模块 docstring）
"""可观测模块的桥接层。

**为什么需要这一层**：`observability/` 是横切关注点，业务代码不应该因为它
「没被装载 / 版本不匹配 / 导入时报错」就跑不起来。所以这里做一次
防御性导入，对外暴露稳定的名字：

- 正常情况：转发到真实实现；
- 任何异常：退化成 no-op（埋点丢失，但业务照常）。

这条规则和"降级可以，静默不行"并不冲突 —— 这里的降级会在首次失败时
打一条 warning 日志，而不是完全静默。区别在于：**丢埋点不影响用户拿到答案**，
而丢向量化会让答案质量崩掉，两者不该同样处理。
"""
```

落库出口只有一个，`commit()` 就在那里：

```python
# backend/src/knowflow/services/obs_bridge.py L108-L134（safe_persist，节选）
    """落库 trace。**任何异常都吞掉**：可观测失败不该让一次成功的问答变成 500。

    **这里负责 commit**（真实实现的 `persist` 只 flush，事务边界交给调用方）。
    为什么把 commit 放在这一层而不是每个调用点：调用点有 4 处（非流式成功/失败、
    流式成功/落库失败），任何一处忘了 commit 都会变成
    "接口一切正常、但 /obs 里一条 trace 都没有" —— 一个静默丢失埋点的 bug。
    放在唯一的出口上，这类错误在结构上就不可能发生。
    """
    if recorder is None or not OBSERVABILITY_AVAILABLE:
        return None
    try:
        trace_id = persist(recorder, session, ...)
        session.commit()
        return trace_id
    except Exception as exc:  # noqa: BLE001
        logger.warning("observability.persist_failed", error=f"{type(exc).__name__}: {exc}"[:200])
        try:
            session.rollback()
        except Exception:  # noqa: BLE001
            pass
        return None
```

**"4 个调用点"这个数字本身就是要写进文档的**：它说明"放在调用点各自 commit"
的方案有 4 次犯错机会，而放在唯一出口只有 0 次。
阶段 11 会把 `flush` / `commit` 的分工再讲一遍。

### 2.12 为什么 `build_request_services` 不做缓存

有人会想："每次请求都重建检索器、工具、图，也太浪费了吧？"
答案在 `container.py` 的 docstring 第 3 条已经给了，但这里要补一个**更硬的**理由：

| 方案 | 后果 |
| --- | --- |
| 缓存 `RequestServices`（带 session） | 请求 A 的 session 被请求 B 使用 → 数据串号、连接永不归还 |
| 缓存"不带 session 的部分"（模型/向量库/BM25） | ✅ 这正是 `Container` 做的事 |
| 每请求重建全部 | ✅ 本项目选的：多几毫秒，但结构上不可能错 |

也就是说，**缓存边界与生命周期边界必须重合**：

- `Container`：进程级（模型、向量库客户端、BM25 索引、engine）→ 启动建一次；
- `RequestServices`：请求级（session、检索器、图运行器、`recorder_box`）→ 每请求建一次。

`build_request_services` 里那个 `chat_service_placeholder` 字典是个有趣的小技巧，
值得留意（它解决的是"工具要回调 chat_service、但 chat_service 又需要工具"的循环）：

```python
# backend/src/knowflow/container.py L172-L186（节选）
        chat_service_placeholder: dict[str, ChatService] = {}

        def _kb_stats() -> dict[str, Any]:
            return chat_service_placeholder["svc"].kb_stats_for_tool(None)

        def _list_documents(keyword: str | None) -> list[dict[str, Any]]:
            return chat_service_placeholder["svc"].list_documents_for_tool(
                kb_id=None, keyword=keyword
            )

        tool_registry = ToolRegistry(
            retriever=retriever, kb_stats=_kb_stats, list_documents=_list_documents,
        )
        ...
        chat_service_placeholder["svc"] = chat_service
```

**用闭包延迟绑定而不是 `setattr` 或"先赋 None 再改"**：后者在类型检查下
是 `Optional[ChatService]`，每个调用点都要 `assert ... is not None`；
闭包 + 一个 cell 让类型始终是 `ChatService`，代价是 3 行。

### 验证 4：`append_message` 的加锁语义（不连数据库也能看出来）

```powershell
cd D:\Projects\pythonProjects\knowflow\backend

```

**预期输出**：

```
用了 with_for_update: True
用了 threading.Lock: False
```

**判断标准**：第一行必须 `True`、第二行必须 `False`。
如果第二行变成 `True`，说明有人加了进程内锁——**它能过单测，但在多 worker 下是错的**。

## 4. 常见错误

| 错误信息 / 现象 | 原因 | 解决 |
| --- | --- | --- |
| 上传失败后列表里空无一物 | 入库只有一个事务，异常全回滚 | 拆两段：先 commit `UPLOADED` 行，再进事务 2 |
| `PendingRollbackError`（在 `_mark_failed` 里） | 事务已失败就改动对象并 commit | 先 `session.rollback()`，再 `session.get(Document, doc_id)` 重新取 |
| 失败记录写不进库 | 跨事务复用了旧的对象引用 | 跨事务**传值（`doc_id`）不传引用（`doc`）** |
| 列表显示 `READY` 但搜不到 | 先置 `READY` 再写向量/BM25 | 置 `READY` 必须是流水线最后一步，紧随 `commit()` |
| 删除后仍能检索到正文 | 只软删了 DB 行，没清向量库/BM25 | 先清外部索引再软删；向量删失败也要继续并记 warning |
| 重启后精确关键词查不到，日志里什么都没有 | BM25 内存索引没重建（**静默降级**） | 启动时 `rebuild_bm25_index()`；`/health` 报 `bm25_doc_count` |
| `/health` 一直报 `local`，第一次上传才暴露降级 | 本地模型惰性加载、启动没预热 | `build_container` 里 `warmup_embedder()`（代价 5~8 秒） |
| 两个用户的检索结果互相串 | 复用了一个带 session 的 service 实例 | `build_request_services(session)` **每请求重建** |
| `messages` 插不进去（MySQL 报外键错误） | `messages.conversation_id` 有外键，造数据必须先建 `users` + `conversations` | SQL 造数据时按 `users → conversations → messages` 顺序插；用 SQLite 内存库测则无此限制 |
| 并发提问后 `message_count` 比实际条数少 | 用 Python 线程锁保护"读计数→加一"，多 worker 下失效 | `session.get(Conversation, id, with_for_update=True)` |
| 接口全 200，但 `/obs` 里一条 trace 都没有 | `persist` 只 `flush`、**没人 commit** | commit 放在唯一出口 `obs_bridge.safe_persist` |
| 一次上传后 `consistent=False` | 某个外部索引写失败被吞掉了 | 看 `/kbs/{id}/stats` 的哪两个数不等（向量少 = 写入中断；BM25 少 = 重建失败），再手工清残留（`scripts/verify_consistency.py` 在本工作区不存在，见 2.7 节的诚实标注） |
| 服务里出现 `HTTPException` / 路由里出现 `select()` | 分层被打破 | 业务异常用 `core/exceptions.py` 的 `KnowFlowError` 子类；查询放进 service |
| 一个 KB 有几万切片时重建 BM25 时内存爆掉 | 一次性 `all()` 读全表 | `iter_kb_chunks` + `yield_per(batch_size)` 分批 |
