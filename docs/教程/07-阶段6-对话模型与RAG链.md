# 阶段 6：对话模型与 RAG 链

> **本阶段目标**：定义一个**供应商无关**的 `ChatModel` 协议，加一个**离线也能真实触发每条分支**的 Mock，再用 Prompt 把答案钉死在 `[n]` 编号引用上。
> **预计耗时**：90 分钟
> **前置阶段**：阶段 5（它的 `retrieval/rerank.py` 反过来 `import` 本阶段的 `llm/`，见 06 §0）
> **本阶段产出**：`llm/` 八个模块（1,393 行）+ 6 个角色的离线 Mock + 全部 Prompt 模板

## 0. 为什么先做这一步

因为**阶段 7 的每一个节点都是"调一次模型 + 解析 JSON"**。协议、解析器、
Prompt 三件事没稳定下来之前，写 Agent 图只是在沙滩上盖房子：
`grade` 判得对不对、`reflect` 能不能发现缺引用、`rewrite` 有没有真的改写，
**全部依赖本阶段这三个东西**。所以顺序必须是：**先让"一次模型调用"可靠，再编排多次调用。**

第二个理由：**离线 Mock 不是"凑合能用"，它有三条硬需求**（写在 `llm/mock.py` 开头）：

| 需求 | 具体含义 |
| --- | --- |
| **CI 零成本** | 测试每次提交都跑，不能花钱、不能依赖外网 |
| **clone 下来 30 秒能看到完整效果** | 面试官/评审者不会去申请 API Key |
| **把"模型质量"与"工程质量"解耦** | 链路出错时能立刻排除"是不是模型抽风" |

而它最关键的一个设计是：**Mock 会按 system prompt 扮演 6 种角色，返回格式合法的 JSON**。
为什么这一点如此重要——

> 这样离线模式下 LangGraph 的**每一条条件边都能被真实触发**，
> 测试才能覆盖"grade 判定不相关 → 走 rewrite 分支"这类路径。
> **用一个永远返回固定文本的 mock，图的分支就等于没测。**

第三个理由：**同步优先（sync-first）**。本项目的两个重组件（本地 BGE-M3 推理、
Chroma 查询）都是同步阻塞 API。如果对话模型单独走 async，就会出现
"async 路由里 `await` 模型，但检索却同步阻塞事件循环"的混合状态——
**反而更容易卡死**。所以选择：内部全同步，在边界处交给线程池。

第四个理由：**Prompt 是产品逻辑**。改一句话就可能让幻觉率翻倍，
所以它们必须集中在一处、能被 review、能被 diff、能被测试引用
（测试可以断言"防幻觉那句话必须还在"）。散落各处的 Prompt 最终会互相矛盾。

---

## 1. 要解决的问题

不做这一步，你会遇到的具体失败现象：

| 现象 | 真实原因 |
| --- | --- |
| 换一家模型供应商要改十几个业务文件 | 业务代码直接 `import openai`，没有协议层 |
| 模型多说了半句话，整个问答 500 | 直接 `json.loads(模型输出)`，没有逐级降级 |
| 流式请求的成本统计**永远是 0** | 没开 `stream_usage=True`（OpenAI 协议要求显式声明） |
| 非流式有 token 数、流式没有 | 只读了 `usage_metadata`，没兜底读 `response_metadata["token_usage"]` |
| 正常答案被标成"拒答"，拒答率虚高 | `detect_refusal` 只按关键词判，没有长度条件 |
| 前端一帧里收到全部 token，看不出在流式 | Mock 不 `sleep`，所有块在同一时刻产出 |
| 累计 token 少了后面几轮 | 把 usage 当"覆盖"而不是"合并"（generate 会被 reflect 打回重试） |
| 离线模式下图的分支一条都测不到 | Mock 永远返回同一段文本，`grade` 永远"相关" |
| 排障时不知道"模型到底看到了什么" | Prompt 拼装逻辑散落各处，没有 `messages_to_text` 这类可记录入口 |
| 配了 Key 但模型挂了，用户拿到"看起来正常"的烂答案 | 对话模型**偷偷降级**成了离线抽取式（本项目刻意不允许，见 §2.13） |

### 2.2 关键代码 1：为什么是"同步优先"

```python
# backend/src/knowflow/llm/base.py L1-L21（节选）
"""对话模型的统一抽象。

**为什么是同步优先（sync-first）**：本项目的两个重组件 —— 本地 BGE-M3 推理与
Chroma 查询 —— 都是同步阻塞 API。如果对话模型走 async，就会出现
「async 路由里 await 模型，但检索却同步阻塞事件循环」的混合状态，
反而更容易卡死。所以选择：**内部全同步，在边界处交给线程池**
（Starlette 对同步生成器会自动用 `iterate_in_threadpool`）。

代价（诚实写在这里，面试主动说）：
- 一个流式问答会占住一个线程池线程直到回答结束，长连接多时线程是瓶颈；
- 要换 async 客户端（如 httpx.AsyncClient + async chroma）才能真正并发。

`ChatModel` 只暴露 2 个方法，让上层（RAG 链 / Agent 节点）不关心供应商：

    complete(messages) -> ChatResult          一次性拿完整回答（要用量、要判官）
    stream(messages)   -> Iterator[Chunk]     逐块拿（SSE 流式）

工具调用（tool calling）刻意**不放进这个协议**：Agent 的工具循环由
LangGraph 节点自己编排（见 `agent/`），模型层只负责"把消息变成文本"。
"""
```

**"工具调用不放进协议"这个决定要单独理解**：`ToolChatResult` 与 `ToolCall`
这些类型确实定义了（`agent/` 要用），但**协议只有 2 个方法**。
这样换供应商时，**工具协议差异被隔离在 `openai_compat.py` 一个文件里**——
离线 Mock 只需要声明"我不支持工具"（§2.6），图就能优雅降级。

### 2.3 关键代码 2：协议与四个数据类型

```python
# backend/src/knowflow/llm/base.py L128-L153
@runtime_checkable
class ChatModel(Protocol):
    """对话模型协议。`model` / `offline` 会被 `/health` 与指标读到。"""

    model: str
    offline: bool

    def complete(
        self,
        messages: Sequence[ChatMessage],
        *,
        temperature: float | None = None,
        max_tokens: int | None = None,
        stop: Sequence[str] | None = None,
    ) -> ChatResult: ...

    def stream(
        self,
        messages: Sequence[ChatMessage],
        *,
        temperature: float | None = None,
        max_tokens: int | None = None,
        stop: Sequence[str] | None = None,
    ) -> Iterator[Chunk]: ...

    def supports_tools(self) -> bool: ...
```

`model` 与 `offline` 是**数据属性**而不是方法，因为它们要进 `/health` 与 trace。
E6.3 的 `/health` 输出里 `llm_mode=offline`、`model=offline-mock` 就是从这两个属性来的。

**`Chunk` 的设计里藏着一个必须处理的事实**：

```python
# backend/src/knowflow/llm/base.py L83-L94
@dataclass(slots=True)
class Chunk:
    """流式增量块。

    `usage` 只在最后一个块里出现（OpenAI 协议里 usage 是收尾才给的），
    所以类型是可选。消费方必须处理"中间块没有 usage"这件事。
    """

    text: str = ""
    usage: ChatUsage | None = None
    finish_reason: str | None = None
```

**为什么是 `usage | None` 而不是 `usage: ChatUsage = ChatUsage()`**：
如果中间块也带一个默认的 `ChatUsage()`，消费方会"以为有值"，
于是 `usage.prompt_tokens` 读出来是 0 却不报错——**统计悄悄少算**。
写成可选，类型检查器会逼着每个消费方显式处理"这一块没有 usage"。

`ChatUsage.merge()` 是另一个容易写错的地方（**必须是累加，不能覆盖**）：

```python
# backend/src/knowflow/llm/base.py L55-L61
    def merge(self, other: ChatUsage) -> None:
        """把一次调用的用量累加进来（Agent 一轮会调多次模型）。"""
        self.prompt_tokens += other.prompt_tokens
        self.completion_tokens += other.completion_tokens
        self.llm_calls += max(other.llm_calls, 1)
        if other.model:
            self.model = other.model
```

**为什么"必须累加"**：一次 Agent 问答会调多次模型（`analyze` → `grade` →
`generate` → 可能再来一次 `generate`）。如果覆盖，E6.3 里
`usage={'prompt_tokens': 3639, 'completion_tokens': 665, 'total_tokens': 4304}`
这种完整统计就永远拿不到，成本归因直接失真。

### 2.4 关键代码 3：离线 Mock 扮演 6 种角色

```python
# backend/src/knowflow/llm/mock.py L49-L65
def _detect_role(system_text: str) -> str:
    """按 system prompt 里的特征词识别这次调用要扮演什么角色。

    依赖 prompt 文本是有意的耦合：`llm/prompts.py` 与 `llm/mock.py` 必须一起改，
    而这个耦合会**在测试里立刻暴露**（改了 prompt 关键词，mock 的 JSON 就断言失败）。
    """
    if "问答路由器" in system_text:
        return "analyze"
    if "检索质量评审员" in system_text:
        return "grade"
    if "检索查询优化器" in system_text:
        return "rewrite"
    if "答案审核员" in system_text:
        return "reflect"
    if "评测判官" in system_text:
        return "judge"
    return "answer"
```

**六个角色对应阶段 7 图里的六个位置**（这就是"每条条件边都能被触发"的实现方式）：

| 角色 | 触发它的 system prompt 特征词 | 返回的 JSON | 谁能被它触发 |
| --- | --- | --- | --- |
| `analyze` | 问答路由器 | `{"needs_retrieval": true, "queries": [...], "question_type": "factual"}` | `analyze → generate` 那条"不检索直答"的边 |
| `grade` | 检索质量评审员 | `{"items": [{"id": 1, "relevant": true, ...}]}` | `grade → rewrite` 那条"召回不足"的边 |
| `rewrite` | 检索查询优化器 | `{"queries": [...], "reason": "..."}` | `rewrite → retrieve` 回到检索 |
| `reflect` | 答案审核员 | `{"passed": false, "unsupported": [{"sentence": ...}]}` | `reflect → generate` 那条"重试"的边 |
| `judge` | 评测判官 | `{"score": 0.85, "reason": "..."}` | 阶段 10 的 faithfulness / relevance 指标 |
| `answer` | 以上都不是 | 抽取式答案 + `[n]` 引用 | `generate → END` 正常出口 |

`grade` 的判定阈值**刻意取得比线上闸门宽**（这条注释值得抄下来）：

```python
# backend/src/knowflow/llm/mock.py L147-L156（节选）
    def _grade(self, question: str, contexts: list[tuple[int, str, str]], user_text: str) -> str:
        """按查询词覆盖率判相关性。阈值取得比真实闸门略宽，让 rewrite 分支也能被触发。"""
        ...
        for rank, _source, body in contexts:
            score = coverage(question, body)
            relevant = score >= 0.4
```

**为什么 mock 的阈值要和线上不一样**：mock 存在的目的**不是复现线上判定**，
而是**让每条分支都能在测试里走到**。如果 mock 用和闸门一模一样的阈值，
它能通过的用例闸门早就通过了，`rewrite` 分支永远走不到。

⚠ **本会话实测的环境事实**（会决定你看到的输出）：当前 `core/config.py` 里
`AGENT_GRADING_ENABLED` 默认 `true`、`VECTOR_MIN_SCORE=0.60`、`KEYWORD_MIN_COVERAGE=0.40`
（第六节会看到）。如果你在自己机器上看到 `grading_skipped=True`，
那是因为候选数 ≤ 3 时 `grade` 会直接全放行（省一次模型调用，见阶段 7 §2.6）。

### 2.5 关键代码 4：Mock 的抽取式回答与"离线也不编"

```python
# backend/src/knowflow/llm/mock.py L208-L230（节选）
    def _answer(self, question: str, contexts: list[tuple[int, str, str]]) -> str:
        """抽取式回答：挑覆盖率最高的上下文块，再挑块里最相关的句子。"""
        if not contexts:
            return REFUSAL_ANSWER

        ranked: list[tuple[float, int, str, str]] = []
        for rank, source, body in contexts:
            ranked.append((coverage(question, body), rank, source, body))
        ranked.sort(key=lambda item: -item[0])

        best_score, best_rank, best_source, best_body = ranked[0]
        if best_score < _MIN_BLOCK_COVERAGE:
            return REFUSAL_ANSWER
```

`_MIN_BLOCK_COVERAGE = 0.25`（L44-L46）：

```python
# 抽取式回答的最低覆盖率门槛。低于它就拒答——保证离线模式也"不编"。
_MIN_BLOCK_COVERAGE = 0.25
_MIN_SENTENCE_SCORE = 1
```

**离线模式也有拒答底线**：如果最相关的块覆盖率都低于 0.25，
Mock 返回的是**和线上完全相同的 `REFUSAL_ANSWER` 固定话术**。
这一点让 E6 的第 [7] 项断言成立：
"**拒答用的是固定话术（说明是短路，不是模型生成的）**"——
不管是"闸门拦下"还是"模型拒答"，用户看到的是同一句话，测试才能断言。

⚠ **离线 Mock 的能力边界（必须诚实标注）**：它**只能验证链路连通性与引用格式，
不能验证生成质量**。所以每个离线答案里都会带一句 `OFFLINE_NOTICE`：

```python
# backend/src/knowflow/llm/prompts.py L322-L325
OFFLINE_NOTICE: Final[str] = (
    "（离线模式：未配置大模型 API Key，以下答案由检索结果直接抽取生成，"
    "仅用于验证链路是否连通，不代表真实生成质量。）"
)
```

而且 `/health` 会把它报出来（E6.3 第 [1] 项的真实输出）：

```
status=ok  offline=True  llm_mode=offline  embedding_mode=local
warnings=['未配置 OPENAI_API_KEY，当前为离线模式（抽取式回答）']
```

### 2.6 关键代码 5：Mock 的"假流式"与 usage 只出现一次

```python
# backend/src/knowflow/llm/mock.py L258-L281（节选）
    def stream(...) -> Iterator[Chunk]:
        """按 8 个字符一块"假装"流式，并 yield 一个收尾块带上 usage。

        刻意加一点 `sleep`：不加的话前端会在同一帧里收到所有 token，
        看起来像非流式，"流式效果"就没法验证了。
        """
        result = self.complete(messages, temperature=temperature, max_tokens=max_tokens)
        text = result.text
        step = 8
        for i in range(0, len(text), step):
            yield Chunk(text=text[i : i + step])
            time.sleep(0.012)
        yield Chunk(text="", usage=result.usage, finish_reason="stop")

    def supports_tools(self) -> bool:
        """离线模式不支持工具调用 → Agent 走"优雅降级"分支（见 `agent/graph.py`）。"""
        return False
```

三个细节都值得说：
1. **`step = 8` 个字符一块**：块大小决定"看起来像不像在打字"；
2. **`time.sleep(0.012)`**：不加 sleep 的话 32 个 token 帧会在同一毫秒内产出，
   SSE 的"流式感"完全消失（E6 的流式校验里有 `token 帧数 = 32` 这一条）；
3. **最后一个块 `text=""` 只带 `usage` 与 `finish_reason`**：
   这正是 OpenAI 协议的行为，消费方必须能处理"空文本但有 usage 的块"。

**`supports_tools()` 返回 `False` 是刻意的**（见 §0 的"优雅降级"）：
离线 Mock 不支持工具调用，于是 `retrieve` 节点会退化成"按 analyze 给出的查询逐条检索"
——**能力下降但功能完整、行为可预测**。E6.1 的检索轮数对比就是这条路径的产物：

```
mode=rag    总耗时=  317ms retrieval_rounds=1 reflect=True  tokens=1704+255
mode=agent  总耗时=  691ms retrieval_rounds=3 reflect=False tokens=5433+739
```

### 2.7 关键代码 6：Prompt 设计的三条规则

```python
# backend/src/knowflow/llm/prompts.py L1-L16（节选）
"""全部 Prompt 模板集中在这一处。

**为什么不散落在各模块**：Prompt 是这个项目的"产品逻辑"，改一句话就可能让
幻觉率翻倍。集中放置才能被 review、被 diff、被测试引用（测试会断言
"防幻觉那句必须还在"）。散落各处的 Prompt 最终会互相矛盾。

模板设计的三条规则（每条都有踩坑背景）：

1. **给编号、要求引用**：上下文用 `[1] [2]` 编号，要求模型在句末标 `[n]`。
   这样答案可溯源，也让"没依据的句子"在结构上就显眼（前端能高亮没有引用的句子）。
2. **明确"资料不足"的出口**：必须告诉模型**怎么拒答**。
   只写"不许编"是不够的——模型会退而求其次去编一个"看起来安全"的答案。
   所以给出固定话术，并让链路能识别它（`REFUSAL_MARKERS`）。
3. **把格式约束写成可解析的样子**：需要 JSON 的地方要求"只输出 JSON"，
   并给出**带字段的示例**。经验：给示例比写十行规则有效。
"""
```

### 2.8 关键代码 7：编号、出处与"资料不足"的出口

```python
# backend/src/knowflow/llm/prompts.py L48-L58
RAG_SYSTEM_PROMPT: Final[
    str
] = """你是一个严谨的企业知识库问答助手。你的唯一信息来源是用户提供的「参考资料」。

必须遵守的规则：
1. 只依据参考资料回答，**不得使用你自己的先验知识**补充任何事实。
2. 每一条事实性陈述后面必须标注来源编号，格式为 [1]、[2]（可多个： [1][3]）。
3. 如果参考资料不足以回答问题，直接回复：「知识库中没有找到与该问题相关的内容，因此我无法给出有依据的回答。建议换一种问法，或确认相关文档已经上传。」**不要猜测，不要部分编造。**
4. 如果参考资料之间互相矛盾，要指出矛盾，并分别标注来源，不要替用户做选择。
5. 回答简洁、直接，不要复述问题，不要写「根据参考资料」这类开场白。
6. 使用与提问相同的语言回答。"""
```

注意第 3 条：**拒答话术在 Prompt 里是逐字给出的，而且和 `REFUSAL_ANSWER` 常量完全一致**。
这不是重复，而是**契约**：链路靠 `REFUSAL_MARKERS` 识别拒答，
所以"模型应该说的话"和"链路认得出的话"必须是同一份文本。

上下文块带**出处描述**，这一条对引用准确率影响很大：

```python
# backend/src/knowflow/llm/prompts.py L64-L75（节选）
def format_contexts(contexts: Sequence[tuple[int, str, str]]) -> str:
    """把检索结果拼成带编号的上下文块。

    参数是 `(编号, 出处描述, 正文)` 三元组。
    出处描述会出现在模型眼前——**这一步很关键**：让模型看到
    「员工报销制度 > 差旅报销标准」这种小节路径，它能判断该引用哪一段，
    引用准确率明显高于只给正文。
    """
    blocks: list[str] = []
    for rank, source, text in contexts:
        blocks.append(f"[{rank}] （出处：{source}）\n{text.strip()}")
    return "\n\n".join(blocks)
```

`source` 是 `Candidate.source_label`（阶段 5 的 `types.py`）拼出来的三级信息：
`员工报销制度.md > 差旅报销标准 > 第3页`。E6.3 的 `/search` 输出里那三行
`[1] KnowFlow接口说明.md | ... > 问答（非流式） | score=...` 就是它。

**Self-RAG 的重试靠 `extra_instruction` 传"上一轮错在哪"**：

### 2.9 关键代码 8：`detect_refusal` 为什么要加长度条件

```python
# backend/src/knowflow/llm/prompts.py L328-L338
def detect_refusal(answer: str) -> bool:
    """判断一段回答是否属于"拒答"。

    规则：命中任一 `REFUSAL_MARKERS` 且答案很短（< 200 字）才判为拒答。
    加长度条件是因为长答案里出现"没有找到相关"可能只是在描述某个流程——
    只按关键词判会把正常答案误标成拒答，污染拒答率指标。
    """
    text = answer.strip()
    if not text or len(text) > 200:
        return False
    return any(marker in text for marker in REFUSAL_MARKERS)
```

标记表本身 + 一句提醒（**半拒答是最难判的情况**）：

```python
# backend/src/knowflow/llm/prompts.py L25-L38（节选）
# 拒答标记：链路靠它判断"模型是否说了没有依据"
# 注意：判定必须**同时**看这几个特征，单看某一句话会误判
# （例如模型答"知识库中没有提到年假，但根据差旅制度…"这种半拒答）。
REFUSAL_MARKERS: Final[tuple[str, ...]] = (
    "知识库中没有",
    "资料中没有",
    "没有找到相关",
    ...
)
```

**这个 bug 的形状值得单独记**：它**不会让任何一个功能测试失败**——
答案照样返回、引用照样有、接口照样 200。
它污染的只有一个指标：**拒答率**。而"拒答率"恰恰是用来判断
"防幻觉机制有没有生效"的那个指标。**指标被污染 = 你失去了唯一的观测手段。**

### 2.10 关键代码 9：OpenAI 兼容协议与四件麻烦事

```python

"""真实模型接入：LangChain + OpenAI 兼容协议。

**为什么走 OpenAI 兼容协议而不是某个厂商的 SDK**：换供应商只改

1. **token 用量有两种来源**：新版在 `usage_metadata`，老/第三方网关只在

4. **重试要指数退避且只重试可重试的错误**：429/5xx/超时重试，
   401/400 立刻失败（重试只是浪费用户 10 秒）。

```

### 2.11 关键代码 10：解析 JSON 的逐级降级

```python
# backend/src/knowflow/llm/parsing.py L1-L14（节选）
"""从模型输出里稳妥地抠出 JSON。

**为什么需要单独一个模块**：所有"让模型输出 JSON"的地方都会遇到同一批脏数据：

1. 包了 ```json 代码块（最常见）；

3. 中文全角标点（`“key”：`）、尾随逗号；

### 2.12 关键代码 11：token 估算 vs 真实 usage

```python
# backend/src/knowflow/llm/tokenizer.py L1-L13（节选）
"""token 估算。

**为什么需要它**：token 就是钱。但精确 tokenize 需要引入 tiktoken（还要按模型
下载词表），而本项目要支持任意 OpenAI 兼容供应商，词表不一定对得上。
所以这里做**估算**，用途是「成本量级判断 + 上下文预算控制」，
不是用来对账。真实用量从模型响应里的 `usage` 字段拿（那才是准的）。

估算规则（经验值，注释里给出依据）：
- 中文/日文/韩文汉字：约 1 token / 字（主流 BPE 词表对 CJK 通常 1~1.5 字/token，
  取 1.0 是**偏保守**（高估）的，用于预算控制更安全）；
- 其他可见字符：约 1 token / 4 字符（GPT 系列英文经验值）；
- 换行、空格也计入字符。
"""
```

```python

    cjk_count = len(_CJK_PATTERN.findall(text))
    other_count = len(text) - cjk_count

    # ceil，保证非空文本至少算 1 个 token（否则短文本会算出 0，成本统计会漏）

**"估算"与"真实"各自用在哪，必须分清**（这是面试会追问的点）：

| 用途 | 用什么 | 为什么 |
| --- | --- | --- |
| 组装上下文时的**预算控制** | `estimate_tokens`（客户端估算） | 要**发请求之前**就知道装不下，真实 usage 还没产生 |
| 成本归因 / 账单 | `usage` 字段（服务端返回） | 估算只是量级判断，**不能对账** |
| 离线 Mock 的 usage | 字符数（`len(text)`） | 没有服务端，只能给个同量级的值 |

⚠ 注意 Mock 的 usage **不是真 token 数**：`prompt_tokens = len(messages_to_text(messages))`
（字符数）、`completion_tokens = len(text)`。所以 **E6.3 里那些
`usage={'prompt_tokens': 3639, ...}` 是离线 Mock 的数字，不代表真实模型的计费**。
接上真实 Key 后这些数字会变（而且那时才第一次真正验证 `stream_usage` 有没有生效）。

### 2.13 关键代码 12：`factory` 的"刻意不对称"

```python
# backend/src/knowflow/llm/factory.py L1-L13（节选）
"""按配置构造对话模型。

**一个刻意的非对称设计**：

- **embedding 会自动降级**（`embeddings/factory.py`：本地模型加载失败 → 哈希向量），
  因为向量化失败会让整条链路完全不可用，降级至少能跑通、且 `/health` 会标记 degraded；
- **对话模型不自动降级**：配了 Key 但调用失败时**必须报错**，
  绝不偷偷换成离线抽取式回答 —— 那会让用户拿到质量极差却看起来正常的答案，
  是最糟糕的一种失败。宁可 502。

答案：**降级可以，静默不行**。凡降级必向上暴露（`/health` + 响应里的 `offline` 字段）。
"""
```

**"embedding 降级、chat 不降级"这个不对称，是本项目最值得讲的一个设计取舍**：

| | 失败时的选择 | 理由 |
| --- | --- | --- |
| 向量化 | **降级**到 hash | 向量化挂了 = 整条链路不可用；降级后检索质量下降但**功能在**，而且 `status.mode` 会显示 `hash(fallback:load_failed)` |
| 对话模型 | **报错**（502） | 降级成抽取式回答 = 用户拿到"看起来正常但质量极差"的答案，**这比报错更糟** |

判据是同一句：**降级可以，静默不行**。区别在于"降级的代价会不会被用户误认为正常输出"。

## 4. 常见错误

| 错误信息 | 原因 | 解决 |
| --- | --- | --- |
| `json.decoder.JSONDecodeError` 直接冒到 HTTP 层（500） | 直接 `json.loads(模型输出)` | 用 `llm/parsing.extract_json_object`，失败走降级分支 |
| 流式请求的成本统计**永远是 0** | 没开 `stream_usage=True` | `ChatOpenAI(..., stream_usage=True)` |
| 非流式有 token、流式没有（或反过来） | 只读 `usage_metadata`，没兜底 `response_metadata["token_usage"]` | 两个来源都读，且用 `if usage.total_tokens == 0` 防重复计 |
| token 数是真实值的两倍 | 两个来源都**累加**了 | 新版优先，只在为 0 时兜底 |
| 累计 usage 少了后面几轮 | 用"覆盖"语义写 state 的 `usage` | 用 `ChatUsage.merge()` / `merge_usage` reducer（阶段 7） |
| 成本统计算出来是负数或乱跳 | 把 `estimate_tokens` 当真实 usage 用于对账 | 估算只用于预算控制，计费用响应里的 `usage` |
| 拒答率虚高（正常答案被标成拒答） | `detect_refusal` 没有长度条件 | 命中标记 **且** 长度 < 200 字才算拒答 |
| 401 也重试 3 次，用户白等 3.5 秒 | 重试策略没区分可重试状态码 | `_RETRYABLE_STATUS = {408,409,425,429,5xx}`，其余立刻失败 |
| 配了 Key 却拿到"离线抽取式"的答案 | 对话模型被静默降级了（**本项目刻意不允许**） | 宁可 502，也不静默降级；`offline` 必须如实上报 |
| 前端看不出在流式（一次收到全部 token） | Mock 没有 `sleep`，或服务端攒够一批才 flush | Mock 每 8 字符 `sleep(0.012)`；服务端逐块 `yield` |
| 中间块的 usage 读出来是 0 却不报错 | `Chunk.usage` 用了默认 `ChatUsage()` 而不是 `None` | 类型写成 `ChatUsage \| None`，逼消费方处理 |
| 答案里出现 `{"a": {"b": 1}}` 这种 dict 字符串 | `content` 可能是块列表（多模态/推理模型） | 统一走 `openai_compat._extract_text` |
| `ValueError: Expected ids to be a non-empty list` 之外的 Chroma 报错被吞 | 上层的异常类型不匹配（阶段 5 的 `_failure_reason` 那个坑） | 统一用项目自己的异常类型；降级路径要有测试 |
| Mock 改了 Prompt 关键词后测试全挂 | `mock._detect_role` 依赖 prompt 特征词（**有意的耦合**） | 改 `prompts.py` 与 `mock.py` 必须同时改，测试会提醒 |
| 改了 Prompt 关键词，Mock 静默退化成 `answer` 角色 | 特征词不匹配就 `return "answer"` | 同上：两处一起改；并把角色打印进测试输出 |
