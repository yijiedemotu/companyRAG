> **本阶段目标**：把前 12 个阶段的"设计承诺"变成**可执行、可回归、零成本**的门禁——204 个离线用例、四层验证、一条 `check` 命令、三个 CI job。

## 0. 为什么先做这一步

因为**这个项目最大的风险不是"写不出来"，而是"改坏了没人知道"**。

前 11 个阶段里，每一阶段都留下过这种形态的 bug：

| 阶段 | 那个 bug 的表现 | 功能测试能不能发现 |
| --- | --- | --- |
| 5 | RRF 的 `rank` 从 0 起算（应该是 1） | ❌ 接口 200、结果"看起来合理" |
| 7 | 拒答路径仍然调用了生成模型（白花 token） | ❌ 答案照样返回 |
| 9 | **21 个端点漏鉴权**（E6.4） | ❌ 不带 token 打 `GET /kbs` 返回 **200 + 正常数据** |
| 9 | 流式 `contextvars` 跨线程崩溃（E6.5） | ❌ 204 个单测全绿也漏掉 |
| 11 | `VECTOR_MIN_SCORE=0.35` 让闸门 100% 失效（E7） | ❌ 误放行率 1.000，而接口一切正常 |

这五行是同一个教训的五种写法：**"跑通了"和"跑对了"是两件事**。
所以最后这一步不是"补点单测"，而是**按"错误能被哪一层抓到"来分层设计验证**。

第二个理由更实际：**只有测试快了，才有人愿意跑它**。

```
E1.5  204 passed, 1 warning in 4.63s
```

4.63 秒意味着"改一行代码、随手跑一遍全套"是零心理成本的。
如果它需要 3 分钟（加载 2GB 模型）或需要先起 MySQL，那它就会退化成
"发版前跑一次"，而发版前跑一次的门禁等于没有门禁。

第三：**工程化配置是"团队里唯一不能被跳过的东西"**。
`ruff` / `mypy --strict` / drift 门禁 / 鉴权审计这几条，都是"人可能会忘、但机器不会忘"的检查。

| --- | --- | --- | --- |
| 单元 / 集成 | `.\tasks.ps1 test` | **204 个用例 / 4.63 秒**（E1.5） | 边界、契约、降级分支 |
| 链路冒烟 | `.\tasks.ps1 smoke` | **41 项**（E6） | 入库一致性、四种检索、拒答短路 |

### 2.2 关键代码 1：测试怎么做到"全离线 + 4 秒"

核心在 `backend/tests/conftest.py` 的 `settings` fixture（L94-L106）：

```python
# backend/tests/conftest.py L94-L106
return Settings(
    _env_file=None,
    env="test",
    debug=True,
    database_url="sqlite+pysqlite:///:memory:",
    data_dir=tmp_path,
    embedding_provider="hash",
    vector_backend="memory",
    openai_api_key="",
    agent_checkpoint_backend="memory",
    jwt_secret="test-secret-0123456789abcdef01234567",
    log_level="WARNING",
)
```

这 11 行里有 5 个刻意的选择，每一个都对应一个"不做就会出事"：

| 参数 | 作用 | 不做会怎样 |
| --- | --- | --- |
| `_env_file=None` | **不读** `backend/.env` / 仓库根 `.env` | 别人本机的一份 `.env` 就能让断言飘（最典型的"在我机器上是绿的"） |
| `embedding_provider="hash"` | 用 `HashEmbedder` 而不是 BGE-M3 | 每个测试会话加载 2GB 模型 → 4 秒变 3 分钟 |
| `vector_backend="memory"` | 用 `InMemoryVectorStore` 而不是 Chroma | 要在磁盘上建/清集合，还会留下状态 |
| `database_url="sqlite+pysqlite:///:memory:"` | 内存 SQLite | 要连 MySQL、要建库、要清理 |
| `openai_api_key=""` | `is_offline=True` → `MockChatModel` | 真调外部 API：要钱、要网络、不可复现 |

**所以"204 个用例 4 秒跑完"的完整答案是**：
`MockChatModel` + `HashEmbedder` + `InMemoryVectorStore` + SQLite 内存库
——**不加载 2GB 模型、不连 MySQL、不调任何外部 API**（E1.5 原话）。
这不是"测试写得快"，而是**这四样东西在架构上就是可替换的**：
阶段 4 的 `Embedder` 协议、阶段 5 的 `VectorStore` 协议、阶段 6 的 `ChatModel` 协议，
在写它们的那一天就决定了今天测试能有多快。

### 2.3 关键代码 2：SQLite `:memory:` 必须配 `StaticPool`

这是本项目"最容易误判"的一个坑：**代码里明明调了 `create_all`，查询却说"表不存在"**。

```python
# backend/src/knowflow/db/session.py L42-L46
if _is_sqlite(url):
    kwargs["connect_args"] = {"check_same_thread": False}
    if ":memory:" in url or url.endswith("sqlite://"):
        # 内存库必须共享同一个连接，否则每次 connect 都是一个新空库
        kwargs["poolclass"] = StaticPool
```

**为什么会这样**：`:memory:` 是**进程内**的库，作用域是"那一个连接"。
SQLAlchemy 默认用连接池，于是：

1. 第一个连接 A 建表 → 表建在 A 的内存库里；
2. 第二个连接 B 来查询 → B 是**另一个全新的空库** → `no such table: users`。

**它只在第二个连接出现时才报错**，所以很容易被误判成"建表逻辑写错了"。
`StaticPool` 让所有 `connect()` 返回**同一个连接**，问题消失。

`conftest.py` 的 `db_engine` fixture 刻意**复用生产代码的
`create_engine_from_settings`**（L113-L116），而不是在测试里手写一份引擎参数——
手写一份的后果是"测试绿、生产炸"：

```python
# backend/tests/conftest.py L110-L121
@pytest.fixture
def db_engine(settings: Settings) -> Iterator[Engine]:
    """SQLite 内存引擎 + 建表。

    **复用 ``create_engine_from_settings``**：它已经处理了 ``:memory:`` 必须配 ``StaticPool``
    这件事（否则每个连接都是一个新空库，表现为"表不存在"）。
    """
    engine = create_engine_from_settings(settings)
    Base.metadata.create_all(engine)
    try:
        yield engine
    finally:
        engine.dispose()
```

### 2.4 关键代码 3：pytest 打的是 ASGI，不是服务器（这是它的盲区）

`pytest` 里打 HTTP 用的是 `httpx.ASGITransport`：**直接把请求交给 ASGI app 对象**，
不起服务器、不占端口、不走网络。好处是快；**代价是它跳过了三样东西**：

1. **真实服务器**（uvicorn 的 lifespan、真实的并发调度）；
2. **真实中间件栈**（顺序、`send` 包装）；
3. **真实的流式输出**——尤其是"同步生成器被 `iterate_in_threadpool` 分次驱动"这件事。

第 3 条就是 E6.5 那个 bug 的全部原因：

```
[error] chat.stream_failed
error="ValueError: <Token var=<ContextVar name='current_recorder' default=None>>
       was created in a different Context"
```

`docs/03` E6.5 的原话：

> **为什么这个 bug 值得记住**：它只在**流式**路径出现，而流式恰好是这个项目的主路径；
> `pytest` 用 `ASGITransport` 打请求时**不会**触发这种分次线程调度，
> 所以 204 个单测全绿也照样漏掉它 —— **只有真起 uvicorn 打一次流式接口才会暴露**。

这就是为什么 `smoke_http.py` 必须真起 uvicorn（它的模块 docstring 第一句就是这个理由）：

```python
# backend/scripts/smoke_http.py L1-L13（节选）
"""HTTP 层端到端冒烟：真起 uvicorn，真打接口，真解析 SSE。

**为什么必须有这一层**：`pytest` 打的是 ASGI（`httpx.ASGITransport`），
它跳过了真实服务器、真实端口、真实中间件栈与**真实的流式输出**。
而本项目最容易坏的地方恰好都在这一层：

- SSE 被中间件缓冲住（`BaseHTTPMiddleware` 的经典问题）；
- CORS 的 `expose_headers` 没配，前端读不到 `X-Request-ID`；
- 异常处理器没覆盖到，返回的 500 不是统一错误信封；
- 路由前缀 / 依赖注入在真实 `lifespan` 下才暴露问题。
"""
```

**一般化这条教训**：一个测试层能抓到什么，取决于它**经过了哪些真实组件**。
"204 个用例全绿"只证明"我认为会发生的事都发生了"，不证明"真实路径没有别的行为"。

### 2.5 关键代码 4：鉴权审计——安全属性也要可验证

E6.4 记录了这个项目最典型的一次"功能测试发现不了"的漏洞：

> **修复前**：39 个端点里 **21 个没有鉴权**，包括
> `GET /kbs`、`GET /kbs/{id}`、`GET /kbs/{id}/stats`、`GET /kbs/{id}/documents`、
> `GET /documents/{id}`、`GET /documents/{id}/chunks`、`POST /kbs/{id}/search`、
> `GET /eval/*`（8 个）、`GET /obs/*`（4 个）。
>
> 它们的表现是 **返回 200 + 正常业务数据**，所以任何"断言字段对不对"的功能测试都发现不了；
> **只有"不带 token 打一次"才会暴露**。

修复分两步，**第二步比第一步重要**。

第一步是"路由级默认需要、例外公开"（`api/router.py` L55-L58、L80-L92）：

```python
# backend/src/knowflow/api/router.py L55-L58
#: 挂在业务路由上的**路由级鉴权依赖**。
#: 单个端点再声明 `user: CurrentUser` 也不会重复执行 —— FastAPI 对同一依赖
#: 在同一请求内会缓存结果。
AUTH_REQUIRED = [Depends(get_current_user)]
```

```python
# backend/src/knowflow/api/router.py L80-L92（节选）
api_router.include_router(auth.router)  # 公开：登录/注册；/auth/me 自行声明鉴权
...
api_router.include_router(knowledge_bases.router, dependencies=AUTH_REQUIRED)
api_router.include_router(search.router, dependencies=AUTH_REQUIRED)
api_router.include_router(documents.router, dependencies=AUTH_REQUIRED)
api_router.include_router(chat.router, dependencies=AUTH_REQUIRED)
api_router.include_router(conversations.router, dependencies=AUTH_REQUIRED)
api_router.include_router(evaluation.router, dependencies=AUTH_REQUIRED)
api_router.include_router(observability.router, dependencies=AUTH_REQUIRED)
```

**为什么"路由级"比"逐个端点声明"强**：默认值的方向决定了犯错时的后果。
"默认公开、逐个声明"时，忘记声明 = 漏洞；"默认需要、例外公开"时，
忘记排除 = 多要一次登录（能被立刻发现的小问题）。
**把默认值设在安全的一侧，是把"靠人记得"换成"靠机器兜底"。**

第二步是**把这条属性变成可执行的门禁**——`scripts/audit_auth.py` 静态读 FastAPI 的依赖图：

```python
# backend/scripts/audit_auth.py L108-L124（节选）
for path, methods, own_deps, inherited_deps in walk_routes(app.routes):
    if path in PUBLIC_PATHS:
        continue
    has_auth = bool(AUTH_CALLABLES & (own_deps | inherited_deps))
    for method in methods:
        if method in ("HEAD", "OPTIONS"):
            continue
        label = f"{method:6s} {path:44s}"
        if (method, path) in PUBLIC_ROUTES:
            public.append(label)
            print(f"  ○ {label} 刻意公开（登录/注册）")
        elif has_auth:
            protected.append(label)
            print(f"  ✓ {label} 已鉴权")
        else:
            problems.append(label)
            print(f"  ✗ {label} **缺少鉴权**")
```

这个脚本自己也踩了两个坑，**这两个坑比脚本本身更值得记**（E6.4 原文）：

> 1. **不能只扫端点自身的依赖**。`include_router(..., dependencies=[Depends(get_current_user)])`
>    这种"统一加鉴权"的写法挂在 `include_context.dependencies` 上，不在端点的 `dependant` 里。
>    只查后者会把正确写法**误报**成漏洞。
> 2. **不能直接遍历 `app.routes`**。FastAPI 0.142 的 `include_router` 是**惰性**的：
>    `app.routes` 里只有 `_IncludedRouter` 占位对象（`path`/`methods` 都是 None），
>    真正的 `APIRoute` 在 `original_router.routes` 里，前缀在 `include_context.prefix`。
>    第一版脚本直接遍历 `app.routes`，只找到 1 个端点 —— **差点得出"没有漏洞"的错误结论**。

**"差点得出没有漏洞的错误结论"是审计工具最危险的失败模式**：
一个会漏报的检查器，比没有检查器更糟——它给你一个"已经检查过了"的假安全感。
所以这条审计也被放进 CI（见 §2.8），**它自己也被验证过**（对着修复前的 21 个漏洞跑出过红）。

### 2.6 关键代码 5：迁移与模型零 drift 的 CI 门禁

数据库这一层的经典事故是：**模型改了、迁移忘了写**，本机因为表已存在所以不报错，
部署到新库才 `Unknown column`。CI 里的做法是"跑一次 autogenerate，看它有没有话要说"：

```yaml
# .github/workflows/ci.yml L134-L151
      # 迁移与模型必须一致：跑一次 autogenerate，产出里如果有 op.* 就说明模型改了但没写迁移
      - name: Check for model/migration drift
        working-directory: backend
        run: |
          python -m alembic revision --autogenerate -m "ci drift check" > /tmp/drift.log 2>&1 || true
          NEW_FILE=$(ls -t alembic/versions/*ci_drift_check*.py 2>/dev/null | head -1 || true)
          if [ -z "$NEW_FILE" ]; then
            echo "生成了迁移文件（说明存在 drift）"
            exit 1
          fi
          # 迁移文件里除了 pass 没有别的操作 → 无 drift
          if grep -qE '^\s+op\.' "$NEW_FILE"; then
            echo "❌ 模型与迁移不一致（检测到未生成的 DDL 变更）："
            grep -E '^\s+op\.' "$NEW_FILE"
            exit 1
          fi
          echo "✅ 模型与迁移一致（无 drift）"
          rm -f "$NEW_FILE"
```

**判据为什么是"有没有 `op.` 调用"**：autogenerate 生成的文件一定存在（这就是它会被
`ls` 找到的原因），区别只在内容——无 drift 时 `upgrade()`/`downgrade()` 里只有 `pass`。
E4 的原始记录就是这个形态：

```
=== drift check：autogenerate 没有打印任何 "Detected" 行 ===
生成的临时文件里：
    def upgrade() -> None:
        pass
    def downgrade() -> None:
        pass
op. 调用数 = 0   → 模型与迁移完全一致，无 drift
```

同一条检查在本地也能手工跑（`backend/MIGRATIONS.md` §4 写了跑法），
只是 CI 里它是**强的**：忘了写迁移 → 红。

**两个附带的坑**（详见附录 A A1 / A2）：
`alembic.ini` 必须是纯 ASCII；`-x db_url=...` 必须放在子命令**之前**。

### 2.7 关键代码 6：`ruff` + `mypy --strict`——把"代码质量"变成事实

`backend/pyproject.toml` 是工具链的唯一真相来源（依赖、ruff、mypy、pytest 都读这一份）。
其中**最反直觉的一条**是行宽：

```toml
# backend/pyproject.toml L104-L109
[tool.ruff]
# ⚠ line-length = 100 是本仓库的**事实口径**，不是随手填的数：
#   源码里有大量中文注释/文档字符串，ruff 按 **unicode 显示宽度** 计数（一个汉字 = 2 列），
#   所以同样内容的行，中文比英文"长"一倍。88（ruff 默认）会让几乎所有带中文注释的
#   文件都过不了；100 是本仓库现有代码实际排布出来的宽度。
line-length = 100
```

**为什么 `88` 会让中文注释文件全红**：ruff 数的是**显示宽度**，一个汉字占 2 列。
所以"一行 45 个汉字的中文注释"= 90 列 > 88 → 报错，而报错只会说"行太长"，
**完全不会提"因为你写了中文"**。这个坑值得记，因为它的报错信息指向了错误的修改方向
（人第一反应是"我把这行拆短一点"，而不是"行宽口径不对"）。

mypy 用的是 `strict = true`（`pyproject.toml` L167-L181），并且刻意关掉了一个检查，
理由写在配置里（这是"关检查"的正确姿势——每一条都要有据可查）：

```toml
# backend/pyproject.toml L175-L181
# ⚠ comparison-overlap 必须关掉，理由写在这里（这是唯一一个为了"不改源码"而关的检查）：
#   schemas/__init__.py 第 136 行是**刻意的** import 期契约自证：
#       assert MessageOut is not _CommonMessageOut, "..."
#   两个类在类型上没有继承关系，strict 模式会判它"恒真的身份比较"。
#   但这个 assert 的价值恰恰在于**运行期拿到的是哪个对象**，类型系统看不出来。
#   删掉 assert 就等于删掉那道防线，所以选择关检查而不是改源码。
disable_error_code = ["comparison-overlap"]
```

**本会话实测**（这两条是本阶段的"硬证据"，可以自己复跑）：

```powershell

# Success: no issues found in 97 source files
```

换句话说：**CI 用降级路径也验证了"降级路径本身是通的"**，这比"跳过这一层"强得多。

三个 job 的分工（`scripts/check_yaml.py` 会把结构直接打出来，本会话实测）：


已做的全部工作只有两件：

| --- | --- | --- |
| `docker-compose.yml` | MySQL 用 `mysqladmin ping` 做健康检查、`start_period: 40s` | `mysql -e 'select 1'` 在初始化阶段会因 root 密码未生效而永远不健康 |

| `docker-compose.yml` | 容器内 `DATABASE_URL` 指向服务名 `mysql`，不是 `127.0.0.1` | 后者是容器自己的回环口 |
| `docker-compose.yml` | `DATA_DIR` 与 `DATABASE_URL` 一一对应 | 挂错卷会让向量库和 MySQL **串库**（docs/00 第 8 节） |
| `backend/Dockerfile` | 先装 **CPU-only torch**（`--index-url .../whl/cpu`） | 不加会拉 2.5GB CUDA 版，而容器里没有 GPU |
| `backend/Dockerfile` | 多阶段构建；runtime 只装 `libgomp1` + `curl` | `libgomp1` 是 torch/numpy 的 OpenMP 运行库，缺了 `import torch` 直接失败 |
| `backend/Dockerfile` | 非 root 用户 UID/GID=10001；`HEALTHCHECK` 打 `/health`，`start-period=60s` | 首次启动要连库、建 Chroma 客户端、重建 BM25 索引 |
| `backend/Dockerfile` | 刻意**不**预下载 BGE-M3（`PRELOAD_MODEL=0`） | 镜像 +2GB；推荐运行时挂载 HF 缓存（选择 B） |
| `frontend/Dockerfile` | 多阶段：pnpm 构建 → nginx 托管；`pnpm build` 含 `vue-tsc` | **类型检查不过就产不出镜像**，这是刻意的门禁 |
| `frontend/nginx.conf` | `proxy_buffering off` + `proxy_cache off` + `proxy_read_timeout 300s` | ⭐ SSE 最容易踩的部署坑：nginx 默认缓冲上游，“后端逐字推、nginx 攒着发”会让流式效果完全消失 |

**这条"未实测"要主动说，不要说成"已验证"**（E11 与 README §5 都反复标注）。
一次诚实的"我没在 Docker 上跑过，我只做了 YAML 校验与人工核对"，
比一次含糊的"部署也做了"可信得多——后者被追问一句"镜像多大"就露馅。

## 4. 常见错误

| 错误信息 | 原因 | 解决 |
| --- | --- | --- |
| `sqlite3.OperationalError: no such table: users`（刚建过表） | 内存 SQLite 每个连接都是新空库 | `poolclass=StaticPool`（§2.3） |
| `SQLite objects created in a thread can only be used in that same thread` | SQLite 默认禁止跨线程 | `connect_args={"check_same_thread": False}` |
| `204 passed` 但流式接口仍然报 `error` 帧 | 单测走 `ASGITransport`，抓不到分次线程调度 | 跑 `.\tasks.ps1 smoke-http`（真起 uvicorn） |
