# 阶段 2：数据库与迁移

> **本阶段目标**：用**同一套** ORM 模型定义，在 MySQL（生产）与 SQLite（测试）上都能正确建表，并让迁移与模型零 drift。
> **预计耗时**：90 分钟
> **前置阶段**：阶段 1
> **本阶段产出**：14 张表的 ORM 模型（921 行）+ 会话管理 + 一条初始迁移

## 0. 为什么先做这一步

因为 `chunks` 表是**检索单位的落点**，而 `chunks.vector_id`（= `"{doc_id}:{chunk_index}"`）
是"关系库 ↔ 向量库"的唯一一致性锚点。阶段 4 写向量库、阶段 5 做一致性校验、
阶段 8 删文档清三方，**全都围绕这一个字段**。它现在不定下来，后面每加一个功能都要改。

第二个理由更实际：**测试速度**。E1.5 记录 204 个用例 **4.63 秒**跑完，
这个数字能成立的前提是"测试不连 MySQL、不落盘"——
也就是**同一套模型定义必须能在 SQLite 内存库上建表**。
如果模型里写了 `MEDIUMTEXT`、`BIGINT UNSIGNED` 这种 MySQL 专有类型，
SQLite 测试**直接建表失败**，你就只剩下"每个用例都连真 MySQL"这一条路，
测试时间会从 4 秒变成几分钟，CI 也就没人跑了。

第三个理由：**Alembic 的 autogenerate 是"模型 ↔ 数据库"的自动对账工具**。
但这个工具有一个致命前提——`target_metadata` 必须认识**所有**模型类。
漏导入一个模型，autogenerate 会认为那张表"多余"，生成一条 `DROP TABLE` 迁移。
所以"模型汇总文件必须 import 全部模型"这条约定，必须在写表的时候就建立。

## 1. 要解决的问题

不做这一步，你会遇到的具体失败现象：

| 现象 | 真实原因 |
| --- | --- |
| `sqlalchemy.exc.CompileError: (in table 'chunks', column 'content'): Compiler <SQLiteTypeCompiler> can't render element of type MEDIUMTEXT` | 模型里直接用了 MySQL 专有类型 |
| `NOT NULL constraint failed: users.id` | SQLite 只把**声明类型恰好是 `INTEGER`** 的主键当 rowid 别名；声明成 `BIGINT` 时 INSERT 不带 id 就报错 |
| `sqlalchemy.exc.OperationalError: no such table: users` | SQLite `:memory:` 没配 `StaticPool`，每个连接都是**新的空库** |
| `ProgrammingError: SQLite objects created in a thread can only be used in that same thread` | 没设 `check_same_thread=False`，而 FastAPI 用线程池跑同步路由 |
| 服务跑几小时后 `Lost connection to MySQL server during query` | 连接池里的连接被服务端 `wait_timeout` 关掉，没开 `pool_pre_ping` |
| `alembic revision --autogenerate` 生成了一条 `op.drop_table('documents')` | 模型汇总文件漏 import 了那个模型 |
| autogenerate 出来的约束名是随机字符串，想改索引无从下手 | `MetaData` 没配 `naming_convention` |
| 存进去的 emoji 变成 `?` | 连接没 `SET NAMES utf8mb4`（MySQL 的 `utf8` 其实只有 3 字节） |
| `UnicodeDecodeError` 在跑 alembic 时（而且报错指不到任何文件） | 🔻 `alembic.ini` 里有非 ASCII 字符 |

最后一条特别值钱，阶段 2 会专门写它。

### 2.2 关键代码 1：让同一套模型在两个数据库上都能建表

完整实现在 `backend/src/knowflow/db/types.py`（44 行）。核心是 `with_variant`：

```python
# backend/src/knowflow/db/types.py L29-L45
BigIntType: Final[TypeEngine[int]] = (
    BigInteger()
    .with_variant(mysql.BIGINT(unsigned=True), "mysql")
    .with_variant(sqlite.INTEGER(), "sqlite")
)

# 小整数（反馈评分 -1/0/1 等）
SmallIntType: Final[TypeEngine[int]] = SmallInteger()

# 长文本：MySQL 用 MEDIUMTEXT（最大 16MB，足够放整篇文档的 chunk 合并）；
# 其它方言退回 TEXT（SQLite 的 TEXT 本身无长度上限）。
LongText: Final[TypeEngine[str]] = Text().with_variant(mysql.MEDIUMTEXT(), "mysql")

# 高精度时间：DATETIME(6) 保留微秒，排序稳定（同秒内多条记录不会乱序）。
DateTime6: Final[TypeEngine[datetime]] = DateTime().with_variant(mysql.DATETIME(fsp=6), "mysql")
```

🔻 **`sqlite.INTEGER()` 这个 variant 绝对不能省**，理由写在同一文件的注释里：

```python
# backend/src/knowflow/db/types.py L19-L33（节选）
# ⚠ SQLite 侧必须显式映射成 INTEGER：SQLite 只把「声明类型恰好是 INTEGER」的
# PRIMARY KEY 当作 rowid 别名来自动分配主键。声明成 BIGINT 时建表照样成功，
# 但 INSERT 不带 id 会直接报 `NOT NULL constraint failed: users.id` ——
# 于是"同一套模型定义在 SQLite 上也能跑测试"这个承诺在**写入**时才崩，
# 而 SQLite 单测恰好全靠写入（见 db/session.py 的 StaticPool 说明）。
```

**这是"测试假通过"的经典形态**：建表成功、模型定义看起来没问题，
错误只在第一次 INSERT 时出现。如果 SQLite 测试恰好只读不写，
这个 bug 会一直藏到你上生产才暴露。

时间工具也是同一个文件：

```python
# backend/src/knowflow/db/types.py L48-L67
def utcnow() -> datetime:
    """当前 UTC 时间（naive）。

    用 `datetime.now(UTC).replace(tzinfo=None)` 而不是已废弃的 `utcnow()`，
    同时保证写进库的值一定是 naive UTC，读出来不会带时区歧义。
    """
    return datetime.now(UTC).replace(tzinfo=None)


def to_iso_z(value: datetime | None) -> str | None:
    """把库里的 naive UTC datetime 序列化成带 `Z` 的 ISO8601 字符串。

    这是唯一的时间出口，所有 schema 都调它 —— 避免有的地方输出 `+00:00`、
    有的地方输出本地时间，前端解析要写两套。
    """
    if value is None:
        return None
    if value.tzinfo is None:
        value = value.replace(tzinfo=UTC)
    return value.astimezone(UTC).isoformat(timespec="milliseconds").replace("+00:00", "Z")
```

**为什么统一存 naive UTC**：MySQL 的 `DATETIME` 不带时区。
存"带时区的 datetime"到 `DATETIME` 列时，MySQL 会静默丢掉时区信息；
读出来的是 naive 的。与其让"有时 naive 有时 aware"混着来，
不如**约定一律 naive UTC**，只在序列化出口补 `Z`。

### 2.3 关键代码 2：显式命名约定，让迁移可 review

```python
# backend/src/knowflow/db/base.py L18-L34
NAMING_CONVENTION: dict[str, str] = {
    "ix": "ix_%(table_name)s_%(column_0_N_name)s",
    "uq": "uq_%(table_name)s_%(column_0_N_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}


class Base(DeclarativeBase):
    """全项目唯一的声明式基类。

    所有模型都必须继承它 —— 否则 Alembic 的 `target_metadata` 扫不到，
    autogenerate 会生成一个「把所有表都删掉」的迁移（真实踩过的坑）。
    """

    metadata = MetaData(naming_convention=NAMING_CONVENTION)
```

**不配 `naming_convention` 会怎样**：约束名由数据库随机生成（MySQL 上会得到
`PRAGMA` 风格的名字）。后果有两层：

1. **无法可靠 autogenerate 出 `DROP`**：Alembic 要按名字比对约束，
   名字随机时它认不出"这个索引就是模型里那个"，会生成"删旧的 + 建新的"这种噪音迁移；
2. **想改一个索引时无从下手**：你连它叫什么都不知道。

两个 Mixin：

```python
# backend/src/knowflow/db/base.py L37-L62
class TimestampMixin:
    """创建/更新时间。用 Python 侧默认值而不是 `server_default`，
    这样测试里 `session.flush()` 之后对象上立刻能读到值，不用 refresh 回查。"""

    created_at: Mapped[datetime] = mapped_column(DateTime6, default=utcnow, nullable=False)
    updated_at: Mapped[datetime] = mapped_column(
        DateTime6, default=utcnow, onupdate=utcnow, nullable=False
    )


class SoftDeleteMixin:
    """软删除。

    为什么软删：`message_citations` 可能引用已被删除文档的 chunk，
    物理删除会让引用悬空、历史会话的引用点开就是 404。
    """

    deleted_at: Mapped[datetime | None] = mapped_column(DateTime6, default=None, nullable=True)

    @property
    def is_deleted(self) -> bool:
        return self.deleted_at is not None

    def mark_deleted(self) -> None:
        self.deleted_at = utcnow()
```

**`default=utcnow`（Python 侧）而不是 `server_default=func.now()`（数据库侧）**：
用数据库默认值时，`session.add(obj)` 之后 `obj.created_at` 是 `None`，
必须 `refresh` 回查才有值。而 `message_citations.rank` 之类的逻辑
经常要在 flush 后立刻用时间戳排序——多一次回查既慢又容易 forgot。
代价：时间由应用进程生成，多副本部署时依赖机器时钟同步（可接受，NTP 是标配）。

### 2.4 关键代码 3：会话管理里的三个现实问题

```python
# backend/src/knowflow/db/session.py L37-L59
def create_engine_from_settings(settings: Settings) -> Engine:
    """按配置创建引擎（不做全局缓存，测试要能造多个）。"""
    url = settings.database_url
    kwargs: dict[str, Any] = {"echo": settings.db_echo, "future": True}

    if _is_sqlite(url):
        kwargs["connect_args"] = {"check_same_thread": False}
        if ":memory:" in url or url.endswith("sqlite://"):
            # 内存库必须共享同一个连接，否则每次 connect 都是一个新空库
            kwargs["poolclass"] = StaticPool
    else:
        kwargs.update(
            pool_pre_ping=True,
            pool_size=settings.db_pool_size,
            max_overflow=settings.db_max_overflow,
            pool_recycle=settings.db_pool_recycle,
        )

    engine = create_engine(url, **kwargs)
    ...
```

🔻 **`StaticPool` 是 SQLite 内存测试的生死线**。SQLite `:memory:` 的库
**属于连接**，不属于进程。默认连接池下，第二次 `connect()` 拿到的是**另一个空库**，
于是你会看到 `no such table: users` —— 而表明明"刚建过"。
`StaticPool` 让所有请求复用同一个连接，库才在。

🔻 **`check_same_thread=False`**：SQLite 默认禁止跨线程使用连接。
FastAPI 把同步路由函数放到线程池执行，所以建表在 A 线程、插数据在 B 线程是常态。
不关这个检查，第一个并发请求就报 `ProgrammingError`。

**`pool_pre_ping=True`** 防的是"隔夜第一个请求失败"：MySQL 默认
`wait_timeout = 8 小时`，第二天连接池里的连接已被服务端关闭。
`pre_ping` 在借出连接前 ping 一次，代价是每次多一个往返。

**为什么要给 MySQL 会话设严格模式**：

```python
# backend/src/knowflow/db/session.py L62-L76
def _install_mysql_session_settings(engine: Engine) -> None:
    """把 MySQL 会话设成严格模式 + utf8mb4。

    - `STRICT_TRANS_TABLES`：类型不符/超长直接报错而不是静默截断
      （MySQL 非严格模式下会"帮你"截断字符串，数据悄悄坏掉）；
    - `utf8mb4`：能存 emoji 与生僻字（`utf8` 在 MySQL 里其实只有 3 字节）。
    """

    @event.listens_for(engine, "connect")
    def _set_session(
        dbapi_connection: Any, _connection_record: Any
    ) -> None:
        with dbapi_connection.cursor() as cursor:
            cursor.execute("SET SESSION sql_mode='STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION'")
            cursor.execute("SET NAMES utf8mb4")
```

E3 的**附加验证**就是查这行到底有没有生效：

```
[附加] 字符集验证：写入含 emoji 与生僻字的数据
      写入 '一线城市🏨住宿标准' -> 读回 '一线城市🏨住宿标准'  ✓
```

**为什么用 `connect` 事件而不是在 DSN 里加参数**：`SET NAMES` 与 `sql_mode`
是**会话级**设置，写在连接建立时最可靠。DSN 里的 `charset=utf8mb4`
只影响客户端编解码，不管服务端会话变量。

**事务边界由 service 决定，依赖只负责关闭**：

```python
# backend/src/knowflow/db/session.py L117-L129
def get_db() -> Generator[Session, None, None]:
    """FastAPI 依赖：每个请求一个会话。

    注意 **不在这里 commit**：事务边界由 service 层决定（一个请求可能要做
    "写消息 + 写引用 + 写 trace" 这一组要么全成要么全败的操作）。
    依赖只负责"一定关闭"。
    """
    factory = get_session_factory()
    session = factory()
    try:
        yield session
    finally:
        session.close()
```

**为什么 `autoflush=False`**（同一文件 L94）：

```python
autoflush=False,  # 查询前不自动 flush，避免"查着查着把半成品写进库"
```

`autoflush=True` 时，任何 `SELECT` 之前 SQLAlchemy 会把 pending 对象 flush 出去。
在"先建 document 行、再解析、解析失败要标记 FAILED"这个流程里，
autoflush 会在你不期望的时刻把 `status=UPLOADED` 的半成品写进库并触发唯一约束冲突。
显式 `flush()` 让每一步写入时机**可读**。

### 2.5 关键代码 4：模型汇总文件与 `vector_id` 契约

```python
# backend/src/knowflow/db/models/__init__.py L1-L11（节选）
"""ORM 模型汇总。

**这个文件必须导入所有模型**，原因有两个，都不是可选的：

1. Alembic 的 `target_metadata = Base.metadata` 只认识「已经被导入过」的模型类。
   漏导入一个模型，autogenerate 就会认为那张表"多余"，生成一条 DROP TABLE 迁移。
   这是最危险的一类迁移事故。
2. `Base.registry.configure()` 在处理多表 relationship 时需要所有类都已注册。

因此约定：**新增模型文件后，必须在这里 import 一次。**
"""
```

`vector_id` 的唯一构造入口：

```python
# backend/src/knowflow/db/models/knowledge.py L48-L50
def make_vector_id(doc_id: int, chunk_index: int) -> str:
    """`vector_id` 的唯一构造入口。散落在各处手拼字符串迟早会不一致。"""
    return f"{doc_id}:{chunk_index}"
```

**为什么必须是"唯一入口"**：这个字符串在**四处**出现——
MySQL `chunks.vector_id` 列、向量库的 `id`、BM25 的 `doc_key`、
`scripts` 里的一致性校验。任何一处手写成 `f"{doc_id}-{chunk_index}"`
（用了横线）就会造成"写进去查不出来"，而且**不报错**。

父子块的设计也在 model 里落地：

```python
# backend/src/knowflow/db/models/knowledge.py L133-L172（节选）
class Chunk(Base):
    """检索单位。

    两个字段值得解释：

    - `content` 是**子块**（约 `chunk_size`），用于向量化与 BM25 —— 小才能检索准；
    - `parent_content` 是**父块**（约 `parent_chunk_size`），命中后交给模型 ——
      大才有完整上下文。「用小检索、用大写答案」是切分两难的标准解法。
    """

    __tablename__ = "chunks"
    __table_args__ = (
        UniqueConstraint("doc_id", "chunk_index", name="uq_chunks_doc_id_chunk_index"),
        Index("ix_chunks_kb_id", "kb_id"),
        Index("ix_chunks_vector_id", "vector_id"),
    )

    ...

    @property
    def context_text(self) -> str:
        """喂给模型用的文本：有父块用父块，否则退回子块。"""
        return self.parent_content or self.content
```

**`context_text` 这个 property 的价值**：它保证**下游永远不需要判空**。
调用方写 `chunk.context_text` 就对了，不用记"父块可能为 None"。
"字段可空但语义不空"是减少分支的标准做法。

引用用 `SET NULL` 而不是 `CASCADE`：

```python
# backend/src/knowflow/db/models/chat.py L119-L123
# 用 SET NULL 而不是 CASCADE：chunk 被物理清掉时，引用行应保留（只失去指针），
# 否则答案里的 [1] 会凭空消失，看起来像 bug。
chunk_id: Mapped[int | None] = mapped_column(
    BigIntType, ForeignKey("chunks.id", ondelete="SET NULL"), default=None

```

**这是"删文档后历史答案还能核对出处"的实现基础**：
阶段 8 删文档时会物理删 `chunks` 行，但 `message_citations` 保留，
`doc_id` + `snippet` 还在，所以历史对话里的引用依然能显示"来自哪个文档的哪一段"。

### 2.6 Alembic：一条初始迁移

```powershell
cd D:\Projects\pythonProjects\knowflow\backend
# ① 生成初始迁移
..\.venv\Scripts\python.exe -m alembic -x "db_url=$env:DATABASE_URL" revision --autogenerate -m "initial schema"
# ② 应用
..\.venv\Scripts\python.exe -m alembic -x "db_url=$env:DATABASE_URL" upgrade head
# ③ 对账：应当**没有任何 "Detected" 行**
..\.venv\Scripts\python.exe -m alembic -x "db_url=$env:DATABASE_URL" revision --autogenerate -m "drift check"
```

🔻 **`-x` 必须放在子命令之前**。写成
`alembic upgrade head -x db_url=...` 会报
`unrecognized arguments: -x db_url=...`，而这个报错完全不会提示"位置错了"。
这是 E4 里明确记录的一条：

```powershell
# 先注：-x 必须放在子命令之前，否则报 unrecognized arguments
..\.venv\Scripts\python.exe -m alembic -x "db_url=<url>" upgrade head
```

🔻 **`alembic.ini` 必须是纯 ASCII**。E4 的原文：

> `alembic.ini` 里的注释**必须是纯 ASCII**。
> Alembic 用**系统 locale 编码**读它，中文 Windows 上是 GBK，
> 里面只要有一个中文字符就 `UnicodeDecodeError`，而且**报错信息完全指不到这一点**。

这条坑的可怕之处在于：报错是一个 `UnicodeDecodeError`，堆栈全是 alembic 内部，
**完全不会提到 `alembic.ini`**。你会去查迁移脚本、查 `env.py`、查数据库编码，
就是想不到问题在一个"配置文件里的中文注释"。

**为什么会这样**：`alembic.ini` 是 `configparser` 读的，
而 Alembic 用 `open(path)` 打开它——**没有指定 `encoding`**，
于是用系统 locale（中文 Windows 上是 GBK）。文件是 UTF-8 保存的中文，
按 GBK 解就炸。

### 验证 2：同一套模型在 SQLite 内存库上也能建表**并写入**

这条是"测试能 4 秒跑完"的前提，也是最容易假通过的一步，所以要**验证写入**：

```powershell
cd D:\Projects\pythonProjects\knowflow\backend
$env:PYTHONPATH='D:\Projects\pythonProjects\knowflow\backend\src'
D:\Projects\pythonProjects\knowflow\.venv\Scripts\python.exe -c @"
from sqlalchemy import create_engine
from sqlalchemy.orm import Session
from sqlalchemy.pool import StaticPool
from knowflow.db.models import Base, User, KnowledgeBase, Document, Chunk, make_vector_id

engine = create_engine('sqlite://', connect_args={'check_same_thread': False}, poolclass=StaticPool)
Base.metadata.create_all(engine)
print('建表数 =', len(Base.metadata.tables))

with Session(engine) as s:
    u = User(username='demo', password_hash='x'); s.add(u); s.flush()
    print('users.id 自动分配 ->', u.id, type(u.id).__name__)
    kb = KnowledgeBase(name='kb', owner_id=u.id, embedding_provider='hash',
                       embedding_model='hash-blake2b-1024', embedding_dim=1024)
    s.add(kb); s.flush()
    doc = Document(kb_id=kb.id, filename='a.md', ext='md', sha256='0'*64, storage_path='x')
    s.add(doc); s.flush()
    c = Chunk(kb_id=kb.id, doc_id=doc.id, chunk_index=0, content='住宿标准 600 元',
              parent_content='住宿标准 600 元', char_count=11, vector_id=make_vector_id(doc.id, 0))
    s.add(c); s.commit()
    print('vector_id ->', c.vector_id)
    print('context_text ->', c.context_text)
"@
```

**本会话真实输出**：

```
建表数 = 14
users.id 自动分配 -> 1 int
vector_id -> 1:0
context_text -> 住宿标准 600 元
```

**判断标准**：
- ✅ `建表数 = 14`：两个方言建出的表数**必须相同**；
- ✅ `users.id 自动分配 -> 1`：**这一行是关键**。如果 SQLite 侧漏了
  `.with_variant(sqlite.INTEGER(), "sqlite")`，你会在这里拿到
  `NOT NULL constraint failed: users.id`，而不是拿到 `1`；
- ✅ `vector_id -> 1:0`：格式是 `{doc_id}:{chunk_index}`，用冒号。

## 4. 常见错误

| 错误信息 | 原因 | 解决 |
| --- | --- | --- |
| 🔻 `UnicodeDecodeError` 跑 alembic 时，报错完全不提文件 | `alembic.ini` 里有中文/非 ASCII 字符 | 把 `alembic.ini` 改成**纯 ASCII**（中文注释挪到 `MIGRATIONS.md`） |
| 🔻 `unrecognized arguments: -x db_url=...` | `-x` 写在了子命令**后面** | `alembic -x "db_url=..." upgrade head`（`-x` 必须在子命令前） |
| `CompileError: can't render element of type MEDIUMTEXT` | 模型直接用了 MySQL 专有类型 | 用 `LongText = Text().with_variant(mysql.MEDIUMTEXT(), "mysql")` |
| `NOT NULL constraint failed: users.id` | SQLite 侧 `BIGINT` 主键不是 rowid 别名 | 加 `.with_variant(sqlite.INTEGER(), "sqlite")` |
| `no such table: users`（刚建过表） | SQLite 内存库没配 `StaticPool` | `poolclass=StaticPool` |
| `SQLite objects created in a thread can only be used in that same thread` | 没关线程检查 | `connect_args={"check_same_thread": False}` |
| autogenerate 生成 `op.drop_table('xxx')` | 模型汇总文件漏 import 该模型 | 在 `db/models/__init__.py` 里 import |
| emoji 存进去变 `?` | 会话没 `SET NAMES utf8mb4` | 见 `_install_mysql_session_settings` |
| autogenerate 生成一堆"删索引再建索引"噪音 | 没配 `naming_convention` | 给 `MetaData` 配命名约定 |
| `Lost connection to MySQL server during query`（隔夜后第一次） | 连接池里的连接被服务端关掉 | `pool_pre_ping=True` |
| `Can't create table ... (errno: 150)` | 主键与外键类型不一致（一个 `BIGINT` 一个 `BIGINT UNSIGNED`） | 所有主外键统一用 `BigIntType` |
| MySQL 造数据时报外键约束失败，SQLite 不报 | SQLite 默认不强制外键 | 见附录 A 的同名条目（`messages` 必须先有 `users`/`conversations`） |
