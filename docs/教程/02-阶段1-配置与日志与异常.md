# 阶段 1：配置与日志与异常

> **本阶段目标**：把"全项目唯一真相来源"建立起来——配置写错在**启动期**就炸，错误响应有稳定契约，日志能把一次请求串成一条链。
> **预计耗时**：60 分钟
> **前置阶段**：阶段 0
> **本阶段产出**：`core/` 四个模块（609 行）+ 5 个可执行的配置实验

## 0. 为什么先做这一步

阶段 2 的表结构要用 `CHUNK_SIZE` / `CHUNK_OVERLAP`；阶段 4 的向量化要用 `EMBEDDING_DIM`；
阶段 5 的闸门要用 `VECTOR_MIN_SCORE`。**如果配置没有单一来源**，这些参数会散落在
十几个文件里，表现为：

```python
# 五个文件里各写一遍
chunk_size=600      # vectorstore/chroma_store.py
chunk_size=600      # ingest/chunkers.py
CHUNK = 600         # retrieval/engine.py
```

改一个参数要改五处，**必然漏一处**。而漏掉的表现是"某个接口的检索行为和别的接口不一样"——
这种不一致极难查，因为每个文件单独看都是对的。

第二个理由更硬：**配置错误必须死在启动期，而不是第一个请求。**
在容器化环境里，"服务起来了但第一个请求 500"会表现为"pod 反复重启但日志里只有请求报错"。
所以本阶段的 `Settings` 里有一组**交叉校验**（`overlap < size`、`parent >= size`、
`rerank_top_n <= fetch_k`），写错时进程**起不来**。

第三个理由：后面的每个模块都要 `from knowflow.core.logging import get_logger`，
都会 `raise KBNotFoundError(...)`。这两个契约现在不定，后面每加一个模块都要回头改。

---

## 1. 要解决的问题

不做这一步，你会遇到的具体失败现象：

| 现象 | 真实原因 |
| --- | --- |
| 服务能起，第一次上传文档 500：`ValueError: chunk_overlap must be less than chunk_size` | 配置没做交叉校验，递归切分器在运行期才炸 |
| 服务能起，第一次提问返回 401，但 `.env` 里明明写了 Key | 写了 `OPENAI_API_KEY=" "`（一个空格），被当成"在线" |
| 前端抱怨"错误提示里没有 request_id，我没法排查" | 异常响应里没带 `request_id`；或 CORS 没 `expose_headers` |
| `CORS_ORIGINS=http://a,http://b` 导致启动时 `json.decoder.JSONDecodeError` | pydantic-settings 把 list 类型当 JSON 解析，逗号写法没救回来 |
| 日志里两个不同请求的记录混成一条链 | `contextvar` 用完没 `clear()`，下一个请求带上了上一个的 `request_id` |
| 日志里出现 `request_id=None` 污染 JSON 结构 | 后台任务没经过中间件，往每条日志都塞了 `None` |

最后一条容易被忽略但很烦：生产用 `LOG_JSON=true` 时，
`{"request_id": null}` 会让 ELK 里的字段类型推断变得不可靠。

### 2.1 目标：`core/config.py`（273 行）

这是全项目最重要的一个文件。它做三件事：**集中声明**、**启动期交叉校验**、

#### 2.1.1 路径常量：不依赖"当前工作目录"

```python
# backend/src/knowflow/core/config.py L26-L38
# --------------------------------------------------------------------------------------
# 路径常量：全部由本文件位置推导，不依赖"当前工作目录"
#   config.py -> core -> knowflow -> src -> backend -> <repo root>
# --------------------------------------------------------------------------------------
BACKEND_DIR = Path(__file__).resolve().parents[3]
REPO_ROOT = Path(__file__).resolve().parents[4]

EmbeddingProvider = Literal["local", "hash", "api"]
VectorBackend = Literal["chroma", "memory"]
FusionStrategy = Literal["rrf", "weighted"]
RetrievalMode = Literal["vector", "bm25", "hybrid", "hybrid_rerank"]
ChatMode = Literal["rag", "agent"]
CheckpointBackend = Literal["memory", "sqlite"]
```

**为什么不用 `os.getcwd()`**：脚本、pytest、uvicorn 三种启动方式的
"当前目录"各不相同（仓库根 / `backend/` / 两者都不是）。
用 `Path(__file__).resolve().parents[N]` 推导出来的路径**与启动位置无关**，
这是让 `data/`、`uploads/`、`chroma/` 三个目录在所有入口下都指向同一处的唯一办法。

`Literal[...]` 那一组类型别名的价值在**拼错立刻报错**：
`EMBEDDING_PROVIDER=locla` 会在启动期抛 ValidationError，
而不是等到第一次向量化时走进一个分支然后行为诡异。

#### 2.1.2 CORS：一个 `NoDecode` 救回一种写法

```python
# backend/src/knowflow/core/config.py L60-L67
# CORS 同时支持两种写法：
#   CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173   （逗号，更符合直觉）
#   CORS_ORIGINS=["http://localhost:5173"]                     （JSON，pydantic 默认）
# NoDecode 关掉 pydantic-settings 对复杂类型的 JSON 预解析，交给下面的校验器统一处理。
# 不加 NoDecode，逗号写法会在**启动时**抛 JSONDecodeError —— 真实踩过的坑。
cors_origins: Annotated[list[str], NoDecode] = Field(
    default_factory=lambda: ["http://localhost:5173", "http://127.0.0.1:5173"]
)
```

配套的校验器：

```python
# backend/src/knowflow/core/config.py L169-L182
@field_validator("cors_origins", "allowed_extensions", mode="before")
@classmethod
def _split_comma_or_json(cls, v: Any) -> Any:
    """让列表型配置同时接受 `a,b,c` 与 `["a","b"]` 两种写法。"""
    if v is None or isinstance(v, list):
        return v
    if isinstance(v, str):
        raw = v.strip()
        if not raw:
            return []
        if raw.startswith("["):
            return json.loads(raw)
        return [item.strip() for item in raw.split(",") if item.strip()]
    return v
```

🔻 **细节在 `mode="before"`**：必须在 pydantic 尝试把字符串转 list **之前**介入。
用默认的 `mode="after"` 时，pydantic 已经先抛 `JSONDecodeError` 了，
你的校验器根本没机会运行——**报错信息只会说"JSON 解析失败"，
完全不会提到 `CORS_ORIGINS`**，你会去查一个根本不存在的问题。

**为什么两种写法都要支持**：`CORS_ORIGINS=a,b` 在 `.env` 和 Docker Compose 里
是常见写法（Dotenv 传统），而 pydantic-settings 对 `list[str]` 类型默认按 JSON 解析。
支持两种写法成本只有 12 行，不支持的话每个使用者都要踩一次。

#### 2.1.3 交叉校验：这些错误一旦放过，会在运行期变成难查的怪问题

```python
# backend/src/knowflow/core/config.py L195-L218
@model_validator(mode="after")
def _cross_check(self) -> Settings:
    """交叉校验：这些错误一旦放过，会在运行期变成难查的怪问题。"""
    if self.chunk_overlap >= self.chunk_size:
        raise ValueError(
            f"CHUNK_OVERLAP({self.chunk_overlap}) 必须小于 CHUNK_SIZE({self.chunk_size})，"
            "否则递归切分器无法收敛（会无限切分）"
        )
    if self.parent_chunk_size < self.chunk_size:
        raise ValueError(
            f"PARENT_CHUNK_SIZE({self.parent_chunk_size}) 不能小于 "
            f"CHUNK_SIZE({self.chunk_size})，父块必须能容纳子块"
        )
    if self.rerank_top_n > self.fetch_k:
        raise ValueError(
            f"RERANK_TOP_N({self.rerank_top_n}) 不应大于 FETCH_K({self.fetch_k})，"
            "重排只能作用于已召回的候选"
        )
    if self.env == "prod":
        if self.jwt_secret == "change-me-in-production":
            raise ValueError("生产环境必须设置 JWT_SECRET")
        if self.debug:
            raise ValueError("生产环境必须关闭 DEBUG")
    return self
```

**四条校验分别防什么**（每一条都对应一个具体的运行期灾难）：

| 校验 | 不做的后果 |
| --- | --- |
| `overlap < size` | `RecursiveCharacterTextSplitter` 的窗口推进量是 `size - overlap`，`≤ 0` 时**无法收敛** —— 上传任何文档都会卡住或产生天文数字个 chunk |
| `parent >= size` | 父块比子块小，"父块窗口"装不下任何子块，`_assign_parents` 会退化成"每块一个父块"，父子块设计失效 |
| `rerank_top_n <= fetch_k` | 重排只能作用于**已召回**的候选；`top_n > fetch_k` 意味着有一部分候选根本不存在，是配置语义错误 |
| prod 下 `jwt_secret` / `debug` | 用默认密钥上线 = 任何人都能伪造 token；`debug=true` 会泄露 traceback |

**注意 `env == "prod"` 那一组**：这是"**默认值的方向决定犯错时的后果**"的一次应用。
本地开发用默认密钥很方便（不用配），但生产用了默认密钥就是灾难。
所以校验只在 `prod` 下触发——**开发便利与生产安全的取舍点选在了"环境变量"上**。

#### 2.1.4 派生属性：只算不配，避免第二个真相来源

```python
# backend/src/knowflow/core/config.py L223-L246
@property
def is_offline(self) -> bool:
    """没有可用 API Key = 离线模式。

    注意 `.strip()`：`OPENAI_API_KEY=" "`（一个空格）在 shell 里很常见，
    不做 strip 会误判成"在线"，然后在第一次提问时 401 —— 这类问题极难排查。
    """
    return not self.openai_api_key.strip()

@property
def llm_mode(self) -> str:
    return "offline" if self.is_offline else "online"

@property
def judge_model(self) -> str:
    return self.llm_judge_model.strip() or self.openai_model

@property
def upload_dir(self) -> Path:
    return self.data_dir / "uploads"

@property
def chroma_path(self) -> Path:
    return self.chroma_dir or (self.data_dir / "chroma")
```

🔻 **`.strip()` 这一行是真踩出来的**。`OPENAI_API_KEY=" "`（一个空格）
在 Windows 的 `set`、Linux 的 `export`、Docker Compose 的 `environment:`
里都很容易写出来。不 strip 的结果是：服务报告自己是**在线模式**，
`/health` 里 `offline=false`，然后第一次提问返回 401。
排查方向会完全跑偏到"Key 是不是过期了"。

**"只算不配"这条原则怎么用**：如果 `is_offline` 也做成一个配置项，
就会出现 `OPENAI_API_KEY=""` 与 `IS_OFFLINE=false` 同时存在的情况——
两个字段互相矛盾时**没有权威**。派生属性让这种矛盾**不可能被表达出来**。

#### 2.1.5 DSN 脱敏：日志里绝不出现密码

```python
# backend/src/knowflow/core/config.py L311-L322
def _mask_dsn(dsn: str) -> str:
    """隐藏 DSN 里的密码，日志与 /health 里只留 `user:***@host`。"""
    if "://" not in dsn:
        return dsn
    scheme, rest = dsn.split("://", 1)
    if "@" not in rest:
        return dsn
    creds, host = rest.rsplit("@", 1)
    if ":" in creds:
        user, _ = creds.split(":", 1)
        return f"{scheme}://{user}:***@{host}"
    return dsn
```

配合 `public_snapshot()`（L284-L308）：给 `/health` 与启动日志用的脱敏快照，
**绝不输出任何 Key**。`database_url` 走 `_mask_dsn`。

**为什么用 `rsplit("@", 1)` 而不是 `split("@")`**：密码里可能有 `@`。
`rsplit(..., 1)` 从右边切，保证拿到的是"最后一个 `@` 之前是凭证"。

最后是单例：

```python
# backend/src/knowflow/core/config.py L325-L332
@lru_cache(maxsize=1)
def get_settings() -> Settings:
    """进程内单例。

    用 `lru_cache` 而不是模块级全局变量，是为了测试能 `get_settings.cache_clear()`
    换一套配置重建容器（否则测试之间会互相污染）。
    """
    return Settings()
```

**为什么不用模块级全局变量**：`Settings()` 在 `import` 时就求值，
于是"改了环境变量再重建"这件事**做不到**。`lru_cache` 版本的 `get_settings`
可以 `cache_clear()` 后重新求值——这是整个测试体系能跑起来的前提之一。

### 2.2 `core/logging.py`（94 行）：一次请求串成一条链

```python
# backend/src/knowflow/core/logging.py L24-L42
# 请求级上下文：request_id 与 trace_id 在中间件里绑定，之后全流程可读
request_id_var: ContextVar[str | None] = ContextVar("request_id", default=None)
trace_id_var: ContextVar[str | None] = ContextVar("trace_id", default=None)

_configured = False


def _add_context(_logger: Any, _method_name: str, event_dict: dict[str, Any]) -> dict[str, Any]:
    """把 contextvar 里的 request_id / trace_id 注入每条日志。

    没用 `structlog.contextvars.merge_contextvars` 是因为这里还需要兜底：
    某些后台任务（评测线程、启动过程）没有经过中间件，contextvar 是空的，
    这时不应该往日志里塞 `request_id=None`（会污染 JSON 结构）。
    """
    if (rid := request_id_var.get()) and "request_id" not in event_dict:
        event_dict["request_id"] = rid
    if (tid := trace_id_var.get()) and "trace_id" not in event_dict:
        event_dict["trace_id"] = tid
    return event_dict
```

**关键在 `if ... and` 而不是直接赋值**：后台评测线程、启动过程都没有 `request_id`。
无条件写入会得到 `{"request_id": null, "trace_id": null}`，
在 ELK/Loki 里会让字段类型推断不稳定，也会掩盖"这条日志到底有没有请求上下文"这个事实。

标准库日志的导流：

```python
# backend/src/knowflow/core/logging.py L81-L103（节选）
formatter = structlog.stdlib.ProcessorFormatter(
    foreign_pre_chain=shared_processors,
    processors=[
        structlog.stdlib.ProcessorFormatter.remove_processors_meta,
        renderer,
    ],
)

handler = logging.StreamHandler(sys.stderr)
handler.setFormatter(formatter)

root = logging.getLogger()
for existing in list(root.handlers):
    root.removeHandler(existing)
root.addHandler(handler)
root.setLevel(log_level)

# uvicorn 自带的 access 日志会和我们的中间件访问日志重复，关掉它
logging.getLogger("uvicorn.access").disabled = True
for noisy in ("httpx", "httpcore", "urllib3", "chromadb", "sentence_transformers"):
    logging.getLogger(noisy).setLevel(max(log_level, logging.WARNING))
```

**这里解决的是"两套格式并存"问题**：uvicorn 与 SQLAlchemy 用标准库 `logging`，
业务代码用 `structlog`。不做 `ProcessorFormatter` 导流的话，
日志里会出现两种格式混排，而且标准库那部分**没有 `request_id`**——
最需要排查的那条日志恰好缺字段。

**为什么先 `removeHandler` 再 `addHandler`**：uvicorn 启动时会先加自己的 handler。
不清掉的话每条日志打两遍。这也是 `configure_logging` 里 `global _configured`
幂等标志存在的原因。

### 2.3 `core/exceptions.py`（166 行）：错误响应必须有稳定契约

```python
# backend/src/knowflow/core/exceptions.py L23-L60
class KnowFlowError(Exception):
    """所有业务异常的基类。

    子类通过类属性声明 `code` / `http_status` / `default_message`，
    调用方只需 `raise KBNameConflictError(f"知识库 {name!r} 已存在")`。
    """

    code: str = "INTERNAL_ERROR"
    http_status: int = 500
    default_message: str = "服务内部错误"

    def __init__(
        self,
        message: str | None = None,
        *,
        detail: Any = None,
        code: str | None = None,
        http_status: int | None = None,
    ) -> None:
        self.message = message or self.default_message
        self.detail = detail
        if code is not None:
            self.code = code
        if http_status is not None:
            self.http_status = http_status
        super().__init__(self.message)

    def to_dict(self, *, request_id: str | None = None) -> dict[str, Any]:
        """转成对外统一的错误信封（见 `docs/01-数据库与接口契约.md` 第一节）。"""
        return {
            "error": {
                "code": self.code,
                "message": self.message,
                "detail": self.detail,
                "request_id": request_id,
                "timestamp": _utc_now_iso(),
            }
        }
```

**三个设计点**：

1. **业务代码只抛语义化异常**（`KBNameConflictError`），不关心 HTTP 状态码。
   状态码映射表集中在这个文件里（每个子类两个类属性），改错误码只改一处。
2. **`code` 是给机器看的稳定标识**，`message` 是给人看的中文。
   前端按 `code` 分支，**绝不应该匹配 `message` 文本**——文案会改，`code` 不会。
3. **`to_dict()` 里就有 `timestamp`**，而且格式必须与 `main.py` 的 `_now_iso()`
   **逐字一致**（阶段 9 会讲为什么：不一致会让前端只在部分错误上拿到 `Invalid Date`）。

子类的写法全部是"三个类属性"，全文 166 行里有 20 个异常类：

```python
# backend/src/knowflow/core/exceptions.py L129-L141（节选）
class KBNotFoundError(NotFoundError):
    code = "KB_NOT_FOUND"
    default_message = "知识库不存在"

class DocumentNotFoundError(NotFoundError):
    code = "DOCUMENT_NOT_FOUND"
    default_message = "文档不存在"
```

**继承的作用**：`KBNotFoundError` 继承 `NotFoundError`（`http_status = 404`），
所以子类只需要声明 `code` 与 `default_message`。
如果每个异常类都要写一遍 `http_status`，改 404 的语义时要改二十处。

### 2.4 `core/security.py`（76 行）：bcrypt 的 72 字节陷阱

```python
# backend/src/knowflow/core/security.py L28-L55
_BCRYPT_MAX_BYTES = 72


def _prepare_password(password: str) -> bytes:
    """把任意长口令压到 bcrypt 能接受的 72 字节以内。

    <= 72 字节：原样使用（保持与"直接 bcrypt"的兼容性）；
    >  72 字节：sha256 后 base64（44 字节），并在前面加固定标记，
               避免"长口令的 sha256"与"某个恰好等于该 base64 的短口令"撞车。
    """
    raw = password.encode("utf-8")
    if len(raw) <= _BCRYPT_MAX_BYTES:
        return raw
    digest = base64.b64encode(hashlib.sha256(raw).digest())
    return b"$bcrypt-sha256$" + digest


def hash_password(password: str) -> str:
    """生成 bcrypt 哈希（每次调用 salt 不同，同口令两次结果不同，这是对的）。"""
    return bcrypt.hashpw(_prepare_password(password), bcrypt.gensalt()).decode("utf-8")
```

🔻 **这个坑很隐蔽**：bcrypt 只取输入的前 72 字节；而 `bcrypt` 5.x 对超过
72 字节的输入**直接抛 `ValueError`**，不是静默截断。一个用 emoji 或长中文密码的
用户会在**注册时拿到 500**，而且报错信息完全指不到"密码长度"。

**`$bcrypt-sha256$` 前缀的作用**：不加前缀的话，如果某个短口令的字节序列
恰好等于"某个长口令的 sha256 base64"，两者会互相能登录——概率极低但不是零，
而且这类问题一旦发生**无法排查**。加固定标记让两个空间**不可能重叠**。

```python
# backend/src/knowflow/core/security.py L84-L102
def decode_access_token(token: str, *, settings: Settings | None = None) -> dict[str, Any]:
    """解析并校验 token，失败统一抛 `UnauthorizedError`（不区分"过期"与"伪造"）。

    不区分是有意的：告诉攻击者"签名对但过期了"会泄露信息。
    真正需要区分时看服务端日志里的异常类型。
    """
    cfg = settings or get_settings()
    try:
        return jwt.decode(
            token,
            cfg.jwt_secret,
            algorithms=[cfg.jwt_algorithm],
            issuer=cfg.app_name,
            options={"require": ["exp", "sub", "iat"]},
        )
    except jwt.ExpiredSignatureError as exc:
        raise UnauthorizedError("登录已过期，请重新登录") from exc
    except jwt.InvalidTokenError as exc:
        raise UnauthorizedError("身份凭证无效") from exc
```

**`options={"require": [...]}` 不能省**：不写的话，一个**没有 `exp` 字段**的
token 会被 PyJWT 接受，也就是**永不过期**。这是 JWT 实现里最常见的一处漏洞。

**`algorithms=[cfg.jwt_algorithm]` 必须是白名单而非 `None`**：
`algorithms=None` 会允许 `alg: none` 的伪造 token（经典 `alg=none` 攻击）。

### 验证 5：安全模块的三个边界

```powershell
@'

print("同口令两次哈希不同(加盐):", h1 != h2)
print("校验正确口令:", verify_password("admin123", h1))
print("校验错误口令:", verify_password("wrong", h1))
long_pw = "长" * 200          # 600 字节，远超 bcrypt 的 72
print("超 72 字节口令可注册:", verify_password(long_pw, hash_password(long_pw)))
token, expires_in = create_access_token(subject=1)
payload = decode_access_token(token)
print("token sub/iss/exp:", payload["sub"], payload["iss"], "exp" in payload, "expires_in=", expires_in)
'@ | & $py -
```

**预期输出**：

```

校验正确口令: True
校验错误口令: False
超 72 字节口令可注册: True
token sub/iss/exp: 1 KnowFlow True expires_in= 86400
```

**判断标准**：
- 第 1 行 `True` = 加盐生效（同口令两次结果必须不同，这是对的，不是 bug）；
- 第 4 行 `True` = `bcrypt-sha256` 兜底生效；这一行**如果是异常，就是阶段 1 没做完**；
- 第 5 行 `expires_in= 86400` = 1440 分钟（`ACCESS_TOKEN_EXPIRE_MINUTES` 默认值）。

## 4. 常见错误

| 错误信息 | 原因 | 解决 |
| --- | --- | --- |
| `json.decoder.JSONDecodeError` 且在启动时（不是处理请求时） | `CORS_ORIGINS=a,b` 逗号写法，但没加 `NoDecode` | 加 `Annotated[list[str], NoDecode]` + `mode="before"` 校验器 |
| `pydantic_core.ValidationError: ... chunk_overlap ...` | 测试里构造 `Settings` 时忘了传 `database_url` 等必填项，或环境变量冲突 | 显式传参；测试间 `get_settings.cache_clear()` |
| `ValueError: 生产环境必须设置 JWT_SECRET` | `ENV=prod` 但没改默认密钥 | 设一个 ≥32 字节的随机串 |
| `ValueError: password cannot be longer than 72 bytes` | 用了原生 `bcrypt.hashpw` 而没走 `_prepare_password` | 只通过 `hash_password()` 入口哈希 |
| `jwt.exceptions.InvalidAlgorithmError` / token 伪造成功 | `algorithms` 传了 `None` | 传 `[cfg.jwt_algorithm]` |
| 日志里两条不同请求混成一条链 | 中间件 `finally` 里没 `clear_request_context()` | 见阶段 9 的中间件写法 |
| 日志里每条都有 `"request_id": null` | `_add_context` 里用了无条件赋值 | 改成 `if (rid := ...) and ...` 形式 |
| `ModuleNotFoundError: No module named 'knowflow'` | 忘了设 `PYTHONPATH` | 见阶段 0 §2.3 的三种方式 |
| `structlog` 日志打印两遍 | `configure_logging` 没清掉已有 handler | 循环 `removeHandler` |
