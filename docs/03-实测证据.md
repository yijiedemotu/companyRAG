### E2.1 两个向量库后端的等价性（同一份 96 项验证脚本）

`ChromaVectorStore`（持久化）与 `InMemoryVectorStore`（numpy）对**同一输入**逐项比对：

```
  upsert 条数一致          chroma=3 memory=3
  upsert 幂等              重复写入不增加 count
  top-1 是同一个 id        1:0 vs 1:0
  score 差异 < 1e-5（浮点精度内一致）   Δ = 1.79e-07
  Chroma 的 score = 1 - distance（cosine 转相似度）  0.9558 > 0.1644
  metadata 完全相同
  where 过滤 7 组结果一致（含 $and/$or 嵌套、$in/$nin/$gte）
  非法 where 5 组两端抛同样错误（每层多条件 / 一键多算子 / $and 只有一个条件 / $contains 用于标量 / $regex）
  delete 四种组合（按 ids / 按 doc_id / doc_id+ids 取交集 / 清整个 KB）条数与剩余 id 全部一致
  health 自述 backend
```

**为什么要做这个比对**：`VectorStore` 是一个 Protocol，有两个实现。
如果它们行为不一致（尤其 **score 方向**），那么"换后端"就会静默改变检索结果 ——
用内存库跑测试全绿、切到 Chroma 上线后排序反了。**协议的价值取决于实现是否真的等价**，
所以等价性本身必须是**被测量出来的**，而不是"按同样的约定写的"。

> 这条同时也解释了一个测试设计取舍：**`InMemoryVectorStore` 不是"测试用的假实现"，
> 它是行为等价的第二个真实实现** —— 所以单测里用它，测出来的结论对 Chroma 也成立。

**踩过的坑（写在这里给读者避坑）**：`alembic.ini` 里的注释**必须是纯 ASCII**。

## E6.4 接口鉴权审计（**发现的真实安全漏洞**）

命令：`.venv\Scripts\python.exe backend\scripts\audit_auth.py`

**修复前**：39 个端点里 **21 个没有鉴权**，包括
`GET /kbs`、`GET /kbs/{id}`、`GET /kbs/{id}/stats`、`GET /kbs/{id}/documents`、
`GET /documents/{id}`、`GET /documents/{id}/chunks`、`POST /kbs/{id}/search`、
`GET /eval/*`（8 个）、`GET /obs/*`（4 个）。

它们的表现是 **返回 200 + 正常业务数据**，所以任何"断言字段对不对"的功能测试都发现不了；
**只有"不带 token 打一次"才会暴露**。

**修复后**（把鉴权从"逐个端点声明"改成"路由级默认要求"）：

```
  ○ POST   /api/v1/auth/register                        刻意公开（登录/注册）
  ○ POST   /api/v1/auth/login                           刻意公开（登录/注册）
  ✓ GET    /api/v1/auth/me                              已鉴权
  ✓ GET    /api/v1/kbs                                  已鉴权
  ...（其余 33 个全部 ✓）...
已鉴权端点 = 34   刻意公开 = 2
RESULT: OK
```

**两个踩过的坑（写下来给读者）**：

1. **不能只扫端点自身的依赖**。`include_router(..., dependencies=[Depends(get_current_user)])`
   这种"统一加鉴权"的写法挂在 `include_context.dependencies` 上，不在端点的 `dependant` 里。
   只查后者会把正确写法**误报**成漏洞。
2. **不能直接遍历 `app.routes`**。FastAPI 0.142 的 `include_router` 是**惰性**的：
   `app.routes` 里只有 `_IncludedRouter` 占位对象（`path`/`methods` 都是 None），
   真正的 `APIRoute` 在 `original_router.routes` 里，前缀在 `include_context.prefix`。
   第一版脚本直接遍历 `app.routes`，只找到 1 个端点 —— **差点得出"没有漏洞"的错误结论**。

## E6.5 contextvars 跨线程失效（流式路径必崩的真实 bug）

**现象**：非流式 `/chat` 完全正常，但 `/chat/stream` 每次都在最后发一个 `error` 帧，
`done` 帧永远不出现。服务端日志：

```
[error] chat.stream_failed
error="ValueError: <Token var=<ContextVar name='current_recorder' default=None>>
       was created in a different Context"
```

**原因**：Starlette 迭代**同步生成器**时用 `iterate_in_threadpool`，
**每取一个元素就是一次 `run_in_threadpool(next, ...)`** ——
也就是每个 `next()` 可能落在不同线程、拿到**各自的 context 副本**。
而 `ContextVar.set()` 返回的 token 只能在**同一个 context** 里 `reset()`。
生成器第 1 次 `yield` 时 set、第 N 次退出 `with` 时 reset → 直接抛异常。

**修复**：不再用 contextvar 传 recorder，改成**挂在依赖对象上显式传递**
（`agent/nodes.py::RecorderBox` → `AgentDeps.recorder_box` → `RequestServices.recorder_box`）。
生成器在哪个线程跑都无所谓，它读的是同一个对象。修复后 70 项 HTTP 断言全绿。

**为什么这个 bug 值得记住**：它只在**流式**路径出现，而流式恰好是这个项目的主路径；
`pytest` 用 `ASGITransport` 打请求时**不会**触发这种分次线程调度，
所以 222 个单测全绿也照样漏掉它 —— **只有真起 uvicorn 打一次流式接口才会暴露**。

### 怎么诚实地读这张表（面试时这段比数字本身更重要）

1. **唯一显著的结论是：混合检索显著优于纯关键词检索。**
   `bm25 → hybrid_rerank`：recall@5 **0.721 → 0.849**，
   Δ = **+0.128**，95% CI **[+0.035, +0.244]**，**p = 0.010**（配对 bootstrap, n=43）。
   这条可以写进简历，因为它过了显著性检验。

2. **"vector 比 hybrid 高 1.2 个百分点"是不显著的（p = 0.820，CI 跨 0）。**
   43 条用例翻转 1 条就是 2.3 个百分点，所以这 1.2 个点**完全是噪声**。
   这一条**不能**写进简历 —— 写了就是拿随机波动当成果。

3. **RRF 在这个小语料上略逊于纯向量**（0.849 vs 0.860，不显著）。
   原因是 RRF **丢弃分数幅度、只用排名**：语料只有 34 个切片时，
   BGE-M3 的稠密向量本身就足够强，而 BM25 贡献的候选会把部分正确的向量命中挤下去。
   代价评估：`hybrid` 比 `vector` 慢不了多少（56ms vs 58ms，因为 BM25 只花 5ms），
   但**鲁棒性更好**（专有名词类问题靠 BM25 兜底）——这就是选 RRF 做默认值的理由：
   **在没人持续调参的系统里，鲁棒性比理论最优更重要。**

4. **`hybrid` 与 `hybrid_rerank` 完全相同（Δ = 0）**，因为**离线模式下重排走的是启发式兜底**
   （`MockChatModel.offline=True` → 不调 LLM 重排）。所以这一列**测不出 LLM 重排的价值**，
   接上真实 Key 后必须重跑。**不要把这一行解读成"重排没用"。**

5. **延迟**：BM25 5ms、向量 58ms、混合 56ms。这里向量召回是主要成本（本地 CPU 推理），
   而 BM25 几乎免费 —— 这也是"混合检索很划算"的量化依据。
   （注意：这是 34 个切片的小库；库变大时 BM25 的倒排索引优势会更明显，
   而向量库的 HNSW 也仍然是亚线性。）

### E7.6 顺带修掉的一个"静默测了个空"的 bug

第一次跑消融时得到的是这样一张表：

```
  vector          recall@5 = 0.000
  bm25            recall@5 = 0.721
  hybrid          recall@5 = 0.721     ← 与 bm25 完全相同
  hybrid_rerank   recall@5 = 0.721     ← 与 bm25 完全相同
```

**"hybrid 与 bm25 一模一样"就是"向量那一路完全没参与"的指纹。**

根因：`run_evaluation(kb_ids=None)` 时，脚本调用方没有传 KB 列表，
而检索引擎在"没有任何 KB 目标"时会**跳过向量召回**（向量库按 KB 分集合，没目标无从查起；
BM25 则可以跨库搜）。于是 `vector` 模式**根本没检索**，返回 0 —— 但接口 200、指标算得出、表打得出来。

**修法**：`kb_ids=None` 时由 harness **自己从库里取活跃 KB**，并在一个都没有时打 warning。
（另一个候选修法是"让检索引擎在向量模式下无 KB 就报错"，但那会破坏"全局 BM25 检索"这个合法用法，
所以选择在评测层兜底。）

**教训**：评测工具最怕的就是**静默地测了个空**。
凡是"跑完了、有数字、全绿"但结果不合常理的情况，先怀疑"这一步真的执行了吗"。
