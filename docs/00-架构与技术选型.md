# KnowFlow 架构与技术选型（主流 Agent 方案落地版）

> 这份文档回答一个问题：**2026 年做一个「企业知识库智能问答」类 AI 应用，
> 主流方案是什么、每一层为什么这么选、面试官会追问什么。**
>
> 它是整个仓库的**设计源头**：后面所有代码、测试、教程都以这份文档为准。
> 如果代码和本文不一致，是代码的 bug。

---

## 0. 先给结论：一个「主流 Agent 应用」到底由什么组成

市面上绝大多数 AI 应用 demo 只有 3 层：`前端 → 一个 /chat 接口 → 调大模型`。
能上生产的方案是 **7 层**。缺哪一层，就会在某个具体场景崩掉：

| 层 | 职责 | 缺了它会怎样 |
| --- | --- | --- |
| ① 接入层 | HTTP/SSE、鉴权、限流、统一错误、request-id | 前端拿不到稳定契约；出问题无法定位是哪个请求 |
| ② 编排层（Agent） | 决定「要不要检索、检索几次、查得够不够、答得有没有依据」 | 只能一问一答，多跳问题必错；错了也不会自我纠正 |
| ③ 检索层 | 向量召回 + 关键词召回 + 融合 + 重排 + 相关性闸门 | 检索不准 → 模型再强也答不对（90% 的「答不准」死在这里） |
| ④ 模型层 | 对话模型 + 向量化模型（可换供应商） | 被单一厂商锁死；换模型要改业务代码 |
| ⑤ 数据层 | 关系库（业务事实）+ 向量库（语义索引）+ 对象存储（原文件） | 数据不一致；重启后索引丢失且无人知道（静默降级） |
| ⑥ 可观测层 | 全链路 trace、token/成本归因、P50/P95 | 回答不了「这个功能一天花多少钱」「为什么这次慢了 8 秒」 |
| ⑦ 评测层 | 标注集 + 指标 + 消融实验 + CI 门槛 | 只能靠「我感觉更好了」改参数，改坏了也发现不了 |

**KnowFlow 把这 7 层都实现了**，这是它相对「LangChain + 向量库」型 demo 的核心差异。

## 1. 主流 Agent 方案的形态：RAG 是工具，Agent 是编排

### 1.1 三种形态，按控制流归属划分

| 形态 | 控制流由谁决定 | 适用 | 本项目 |
| --- | --- | --- | --- |
| **固定 RAG 链** | 代码写死（先检索→再生成） | 单跳事实型问答，占 80% 流量 | 作为**快路径**保留，延迟最低 |
| **Agent（工具调用）** | 模型决定调不调、调几次 | 需要多跳、需要算术/查库 | LangGraph 图的主力路径 |
| **Workflow（图/状态机）** | 代码定义骨架，模型只填节点内部 | 需要可控、可观测、可断言 | **本项目的 Agent 就是 LangGraph 状态图** |

> 面试话术：**「我没有把控制流交给模型，我把控制流画成了图；
> 模型只在图的每个节点内部做判断。这样既有自适应的好处，又保证每一步可观测、可兜底、可测试。」**

### 1.2 本项目的 Agent 图（LangGraph StateGraph）

这是全项目的核心资产，背下来：

```
                       ┌──────────────┐
        START ────────►│   analyze    │  ① 规划：判断问题类型 + 是否需要检索
                       │  (规划节点)   │     产出：needs_retrieval / sub_queries / query
                       └──────┬───────┘
                              │
                 needs_retrieval? ──no──►┌──────────────┐
                              │yes       │   generate   │
                              ▼          └──────┬───────┘
                       ┌──────────────┐         │
              ┌───────►│   retrieve   │  ② 工具：混合检索（可调多次，多查询并行）
              │        │  (工具节点)   │
              │        └──────┬───────┘
              │               ▼
              │        ┌──────────────┐
              │        │    grade     │  ③ 反思-1（CRAG）：逐条判断召回是否相关
              │        └──────┬───────┘
              │               │
              │     相关性不足且 rewrite 次数 < MAX
              └──── rewrite ──┤  产出：改写后的 query（去口语化 / 换同义词 / 拆子问题）
                    (改写节点)  │
                              │ 相关性足够
                              ▼
                       ┌──────────────┐
                       │   generate   │  ④ 生成：只依据 [n] 编号的上下文作答
                       └──────┬───────┘
                              ▼
                       ┌──────────────┐
                       │   reflect    │  ⑤ 反思-2（Self-RAG）：检查每句是否有引用支撑
                       └──────┬───────┘
                              │
              不通过且 retry < MAX_RETRY
                              └────► 回到 generate（收紧约束，禁止无引用断言）
                              │通过
                              ▼
                             END

  附带能力：全流程每个节点产出「事件」→ 直接映射成 SSE 帧推给前端；
           每个节点耗时/输入输出 → 落 `trace_spans` 表。
```

**四个可讲的设计点**（面试官几乎必问）：

1. **为什么 `grade` 用 LLM 判定而不是复用检索分数？**
   检索分数是「和 query 的字面/语义相似度」，不等于「能不能回答这个问题」。
   实测里经常出现「高分片段答的是另一个问题」。LLM 判定多花一次便宜的小模型调用，
   但能拦掉一整类错误。（代价：多一次调用、多 300~800ms，所以做成可开关 `AGENT_GRADING_ENABLED`。）
2. **为什么 `rewrite` 要有次数上限？**
   避免「死循环烧钱」。上限 2 次：第一次改写查询，第二次拆子问题；还没料就直接
   走 `generate` + **明确告知「知识库中没有足够信息」**——宁可拒答也不编。
3. **为什么 `reflect` 不重新检索？**
   职责分离：`grade` 管「料找对没」，`reflect` 管「话有没有依据」。
   混在一起会出现「越反思越跑偏」。
4. **为什么图要有 checkpointer？**
   多轮记忆不该只靠「把历史塞进 prompt」。用 LangGraph 的 checkpointer 持久化状态（**`thread_id` 用 `trace_id`，不是 `conversation_id`** —— 见 `agent/graph.py` 的说明：`candidates` 等字段是累加 reducer，同一会话共用 thread 会让上一轮的候选混进这一轮）；多轮记忆的事实来源是 MySQL；
   再叠加「滑动窗口 + 字符预算」双重截断控制成本。

### 1.3 会话记忆：为什么是「双重截断」

| 方案 | 问题 |
| --- | --- |
| 全量历史 | 第 20 轮时 prompt token 是第 1 轮的 20 倍，成本和延迟线性炸 |
| 只按轮数截断 | 一轮可能是一篇 3000 字粘贴，10 轮照样超窗 |
| **轮数 + 字符预算（本项目）** | 两个上限取更严者；实现是「从最新往回装，装不下就停」 |

再加一条工程约束：**记忆读写要线程安全**，因为 FastAPI 的 `async` 路由与
后台线程可能同时碰同一会话。

## 2. 检索层：为什么必须混合 + 重排 + 闸门

### 2.1 三路信号的盲区互补

| 信号 | 强项 | 盲区 | 本项目实现 |
| --- | --- | --- | --- |
| 稠密向量（BGE-M3） | 同义改写、口语提问 | 专有名词/错误码/型号 | Chroma + cosine |
| 稀疏 BM25 | 精确词面、罕见词 | 换个说法就查不到 | 自研倒排 + 中文 bigram |
| 重排（Rerank） | 把「相关的」排到「相似的」前面 | 贵、慢，只能用在 top-N | LLM 重排 + 启发式兜底 |

**为什么中文字段不能用空格分词**：`一线城市住宿标准` 用 `split()` 切出来是 **1 个词**，
BM25 直接失效。本项目的做法是 **1-gram + 2-gram 混合切分**（不引 jieba）：
`一线城市` → `一 线 城 市 一线 线城 城市`。
1-gram 保证召回（不会漏），2-gram 提供区分度（`城市`/`住宿`比单字有信息量）。

### 2.2 融合：为什么先归一化

向量分数（cosine，0~1）和 BM25 分数（无上界，可能 0.3 也可能 37）**量纲不同，
不能直接加权**。两种主流做法本项目都实现了：

- **加权 min-max 归一化**：把两路各自压到 `[0,1]` 再加权。优点是可解释、参数少。
- **RRF（Reciprocal Rank Fusion）**：只用排名不用分数，`score = Σ 1/(k + rank)`。
  优点是对「某一路分数尺度漂移」免疫，工业界默认选择。

默认走 RRF（更稳），配置可切到加权归一化——**这本身就是一个可讲的取舍**。

### 2.3 相关性闸门：防幻觉的最后一道

双阈值：`向量相似度 ≥ 阈值` **或** `查询词覆盖率 ≥ 阈值` 才算「有料」。
两条都不过 → **不调大模型，直接返回「知识库中没有找到相关内容」**。

为什么值得单独做一层？
- **省钱**：无召回时短路，不花 token；
- **防幻觉**：模型手里没资料时最容易编。工程上把钱花在「确保它手里有对的资料」，
  比花在「让它别编」更有效。

阈值不能拍脑袋——本项目的 `scripts/calibrate_threshold.py` 会在标注集上扫参数，
输出「阈值 vs 召回率/拒答率」曲线，取 F1 最优点写回 `.env`。**这一步是面试加分项**。

### 3.1 三条选型原则（面试可讲）

1. **协议优先于厂商**：模型能力走 OpenAI 兼容协议，任何一家都能换。
   代价：拿不到厂商独有参数（如某些 `reasoning_content` 细节）。
2. **能自己写的核心算法就自己写**：BM25、融合、闸门、指标全部自研。
   原因：这几处引库带来的**调试成本 > 收益**，而且面试时「我用过 rank_bm25」和
   「我实现过 BM25 并解释为什么 k1=1.5」是两个层次。代价：没有分布式、没有高级重排模型。
3. **降级路径与主路径同等对待**：`EMBEDDING_PROVIDER=hash` + 无 API Key 时
   抽取式回答，保证 **clone 下来零成本跑通全链路**，CI 里不花一分钱。
   代价：要额外维护 `/health` 如实上报「当前真实模式」，不能骗人。

## 4. 数据流：一次上传写了几处，一处提问读了几处

### 4.1 写入（离线，低频）

```
上传文件
  → 存原文件到 data/uploads/{sha256}.{ext}         （对象存储位）
  → MySQL: documents 行（status=UPLOADED）
  → 解析 loaders.py        → 纯文本 + 元信息（页码/编码/行数）
  → 切分 chunkers.py       → 子块（检索单位）+ 父块（喂模型单位）
  → 向量化 BGE-M3          → 1024 维向量（批量、归一化）
  → Chroma upsert          → 向量 + 元数据（kb_id/doc_id/chunk_index/section_path/page_no）
  → MySQL: chunks 行       → 正文 + 元数据 + vector_id（供 JOIN 与回溯）
  → MySQL: documents 行    → status=READY, chunk_count, token_count, 耗时
```

**顺序是刻意设计的**：先写向量库、再写 MySQL 的 chunks、最后把 document 置 READY。
中途失败最坏是「向量库里有孤儿 chunk」（`delete_document` 能清），
而不是「列表显示成功、实际搜不到」——**后者是最难排查的一类 bug**。

### 4.2 读取（在线，高频）

```
提问
  → 鉴权 + 取容器
  → ChatService：落 user message 到 MySQL，起 trace
  → 记忆：按 conversation_id 取最近 N 轮（窗口 + 字符预算）
  → LangGraph：
       analyze → retrieve(向量+BM25→融合→重排→闸门→上下文) → grade → (rewrite→retrieve)*
              → generate → reflect → (generate)*
  → 每步产出 SSE 事件：meta / trace / sources / tool / token / reflect / done / error
  → 落 assistant message + message_citations 到 MySQL
  → 更新 trace_spans / token / 成本
```

**为什么 BM25 索引在内存、重启要重建**：BM25 是纯计算结构，放 MySQL 反而更慢；
但内存索引进程退出就没了。所以启动时从 `chunks` 表全量重建——
**如果漏了这一步，服务不报错、不掉线，只是精确关键词查询变差，属于最危险的静默降级**。
`/health` 会把 `bm25_doc_count` 报出来，让这种降级可见。

## 5. 数据库设计（MySQL 8）

14 张表，分四组。完整 DDL 见 `docs/01-数据库与接口契约.md`。

| 组 | 表 | 说明 |
| --- | --- | --- |
| 身份 | `users` | 用户名唯一、bcrypt 口令、角色（admin/user） |
| 知识资产 | `knowledge_bases` / `documents` / `chunks` | KB 是检索边界；chunk 是检索单位，带 `vector_id` 与 `section_path` |
| 会话 | `conversations` / `messages` / `message_citations` / `feedback` | 引用落到 `chunk_id`，可反查原文与页码 |
| 工程 | `traces` / `trace_spans` | 每次请求一棵 span 树，支撑「为什么慢/贵」 |
| 评测 | `eval_datasets` / `eval_cases` / `eval_runs` / `eval_case_results` | 指标可回归、可对比、可进 CI |

设计要点：
- **软删除**：`documents.deleted_at`，删文档不物理删，避免引用悬空。
- **向量库与 MySQL 的一致性锚点**：`chunks.vector_id`（= `doc_id:chunk_index`），
  双向可查，`scripts/verify_consistency.py` 会比对两边数量并报告差异。
- **金额/成本用 `DECIMAL(12,6)`**，不用 `FLOAT`（浮点累加会漂）。
- **时间统一 `DATETIME(6)` 存 UTC**，展示层转本地时区。

## 6. 可观测：AI 应用的成本就是 token 成本

三样东西必须能回答：
1. **这次请求为什么慢？** → `trace_spans` 瀑布图，每个节点耗时；
2. **这个功能一天花多少钱？** → `messages.token_* + cost_usd` 按天聚合；
3. **线上质量有没有退化？** → P50/P95 延迟 + 拒答率 + 引用数分布。

实现上「零侵入」：`@traced("retrieve")` 装饰器 + 上下文变量绑定 `trace_id`，
业务代码不写埋点逻辑也能被记录。

---

## 7. 评测：把「感觉更好了」变成数字

- **数据集**：`eval_cases`（问题 + 标准答案 + 应命中的文档/小节），覆盖三类难点：
  同义改写、专有名词、多跳。
- **检索指标**：`recall@k`、`MRR`、`nDCG@k`。
- **生成指标**：`faithfulness`（答案每句是否有引用支撑，LLM judge + 兜底正则）、
  `answer_relevance`、`citation_precision`。
- **消融实验**：纯向量 / 纯 BM25 / 混合 / 混合+重排，四组同一数据集跑，
  输出对比表 → **这就是简历上「混合检索把 recall@5 从 X 提到 Y」的数字来源**。
- **统计显著性**：bootstrap 抽样给置信区间，避免「提升了 1.2%」其实是噪声。
- **CI 门槛**：`recall@10` 低于基线即失败，防止改坏。

## 8. 已知边界与 roadmap（诚实清单，面试主动说）

| 边界 | 现状 | 怎么修 |
| --- | --- | --- |
| 检索路径有同步阻塞调用 | BGE-M3 与 Chroma 是同步 API，跑在线程池里（`run_in_threadpool`），已收口 | 换 GPU 推理服务 / 用 async 客户端 |
